# factory

The factory's code. What it is for and what it is built toward are in [`../end-goal/`](../end-goal/README.md); the order it is built in is [`../roadmap.md`](../roadmap.md); the rules it is written under are the _Code_ section of [`../CLAUDE.md`](../CLAUDE.md#code). This file is the map those rules require to ship with the code: every package, what it owns, where the edges between them are stated, and how to run it.

## The packages

| Package | What it owns |
|---|---|
| [`record`](record) | The graph's conventions: the actor — one of three kinds, `human`, `component` or `agent`, an opaque key that is never a name, and, on every one of the three, whether that key is claimed or verified — identifier generation, the timestamp format, and the SQL text every record table composes for its columns, their constraints, and the format version each row carries. It owns no table. |
| [`decisionlog`](decisionlog) | The chained log: one table of ten shapes, and one writer with a method per shape and part. A decision is up to four rows — an open event appended when a gate fires, a close event naming it and carrying the verdict, an abandonment where no verdict is coming, and an acknowledgement per human — a wait is two, and the other eight shapes are one row each; `Truncate` is the one method that deletes, refused wherever a legal hold stands. Reading goes through a `Reader`, which holds the same fencing token a writer does and appends a read event naming the principal — its actor in the row's own columns, an agent's dispatch and scope in the payload — before every answer, `Verify` walking the chain and naming the first row that breaks it. |
| [`lease`](lease) | The store's account of itself: the one row that makes exactly one instance of the factory run at a time — who holds it, when the hold lapses, and the number that rises at every acquisition — the acquisition that takes it where it is unheld or expired and fails where anything holds it, the release a process stopping cleanly makes, and the fencing token every write elsewhere in the store is checked against inside its own transaction. It is not a record of the graph and carries no actor. |
| [`principal`](principal) | Who a call is made as: a human's actor, a component's, or an agent's plus the dispatch that put it on an item and the scope it was dispatched under. It decides nothing and is recorded by whatever the call reaches. |
| [`secretref`](secretref) | The reference type every other package uses in place of a secret, and the one resolver that reads a value, recording the principal that asked for it beside the name. A `Ref` has one field and it is the name, so nothing that renders one can render a value. |
| [`targetseam`](targetseam) | The named operations the deployer reaches a deploy target through — `Deploy`, `Stop`, `ReadRunning`, `ShiftTraffic`, `SetInstanceCount`, `ApplySchemaChange`, `Snapshot` — as an interface, every operation taking the principal making the call. `Deploy` and `Stop` each report how the instances they ended were replaced, a drain or a cut, which is what the deploy record's row per target names. A schema change carries the release that ships it and, at an adopted service's first release, the mark that says the store arrived carrying it; a history row carries both back. `Fake` records what was called on it and reaches nothing; `localtarget` is the implementation the demonstrations deploy against. No agent reaches a deploy target at all. |
| [`postgres`](postgres) | Opening the pool, applying package `lease`'s table alone — the one thing created before the lease is acquired — and applying each package's DDL from one ordered list written in the source. No ORM, no migration framework. Beside it, the store's schema history — one row per change, naming the version that shipped it, its identity, a checksum of its text, and whether it widened the store or removed something — and the start that reads it and refuses to start against a store this version cannot read. |
| [`cmd/depscheck`](cmd/depscheck) | Failing the build on an import between two packages of this module that [`deps.txt`](deps.txt) does not allow. |
| [`cmd/tracecheck`](cmd/tracecheck) | Failing the build on a reference from the code or its documentation into a Markdown file that points at nothing — a target that does not exist, or an anchor matching no heading in it — and on a `doc.go` that carries no reference at all. |
| [`intent`](intent) | The intent — its source, its statement, its six-state refinement state, its two attempt counts, its tier, project, evidence, deadline and constraint — the question attached to it, and the requirement recording what the factory understood is wanted, `Intake` being the one writer of all three. |
| [`project`](project) | The project record: an owner's widest grouping of work, and the root every area chain ends at. One writer, an owner at Factory: it is created with production's environment and ended with it, once every service in it is retired, and the row is never deleted. |
| [`service`](service) | The service record: its identity — name, repository, and project — written at decomposition; provisioned, retired, the targets it runs on, the window's size and power per quantity, its confidence, cap, window limit and exposure bound, the bake volume between one target of a rollout and the next, the backlog cap on how many releases wait behind a rollback hold, the environment-hour and instance-hour rates a span is converted at, the operation cap and the overflow operation the excess lands in, the explicit threshold per quantity a safeguard sets with the size beside it, the search budget, the mutant cap, the failure-record key cap, the unreliable bound, the incident-raised item bound, the objective and paging hours, the mutation floor, the fraction of its instances a release keeps, the maximum concurrent kept fleets, the size and average run length of the reading against its own recent history, the proof test rate, the periods of a change freeze, the product licence and the snapshot retention, each authored by an owner at Factory; and the deployer's four reachability fields written at adoption and at every first release. Three writers, and the seam between them is the field. |
| [`item`](item) | The item — its intent, service, area, branch, what it waits on, and the requirements it answers — written once by decomposition's `Create`, which also `Supersede`s an item at its replacements and `Repoint`s what a standing item waits on, both refusing an edge that would close a cycle over what waits on what. `Dispatch` writes the stage, the attempt count, and the priority after: `Advance` one stage forward with an attempt counted on entry, `ReturnTo` a stage with nothing counted until it is entered again, `Escalate` and `ClearEscalation` for the attempt limit, `Drop`, `SetPriority`, and `End`. What a stage spent is `agentrun`'s and no field here. |
| [`agentrun`](agentrun) | The agent run record: one per run of any agent, written once by the component that performed it — what ran, what it ran on (an item and its stage, or an intent), what it served the run on (the credential, the processing location, and the account it drew on), and what it spent (units per kind, the time they were returned, the sources handed over, and the amount converted at the owner's rates, absent where a kind has no rate). Reads: by item, by intent, by model version, and the sum by credential since a period start that a spend ceiling compares against. |
| [`inputmanifest`](inputmanifest) | The input manifest: what context assembly hands an agent before a run, named by reference — the item or intent and its stage, the material handed over, the read-at-once bound applied, the selection rule version, and what was withheld or truncated and why. Written once per dispatch; context assembly is not built, so the caller that dispatches writes it for now. |
| [`artifact`](artifact) | The artifact store: an artifact's version chain — an item's, a role's, a subject's, or the one selection rule's — its content digest, its authorship and author, and the calls in which a version and the records it introduces are submitted together: a spec version with its criteria, its withdrawals and its screen state machines, and a consumer contract version with its predicates. Also the input manifest a version was authored from, the one entry an authorship does not name — the shipped version the factory enters itself, naming which of the two events entered it, the install's alone standing in force ungated — and `Redact`, the one exception to insert-and-never-update. |
| [`criterion`](criterion) | A criterion of a service: its stable id, its pattern, its provenance queries, the query for which criteria are in force for one build — a build being a set of items — the encoding checks that tie a criterion to the test code deciding it, the Spec gate's rejection of a build in an irreversible area no criterion in force bounds, what deciding one against a build produced, undecided among the three outcomes, the mutation score read over a run's encodings with its coverage and its could-not-derive, and the outcome history a bound reads as unreliable. |
| [`screenstatemachine`](screenstatemachine) | A screen's state machine: its states, events and transitions, the chain of supersessions that is the screen's identity, the well-formedness checks a closed machine must pass, the check that a transition leaving the screen names one still in force, the transition check derived from a build with its Go extractor, and the drivers that put a screen in each declared state. |
| [`dispatch`](dispatch) | The dispatch component: the match of an item's stage against a role and of its service and area chain against a scope, and what runs an agent. One dispatch reads the intent's state, matches the role and the scope against a fleet entry and the role prompt version in force, writes the transition onto the item, writes the input manifest, runs the role under a principal naming the model version and the dispatch, asking the provider for the effort the entry names, records one agent run per call, and compares the item's own count for the stage against the attempt limit — escalating over it and telling the notifier that it did. It also orders admission where more is ready than the infrastructure admits, by the intent's tier and then the item's priority. Three of the six conditions that stop a dispatch are computed here and each is a hold row in the log, one per item and stage, re-matched and closed when its condition is gone. It owns no table: the item's stage is `item`'s, the manifest `inputmanifest`'s, the run record `agentrun`'s, and the hold the log's. |
| [`gate`](gate) | The gate component: firing the eight rows of the default path, a row per further deploy environment, and the five that belong to no item; reading the intent's state, the rows already pending, the version under decision, the holds standing and who holds the row's duty before it appends anything; and opening and closing a decision through `decisionlog`. A decision is two rows and may carry two more — an acknowledgement, and an abandonment where no verdict is coming. The verdict is a human's where a mark put one at the row and the factory's own otherwise, and the factory has two: it may not approve over a human, and it rejects before one is asked, because a mechanical check rejects on its own terms before anyone gives a verdict. Refer is the fourth verdict and the one that closes a row and re-fires it. | [`build`](build) | A build record, one per commit built, naming the service and, where there is one, the item it was built for, the commit, the artifact digest, the resolved set of third-party packages with its per-ecosystem coverage, the notice file, the design system constraint in force, the exposure list the build runner derived from its own checkout and whether that checkout declares a schema change, and what the build's own process decided about the criteria whose encodings declare it. |

## The allowed edges

[`deps.txt`](deps.txt) is the allowed package graph: one line per package naming what it may import, a `test` line for an edge that appears only in a package's tests, and the reason for every edge that needs one in the comment above the list. An arrow reads as "imports". `cmd/depscheck` is what makes the file binding — a package the file does not list is an error, an edge it does not allow is an error, and a line naming a package that does not exist is an error. The compiler already refuses a cycle; this refuses an edge that would compile. The list is not copied here, so that it exists once.

## Running it

The toolchain is pinned by [`../mise.toml`](../mise.toml). The dev database is [`docker-compose.yml`](docker-compose.yml), on port 5433 so a PostgreSQL installed on the machine keeps 5432.

```sh
docker compose up -d           # the database
go vet ./...
go run ./cmd/depscheck
go run ./cmd/tracecheck
go test -count=1 ./...
```

Every start acquires the lease and then calls `postgres.Start`, which reads the store's schema history, refuses to start against a store this version cannot read, and applies the schema. What the history does not do is alter a table: `create table if not exists` leaves one that already exists as it is, and this version declares one change — the first schema — so a dev database written while that schema was being edited is not brought forward by running against it. Drop the schema and let it be applied again, which for the dev database is `drop schema public cascade; create schema public;`. [`postgres/doc.go`](postgres/doc.go) says which caller of `Start` is not built.

The database tests read `DATABASE_URL` and fall back to `postgres://factory:factory@localhost:5433/factory`. They do not skip when the database is unreachable — a silent skip is how a green run comes to mean nothing — so an unreachable database fails them. `-count=1` is what keeps that promise: `go test` caches a result against the test binary and what the test read, and a database is neither, so a re-run with the database stopped reports the cached `ok` without opening a socket. Each database test creates a PostgreSQL schema of its own, applies the DDL inside it, and drops it when it ends, so a rerun on a database a previous run left dirty starts clean.

[`../.github/workflows/factory.yml`](../.github/workflows/factory.yml) runs the same commands against a `postgres:17` service container.

A fourth command runs the same demonstration against the model API instead of a fake, and it is the only thing that tests the stretch between a role and the provider — the credential's header, the shape of a real answer, a reply the protocol refuses, an encoding named the way a model chose to name it. It is run whenever something on that stretch changes:

```sh
FACTORY_MODEL=deepseek/deepseek-v4-flash go test -tags realmodel -count=1 -v -run RealModel ./cmd/factory/
```

`FACTORY_PROVIDER` names which provider answers — `openrouter` by default, or `anthropic` — and `FACTORY_MODEL` is that provider's model id, so the two are set together or neither is: OpenRouter's ids are namespaced and Anthropic's are not. The credential is `model.openrouter` or `model.anthropic` in `secrets.local` by the provider named, which [`../.gitignore`](../.gitignore) refuses to track; [openrouter.ai/keys](https://openrouter.ai/keys) mints the first and `claude setup-token` the second. The test fails rather than skips when the file holds no key for the provider named, for the reason the database tests do not skip, and it keeps its git repository on a failure so what the model wrote can be read. The build tag is what keeps it out of `go test ./...` and out of CI, neither of which has a credential to spend — and what the tag costs is that this one file is not compiled in the default build, so `go vet -tags realmodel ./cmd/factory/` is how a change to it is checked.

The end-to-end tests are in `cmd/factory` and run under `go test` above along with everything else. To walk the path against a real model and a real process, run it directly — [`DEMO.md`](DEMO.md) is that run as a runbook, with what to set up, what to type at each prompt, what to show afterwards, and what the run deliberately does not cover:

```sh
go run ./cmd/factory run -secrets <file> [-provider <name>] -model <name> -service <name>=<dir> [-service <name>=<dir> …] -area <name> [-project <name>] -targets <dir> -intent <statement>
go run ./cmd/factory walk <deploy-id>
go run ./cmd/factory watch <service> -secrets <file> -targets <dir> [-for 1m] [-every 1s]
go run ./cmd/factory approve <item-id> -secrets <file> -targets <dir> [-verdict approve|hold] [-reason <words>]
go run ./cmd/factory approve -safeguard-withdrawal <id> | -halt-withdrawal <id> | -legal-hold-withdrawal <id> | -retention <seconds> [-human <name>]
go run ./cmd/factory contracts -secrets <file> -targets <dir> [-breaks <item-id>]
go run ./cmd/factory learn [-dry]
go run ./cmd/factory rollback <service> -secrets <file> -targets <dir> -reason <words> [-revert] [-human <name>]
go run ./cmd/factory drop <item-id|intent-id> [-human <name>]
go run ./cmd/factory accept-commit <service> <commit> -secrets <file> -targets <dir> [-human <name>]
go run ./cmd/factory mark-rollback <deploy-id> -reason <words> [-human <name>]
go run ./cmd/factory mitigate <deploy-id> -secrets <file> -targets <dir> -operation <name> [-share <v>] [-count <n>]
go run ./cmd/factory mitigate -end <mitigation-id> -secrets <file> -targets <dir>
go run ./cmd/factory truncate -boundary <row-id> [-human <name>]
```

`run` reads two secrets from `<file>`: the model credential of the provider `-provider` names, which the model call resolves and sends as a bearer token, and `deploy.local`, the credential `targetseam` requires on every operation and `localtarget` never reads. `-provider` is `openrouter` by default, reading `model.openrouter`, or `anthropic`, reading `model.anthropic` — and `-model` is that provider's model id, OpenRouter's being namespaced (`anthropic/claude-opus-4.8`) and Anthropic's not. A subscription token is served `claude-haiku-4-5` and refused every model above it, which is what the second provider is for and what [`DEMO.md`](DEMO.md) records the measurement of. `-service` is a service as `<name>=<path>`, the path being its git repository and created when absent, and it is given once per service the install knows: an interface has consumers and the consumers are other services in the same factory, so a run that could name one service could never demonstrate a contract. `-targets` is the directory `localtarget` runs releases from, and production's environment record is created naming it. `-human` names the deciding human by name, which every subcommand resolves to the per-person key the People mapping holds, minting a key and a mapping where the name is new — every record names a key and a person at a terminal types a name. They are also the owner every authoring write is made as (default `owner`). `-intent` supplies an intent's statement and is given once per decomposition — two of them is two items authored, two candidate environments live at once, and both merges ordered by the queue — and one is prompted for on standard input where the flag is absent. An intent that changes more than one service names them before its statement, comma separated and then a colon — `-intent 'producer,consumer: what is wanted'` — which is this interface being told what decomposition yields, a stage that decides the decomposition being a later milestone's. Where decomposition yields more than one item, Decomposition fires over the set and one verdict covers the whole of it; where an item waits on another, the run takes the layers in order, so a producer ships before the consumer whose environment is composed from it. `-candidate-environments` is how many candidate environments this platform has room for at once (default 8): a candidate that meets it waits, and that wait is written into the log, being neither a record nor a parameter of an owner's. `-area` names the area the item is in, declared where it does not exist — without one the score can read neither context factor and a human decides every gate of that item. Every factor over a build is valued here: package `exposure` derives what a change reaches from the diff and the build's resolved set, the build record carries the list, and each of the four rows over a build reads it off that record — so a number under the threshold auto-passes, the held-out sample can select, and the thresholds it learns have outcomes to learn from. A service's first release is still decided by a human at every row, which is what the supplied threshold is calibrated to. `-pace` is the least time between two model calls, two seconds by default, which is what stops a stage's retry following its refusal with nothing in between; `0` sends them back to back. `-watch` is how long the run reads its own windows before leaving what is still open, open, a minute by default, and `-watch-every` is how often it reads — a window's duration is measured and never set, so a run cannot know in advance how long to wait. `-project` names the project this take installs and works in, `default` unless given, created in the same event as production's environment for it where it does not exist yet. `walk <deploy-id>` follows the links from an existing deploy record back to its intent, printing each stored field it crosses and then every decision the item's gates left in the log.

`watch <service>` is the health monitor alone against an existing database, and it is the one thing that closes a analysis window: what a run gave up on is finished here, and a window nothing closes reaches the window limit and holds that service's production deploys. `approve <item-id>` fires the production deploy row with the factory's own hold named on its open event and takes a human's verdict, which is the emergency action the design keeps there — approve now, not skip. What approving through the hold a rollback leaves accepts is the defect that was just removed. `approve` with `-safeguard-withdrawal`, `-halt-withdrawal`, `-legal-hold-withdrawal` or `-retention` fires one of the four rows that decide a record rather than an item and takes the human's verdict at it: a safeguard leaves force where its withdrawal is approved, a halt ends where its withdrawal is, a legal hold lifts where its withdrawal is, and a shortening of decision-log retention is decided rather than authored. `safeguard -withdraw <id>`, `halt -withdraw` and `legal-hold -withdraw <id>` write the withdrawal pending, and this is where it is decided, by a human other than the one who wrote it — the row is routed away from that human, and where the two are one person the row still fires and the close says so. Each of the four is an open event, a close event, and then the record's own approval, which package policy refuses where the call names no close event. `contracts` is every query contracts make: which toolchains this factory version has an extractor for, each contract with its versions, the elements of the newest and the deprecation mark on each, which version production is running and so which one a producer's own diff is against, the consumer contracts in force per service with the release range they were derived over, and the deprecation list per marked element — and, with `-breaks <item-id>`, what one candidate would break and whom, which is the claim that "what does this break" is a query rather than an estimate, read off the records.

`rollback <service>` is duty 10: the deployer returns production to the release below the one running, with the human who asked as the actor, and `-revert` raises the revert intent instead — the same duty once the build a rollback would return to is gone. `drop` ends an item or an intent for good. `accept-commit` is a human accepting a commit master holds that the queue did not make, which is what ends the stop that commit leaves. `mark-rollback` says a rollback was not caused by the release, and the score and its learning pass exclude that release from then on. `mitigate` is the deployer performing one of the mitigation class's two operations on a target on a human's instruction, and `-end` ends one standing; ending every instance of a service on a target is not one of them, retirement being what calls for that. `truncate` is the decision log's retention pass, refused while a legal hold stands.

None of those takes a service name and a repository the way `run` does. Both are the service record's own fields: a flag naming a repository could disagree with the record, and a flag naming one service would leave a two-service install's other one unknown to the run, so each of these reads every service out of the store.

Eight more subcommands are duty 8, duty 9, the priority a queue is reordered with, and the People declaration a page routes on — none of which has a screen yet:

```sh
go run ./cmd/factory area <name> [-inside <name>] [-project <name>]
go run ./cmd/factory author -parameter <name> -value <v> [-service <name>] [-area <name>] [-gate <row>] [-stage <stage>] [-quantity <name>] [-project <name>]
go run ./cmd/factory safeguard -parameter <name> -subject <kind>:<name> [-bound <v>] [-service <name>] [-route-duty <n> | -route-human <key>]
go run ./cmd/factory safeguard -withdraw <safeguard-id>
go run ./cmd/factory halt -reason <words>
go run ./cmd/factory halt -withdraw <halt-id>
go run ./cmd/factory legal-hold -subject <kind>:<name> -reason <words>
go run ./cmd/factory legal-hold -withdraw <hold-id>
go run ./cmd/factory policy [-service <name>] [-area <name>] [-gate <row>] [-stage <stage>] [-project <name>]
go run ./cmd/factory priority <item-id> -priority <n>
go run ./cmd/factory people [<human>] [-duty <1-12> | -obligation hosting|driftdetector|fleet] [-withdraw]
```

`people` with no argument prints the declaration; an empty one is a factory where every page and every gate row reaches the owner directly, which is a working factory and not a misconfigured one. The owner is not a row in it: a page widens to the owner and the design gives the owner no record, so the notifier is composed with the name `-human` gives it.

`-project` is a flag of `area`, `author` and `policy` of these — and of `run` — defaulting to `default` and naming the project `run` installed; the other five take none, and `safeguard` names a project as a subject kind (`project:<name>`) instead. `area` declares inside the project unless `-inside` names an area. Only `run` creates a project: every other subcommand reads the one it names and refuses where it does not exist. A safeguard on `risk_threshold` is drawn on `-service`, keyed by the gate row named in `gate_row:<row>` — package policy's own reader keys a row-scoped safeguard on the service the row fires for — and `-route-duty`/`-route-human` are read and validated but not yet wired to `policy.Factory.AddSafeguard`, which routes every safeguard it places to the owner until a later dispatch composes a duty or a named human for it to route to. `halt` and `legal-hold` are package policy's writes, so each appends a policy version; each `-withdraw` writes a pending withdrawal, standing until a human approves it at the gate row that decides it, which is `approve` above, and the approval is a second call and a second version.

Drift detection is a second binary, and installing it beside the factory is substrate outside the twelve duties. It reaches its own store through `DRIFTDETECTOR_DATABASE_URL`, defaulting to the dev database with a schema of its own, and it applies that schema itself — nothing in the factory does:

```sh
go run ./cmd/driftdetector pass -secrets <file>
go run ./cmd/driftdetector show
go run ./cmd/driftdetector clear <mismatch-id> -human <name>
go run ./cmd/driftdetector install -address <address>
```

`pass` runs three comparisons: what each production target runs against that service's current release; the log's chain against the head this store recorded last pass, extended and nothing else; and the factory's own last check records, which is what makes a stopped factory component reach a human. `show` prints every mismatch and the last check per target, which is what makes a stopped drift detector visible rather than silent — no mismatches is not health if the last check is a week old. `clear` is the human act the design keeps here and refuses in the factory: clearing a mismatch from the factory would make it a writer of the record that says it is wrong. `install` writes the one address, mail or chat, the detector delivers its own page to when the notifier's own last check is stale or every factory last check is stale at once — the two stops with no carrier inside the factory. A factory run with no drift detector store to reach says so on standard error and decides as a factory with none installed does.

`author` reads the subject flags the parameter needs and no others, the record a parameter is a field of being a fact of the parameter rather than a choice: a threshold is authored on an environment for one gate row, an attempt limit on the factory-wide settings record for one stage, an item-size target on an area, and the analysis window's four on a service. `safeguard` takes no direction, because the direction differs per parameter and points the same way in each — an owner chooses the subject and the bound. `priority` writes the one field that orders a queue: a greater number goes first, and it orders every queue the item waits in as an item — the gates up to and including Merge to master, and the merge queue — and no deploy. `policy` prints every parameter as it is in force, where its value came from, the safeguards that reached it, and what reads it at this milestone, which is where an owner sees which parameters are read by nothing yet. It is also where the third source of the list of allowed predicate kinds shows: an unauthored list is the five kinds the factory can decide, which is what an owner extends rather than replaces.
