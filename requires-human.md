# Requires human

Findings the unattended loop could not take, moved here verbatim, each followed by the decision it needs.

## deferred.md

### No seam between the software the factory writes and the world it acts on: nothing bounds how many irreversible operations a bad release performs
**Raised by:** Safety engineering
**Where:** `deferred.md` — "Security comes last" (the five seams), with `how-the-factory-works/03-gates/02-the-rollout-strategy.md`
**What is wrong or missing:** Five seams are declared now on the argument that they are "nearly free now and expensive to retrofit," and seam 4 names the operations the *deployer* performs on a target. There is no equivalent for the operations the *product* performs on money, people, stores, or actuators — no named class, no count, no per-interval bound, no field populated in the meantime. The only limit on how much irreversible action a bad release takes is the rollout share and the window's cap, and the rollout strategy itself concedes that at `irreversible` on a platform that serves no share "what that human accepts is an exposure the platform gives the factory no way to limit." A protection layer at the point of the hazardous action — a bound on irreversible operations per release per interval, refused and raised past it — is what the field puts there, and it is the one control that does not depend on the detector in the blind-detector finding working.
**What turns on it:** With no bound at the action and no observation of it, the factory's exposure on an `irreversible` area between deploy and window close is unbounded and unrecorded; `06-rollback.md` already concedes the rollback "returns the traffic and never the state," so the design has neither prevention proportional to harm nor a record of how much harm occurred.
**Migration:** This is the design's own seam argument applied once more: the count and the operation class are a field and a declaration that cost nothing now, and retrofitting them means re-instrumenting every service the factory has ever written, an owner authoring a bound per area against code already shipped, and no release before the retrofit having any record of what it did.

**Decision needed:** Whether the factory bounds the irreversible operations the software it writes performs on the world, which is a sixth seam at the point of the hazardous action in every service the factory builds. Taking it means the factory instruments every service it writes with a named class of irreversible operation, a count per release per interval, and an owner-authored bound per area that refuses and raises past it, which is a constraint on the produced software's code rather than on the factory's own. Refusing it leaves the exposure on an `irreversible` area between deploy and window close bounded by the rollout share and the window limit alone, as the rollout strategy already concedes. What turns on it is whether the seam argument in _Security comes last_ extends to the produced software, and what an owner authors per area against code already shipped if it is added later. Only the owner can weigh the cost of a check in every service against an unbounded and unrecorded exposure.

### The build runner resolves and executes third-party code before anything checks it, and no seam is declared where it does
**Raised by:** Supply chain security
**Where:** `deferred.md` — _Security comes last_ (and `components.md` — the build runner's row; `how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md`)
**What is wrong or missing:** Every mechanical defence over third-party code — the advisory match at Implementation, the licence constraint, the source-allowlist constraint, the queue's digest comparison — is decided against the resolved set, and the resolved set is "written by the build runner from the build it performed": resolution and execution of package install hooks, build plugins and generators happen first, and the checks read the record afterwards. Five seams are declared, none of them the boundary where untrusted bytes enter and run; `components.md` gives the build runner "nothing" in _What it may call_, though it necessarily reaches a registry, which by that table's own rule ("a call edge does not exist until the row of the caller names it") is a call that does not exist. `01-one-pipeline.md` is where the design considers this and settles it wrongly: "Resolved dependency contents are not evidence of an intent at all: the digests and the security predicates are their check" — a digest identifies bytes and does not make them safe to execute, and the security predicates are "decided per toolchain against the build", i.e. after it ran.
**What turns on it:** This is the standard delivery path for a compromised dependency (event-stream, ua-parser-js, xz), and here it lands inside a factory that is "one process" holding the log's only writer, the graph, git write access, and seam 3's resolver — of which the design already says "whoever can read the resolver reaches the models, the deploy targets, and a service's own credentials alike". `04-what-the-factory-does-not-build.md` permits the build to run on "the host itself". A build compromise is the one event that both ships the change and writes the records every downstream check reads as true.
**Migration:** A sixth seam cannot be added after installs are running: seam 5's enforcement is a one-way field an owner turns on once, and an install that turned it on has already been told every call carries a principal, while build-time fetch and execution were never calls at any seam — retrofitting means the spread through the codebase seam 4 was declared to avoid, in a running install whose builds all ran unbounded.

**Decision needed:** Whether the build runs where the factory's own process, credentials, and store can be reached, and whether the factory adds a sixth seam between the build runner and the registries it fetches from. Two things the document protects pull against each other: _What the factory does not build_ lets the build run on the host itself so that a customer needs nothing beyond the host, and _Security comes last_ holds the seams to five and puts everything else after the factory is proved. Taking the finding means the build runs in the candidate environment or another place that holds no factory credential and reaches only the registries the source-allowlist names, with the fetch recorded at the seam before the build reads it, and the build runner's row names the registry as a call. That changes what a customer has to host and what the build costs per candidate. Only the owner can decide whether the produced software's build is the sixth seam, and whether the host-only install stays supported.

### The product's release channel has no revocation, no expiry, and no downgrade check, and one key signs everything an agent is told
**Raised by:** Security engineering
**Where:** `deferred.md` — _The product's release channel_
**What is wrong or missing:** The channel verifies a digest and a signature before first start, and rotates the key only by a signed release naming its successor. Nothing revokes a key, nothing expires a release, and nothing requires the release being installed to be newer than the one running — so a signed release replayed after a key compromise, or an install frozen on an old release by withholding upgrades, verifies clean. The same single key covers the whole shipped bundle the section itself enumerates: role prompts, skills, evaluation sets, starting priors, the allowed predicate kinds, and design systems. The document names the trust-on-first-use gap and stops there.
**What turns on it:** One compromise of the builder's key rewrites what every agent in every install is told, and the shipped-bundle identity attests to the substitution rather than exposing it. The freeze case is worse than the replay case because it is silent: an install held on a release with a known defect looks identical to one that is current, and the factory's own store-schema check only refuses a downgrade that happens to cross a schema change.
**Migration:** Installs already hold the key and the verification code they were handed; any revocation, expiry, or monotonic-version rule added later is delivered by the channel it is meant to protect, so it binds only installs that have already taken the upgrade an attacker with the key can prevent.

**Decision needed:** Three choices, each a product trade-off the document does not imply. Expiry: a release that refuses to start past a date detects a frozen install, and it also stops an install the builder cannot reach, which is the regulated customer the tenancy decision was made for; the owner decides whether an install may run indefinitely without the channel. Revocation: a key revoked by a release the same key signs is no revocation, so a real one needs a root the channel does not carry, a second key or an out-of-band root the customer holds; the owner decides whether the trust-on-first-use gap the section names is accepted or closed at that cost. Key separation: one key over the whole shipped bundle or one per kind of content, which decides how many keys a builder keeps and rotates. The downgrade check alone is derivable and the loop can take it once the owner says the rest: a first start refuses a release whose version is not later than the one on the last install event.

## what-the-factory-does/

### The install is the only isolation boundary that exists, and the chained log makes the choice permanent
**Raised by:** Product management
**Where:** `what-the-factory-does/README.md` — _What the factory does_, the no-tenancy paragraph; and `how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md` — _Scope follows the mechanism, not the duty_.
**What is wrong or missing:** "One customer per install" is decided and costed only across customers; below the install there is no boundary at all, and the document never asks whether the install is the right unit for a customer with two products, two regulatory regimes, or two business units. A project is "a grouping of work, not a separate place": the attempt limit, allowed predicate kinds, review sample rate, both retentions, the report channel's rates, the retention floor, seam-5 enforcement and the concurrent-environment cap are fields of one factory-wide settings record; a halt stops every service; every People row reads all four screens; and seam 5 states outright that the resolver answers a Spec-stage agent in one project naming another project's production deploy credential.
**What turns on it:** A buyer choosing one install or several is choosing permanently between a shared policy, credential and read surface and a duplicated fleet, priors and calibration, and the document gives them nothing to choose on — the isolation sold to the regulated customer stops at the customer's edge. This is the assigned row's own subject, and the only cost the document states for the tenancy decision is the one that falls on the builder.
**Migration:** One install is one chain — each row hashes its predecessor, rows are never migrated, the hash rule is fixed by the payload format version, and the score's supplied values exist nowhere but the rows carrying them — so an install can never be split nor two merged, and a customer who guesses the granularity wrong at install time cannot correct it later.

**Decision needed:** Whether the project becomes an isolation boundary inside an install, or the document states that it is not one and what a customer with two regimes does about it. Making it one means per-project fields on the settings record, a halt scoped to a project, a People row scoped to a project, and a resolver that refuses a credential across projects, which is a second scope on nearly every mechanism gate policy gathers. Stating that it is not one means a customer with two regimes runs two installs and the document says so at the no-tenancy paragraph, beside what a second install duplicates. Either answer is a product choice the document does not imply, and the chain makes it one an install cannot revisit.

### The repository is a write boundary with no seam, no component, and no credential on any record
**Raised by:** Software architecture
**Where:** `end-goal/what-the-factory-does/04-what-the-factory-does-not-build.md` — the `git` row of the outside table, and the paragraph "Master's only inbound path being the queue rests on how the repository is administered"; `end-goal/deferred.md` — _Security comes last_, seams 3 and 4
**What is wrong or missing:** The factory writes to git from three places — an implementation agent commits a candidate branch, the build runner clones, the merge queue fast-forwards master — and none of them is mediated by a named component or a declared seam. Seam 4 exists precisely because "without it, production access is spread through the codebase," and seam 3 enumerates the credentials the resolver answers for as exactly three kinds (model, deploy target, a service's own outward credentials); the repository write credential is a fourth kind, held on no record, resolved by nothing, and therefore not in "the item's reach" that `01-one-pipeline.md` filters agent-visible material against. `components.md` has no row for anything that reaches git, so the one-writer/one-caller inventory does not cover the store that holds master. The document considers only humans pushing to a plain repository; it never considers that the same factory credential an implementation agent pushes a candidate branch with is the credential the queue fast-forwards master with, which makes every implementation agent able to write master directly.
**What turns on it:** Two structural claims rest on master's inbound path being the queue alone: "what was verified is what ships" (`06-releases/04-the-release-number.md`) and the release record existing for every commit on master, which is what `02-traceability.md` traverses. Both are asserted as properties of the queue while being enforced only by repository administration that the document places outside the factory and outside the record graph.
**Migration:** Splitting the single factory git credential into per-role, resolver-named credentials with a declared operation set later requires the owner to re-provision write access on every repository of a running install — `provisioned` is a field an owner already authored against "the factory's credential holding write access," and the call sites an agent reaches git through are the spread seam 4 was declared to prevent.
**Also reached separately by:** Product management — "Master's exclusivity is the claim the product is sold on, and no record ever says whether it held" (same precondition, from the record side).

**Decision needed:** Whether the factory mediates its own writes to git: a component every clone, push, and fast-forward goes through, a sixth seam at the repository with a named operation set, and a repository credential the resolver answers per role, so an implementation agent's credential can push a candidate branch and cannot fast-forward master. The joined finding from product management is taken in this run on the record side: the queue tells a commit it minted from one it did not, holds the service, and pages. What that leaves is prevention, and prevention by credential needs a repository host that restricts by branch, which a plain repository does not, so taking it narrows what a customer may host the repository on. Refusing it leaves the exclusivity a matter of administration, detected after the fact by the check in the queue. _What the factory does not build_ places repository administration outside the factory, and only the owner can move that line.

## how-the-factory-works/02-intent-into-items/

### `hazard severity` grades recoverability and carries no magnitude, so the impact half of the score has no input that distinguishes a duplicate email from a wrong dose
**Raised by:** Safety engineering
**Where:** `how-the-factory-works/02-intent-into-items/03-decomposition/03-hazard-severity.md` — "Hazard severity"
**What is wrong or missing:** The field is defined as "the worst harm the software in it can do" but graded "by what the factory can do about that harm afterwards," and the three values are recoverability classes. `irreversible` therefore holds "money paid out, a message delivered to a person, data erased, an actuator driven, a disclosure made" in one bucket, with one response for all of them. Safety engineering keeps severity (magnitude of harm) separate from controllability and from exposure — MIL-STD-882, IEC 61508, ISO 14971, and ISO 26262's S/E/C decomposition all do — because a single ordinal that mixes the two cannot rank two hazards against each other, which is the whole use of the classification.
**What turns on it:** `04-risk-score/01-factors-at-least.md` keeps likelihood and impact separate on the stated ground that "unlikely but catastrophic should be gated regardless," and names hazard severity as "this group's one declared input and the only term in the vector an owner writes." Nothing in the vector carries how bad the harm is, so the rule the score is built around has no input it can read, and the rollout bound and the Implementation resolution treat a marketing unsubscribe and a payment disbursement identically.
**Migration:** The three values sit on owner-authored area records and the value in force is named on every gate firing's factor vector, a chained row of the append-only log that is never migrated; splitting magnitude out later means the owner re-authoring every area (the factory cannot supply it — "nothing the factory observes says what harm the software can do") and leaves every past decision holding a grade under a scale that no longer exists.

**Decision needed:** Whether the area record carries a second owner-authored value beside `hazard severity`: the magnitude of the worst harm, kept apart from how recoverable it is, the way MIL-STD-882 and ISO 26262 keep severity apart from controllability. The document grades the one value by recoverability on purpose, and the rollout bound, the Implementation resolution, and the score's impact term all read that one value. Taking it means the owner authors two values per area, the factor vector carries both, and the rollout bound and the score's published formula are restated over the pair, which is a formula change and so a new score version. Refusing it keeps one value and states at `hazard severity` that a duplicate email and a wrong dose on two `irreversible` areas are treated alike. What turns on it is whether the owner will author magnitude per area, since nothing the factory observes can supply it, and every area a running install holds would need it re-authored. Only the owner can decide what they will author.

### Retiring a service, an environment, or a deploy target has no mechanism
**Raised by:** Absence
**Where:** `how-the-factory-works/02-intent-into-items/03-decomposition/README.md` — Decomposition (the service record and `provisioned`), with the matching row in `records.md`
**What is wrong or missing:** The document has an entrance for software and no exit. A service record gains an identity, owner-authored parameters, `provisioned`, and four deployer-written fields, and nothing ever ends it; the same is true of a persistent environment and of a project. The word appears once as a remedy — `07-contracts/06-what-a-consumer-declares.md` says an unsupported toolchain is "standing, visible pressure to add the extractor or retire the service" — and retiring one is defined nowhere. The only gesture available is deleting a target from the environment record's target field, which `05-environments/01-records-and-one-long-lived-branch.md` states is read "by the drift detector as nothing", so the one check outside the trust domain goes quiet on exactly the software the owner meant to remove.
**What turns on it:** Every per-service mechanism is keyed to a record that outlives the software. The production deploy record still marks a release complete, so *current release* keeps naming a release that runs nowhere, dependants' candidate environments keep being composed from it, and a declared dependency on it keeps holding deploys that nothing lifts. The drift detector's five per-target comparisons, the health monitor's per-service last check, the conformance detector reading "shipped services inside a constraint's reach", and the advisory detector matching "every service's current release" all go on forever: a retired service yields permanent mismatches that hold production deploys and page, and permanent conformance and advisory intents against software nobody runs. `09-gate-policy/03-what-is-not-in-it.md` forbids the obvious escape — records are kept because deleting one breaks a link.
**Migration:** The end state has to be on the service record, the environment record, and the deploy record's completion-per-target, all of which a running install already holds and reads; and *current release* — a query every cross-service check, every candidate composition, and every dependency hold rests on — has no value for "not running", so redefining it later changes what already-shipped installs decided under.

**Decision needed:** What ends a service, a persistent environment, and a deploy target, and what the end does to the records keyed to them. The document has no end state, and the choices are the owner's: whether a retirement is refused while a consumer contract in force names the service, or cascades to a conformance item per consumer; whether *current release* on a retired service is read as none by every cross-service check, the drift detector, the health monitor, and the advisory and conformance detectors; whether the deployer removes the software from its targets, which adds an operation to the set seam 4 declares; and whether a retired record's retention follows the log's or ends sooner. Each is a product choice across mechanisms owned by release engineering, site reliability engineering, security engineering, and data architecture, and *current release* is a query every already-shipped install decided under.

### The requirement carries no form and no atomicity rule, yet it is the unit an owner authors the item-size target in
**Raised by:** Requirements engineering
**Where:** `how-the-factory-works/02-intent-into-items/02-the-interview.md` — _The interview_, and `how-the-factory-works/09-gate-policy/01-what-is-in-it.md` — the **item-size target** row
**What is wrong or missing:** The six EARS patterns bind the criterion; the requirement — the thing EARS is normally a form for — is unstructured prose the factory cuts at its own discretion, with no pattern, no bound, and no check that a statement is singular or verifiable. The document names the consequence twice without a mechanism ("one statement cut too coarsely hides an omission inside itself, where no check downstream can reach it"; "requirements are not commensurable ... an interview that enumerates requirements coarser or finer moves the measured size while the work itself stands still"), then denominates an authored parameter in that unit: the item-size target is "authored in the count of its intent's requirements an item answers," and the score learns a supplied value for it. The interview agent that chooses the granularity is the agent whose decomposition is then measured and gate-checked against that granularity — the same defect the score refuses elsewhere by design ("test coverage is deliberately not among them: it would be computed from the encodings the scored agent authored").
**What turns on it:** Both mechanical completeness rejections (Decomposition's and Spec's) are satisfiable by cutting the reading coarsely, and so is any item-size target; a fleet that drifts toward coarse statements passes every check while the checks measure nothing.
**Migration:** Requirement statements are write-once and "an approval points at what was approved," so a form imposed later binds new intents only, while the owner's authored item-size target and the score's learned value stay denominated in a unit whose meaning changed under them — precisely the silent redefinition the design forbids for a formula change, and one no policy version or score version can name, because the requirement unit has no version for them to name.

**Decision needed:** Whether a requirement takes a form. Two things the document protects pull against each other: the confirming round confirms statements in the requester's words, and the two completeness checks and the item-size target are denominated in the count of those statements. Binding a requirement to a pattern, the six the criterion takes or a rule that one statement holds one condition a check can pass or fail once, changes what a requester confirms and what the interview agent may write; leaving it free leaves the checks and the target measured in a unit the measured agent chooses. A third choice is re-denominating the item-size target in a unit the interview does not set. Only the owner can pick among the three, since each changes what an owner authors or what a requester is shown.

### The only recorded outcome of shipped software is complaint volume, and nobody it was built for is on the record
**Raised by:** Product design
**Where:** `how-the-factory-works/02-intent-into-items/01-intake/02-reports.md` — the intent's **outcome**; `how-the-factory-works/11-screens/01-work-ops-factory-people.md` — Factory ("Beside cost per feature Factory shows each intent's outcome")
**What is wrong or missing:** The outcome of an intent is "computed once at its close" and is one of three things: the requester's acceptance verdict, the before-and-after report rate, or nothing. There is no record anywhere of who the built software is for — no user role, no class of user, no statement of what a person was meant to be able to do — so nothing an owner authors and nothing a criterion states can be about a population, and no signal says whether a shipped change was reached, used, completed, or abandoned. `how-the-factory-works/10-fleet/03-what-an-agent-is-told/01-what-a-version-is-authored-from.md` states the consequence plainly: "the factory learns nothing from the people it builds for." The design system, the state machine, and the four predicates all constrain form; nothing anywhere records effect.
**What turns on it:** The whole autonomy argument rests on the loop closing — the score learns from window outcomes, cost per feature is read beside the intent's outcome, and how much autonomy to allow is decided from the auto-approve and undo pair. That loop is closed on whether software broke and whether strangers complained, which is a floor signal with a long lag and a heavy bias, and it is read as though it said whether the factory built the right thing.
**Migration:** The outcome field is written once at an intent's close, so every closed intent in a running install is fixed as report-rate; and the only thing the factory instruments shipped software to emit is the closed set `what-the-factory-does/04-what-the-factory-does-not-build.md` fixes — "a count and a distribution of durations per interval per closed set of names, and a count of failure records" — which is what the deployer's four service fields, the analysis window's boundary, and the size, confidence and threshold an owner authors are all defined over, and what the comparison against a service's own recent history is computed from.
**Also reached separately by:** Product management — "Nothing on a shipped change records what it was meant to move". Two stances reached this one.

### Nothing on a shipped change records what it was meant to move
**Raised by:** Product management
**Where:** `how-the-factory-works/02-intent-into-items/02-the-interview.md` — _The interview_ (the requirement set and the acceptance round); `how-the-factory-works/08-operations/01-the-health-monitor.md` — _The health monitor_ (the quantities and how they are emitted).
**What is wrong or missing:** The intent carries a statement, confirmed requirements, a tier and a deadline, and nothing saying what the change should move in the running product; the six criterion patterns are decided against a run on a candidate environment; the quantities the factory instruments its own output to emit are fixed and shipped with the product — request rate, error rate, latency and failure counts over a closed set of names, with "nothing of the request's content" — and the window's four exits ask only whether the release regressed. An intent's entire outcome is a requester's yes/no at an explicitly unbounded wait, a before-and-after report rate, or nothing at all where the factory raised it.
**What turns on it:** An install can report throughput, rework rate, gate rejection rate and cost per feature, and can never report that anything it shipped achieved what it was asked for — which is the question the assigned row exists to answer. The window limit, the thresholds and the per-author prior are all calibrated from health-only outcomes, with no field distinguishing "did not regress" from "delivered what was wanted."
**Migration:** The emission format is fixed and versioned with the product and the store's closed name set is a floor the host already satisfies, so any product signal means re-instrumenting every service every install has built and starting its history at zero; and the intents already delivered carry no target to be read against, the statement being written once.
**Also reached separately by:** Product design — "The only recorded outcome of shipped software is complaint volume, and nobody it was built for is on the record". Two stances reached this one.

**Decision needed:** Whether the factory records what a shipped change was meant to achieve and reads whether it did. Two disciplines reached this separately, product design and product management. _What the factory does not build_ fixes what the factory instruments a service to emit as a closed set of counts and durations with nothing of a request's content, and the intent's outcome is the requester's verdict or the report rate. Taking it means an intent carries a target the requester confirms, a service emits a signal the target is read against, and the outcome field gains a value for it, which changes the emission format every built service ships with and puts request content or user identity inside what the factory reads. Refusing it means stating at the outcome that the factory learns whether software broke and whether people complained, and not whether it did what was asked, which is the concession the fleet section already makes. Only the owner can decide whether the factory reads the product's use, since that is what the closed set was fixed to keep out.

## how-the-factory-works/02-intent-into-items/01-intake/

### The harm page is bounded by a source identity that resets every session, and by nothing else
**Raised by:** Trust and safety
**Where:** `how-the-factory-works/02-intent-into-items/01-intake/02-reports.md` — _Reports_ (the opaque key and the two rates), read against `how-the-factory-works/08-operations/07-pages.md` — _Pages_ ("what bounds a stranger's use of it is the same per-source rate the report channel already bounds arrival by") and `how-the-factory-works/09-gate-policy/03-what-is-not-in-it.md` — _What is not in it_ ("where an owner authors neither rate, arrival is unbounded").
**What is wrong or missing:** The only per-source handle is "an opaque key where the deployed software supplies one, derived from its own session and salted", so a source is a session: a stranger gets a fresh identity per submission, and reports may carry no key at all. The two rates that actually exist are per-service and channel-wide, explicitly "never any individual", and are unbounded until an owner authors them — while the harm page is on by default and fires "at any hour" to whoever holds (2), one page per intent, with a grouper that "prefers to group" but is defeated by varied text. Nothing anywhere in the document blocks, suspends, or scores a source; _Pages_ asserts a per-source bound that _Reports_ says does not exist as an authored value and that a session-scoped key could not carry in any case.
**What turns on it:** On a default install, one anonymous stranger can wake named humans indefinitely and spend model quota and Spec attention per fabricated intent; the only lever is the global off switch, which discards the one mechanism the design built for a person being harmed, and the coarse rates, which drop real reports to stop one actor. The mechanism the design most wants to be trustworthy is the one an adversary controls the volume of.
**Migration:** A durable source identity is a field on the report record and on the way-in shipped inside every already-built service; the document states it "cannot be added to reports already written", and adding one later re-cuts the anonymity the channel was published to reporters under, so no running install can retrofit an enforcement handle over the corpus and the population it already collected from.
**Also reached separately by:** Security engineering — "The one inbound path from outside the factory is not a declared seam and carries no identity the store can check" (same missing identity, from the seam side).

**Decision needed:** Whether a stranger's use of the harm mark is bounded by anything more than the two coarse rates and a per-session key, and by what. _Reports_ refuses a reporter identity so that the channel carries nobody's, and the per-source rate _Pages_ cites is keyed on a session the reporter can renew at no cost, so on a default install one anonymous source can page whoever holds (2) once per fabricated intent without limit. Taking it means one of two things the document protects gives way: a durable per-source handle on the report record and in the shipped way in, which re-cuts the anonymity the channel was published under and cannot reach reports already written; or a bound on the harm page itself, a count per service per interval past which a marked intent waits at Work rather than pages, which delays a real person's page behind a stranger's volume. Refusing it means the factory-wide rate and the per-service safeguard stay the only levers, both of which drop real reports to stop one actor. Only the owner can weigh the channel's anonymity against a page whose volume a stranger controls.

### A design system has no compatibility axis and no version an owner can pin, so a factory upgrade detonates a project-wide migration nobody chose
**Raised by:** Design systems
**Where:** `how-the-factory-works/02-intent-into-items/01-intake/01-constraints-and-the-design-system.md` — _Constraints and the design system_
**What is wrong or missing:** "The design system's constraint record is its version," and a move is a withdrawal plus a second record. There is no compatibility promise on that pair, so adding one component, fixing one token value, and renaming every component are indistinguishable: each "sends back every unmerged item in a project whose builds name a design system, whether or not that item touches a screen," and each raises conformance items across every departing service. The document argues the opposite case for contracts — semver exists because "a single number per service cannot express several independent promises" — and gives the design system, which is a published interface with every screen in the project as its consumer, no such promise. Worse, one of the two movers is not the owner: an upgrade that changed the shipped system "is detected by the factory at its first start on the new version, which calls intake to write the pair itself," and upgrading is hosting, done by whoever runs the install for unrelated reasons. There is no field on the constraint by which an owner pins a system version, stages adoption, or defers the pair.
**What turns on it:** A customer who patches the factory for a security fix loses every in-flight item in every project with screens to a re-verification failure and acquires an unbounded conformance backlog in the same start, with no way to have said no. There is also no component identity across the pair: a safeguard (9) names "a component of the design system in force on a project," and the document already concedes "a safeguard naming a subject nobody declared is a dangling reference nothing detects" — so an upgrade that renames a component silently removes the human the owner put in front of it, which is the one operation the design refuses everywhere else without a gate.
**Migration:** The constraint record carries no version or pin field and the build names a single design-system record; adding a compatibility promise or an owner-authored pin changes both record shapes and turns the re-verification test from "the two records differ" into a compatibility judgment, and every install already holds constraint records and builds written under the first meaning — including safeguards owners authored against component names with no identity to carry forward.

**Decision needed:** Whether a design system carries a compatibility promise and an owner-authored pin, or stays one record whose every move is a project-wide migration. _Constraints and the design system_ makes the constraint record the version, so a token fix and a rename of every component take the same pair, send back every unmerged item in the project, and raise conformance items across every departing service; and an upgrade of the factory writes the pair itself where the shipped system changed, so whoever hosts the install moves every project with screens without the owner choosing to. Taking it means a promise on the pair, of the kind contracts carry, that turns the queue's re-verification from a comparison of two fields into a compatibility judgment; a pin field by which an owner holds a project on a shipped system across an upgrade; and a component identity that survives a rename, so a safeguard naming one does not dangle. Refusing it means stating that a design-system move is always the full migration set and that an upgrade moves it, at the cost the finding names. Only the owner can decide whether the design system, which the document holds as one permanent constraint, becomes a versioned interface with a promise of its own.

### The system cannot grow from inside and there is no recorded deviation, so a screen needing anything the system lacks dead-ends
**Raised by:** Design systems
**Where:** `how-the-factory-works/02-intent-into-items/01-intake/01-constraints-and-the-design-system.md` — _Constraints and the design system_
**What is wrong or missing:** Where the system arrived as code, the diff decides "that a screen is built from the system's components, styled from its tokens, and calls no component against its declared interface," and a build-kind constraint "rejects at _Implementation_." A design system is only ever moved by an owner's upload or a factory upgrade; nothing in the pipeline can propose a component, and there is no exception or deviation record by which a screen ships a pattern the system does not cover with the departure named and decided. _Implementation plan_ says the plan settles "what a screen looks like where the design system is silent" — but for a code system, whatever the plan settles there is precisely what the diff rejects, so the two statements cannot both hold. Design-system governance — contribution back, deprecation of a component with the uses waiting on it, an approved exception — is the standard machinery for this and the document names none of it, while it builds all three for contracts.
**What turns on it:** The factory is autonomous everywhere except here: any net-new interface pattern rejects at Implementation until the attempt limit escalates it (11, 12), and the only fix is out-of-band — the owner authors and uploads a new design system, which by the finding above costs a project-wide migration and sends back all in-flight work. The permanent constraint the design calls the one "a project with a user interface always has" is therefore also the one thing that can permanently stop the pipeline, and Factory's three departure numbers report drift without distinguishing a deviation somebody decided from one nobody noticed.
**Migration:** The contents field is derived by intake and "never edited after," and intake is the constraint's only writer, so letting the factory contribute a component, or letting a build carry an approved deviation, adds a second writer to a record with one and a field to a build record installs already hold — and every screen shipped before it has departures recorded as drift with no decision behind them.

**Decision needed:** Whether a screen may depart from a code design system with the departure recorded and decided, and whether the pipeline may propose a component to it. Today the diff at _Implementation_ rejects any screen not built from the system's components, the system moves only by an owner's upload or a factory upgrade, and no record carries an approved departure, so a screen needing a pattern the system lacks fails until the attempt limit escalates it and the only remedy is an upload that sends back every in-flight item in the project. Taking it means either a deviation record on the build that a human decides at a gate, which adds a field to a record installs already hold and a second thing the diff reads, or an item that contributes a component to the system, which gives the constraint's contents field a second writer where the document allows one. Refusing it means stating that a code design system is closed to the pipeline and that a screen it does not cover waits on the owner. Only the owner can decide whether the design system, which the document keeps authored outside the factory, may be changed by the factory's own work or departed from on a record.

## how-the-factory-works/03-gates/

### A human at a gate has no way to record that they could not judge what they were shown
**Raised by:** Human factors
**Where:** `how-the-factory-works/03-gates/03-actions-at-each-gate.md` — _Actions at each gate_; and `how-the-factory-works/03-gates/01-where-a-gate-is-and-what-decides-it.md` — the close event's verdict
**What is wrong or missing:** The close event admits approve, reject, or hold, and hold is defined as a fact about the event rather than about the human, offered only at the two deploy rows. A human put at a gate by a threshold, a safeguard (9), a review-sampled row, or a resolved factor — a factor the score itself could not compute — has no disposition that says "I could not decide this." Reject is not that disposition: it asserts a fault, names a stage the item returns to, spends an attempt there, and is read by the score as a gate the factory needed. Approve is the only exit that costs the human nothing and blocks nothing, which is the exit the field predicts under low competence, time pressure, or a diff larger than a person reads.
**What turns on it:** The design's own claim is that "a human at a gate is an instrument, and the design reads it," and the instrument has no null reading: a human who read the change and agreed, and one who could not tell, write the same row. The auto-approve/undo pair, the per-human pair, and the review-sample comparison that _What the factory auto-approved, and what was undone_ exists to make all rest on that row, and the risk threshold is authored against them. The residual left by leaving the row open instead — the item stalls with no bound and no page — is worse, not an answer.
**Migration:** The verdict is a field of a chained close event and the whole training corpus of the score; a fourth disposition added later leaves every approve already in the chain ambiguous between agreement and inability, and the score and the owner-authored thresholds standing on that mixed number cannot be recomputed.

**Decision needed:** Whether the close event gets a fourth verdict, one that says the human could not judge what they were shown, and what that verdict does to the item and to the score. The document offers three, approve, reject, and hold, and reads a human at a gate as an instrument over them. A fourth needs three things only the owner can settle: what happens to the item, whether the row re-fires to another holder of the duty, to the owner, or waits with a bound; whether the verdict counts an attempt; and how the score reads it, since a row closed with it is neither a gate the factory needed nor a human agreeing. The verdict is a field of a chained close event and the whole training corpus of the score, so the choice is made once: an approve written before a fourth verdict exists cannot be told from an inability afterwards. What turns on it is whether the auto-approve and undo pair, the per-human pair, and the review-sample comparison measure detection or measure the cheapest exit.

### Nothing in the record graph is the unit a user experiences: no flow, and a screen has no record
**Raised by:** Product design
**Where:** `how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/04-the-screen-state-machine.md` — The screen state machine; `records.md` — the "not records" list ("A screen is the chain of state machines superseding one another")
**What is wrong or missing:** The largest user-facing unit the design holds is one screen, and even that is not a record — it is a chain of per-service state machines whose identity is "the id of the state machine that introduced it", and the file admits "nothing mechanical stops two items introducing two chains for what a human would call one screen". Above that there is nothing: the words flow, journey, and navigation appear nowhere in the document, and no record says which screens follow which, or what a person is trying to accomplish across them. An item names one service, a state machine is written per item at Spec, and a candidate environment is composed for one candidate — so a sequence of screens spanning two services is two items, two specs, two criterion sets, two runs, and no gate anywhere decides the whole. The design-system predicates (contrast, name, focus order, target size) are decided per declared state of one screen, which is the smallest scope a product-design defect ever lives in.
**What turns on it:** The seam between two screens — the place a user is dropped, sent back, or left without a way forward — is invisible to every mechanical check, every gate, and every human confirmation, and reaches the factory only as an end-user report. The document's traceability claim reaches back from a release to an intent but never sideways to what a person was doing.
**Migration:** Screen ids are opaque, stable, never reused, and minted per introducing state machine, with no fact anywhere joining two chains; a later screen or flow record has to be assigned by a human, per chain, per install, and the enumeration the screen predicates are decided over ("which are in force for a build") is computed off that per-service chain query.

**Decision needed:** Whether the factory holds a record above one screen: a flow, a sequence of screens a person crosses to accomplish one thing, possibly spanning two services and so two items. The document holds no screen record on purpose, a screen being the chain of state machines a build can check, and it says the seam between two screens rests on a human noticing at Spec. Adding a flow means a new authored record with a writer, a human to author it per chain and per install, a gate or a predicate that decides over it, and a reader for it at decomposition, where an intent is cut into items per service. Refusing it leaves the seam between screens reachable only through an end-user report, which the document already states as the residue. This is a product choice about what the factory checks and who authors it, and only the owner can decide whether a flow is worth a record, a human, and a check.

### A criterion that exists to control a hazard is indistinguishable from any other, and is withdrawn under the same rule
**Raised by:** Safety engineering
**Where:** `how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/01-the-record.md` — "The record" (with `how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/02-in-force-and-withdrawal.md`)
**What is wrong or missing:** Criterion provenance has exactly two named sources — `constraint-derived`, a field written once in the introducing call, and `human-confirmed`, a query over the introducing decision — and everything else is factory-drafted. There is no hazard record and no provenance that says a criterion is the control for an identified unwanted condition, which is the artifact the field normally requires: hazard, cause, control, and the traceable link between them. `03-the-six-patterns.md` supplies the unwanted-condition sentence form and states that "nothing mechanical will ever ask for the unwanted conditions," offering a count instead; the count says how many exist, never which hazard any of them answers. Consequently a factory-drafted control criterion is withdrawn with no routing, while `02-in-force-and-withdrawal.md`'s routed withdrawal reaches only the two named provenances — so a control survives only where the hazard happened to arrive as a law.
**What turns on it:** Withdrawing a criterion is "the one edit that removes protection" by the document's own words, and an agent authoring a spec version may remove a hazard control with no human and no record that a control was what left. It also means no query answers what protects against a named hazard, which is the question an auditor, a regulated customer, and the human at an `irreversible` Implementation gate each ask.
**Migration:** A criterion record is written exactly once, never written again, and correcting one is a withdrawal plus a reintroduction at a Spec gate; adding a hazard provenance later leaves every criterion standing in a running install unlabelled with nothing to derive the label from, and re-provenancing them is one human-decided spec cycle per item across the whole codebase.
**Also reached separately by:** Requirements engineering — "`constraint-derived` provenance names no constraint, so the routing it promises cannot resolve and conformance is unanswerable" (same record, provenance too thin to route on).

**Decision needed:** Whether the factory holds a hazard record, and a third named provenance for a criterion that is the control for one. The half of this finding it shares with requirements engineering is taken in commit cb19fd0: constraint-derived provenance now names the constraint, so a control whose hazard arrived as a law is routed and queryable. What remains is the hazard that arrived as nobody's law. The document holds hazard severity as a grade per area, authored by the owner and read by three things, and holds no hazard as a record: the six patterns say nothing mechanical will ever ask for the unwanted conditions, and offer a count. A hazard record needs an author, which is the owner or a human at Spec since the document refuses to have the factory judge what harm is; a link from the criterion, written once in the introducing call like the constraint link; a routed withdrawal, which the two named provenances already have and the third would take; and a reader at the `irreversible` Implementation gate. Refusing it leaves a factory-drafted control withdrawable by an agent with no human, as the finding states. Only the owner can decide whether a hazard is a thing the factory records and a human authors per area, which is a duty the numbered twelve do not name.

## how-the-factory-works/04-risk-score/

### Every approval acquires an outcome; no rejection ever does, and the per-human numbers are published on the approvals alone
**Raised by:** Human factors
**Where:** `how-the-factory-works/04-risk-score/02-how-it-learns.md` — _How it learns_; and `how-the-factory-works/11-screens/04-what-the-factory-auto-approved-and-what-was-undone.md`
**What is wrong or missing:** An approval is followed to an outcome — undone (10), rolled back, a window that failed — and a rejection is followed nowhere. "A rejection at a review-sampled row is a gate the factory would have passed and a human did not, which the score already learns from" takes the rejection as evidence the gate was needed without any record of whether it was borne out, and the threshold moves down on it and up on nothing but the held-out sample. Beside that, Factory publishes per named human what each approved and how often it was later undone, and publishes nothing about what each rejected. Both asymmetries point the same way: rejecting or holding is the response with no measurable downside to the person, and it is also the input the threshold is learned from. This is the false-alarm cost the design measured for the page channel and did not measure here.
**What turns on it:** The one parameter that decides how much human work the factory removes is trained on rejections nothing validates, by humans who are scored on approvals only. The predicted drift is toward more human review at every gate, indistinguishable in the record from the score having got worse, and the review-sample reading cannot separate them because a rejection there is exactly what moves the threshold.
**Migration:** The counter-evidence has to be written when the rework happens — whether the re-authored artifact changed what the rejection named, and how the rejection resolved. It is not reconstructible from a chained log that stored the verdict and the feedback alone, so an install that has run a year holds a score version and an owner-authored threshold standing on rejections that can never be scored.

**Decision needed:** Whether a human's rejection stays an input the risk threshold falls on. Nothing in the record can bear a rejection out: the rejected version is never shipped, so a rework that then passed is consistent with the rejection having been right and with it having been a false alarm, the same ambiguity _How it learns_ already states for a gated change that turned out well. Two things the document protects pull against each other. _How it learns_ counts a gate the factory would have passed but a human rejected among the outcomes the score learns from, which is the one input a review-sampled row produces; and the review sample exists to measure a human's detection rather than assume it, which a threshold falling on unvalidated rejections defeats, since rejecting becomes the response with no cost to the person and a lever on the one parameter that decides how much human work the factory removes. Taking the finding means the threshold learns from outcomes alone, with a rejection recorded and published per human beside the approvals, split by what put the human at the row and by how each rejection resolved: the re-authored version approved, rejected again, or the item reaching the attempt limit, with whether the re-authored version differed from the rejected one by content digest. Refusing it keeps the rejection as an input and adds the per-human publication only, accepting the drift the finding predicts as the cost of the signal. Only the owner can weigh a threshold that falls on a human verdict nothing scores against losing the one input a review-sampled row contributes.

## how-the-factory-works/05-environments/

### One store per service per environment is assumed but never stated, and the schema history cannot distinguish two
**Raised by:** Database migration engineering
**Where:** `how-the-factory-works/06-releases/05-the-deploy-record/01-a-schema-change.md` — _A schema change_; `how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md` — _Records, and one long-lived branch_
**What is wrong or missing:** An environment names **targets**, plural and ordered, and the deploy record carries completion per target — but the schema change is applied once, "to the service's store", through "the credential the environment's record holds", and the schema history is kept per service store with rows keyed by change identity alone. A service whose targets each hold their own store (a database per region, or shards) has no expression in any of this: the credential is the environment's, not the target's; the history rows say nothing about which store they describe; and the drift detector's fifth comparison reads "the schema history... in each service's store" as one thing. `What the factory does not build` refuses mobile apps, firmware, libraries, CLIs and scheduled pipelines at adoption by name, but never refuses a service whose store is not single.
**What turns on it:** Such a service deploys with its schema applied to one store and its code running against several, and the divergence is invisible to the fifth comparison, which reads the one store the credential resolves to. The rollout order the owner authored over targets — "the whole of what limits how much of production a release reaches before anything has read it" — becomes an order over stores nobody migrated.
**Migration:** The history table lives in stores the factory does not own and is keyed without a store or target identity; giving it one later means rekeying that table in every customer production store, and the environment record would have to move the store credential from the environment onto the target, a field two writers already share by kind.
**Also reached separately by:** Platform engineering — "A service's deploy targets are a field of the environment, so every service in a project must run on every target".

**Decision needed:** Whether a service may hold more than one store per environment, one per target, or whether a service whose store is not single is refused at adoption and at decomposition the way a mobile app or a library is. The document writes "the service's store" throughout: the schema history is kept per service store, the candidate environment creates one store, the schema change is applied once through the environment's credential, and drift detection's fifth comparison reads one history. Taking the finding means the store becomes a thing declared per target, with the credential moved from the environment onto the target, the history rows keyed by store, the schema step of a deploy performed per target under the completion-per-target field, and the fifth comparison reading each store in turn. Refusing it means a row in _What the factory does not build_ naming the shape and a check at adoption that reads one store per environment from the service's declaration. Either is a product choice the document does not imply: the first admits regional and sharded databases at the cost of a per-target schema step and a rollback whose target is several stores; the second rules them out at adoption by name. Which is right turns on whether the customers the factory is for run such services, which only the owner knows. Platform engineering reached the same field from the placement side; that entry follows this one.

### A service's deploy targets are a field of the environment, so every service in a project must run on every target
**Raised by:** Platform engineering
**Where:** `how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md` — "An environment names its **targets**, plural", and `how-the-factory-works/06-releases/05-the-deploy-record/README.md` — "It is keyed by service and environment and not by target"
**What is wrong or missing:** The address list, its rollout order, the per-target "serves a share" flag, and the credential all hang off the environment record, and a persistent environment "contains a project — every service in it", so no record can say that service A runs on two of the environment's four targets and service B on the other two. `records.md` settles the ambiguity against the service record's deployer-written "a target it reaches" by stating flatly that "A deploy target is a field of the environment." Real projects are heterogeneous in placement — an edge-hosted front end, a batch host, a regional backend — and the design has no way to express it.
**What turns on it:** Current release is "marked complete on every production target", so a service that does not run on a target can never become current, its consumers' dependency holds at _Deploy to production_ never lift, and the drift detector reads that target each pass and mismatches on it. The score picks the row with a control "only where every target of the environment serves one", so one service on a share-less platform disables control-based rollout, the analysis window's comparison, and the rollback path for every other service in the project.
**Migration:** Targets, their order, the share flag, and the credential are owner-authored on a record already written, and every deploy record's completion-per-target map plus the current-release rule read over them; re-keying targets per service means re-authoring every environment an install created and re-interpreting the per-target field on every deploy record already written, which the drift detector's separate store is keyed against.
**Also reached separately by:** Database migration engineering — "One store per service per environment is assumed but never stated, and the schema history cannot distinguish two" (the environment-level credential and per-target grain, from the store side).

**Decision needed:** Whether a service may run on a subset of an environment's targets, or every service in a project runs on every target and heterogeneous placement is two projects. Targets, their order, the share flag, and the credential are fields of the environment, and the current-release rule, the deploy record's completion per target, the score's strategy pick, and the drift detector's per-target reads all read them there. Taking the finding means the set of targets a service is deployed to becomes a field the owner authors per service, on the service record or on the environment per service, and every reader over targets re-reads against that set: current release is completion on the service's targets, the drift detector reads those and no other, and the score reads the share flag over those alone. Refusing it means stating that a project's services share one placement and that a front end hosted elsewhere is a service in another project, which the candidate environment's cross-project composition already allows. The first costs a field two writers already share by kind, re-keyed; the second costs a project boundary drawn by hosting rather than by product, and a consumer contract across it for every call. Which is right depends on what placements the factory's customers have, which is the owner's to say. Database migration engineering reached the same field from the store side; that entry precedes this one.

### "The platform" is defined per service and accounted for as one thing per install
**Raised by:** Platform engineering
**Where:** `how-the-factory-works/05-environments/02-an-environment-per-candidate.md` — "How much room the platform has is read rather than modelled", against `how-the-factory-works/03-gates/02-the-rollout-strategy.md` — "the **platform** — whatever a service runs on"
**What is wrong or missing:** The platform is defined per service, but the deployer keeps one unkeyed last check "for the platform" holding three counts, and _Deploy to candidate environment_ authors a single **maximum concurrent candidate environments** on the factory-wide settings record. Nothing on any record names which platform a given service's candidate environment is composed on, or what credential the deployer composes it with — a candidate environment's credential reference is "written by the deployer at creation rather than authored by anybody", with no stated source. Nor is there any declaration that a service's platform can create an environment on demand at all, though the analogous capability question — whether a target serves a share — is a declared field the score reads precisely so the deployer never attempts what the platform cannot do.
**What turns on it:** An install whose services run on more than one platform — two projects, or one adopted service on a different host — sums standing environments, held environments, and room across platforms that hold none of each other's, so the hold at _Deploy to candidate environment_ fires against a total no platform reports and _Factory_ shows an owner a number that means nothing. A service on a platform that cannot compose an environment at all holds at that gate permanently, indistinguishable from "no room now", with no page and nothing for the factory to free.
**Migration:** The concurrency ceiling is authored outright by the owner and the platform last check is a record with no key; keying either per platform after installs have authored one global number changes the shape of a record the store holds and re-scopes a value an owner already authored against, and the candidate environment records already written name no platform to key them by.

**Decision needed:** Whether the platform is a thing the factory records, and at what grain: per install, per environment, per project, or per service. The design defines it per service, as whatever a service runs on, and counts it per install: one unkeyed last check holding three counts, and one factory-wide ceiling on concurrent candidate environments authored at Deploy to candidate environment. Taking the finding means a platform declared on a record, most plausibly the production environment record beside the targets it already holds, carrying the credential the deployer composes candidate environments through and whether it can compose one on demand, with the last check and the ceiling keyed by it; a service on a platform declared unable to compose one would then hold at that gate with a page, distinguishable from no room now. Refusing it means stating that an install has one platform and that a service hosted on another is not adopted, a row _What the factory does not build_ would carry. The choice adds a field an owner authors before the factory can compose anything for a service, and re-scopes the one ceiling an owner may already have authored against an install-wide count, which is why it is the owner's and not the document's to make.
