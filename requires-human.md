# Requires human

Findings the unattended loop could not take, moved here verbatim, each followed by the decision it needs.

## how-the-factory-works/05-environments/

### Nothing outside the factory is part of a candidate environment's composition, so a run against a third party is unrecorded and unisolated
**Raised by:** Test architecture
**Where:** `how-the-factory-works/05-environments/02-an-environment-per-candidate.md` — _An environment per candidate_
**What is wrong or missing:** The composition is "the current releases of its dependencies ... never another service's candidate", and the field the deployer writes names "each dependency and the release of it that was current then" — services the factory releases, and nothing else. _The health monitor_ elsewhere acknowledges "a dependency outside the factory, a third-party API or a store the owner runs". The design never says what a candidate run does when the build calls one: whether it reaches the real provider from every candidate, every mutant run, and every re-verification, or reaches nothing and leaves those criteria permanently undecided. No test double, sandbox, or declared external endpoint appears anywhere, and the only isolation offered is the non-production configuration set, which is optional and which _Records, and one long-lived branch_ says resolves secrets by name at deploy through one resolver.
**What turns on it:** Every criterion, store declaration, consumer contract, and security predicate over a path that leaves the factory is decided against something the record does not name. The merge queue's three-way attribution reads the composition field to decide whether a failure is the author's defect or a moved dependency; an external that moved between the two runs compares equal, so it is booked as the author's defect and moves the per-author prior. And a candidate resolving a production secret by name performs real side effects once per mutant, per rebuild, per re-verification.
**Migration:** The external would have to be a declared thing on the service record and an entry in the composition field a result carries, and the resolver scoped by environment kind — the composition field is copied onto builds already held, so past results can never be re-read to say what a run reached, and priors trained on the mis-attribution cannot be un-trained.

**Decision needed:** What a candidate run reaches when the build calls something the factory does not release: the real provider through a value in the non-production configuration set, a double the owner supplies, or nothing, with every criterion over that path undecided. The document keeps production values off a candidate environment and resolves secrets by name through one resolver, but declares no external dependency on any record, so no run records what it reached and the queue's three-way attribution cannot see one that moved. Taking the finding means an external declared on the service record with the address the non-production set gives it, named in the composition a run's results carry, and the resolver refusing a production value to an environment of the candidate kind; a candidate against a declared external the owner has given no non-production address would then leave those criteria undecided rather than reach the provider. Refusing it means stating that a candidate reaches what its configuration resolves and that the owner's non-production set is the whole of the isolation. The first costs a declaration per external before a service that calls one can merge; the second performs real side effects once per mutant, per rebuild, and per re-verification against whatever the resolver returns. Which is acceptable depends on the externals the customers' services call, which the owner knows and the document does not.

### A release minted for a human-accepted commit names no item, and whether it mints producer contract versions is unstated
**Raised by:** The read-through of the consistency pass, run after the review-findings loop
**Where:** `how-the-factory-works/05-environments/05-what-the-queue-reads-before-it-mints.md` — "Or a human accepts the commit at Work, a log row naming them as actor, and the queue builds it, re-verifies it as it re-verifies a candidate, the contract checks included, and mints its release in master's order naming the build and no item."
**What is wrong or missing:** The identity the read-through confirms is item plus build as a candidate, the same build in production, an ordinal attached at merge, contracts versioned alongside it. For this release the first leg is detached and declared ("A release naming no item is one no gate decided"). The fourth is unanswered: `records.md` writes a contract version "at the fast-forward of the first release that publishes it", and an accepted commit is on master already, with no fast-forward.
**What turns on it:** Whether a consumer that reaches an interface the accepted commit changed sees a contract version naming that release, or reads the version the last queue-merged release published.

**Decision needed:** Whether the queue mints producer contract versions for a release it minted over an accepted commit, and if so at which event, since no fast-forward occurs.

## how-the-factory-works/07-contracts/

### The producer's per-field observables have no emission, no store, and no writer, and would break the cardinality bound the store is specified under
**Raised by:** Observability engineering
**Where:** `how-the-factory-works/07-contracts/05-what-a-diff-cannot-see.md` — "The producer compares its own observables"
**What is wrong or missing:** That layer requires, per field and per release, a population rate, the spread of enum values, and the distribution of numbers. Nothing else in the document provides them: the outside row in `records.md` names exactly two kept kinds (arrival counts and duration distributions on a closed name set, and failure-record counts); the emission the Implementation gate checks is "the numbers that comparison reads", meaning the three quantities; `components.md` gives the health monitor no such reading and gives no other component one. Worse, the health monitor's own store rule says "a record carries nothing of the request's content" and "the number of series grows with releases and targets and never with users or requests" — a per-field value distribution and per-field enum spread are field content, and their key set grows with the schema and with observed enum values.
**What turns on it:** This is one of the three layers the design offers against a semantic break a diff cannot see, and the only one that runs on production traffic; without an emission and a kept shape it is a claim rather than a mechanism. It also contradicts, rather than extends, the cardinality and content bounds the store was designed around.
**Migration:** It is a fourth kept kind in the store and new emission inside every build; every release already shipped emits nothing of it, so "each against the release this one replaced" has no counterpart data for the first release after the change, and the store's cardinality budget and the failure-record key cap have to be re-derived on installs already holding series.

**Decision needed:** Whether the producer's own comparison of its observables stays a layer of the design, and if it does, at what price to the health monitor's store. The layer as written needs, per field of every published contract and per release, a population rate, a count per enum value, and a distribution of a numeric field's values, compared against the release replaced, which means an emission every build carries and a fourth kept kind in the store. The store's two bounds were set on purpose: a record carries nothing of a request's content, and the series count grows with releases and targets and never with users or requests. A per-field profile keyed by contract version stays inside the second bound if the enum keys are the contract's declared domain and the numeric shape is a fixed bucket set, and it is arguable either way on the first, a count per declared value being an aggregate of content rather than content. The alternatives are to keep the layer and extend the store, with a kept shape, a cardinality budget re-derived on installs already holding series, an emission the Implementation gate checks, a writer, and no counterpart for the first release after the change; or to drop the layer and let declared meaning, the consumer contract checked on the candidate, and the consumer's own error rate be what covers a semantic break. What turns on it is whether the design keeps any layer that runs on production traffic against a semantic break, against the cost of an emission inside every build the factory writes and a store whose bounds were chosen so the factory's own footprint stays fixed.

## how-the-factory-works/08-operations/

### Latency and error rate are keyed by service, not by operation, so the quantity the window reads pools every endpoint together
**Raised by:** Observability engineering
**Where:** `how-the-factory-works/08-operations/01-the-health-monitor.md` — "What is kept is not what is emitted" (and the emission paragraph above it)
**What is wrong or missing:** The stored series are keyed on `(service, release, target)` and `(service, release, target, outcome)`; no route, operation, or job-kind name appears anywhere in the document. The design argues at length that pooling across targets dilutes a localized regression — "Pooled, a regression confined to one target is diluted by every target it is not on and can sit under a boundary sized for the whole service" — and then pools across every operation of a service, where the dilution is far larger and the confounding is worse: a shift in traffic mix moves a service's pooled latency and error rate with no code change at all, which is the standard reason latency is keyed per operation.
**What turns on it:** The size an owner authors is a change "in those quantities" of a service as a whole, so a doubling of latency on an endpoint carrying five percent of traffic is below any size a service can support, and the own-history reading crosses on ordinary diurnal mix shifts — a spurious crossing inside a window is an unattended rollback, outside one an item on a service with nothing to fix that exhausts the attempt limit and pages. Both the comparison's per-target argument and the SLO's "proportion of a quantity that must be good" are built on the pooled quantity.
**Migration:** The key of every series the store already holds, the cardinality cap authored on the service record, the set the authored confidence is held over, and the meaning of every explicit threshold and objective an owner authored all change together; a running install's history is not readable at the new key, so the own-history reading and the SLO budget have no comparable past across the change.

**Decision needed:** Whether the kept series carry an operation name beside service, release, and target, so that the comparison and the own-history reading are taken per operation the way they are taken per target. The per-target argument the document makes applies to operations unchanged, and the traffic-mix confound it names is real: a service's pooled latency and error rate move with which endpoints are called and not only with the code. Against it stand three things the document set on purpose. The series count would grow with a service's operations, which are a fact of its code and not of the closed name set the store's bound is stated over, so the cardinality cap on the service record and the store's growth rule would both be restated. The confidence is held over the set of quantities and targets, and a set of quantities, targets, and operations is larger by a factor of the operation count, so the stricter per-quantity boundary needs that much more traffic and a service near the edge of closing a window on evidence loses the early exit on every operation at once. And the size, the explicit threshold, and the objective are each authored per service, so per-operation series either keep a per-service parameter read against per-operation numbers or become a parameter per operation an owner authors. Which of those an owner wants is a product choice: the finer reading with its traffic cost and its authoring surface, or the pooled one with a confound the document would then have to state as a cost of the own-history reading. What turns on it is whether a regression confined to a rarely called operation is one the factory can catch, and whether an ordinary shift in traffic mix is one it wrongly acts on.

### The emission and the retained aggregate fix the variance model before it is chosen
**Raised by:** Applied statistics and sequential testing
**Where:** `how-the-factory-works/08-operations/01-the-health-monitor.md` — _The health monitor_ ("How the three are emitted is fixed"; "What is kept is not what is emitted"), and the store row of `what-the-factory-does/04-what-the-factory-does-not-build.md` — _What the factory does not build_
**What is wrong or missing:** The emission is two records naming service, release, target, outcome and duration, and the store keeps counts plus "a distribution of durations" per interval per that closed set. Two things a comparison needs are absent: any key identifying the unit traffic was split on, so requests are analysed as independent when the platform routes by user, session, or source and their outcomes cluster — which understates variance and breaks the authored confidence in the unsafe direction; and any statement of what form the duration distribution takes, though a quantile summary that is not mergeable across intervals cannot be recombined for the own-history reading, and a fixed-bucket histogram sets a floor under the latency size no authored value can go below.
**What turns on it:** The realized false-rollback rate and the meaning of `passed` both rest on a variance estimate the retained data cannot support, and the latency half of every comparison is bounded by a bucketing choice nobody authored.
**Migration:** Both are shapes the factory bakes into the instrumentation of every service it wrote and into a host store the document already requires to hold a year or more; adding an assignment key or changing the retained distribution re-instruments every service and leaves the history it is read against in the old shape.
**Also reached separately by:** Observability engineering — "The stored "distribution of durations" has no representation and no bucket boundaries".

**Decision needed:** Whether the emitted record and the kept series carry a key for the unit the platform routes traffic on — a user, a session, a source — so that the comparison's variance is estimated over that unit and not over requests. The histogram half of this finding is answered with the observability finding in the same block: the kept distribution is a fixed-boundary histogram the factory ships, mergeable across intervals, instances, and arms, with the bucket width the floor under any latency size. What remains is the clustering. Requests routed by user or session have correlated outcomes, so a boundary that reads them as independent understates the variance and the authored confidence does not hold. Against a key stand three things the document set on purpose: a record carries nothing of the request's content, and a routing key is content; the series count grows with deploys and targets and never with users or requests, and a per-unit key is a per-user series unless it is reduced at the store, which needs a second representation nobody has named; and the store is one the host provisions to hold a year or more, so the key is a requirement on the host. The alternative that needs no key — treating the interval and not the request as the unit the boundary is computed over, so within-interval clustering is absorbed — trades away effective sample size and lengthens every window, and how much is a choice about what the analysis window costs. What turns on it is whether the confidence an owner authors is the rate they actually get, or a number the routing policy of a platform the factory did not write silently loosens.

## how-the-factory-works/08-operations/07-pages.md

### Every channel out of the product runs inside the process whose stopping the design says nothing can see
**Raised by:** Site reliability engineering
**Where:** `how-the-factory-works/08-operations/07-pages.md` — _Pages_ (with `components.md` — _One process is not one failure_, and `how-the-factory-works/08-operations/08-drift-detection.md` — the third comparison)
**What is wrong or missing:** One notifier delivers mail, chat and the page, and it is a component of the single factory process; the drift detector, the one reader deliberately placed outside that process, "calls nothing, so the notifier reads its store itself." `components.md` states the whole-process stop plainly — "the process stopping makes every last check stale at once... and nothing inside the factory is left to read it" — and the answer offered is the detector's third comparison, which "holds what the stopped component reaches and pages." When the process itself is what stopped, that page has no carrier, the hold has no gate component to enforce it, and the home view that would show the stale rows is served by the stopped process; detection reduces to a human happening to open a screen that will not load.
**What turns on it:** This is the worst production state the document names — open windows unevaluated, the release under watch unmeasured, the rollback that is the factory's only unattended authority disarmed — and it is the one state with no path to a human. The fourth page condition was written for exactly it and cannot be delivered, so the design believes a case is covered that is not.
**Migration:** Giving the detector its own delivery path later puts owner-authored People routing into the store no factory component may write and makes page events and delivery records writable by something other than the notifier and the log — a second writer on two records and a break in the claim that the page is the only channel that writes into the log, which the Factory screen's four page-channel numbers and the audit trail are computed from; a running install has its routing and its page history only inside the factory.

**Decision needed:** Whether anything outside the factory process may deliver a page, and if so what. _Pages_ already states the notifier-stopped case as a cost and answers it with a poll at Ops and the home view; the finding is that both are served by the same process, so a whole-process stop reaches nobody. Two mechanisms are possible and each breaks something the document set on purpose. The drift detector could carry one delivery of its own, to one owner-authored address held in its store, fired when its third comparison finds every last check stale at once: that gives the detector a write the document says no factory component makes, a second writer on the page event or a page the log never holds, and a People declaration copied into a store outside the factory. Or the factory could send a heartbeat to a service outside the install that pages on its absence, which is the established dead-man's switch: that makes a page depend on a service the customer runs or subscribes to beside the factory, which the self-hosted, one-way-in shape of the product has so far refused. Which of those the owner will pay for, or whether the poll stands as the answer with the whole-process stop stated as its cost, is a product choice. What turns on it is whether the fourth page condition can be delivered at all, and whether the claim that the page is the only channel writing into the log survives.

## how-the-factory-works/10-fleet/

### Spend is recorded as one scalar and priced by one rate, but providers price input, output, and cached units differently
**Raised by:** Cost engineering
**Where:** `how-the-factory-works/10-fleet/01-what-an-agent-runs-on.md` — _What an agent runs on_ ("Every run of an agent writes an **agent run record**…"), and `how-the-factory-works/10-fleet/08-a-spend-ceiling.md` — _A spend ceiling_
**What is wrong or missing:** The run record carries "the units the provider returned" as a single quantity and "the converted amount where the owner had authored a rate for that model version and effort" — one multiplier. Every commercial model provider returns usage decomposed into at least prompt and completion counts priced several-fold apart, with cached input and reasoning units priced differently again; the mix swings hard by role (a decomposition run is nearly all input, an implementation run is heavy on output). So the ceiling's claim that it "is exact on a credential running one model" is false for a single model at a single effort, and a single rate cannot convert a summed scalar into money for any real workload.
**What turns on it:** Every money figure the design produces — cost per feature at Factory, the burn rate, the projection of when a ceiling exhausts, and the ceiling comparison itself — is a number with no fixed relation to spend. An owner authoring a ceiling in these units is authoring a bound whose real cost varies by a factor of several depending on which roles happened to run under it.
**Migration:** A scalar already summed cannot be decomposed into priced components afterwards, and the converted amount is fixed at the write and explicitly never repriced, so every install's cost history and every authored ceiling stays denominated in a unit that does not mean anything.

**Decision needed:** What the spend ceiling is denominated in. The record half of this finding is taken in this run's edit to the agent run record: the record keeps the units per kind the provider distinguishes, the rate on the People declaration is authored per kind, and the converted amount is the sum over kinds, so cost per feature and the burn rate are priced correctly wherever rates are authored. What remains is the ceiling. _A spend ceiling_ states on purpose that the ceiling stays in the units the provider returns and is never converted, bounding what a credential may spend and not what that spend is worth, so that the one enforced field reads a fact the factory recorded and needs no rate to work. With units kept per kind, a ceiling in units is a bound on a sum of quantities priced several-fold apart, even on a credential running one model. Two ways out, and each gives up something the text protects: denominate the ceiling in the rate's currency and compare it against the summed converted amounts, which makes a ceiling depend on a rate being authored for every kind of every model version and effort the credential's entries name and leaves a credential unbounded until one is; or keep the ceiling in units and state, as its cost, that it bounds volume and not the invoice, which is what the text now says. Which the owner will pay for is a product choice. What turns on it is whether the field the document presents as what stands between a self-hosted factory and an unbounded provider bill bounds the bill.
