# Records and their writers

[_Tight integration_](what-the-factory-does/01-tight-integration.md) states the rule this
file inventories: every record in the graph has one writer, the single component that
writes it, and where two writers reach one record the split between them is a seam declared
in the section that owns the record. Every
seam row below says what the split is on: a field of the record, an event that writes it,
or the kind the record was created as. Each section that owns a record states that record's
writer and says nothing about any other record's, so the rule is stated a record at a time
and nowhere in one place.

Without a list, three things follow. Which component writes a given record is answerable
only by reading the whole document. An edit that gives a second component write access to
an existing record contradicts a sentence in a file the editor never opened. And the seams
between two writers cannot be enumerated at all.

The writers below are components, and [_Components and what they
call_](components.md) is where each of them is listed with what it may call. A writer named
here without a row there contradicts that list, the way a second writer given to a record
contradicts this one.

The writers are [intake](how-the-factory-works/02-intent-into-items/01-intake/README.md), [the
report store](how-the-factory-works/02-intent-into-items/01-intake/02-reports.md),
[decomposition](how-the-factory-works/02-intent-into-items/03-decomposition/README.md),
[dispatch](how-the-factory-works/02-intent-into-items/05-dispatch.md), [the artifact
store](how-the-factory-works/01-one-pipeline.md), [the log](deferred.md), [the merge
queue](how-the-factory-works/05-environments/03-the-merge-queue.md), [the
builder](how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md), [the
deployer](how-the-factory-works/08-operations/01-the-health-monitor.md), [the health
monitor](how-the-factory-works/08-operations/01-the-health-monitor.md), [the drift
detector](how-the-factory-works/08-operations/08-drift-detection.md), [the
notifier](how-the-factory-works/08-operations/07-pages.md), and the screens an owner
writes from, which are [Work, Ops, Factory and
People](how-the-factory-works/11-screens/01-work-ops-factory-people.md).

Each row names the record, its writer, and what the owning section says about that writer's
callers or about the seam where two writers reach it. The record itself links to the
section that defines it, which is where the row is argued and where an edit to it goes. The
table holds no reasons, the way [`terms.txt`](terms.txt) holds names and no argument about
them.

**Some things the document names are not records, and each says so where it is defined.** A
row here would repeat a fact another record already carries, or would give a second writer
to one that has one.

- A [candidate](how-the-factory-works/06-releases/03-what-a-build-is-called-and-when.md) is an item plus the build in force for it, and [a rollback](how-the-factory-works/06-releases/06-rollback.md) is a deploy event whose every field is on the deploy record.
- [The merge queue](how-the-factory-works/05-environments/03-the-merge-queue.md) is a component, its membership and its order read out of records that already hold them.
- A [deploy target](how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md) is a field of the environment. The commit, the set of packages a build resolved, the [design-system record named by a build in a project with screens](how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md), [what a run on a candidate environment produced](how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md), [the notice file produced from the resolved set](how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md), and what the build's own process decided before any environment existed are fields of the build.
- A [contract element](how-the-factory-works/07-contracts/01-two-versioned-things.md) is part of the form the contract version carries, and the [list of consumers a marked element waits on](how-the-factory-works/07-contracts/08-deprecation.md) is a query.
- A [screen](how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/04-the-screen-state-machine.md) is the chain of state machines superseding one another, and [the encoding that decides a criterion](how-the-factory-works/03-gates/07-what-particular-gates-decide/05-implementation/README.md) is code in the build.
- A [design system](how-the-factory-works/02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) is a constraint whose reach is one project, and [what it contains](how-the-factory-works/02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) is a field of that constraint record, derived when the record is written; an [evaluation set](how-the-factory-works/10-fleet/02-a-model-under-a-name.md) is content the product ships.
- The [provider account](how-the-factory-works/10-fleet/01-what-an-agent-runs-on.md) is not one either, the credential's name being the whole of what the factory holds.
- [Current release](how-the-factory-works/06-releases/05-the-deploy-record/README.md), [last known-good release and a rollback's target](how-the-factory-works/08-operations/03-overlapping-windows.md), [the consumer contracts in force](how-the-factory-works/07-contracts/06-what-a-consumer-declares.md), [the criteria in force for a build](how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/02-in-force-and-withdrawal.md), [a release's authorship rollup](how-the-factory-works/06-releases/02-the-release-record.md), and [an intent partly delivered](how-the-factory-works/02-intent-into-items/04-when-an-intents-items-do-not-all-ship.md) are queries over records that exist, and nothing writes any of them.
