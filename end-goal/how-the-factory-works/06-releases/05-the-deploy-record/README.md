# The deploy record

A service's **current release** is the one its production deploy record marks complete on every production [target the service runs on](../../05-environments/01-records-and-one-long-lived-branch.md) — what is running, not what is newest. Merged-and-never-deployed being normal is exactly what makes those different facts, and every cross-service check reads the current one: an environment composed from its dependencies is composed from what runs, and a promise is kept by what serves it.

A deploy record is written by the [deployer](../../08-operations/01-the-health-monitor.md), the one component that reaches a deploy target, through seam 4 of [_Deferred, but not designed out_](../../../deferred.md), when the deploy starts, and marked per target as the deploy advances, with the values set out below. The record names the release it puts on the environment once, and beside each of the environment's targets whether that target has it yet. A revert's deploy also lists the releases it delivers: the ones the [hold](../../08-operations/03-overlapping-windows.md) was holding, whose code is in its build. That list sits beside the one release the record names, the shape [_Rollback_](../06-rollback.md)'s record already keeps for the releases it undid, so a release delivered by a later release's deploy is on a deploy record and not only on master. Without that, [Ops](../../11-screens/01-work-ops-factory-people.md) reads those releases as merged and never deployed while their code is live.

A deploy [the search](../../08-operations/03-overlapping-windows.md) calls for names the build and no release, there being none. What it names as the thing deployed is the build it put there, and the release as well wherever a release exists to deploy: [_Deploy to candidate environment_](../../03-gates/07-what-particular-gates-decide/06-deploy-to-candidate-environment.md) fires one gate before the release number exists, so a record naming a release there would name one nothing had minted. Naming the build on every deploy is also what makes what is running comparable to what the record says: a target reports the build it is running and not the name that build has on master, which is a fact of this store and not of the target. Every reader of what is running reads the records that name a release, a [candidate environment](../../05-environments/02-an-environment-per-candidate/README.md) being a place where nothing is current. One rollout produces one, and [_Rollback_](../06-rollback.md) is a deploy event and produces its own.

Each deploy record carries a digest of the token the deployer minted for the [way in](../../02-intent-into-items/01-intake/02-reports.md) at that deploy, and never the token itself; the way in calls the report store under that token, as seam 5 states. Beside that token the deployer hands every instance it places the record's own identity, which is what [the health monitor](../../08-operations/01-the-health-monitor.md)'s emission names to tell the control's instances from the ones of the same build placed by an earlier deploy.

No agent performs a deploy: deploying is not a stage an agent is dispatched to, so the record's [actor](../../../deferred.md) is the deployer and never an agent — a program the factory runs and can check, where which model an agent is is only what its [fleet entry](../../10-fleet/README.md) says. What that costs is that an agent's [scope](../../01-one-pipeline.md) says nothing about a deploy target, so where a deploy may go is authored on the [environment record](../../05-environments/01-records-and-one-long-lived-branch.md) and never on an entry. What the record does not say is what share of traffic each build takes — that is the rollout's and its [_control_](../../08-operations/01-the-health-monitor.md)'s, and a deploy log recording every shift would scale with the schedule for a fact only the rollout reads while it runs.

It is keyed by service and environment and not by [target](../../05-environments/01-records-and-one-long-lived-branch.md): one record names one release for the whole environment, and completion is a field per target on that record rather than a record per target. A record per target stays refused, because four records could each name a different release and each be right; one record with one release and completion per target cannot. What one record with completion per target expresses is the state the earlier shape could not: a deploy that reached three targets of four is a recorded partial deploy, the fourth target marked not yet complete, rather than an incomplete one caught as a mismatch after the fact. [_Drift detection_](../../08-operations/08-drift-detection.md) reads each production target against what the record marks for that target, so a target marked complete and serving the old build is a mismatch whether or not a window is open. Every cross-service reader reads completion per target and needs a rule for what current means while they differ, and the rule is the strictest: a release is current only once every production target is marked complete, and until then the previous release is. A consumer whose [declared dependency](../../02-intent-into-items/03-decomposition/README.md) is on three targets of four is held at [_Deploy to production_](../../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) until the fourth lands, which is what stops one call in four reaching a producer without the [contract](../../07-contracts/README.md) form the consumer verified against. The cost is the wait on the slowest target, and that every reader of current release evaluates a rule over targets instead of reading one field.

Service and environment are the record's grain and not its identity: a rollout, a rollback, a revert's deploy, and a deploy [the search](../../08-operations/03-overlapping-windows.md) calls for each write one for the same pair. A record is identified by that pair and a sequence number the deployer assigns per pair as it begins each deploy, so two deploys of one release onto one environment are two records. The step the deployer's [restart](../../08-operations/01-the-health-monitor.md) must not repeat is keyed on the record and the target, never on the release and the target: a rollback returning to a release whose earlier deploy completed is a new record whose targets start unmarked, and a search's deploy, naming a build and no release, is keyed the same way. Keyed on the release, the rollback's own record would be the repeat that writes nothing, and the failed release would read as current with the [mismatch](../../08-operations/08-drift-detection.md) as the only trace. What the sequence number costs is one more part to the key, and a reader of current release ordering by release number and never by it.

Every deploy the deployer begins has a record from its first step, the steps before traffic included: a [schema change](01-a-schema-change.md), the snapshot before a destructive one, and the digest [_Rollback_](../06-rollback.md)'s slow way verifies. Per target the record holds one of three values: not reached, complete, or rolled back, the last written target by target as the record of the rollback that undid it completes on each, so a rollback that stopped undoes nothing on the record. The record as a whole is marked failed where the deployer stopped it before any target was complete, naming the step that stopped it; that is where a failure stands for [Ops](../../11-screens/01-work-ops-factory-people.md), what the restart leaves alone, and what [_Overlapping windows_](../../08-operations/03-overlapping-windows.md)' two queries descend past. Every reader of what is running reads a target marked complete, so a failed record moves no reader. A deploy the health monitor never calls for begins nothing and has no record: a failed exit that finds no release to return to, or one while a mismatch stands, is recorded by the [page](../../08-operations/07-pages.md) at that exit and by nothing else. What it costs is a row per refused deploy, and a status a reader has to tell from a record no target has completed yet, which a stopped deployer also leaves.

Current is the highest-numbered release whose deploy completed and was not rolled back, and not the most recently started, and it is none once a [removal](../../02-intent-into-items/03-decomposition/04-retirement.md)'s record, naming no release, is complete on every target; the two disagree exactly while a rollout runs. Composing a dependent's [_candidate environment_](../../05-environments/02-an-environment-per-candidate/README.md) from the release still taking part of the traffic would verify it against a build that may roll back within the hour, and the dependency hold at [_Deploy to production_](../../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) would admit a producer nothing is yet committed to. The number rather than the completion time is what orders them, because rollouts overlap and differ in length. The [strategies](../../03-gates/02-the-rollout-strategy.md) run from minutes to hours and the [score](../../04-risk-score/README.md) picks per release, so a short rollout completing while a longer one below it is still widening would make an older release current under a recency reading, and nothing later would move it — leaving every reader of that record wrong at once while production served something else.
