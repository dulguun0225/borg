# A schema change

A deploy that ships a schema change names it. The [store rule](../../07-contracts/09-the-store-is-a-contract-too.md) makes a breaking change five items, so what one deploy carries is one item's change, applied by the [deployer](../../08-operations/01-the-health-monitor.md) to the service's store before the build takes any traffic, through the credential the [environment's record](../../05-environments/01-records-and-one-long-lived-branch.md) holds — the deployer is the only component that reaches a deploy [target](../../05-environments/01-records-and-one-long-lived-branch.md), and the store is reached the same way. The revert's deploy is the one deploy that can carry more: delivering releases that never deployed on their own, it applies each delivered release's schema change that no deploy applied, in release order, before its build takes traffic. Without that, a migration's additive item delivered in the batch would leave its column on master alone, and the code after it would write to a store that never gained it. The record says whether the change completed, so a schema change is on the trail an [incident](../../08-operations/06-incidents.md)'s links walk. A change that fails to apply stops the deploy before any traffic shifts: no target is marked complete, the previous release stays current, and the failure stands on the record for [Ops](../../11-screens/01-work-ops-factory-people.md). A change stopping halfway is survivable because the store rule holds in both directions. Of the five items, the added form is read by nothing until the backfill's record marks it complete, and the item that moves reads to the new form ships after that; the backfill writes only what the old form already holds and is rerun from where it stopped. The drop ran only once no [declaration in force](../../07-contracts/06-what-a-consumer-declares.md) named the old form and the backfill's record marked it complete, so a store between two forms is one that every release a rollback can restore still reads and writes.

Before it applies a change that destroys stored data (the drop, and any diff the store rule forbids without one), the deployer takes a snapshot of the store through the credential the environment's record holds, verifies it, and names it on the deploy record beside the change. A snapshot the deployer cannot take and verify is a deploy not performed: the deploy record is marked failed at that step, no target is marked complete, and a [page](../../08-operations/07-pages.md) fires, the exit an unverifiable digest already takes in [_Rollback_](../06-rollback.md). The snapshot is kept on the service's own store hosting, so the deploy record says where what the change destroyed can still be read. What it costs: such an item cannot ship where the service's store offers no snapshot until the owner supplies one.

A snapshot is a whole copy of the store, and the one erasure it can take is its own deletion: a [redaction](../../02-intent-into-items/01-intake/02-reports.md) names words inside a record the factory wrote, and nothing the factory holds says which rows of a customer's store are one end user's. The deployer deletes it at the end of the [retention](../../09-gate-policy/03-what-is-not-in-it/02-retention.md) the [service record](../../02-intent-into-items/03-decomposition/README.md) authors, on its own pass, or earlier when an owner calls for it from [Ops](../../11-screens/01-work-ops-factory-people.md) on the deploy record that names it, the call the deployer already takes for a [mitigation](../../../deferred.md). Either way it writes the deletion on the deploy record beside the snapshot's name, so the record says where what the change destroyed could be read and, after that, that it no longer can. The snapshot sits on the service's store hosting, outside the factory's [recovery unit](../../../what-the-factory-does/04-what-the-factory-does-not-build.md), so a restore of the factory's records brings none back and the [erasure list](../../02-intent-into-items/01-intake/02-reports.md) carries no row for one; whether that hosting copies it is [substrate](../../../what-humans-do.md). What it costs: an erasure that reaches a snapshot deletes what the change destroyed for everyone the snapshot held, the copy taking no redaction row by row, and a deploy record read after that names a copy that is gone.

Which changes a store carries is read from the [schema history](../../07-contracts/09-the-store-is-a-contract-too.md) the deployer keeps in the store, never from this record: a deploy applies the changes its build declares that the history lacks, and the record reports what it did.

The store is one per service per environment, and that is a shape the factory refuses to widen rather than an assumption. A service whose [targets](../../05-environments/01-records-and-one-long-lived-branch.md) each hold a store of their own, a database per region or a set of shards, is refused at [adoption](../../02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md) and at decomposition the way [_What the factory does not build_](../../../what-the-factory-does/04-what-the-factory-does-not-build.md) refuses a library or a scheduled pipeline. Three things here read one store: the schema step is applied once through the environment's credential, [_Rollback_](../06-rollback.md)'s target is one store the forward promise was kept on, and [_Drift detection_](../../08-operations/08-drift-detection.md)'s fifth comparison reads one history. A store per target would turn those three into a schema step per target under the completion field, a rollback whose target is several stores, and a history keyed by store. Until all three were rebuilt that way, a service could deploy with its schema on one store and its code running against several, a divergence [_Drift detection_](../../08-operations/08-drift-detection.md)'s fifth comparison could not see. What the refusal costs is a customer with regional or sharded databases told no at the door, which is the cheaper place to hear it, and a service that wants a store per region having to be a service per region.
