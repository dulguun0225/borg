# A schema change

A deploy that ships a schema change names it. The [store rule](../../07-contracts/09-the-store-is-a-contract-too.md) makes a breaking change four items, so what one deploy carries is one item's change, applied by the [deployer](../../08-operations/01-the-health-monitor.md) to the service's store before the build takes any traffic, through the credential the [environment's record](../../05-environments/01-records-and-one-long-lived-branch.md) holds — the deployer is the only component that reaches a deploy [target](../../05-environments/01-records-and-one-long-lived-branch.md), and the store is reached the same way. The revert's deploy is the one deploy that can carry more: delivering releases that never deployed on their own, it applies each delivered release's schema change that no deploy applied, in release order, before its build takes traffic. Without that, a migration's additive item delivered in the batch would leave its column on master alone, and the code after it would write to a store that never gained it. The record says whether the change completed, so a schema change is on the trail an [incident](../../08-operations/06-incidents.md)'s links walk. A change that fails to apply stops the deploy before any traffic shifts: no target is marked complete, the previous release stays current, and the failure stands on the record for [Ops](../../11-screens/01-work-ops-factory-people.md). A change stopping halfway is survivable because the store rule holds in both directions. Of the four items, the added form is read by nothing until the code that reads it ships, and the backfill writes only what the old form already holds and is rerun from where it stopped. The drop ran only once no [declaration in force](../../07-contracts/06-what-a-consumer-declares.md) named the old form and the backfill's record marked it complete — so a store between two forms is one every release a rollback can restore still reads and writes.

Before it applies a change that destroys stored data (the drop, and any diff the store rule forbids without one), the deployer takes a snapshot of the store through the credential the environment's record holds, verifies it, and names it on the deploy record beside the change. A snapshot the deployer cannot take and verify is a deploy not performed: the deploy record is marked failed at that step, no target is marked complete, and a [page](../../08-operations/07-pages.md) fires, the exit an unverifiable digest already takes in [_Rollback_](../06-rollback.md). The snapshot is kept on the service's own store hosting, so the deploy record says where what the change destroyed can still be read. What it costs: such an item cannot ship where the service's store offers no snapshot until the owner supplies one.

Which changes a store carries is read from the [schema history](../../07-contracts/09-the-store-is-a-contract-too.md) the deployer keeps in the store, never from this record: a deploy applies the changes its build declares that the history lacks, and the record reports what it did.
