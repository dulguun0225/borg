# The release record

A release is a record, and it is where [the graph](../../what-the-factory-does/01-tight-integration.md) joins. It names what is known at the merge: the item that caused it, and the build and commit it is made of. The [contract versions](../07-contracts/01-two-versioned-things.md) it publishes are not a field of it — they name the release instead, each carrying that release's own number, because ordering versions is ordering releases and answering "the version in force at release N" by reading release records would make every reader of a contract a reader of releases. A version that names the release cannot also be a column here without the same fact standing in two places, written at one event by one writer. So "the release names the contract versions it publishes" is an inbound edge, which is what every deploy of a release already is, and the cost is the one this record's single writer already carries: a reader asking what a release publishes indexes that edge rather than reading a field. The [gate decisions](../03-gates/01-where-a-gate-is-and-what-decides-it.md) name the item and the build and never the release, whether they were written before it existed or, at the [production deploy gate](../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md), after; every deploy of it to every [environment](../05-environments/01-records-and-one-long-lived-branch.md) is written afterwards and names the release. Ask anything about a shipped change — from what [intent](../02-intent-into-items/01-intake/README.md), on whose approval, under which [policy](../09-gate-policy/README.md), running where, rolled back when — and the answer is reached by traversing edges at the release record, outbound or inbound. Traceability is not added to this; it is what the record is for.

[_The merge queue_](../05-environments/03-the-merge-queue.md) writes it and mints the release number with it. Master's only inbound path is the queue, so the fast-forward is the event and the queue is what performs it, and the serialization that stops two merges taking one number is the per-service ordering the queue keeps already. A writer of its own, called at the fast-forward, would be a component with one caller and that ordering implemented again inside it. What this costs is release identity inside the queue's component. A commit that reached master by another path gets a release record from the same writer only once a human accepts it, and that record names a build and no item, the treatment [_What the queue reads before it mints_](../05-environments/05-what-the-queue-reads-before-it-mints.md) states; until then the service's merges are held.

It is written once and never written again, which is what keeps that one writer. The alternative was five — a [gate component](../01-one-pipeline.md), the [deployer](../08-operations/01-the-health-monitor.md), and the rest writing their links into it — which is five writers on the record the whole graph joins on and a [seam](../../deferred.md) to declare between each pair, and writes to a release after it shipped. The cost of one is that where a release runs and which gates let it through are queries over the records that name it, so every reader asking either needs those inbound edges indexed.

The release's notice is one such inbound edge: the **notice file** the build runner produced from the build's [resolved set](../05-environments/01-records-and-one-long-lived-branch.md), read by following the release's own link to the build it is made of. Where the build carries no notice file because the resolved set [could not derive](../07-contracts/06-what-a-consumer-declares.md), the release reads could not derive too, which [Merge to master](../03-gates/07-what-particular-gates-decide/07-merge-to-master.md) already treats like an undecided criterion.

A release's authorship rollup is also a query and not a field: which of the three [authorship attributes](../01-one-pipeline.md) wrote each stage of the item this release names, read from the [artifact store](../01-one-pipeline.md)'s record of that item's artifact versions. [_What the customer runs it under_](../../what-the-factory-does/05-what-the-customer-runs-it-under.md) reads it the way it reads the rest: a fact a rights question over the produced software asks for, answered from a record rather than argued.
