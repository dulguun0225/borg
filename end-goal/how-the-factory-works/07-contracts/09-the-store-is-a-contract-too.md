# The store is a contract too

A service's store is a contract too, and its consumer is the service's own past — the release that was running a minute ago, which a rollback can restore. That consumer is why a store promises **forward** as well: every rollback reads across the change in the direction backward alone does not cover, and it is the only kind of contract with a consumer of that kind. It is also a consumer that writes: a rollback makes the restored build the store's writer again, so its consumer contract is derived from writes as well as reads — the elements the code writes, and whether each is written populated and inside its domain, from the build like everything else. Those are the two sides an interface's consumer declares as what it reads and what it sends. The [declarations in force](06-what-a-consumer-declares.md) are the same range query, from the last known-good release up to the newest, which is exactly the set of releases a rollback can put back in front of the store.

The rule is the same there: **no single item may break the store.** A breaking schema change is four items, and while it remains, the old form has the same deprecation obligation an old interface has. The store gains the new form beside the old; the code writes both forms and reads the new; a **backfill** copies into the new form every row the old form already holds; the old form is dropped. The code writes both forms until the drop, because until the drop a rollback can restore a release that reads the old one. The backfill is what reaches the rows written before the code item shipped, which nothing else does: a new form filled only by writes made after it reads every earlier row as absent, and the drop then destroys the only copy. The schema change itself is a step of the deploy that ships it, applied by the [deployer](../08-operations/01-the-health-monitor.md) and named on the [deploy record](../06-releases/05-the-deploy-record/README.md), and a rollback undoes none: the schema moves only forward, which is what makes this promise the one a rollback rests on.

Which changes a store already carries is read from the store and never from the factory's records. The deployer keeps a **schema history** in each service's store: one row per change applied, naming the release that shipped it, the change's identity, and a checksum of its text, written in the same transaction as the change where the engine allows one. Every deploy, [the search](../08-operations/03-overlapping-windows.md)'s included, applies exactly the changes its build declares that the history does not hold. So a deploy rerun after a stop skips what landed, a search's build made on a delivered release's commit applies nothing that release applied, and a factory whose records were restored from a backup does not apply again what the store carries. The deploy record reports what the deployer did and is not what it decided from. An engine that cannot put a change and its row in one transaction can leave a change applied with no row, so every change is authored to be applied twice without effect, and [the candidate environment](../05-environments/04-what-the-candidate-environment-decides/README.md) checks that by applying it twice, a second application that changes anything being a rejection at Merge to master. It exercises [the snapshot](../06-releases/05-the-deploy-record/01-a-schema-change.md) the same way, taking and verifying one before the destructive change and rejecting at Merge to master where it cannot. The history is not a record of the graph: it lives where the schema does, reached through the same credential, and [the record inventory](../../records.md) lists no row for it. What it costs is a table the factory writes into a store it does not own, and a history the service's own code could edit, which is what [_Drift detection_](../08-operations/08-drift-detection.md)'s comparison against the build exists to catch.

An adopted service arrives with its store already at the schema its head declares and a history holding nothing, so on the rule above its first deploy would apply the whole of the head's changes to a live production store. The deploy of [the adoption item](../02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md)'s release applies none of them. On every environment it writes into the history one row per change the build declares, naming that release and marked as found applied rather than applied by the deployer, and applies nothing; the mark is a field of every row, so a later reader tells a change the factory applied from one it took on the adoption's word. The next release's deploy then applies exactly what its build declares that the history does not hold, as any deploy does. What it costs is that the factory has checked nothing about those changes, the candidate environment's double application never having run on them, and that the rows claim what the adoption's shape claims. A store not at the head's schema holds rows for changes it does not hold; nothing reads a store's form against its history, and what finds it is the release that fails against the missing form. A change the store holds that the head does not declare is [_Drift detection_](../08-operations/08-drift-detection.md)'s mismatch from its first reading.

A backfill item is a release whose change is data and not form. It declares no schema diff and opens no contract version, only the element it fills and the element it fills from. Its change is written to be rerun from where it stopped, a row already copied being skipped, so a deploy rerun after a stop finishes the copy rather than repeating it. The candidate environment checks that by running the change twice over the seeded store, and a second run that changes anything is a rejection at the Merge to master gate. It runs while the current release writes both forms, so a row written during it lands in the new form once, by the code or by the copy. The deployer marks its deploy record complete only when every row the old form holds is present in the new, and that fact gates the drop. A removal item is rejected at Merge to master while no deploy record marks the backfill for that element complete, the rejection a diff already meets without the migration shipped ahead of it. The constraint rule below reads the same fact: a not-null constraint or a domain check on the new form is addable once the backfill is complete and every declaration in force writes the form populated and inside the constraint's domain. That is the ordinary rule, with the backfill's completion standing for the rows no release in force wrote; before it the new form can never carry a constraint the old one did, because the rows the copy has not reached would violate it. What it costs is a fourth trip through the pipeline for every breaking change, and a copy that on a large store runs for hours while the deploy carrying it stands incomplete on [Ops](../11-screens/01-work-ops-factory-people.md).

Enforcement requires nothing new: the factory diffs the schema a candidate declares against the one in production, and a diff the declarations in force forbid without the migration already shipped ahead of it is a rejection at the Merge to master gate. What the declarations forbid is read over writes as well as reads. Dropping an element a declaration in force still names is destructive, and so is adding a constraint (a not-null constraint, a domain check, a uniqueness rule) that a write declared inside the range would violate. The release that writes that way is one a rollback can restore, and an additive diff that condemns its inserts turns a recovery into a write outage. The middle two items of a migration diff empty by construction, both forms present, the code item moving reads and adding a write, the backfill moving rows, so the diff alone would pass them unconditionally. What decides them is [the candidate environment](../05-environments/04-what-the-candidate-environment-decides/README.md), where the run's writes land in the environment's own store and every store declaration in force, read and write, is decided against the state it holds. The past release's predicate over a column the candidate stopped writing is exercised there or it is undecided, and undecided is read at the gate the way a failure is. The drawback falls on small work — renaming a column is four items and four trips through the pipeline. What it makes possible is the rollback in [_Releases_](../06-releases/06-rollback.md), which is otherwise a promise about code made over data that has already changed.
