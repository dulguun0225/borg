# A service that already exists

Adoption admits one shape: instances on a deploy target, already taking organic traffic, replaceable one at a time and returnable by shifting traffic. [_What the factory does not build_](../../../what-the-factory-does/04-what-the-factory-does-not-build.md) refuses everything else against that shape, at adoption and at decomposition alike. That is what "ordinary" means where [_Decomposition_](README.md) calls this path the ordinary way a factory starts.

Most software a customer brings has been running for years, and it is adopted through the same pipeline as anything else: an owner raises an intent (1) naming a repository and the environment it is running in, and the interview asks what it does — the criteria a human can state for behaviour nobody wrote down, which may be none. Decomposition writes the service record for it, the repository already existing, and yields one item, whose implementation stage authors nothing. The repository's head is the implementation, the candidate branch is its [trunk](../../05-environments/01-records-and-one-long-lived-branch.md), and [the build runner](../../05-environments/01-records-and-one-long-lived-branch.md) builds it as it builds any commit. So the item has a [build](../../05-environments/01-records-and-one-long-lived-branch.md), the [consumer contracts](../../07-contracts/06-what-a-consumer-declares.md) the factory derives from one, and the resolved set the [advisory](../01-intake/03-advisories.md) detector reads. Every gate fires as it fires on any item, the [Implementation](../../03-gates/07-what-particular-gates-decide/05-implementation/README.md) gate's diff being the whole tree against nothing, and the queue's first fast-forward makes the head master and the item release one.

The adoption intent's evidence is the repository named, text the factory did not author that no gate has admitted, so it resolves the source value toward [Spec](../../03-gates/07-what-particular-gates-decide/02-spec/README.md) on the terms [_Factors, at least_](../../04-risk-score/01-factors-at-least.md) sets: a human at the gate whatever the formula returns, once. After the item merges, the repository is on master, admitted content like anything else the factory wrote, so a later item on the adopted service weighs the source rather than resolving it. What it costs: one human per adoption.

Its production deploy is where adoption differs from a first release the factory built. The software is already running, so where the [platform](../../03-gates/02-the-rollout-strategy.md) can shift a share, the release takes traffic [with a control](../../03-gates/02-the-rollout-strategy.md) — the instances already running are the control, kept serving as any control is. The window compares the factory's build of the head against the customer's, which is a comparison between two builds of one commit and establishes that the factory builds and deploys this service the way its owner did. From that deploy the service is inside the factory's checks: it has a current release for [a deploy gate's hold on a dependency](../../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) to read, a deploy record for [_Drift detection_](../../08-operations/08-drift-detection.md) to compare, and a build for the next release's control to start from. So the second release is measured completely, and on a service with organic traffic it is measured sooner than a service the factory built from nothing ever is.

The [design system](../01-intake/01-constraints-and-the-design-system.md) an owner picks for the project reaches it through the [conformance raise](../01-intake/01-constraints-and-the-design-system.md), which reads the diff of that build against what the system contains. The screens of an adopted service are in its build whether or not any item ever declared a [state machine](../../03-gates/07-what-particular-gates-decide/02-spec/04-the-screen-state-machine.md) over them, so the departure is enumerable before the service has authored anything, and the render predicates are not.

What adoption does not give a service is stated rather than promised. Release one has no [rollback target](../../06-releases/06-rollback.md) — what ran before it is not a release — so a window that fails on it finds nothing to return to and takes the [page](../../08-operations/07-pages.md) that [exit](../../08-operations/02-the-analysis-window.md) already has. The interfaces arrive without [declared meaning](../../07-contracts/05-what-a-diff-cannot-see.md), a consumer's contracts are checked against what was never declared, and naming a field afterwards is a breaking change and a migration's four items. Every parameter of the service starts where a new service's does — the [window limit](../../08-operations/03-overlapping-windows.md) at one, the [window's size, confidence, and power](../../08-operations/02-the-analysis-window.md) supplied — because nothing the factory can read says what ten years of shipping taught. And the service is one repository with one trunk: a customer arriving with a monorepo splits it before adoption, the split being work nothing in the factory does for them, for the reason [_Decomposition_](README.md) states. What adoption costs the factory is one item that changes nothing and pays for an environment, a run, and a release number anyway, and a first window whose passed exit says only that the factory reproduced what was running. Following the links out of an incident in adopted code ends at the adoption item, which is where the factory's history of that service starts, and nothing recovers what was behind it.
