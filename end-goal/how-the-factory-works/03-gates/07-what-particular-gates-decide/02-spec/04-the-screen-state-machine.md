# The screen state machine

Where the item has a user interface, the spec version introduces a screen's **state machine**: the states a screen can be in, empty and loading and failed among them, one of them initial, the events each state answers and the state each event moves it to, and which states are terminal. The machine is closed. A transition it does not declare is forbidden, so what each state forbids is everything not declared from it, and an author enumerates what the screen does rather than an unbounded list of what it must not. The open reading, where a transition neither declared nor forbidden is admitted, was refused because under it an implementation is unconstrained wherever the author did not think to write a prohibition, which is the failure a declared machine exists to remove.

This gate rejects a machine that is not well formed, mechanically and whatever the score returns, the way it rejects over the requirement field. Three shapes fail: two transitions on one event from one state, a declared state no path of declared transitions reaches from the initial one, and a state that is not terminal with no event declared from it, which is a screen nothing leaves. What closure costs is that an implementation is rejected for a transition the author left out and not only for one they forbade, so a machine authored thin rejects sound builds until a superseding machine declares what was missing. What well-formedness costs is a check at this gate on every machine and a form the author has to satisfy before a human reads it.

The machine is part of what a human confirms here (6) and not one of the six patterns: the patterns are sentences and lose the transitions, and it is the transitions that make [_Implementation_](../05-implementation/README.md)'s rejection mechanical. It is a record of the service like a criterion, written by the artifact store in the same call, and the screen's identity is the id of the state machine that introduced it. The id is per service, stable and never reused, the rule the criterion id and the release number both keep, and opaque by the criterion id's mechanism rather than the release number's. A revision is a new state machine naming the one it supersedes, and the chain of supersessions is the screen; there is no screen record, because a screen with no state machine is nothing the factory can check. Which machines are in force for a build is the query the criteria are read by, less those a machine in that build supersedes; that set is what the [screen predicates](../../../05-environments/04-what-the-candidate-environment-decides/01-the-third-outcome.md) are decided against. The machine declares no appearance, viewport width, text scale, or text direction: those are the conditions the [design system](../../../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md)'s content declares once for the project, and the predicates are decided over the machine's states in each of them. The cost is that nothing mechanical stops two items introducing two chains for what a human would call one screen, and what catches that is the owner confirming here — the one place the flow's enforcement rests on a human noticing rather than on a link.

A transition may leave the screen: its destination is then another screen, named by id, and not a state of this machine. That is what joins screens into the sequence a person crosses to accomplish one thing, and it is checked here rather than authored anywhere. This gate rejects, mechanically, a transition naming a screen no machine in force declares, on the item's service or on the current release of a service the item's service declares a dependency on, so a person is never sent to a screen that does not exist. Factory reports per project the screens no transition of any machine in force leads to, other than each service's initial one, so a screen nobody can reach is a count and not a silence. A flow record above the screen, a sequence a human authors per chain and per install and a gate decides over, is refused. The sequence is the graph of these transitions, a query over the machines in force and not a second record that could disagree with them, and what a person is trying to accomplish across screens is the intent's [intended effect](../../../02-intent-into-items/02-the-interview.md), confirmed by the requester and shown at every gate of the intent. What the refusal costs is that the seam between two screens is checked for existence and never for sense: a person sent to a screen that exists and does not follow reaches the factory as an end-user [report](../../../02-intent-into-items/01-intake/02-reports.md), and a flow spanning two services is two items whose whole no gate decides.

A superseding machine gets the same treatment where what it removes is protection: one that declares a transition a **human-confirmed** machine did not, which under a closed machine is what admits behaviour the confirmed one forbade, is a [resolved factor](../../../04-risk-score/01-factors-at-least.md) at this gate, routed the way a criterion's withdrawal is. Cost: one human decision per such revision.

The drawback is the authoring, the same one declared meaning has in [_What a diff cannot see_](../../../07-contracts/05-what-a-diff-cannot-see.md) — a sketch is cheaper and checks nothing. What the screen looks like is not here: that is the design system the project chose as a [permanent constraint](../../../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) (2), a screen design that arrived with the request and binds only what was decomposed from it, and, where neither answers, [_Implementation plan_](../03-implementation-plan.md).
