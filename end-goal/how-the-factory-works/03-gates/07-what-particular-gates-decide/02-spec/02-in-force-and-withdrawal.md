# In force, and withdrawal

Which criteria are in force for a build is then a query, and a build is a set of items: the ones merged into the repository it was made from, plus the item whose branch it is. A criterion is in force for a build where the item that introduced it is in that build and no spec version in that build withdraws it. That reading is right for master and for the withdrawing candidate at once, where a field written at either moment would be wrong for the other. Both halves have to read the same set: a criterion introduced by a sibling that has not merged is a promise this build's tree could not keep, so holding it in force would reject every candidate decomposed in parallel with the one that introduced it.

What that costs is that the set in force differs between two candidates of one service at the same moment, so what a service promises is read from the build running in production and never from the criterion records alone. A human confirming (6) reads what the version changes and not the accumulated set. What a service promises now is the set in force for its current release, and [Factory](../../../11-screens/01-work-ops-factory-people.md) reports how many are in force, how many were admitted as exceptions, how many have never failed, and what share of them are [unwanted conditions](03-the-six-patterns.md), so drift is visible rather than re-read. The cost: a set that drifted is never re-read unless an owner's safeguard puts a human here, and an item legitimately changing a behaviour has to withdraw the old criterion and remove its encoding in one item, the one edit that removes protection.

A criterion also carries an outcome history, derived and never authored: each run's results already attach to the build and carry the environment's composition with them, so the history reads the rate at which the criterion's outcome disagrees across builds whose diffs do not reach the requirement it names. Nothing is authored to produce it. [Undecided](../../../05-environments/04-what-the-candidate-environment-decides/01-the-third-outcome.md) reads a disagreement inside one build's own repeated run; this reads one across builds that repeated nothing.

Above a bound the criterion is **unreliable**, what test practice calls flaky. The bound is a field of the service record with a fixed default, which a safeguard (9) may raise and never lower, lowering being what takes a criterion out of the gate. While unreliable, its failure rejects nothing, counts no attempt, and moves no prior, the treatment a [hold](../../04-what-a-gate-may-change.md) already gets, and [Merge to master](../07-merge-to-master.md) reads it as absent; it still runs and its result is still recorded.

Becoming unreliable raises one intent keyed by the criterion, the way a [detector](../../../02-intent-into-items/01-intake/README.md) raises one, so the encoding is re-authored through [the pipeline](../../../01-one-pipeline.md); a second raise while that intent is open joins it. It leaves unreliable when a version of its encoding the intent introduced is in force and the rate falls under the bound. What it costs: a regression reached by a path the diff does not name reads as disagreement too, so the criterion likeliest to catch such a regression is the one likeliest marked unreliable, and the gate rests on the others while it is.

Withdrawal is not silent for the two provenances that name an authority. Withdrawing a **human-confirmed** or **constraint-derived** criterion is a [resolved factor](../../../04-risk-score/01-factors-at-least.md) at this gate, routed to the duty or human its provenance names rather than to the owner by default. Cost: one human decision per such withdrawal.
