# The encoding and the emission

The encoding of the acceptance criteria is authored here as well. A criterion is a predicate and something has to decide it against an observed run. Unit tests are today's form of that, so the encoding is written with the code it checks and is reviewed at this gate as an artifact of the item. An artifact of the item is not always a record: the encoding is code in [the build](README.md), picked out by the criterion id it names and derived from the build the way a consumer contract is, so it cannot outlive the criterion it was written for. It runs where there is a run to observe, on [_the candidate environment_](../../../05-environments/04-what-the-candidate-environment-decides/README.md), and what it produces attaches to the build and is read at [_Merge to master_](../07-merge-to-master.md). This gate rejects in both directions: a criterion in force for the build with no encoding naming it, and an encoding naming a criterion that same build withdraws — otherwise the item that withdraws a criterion leaves its encoding in master, deciding a promise the service no longer makes.

What the [health monitor](../../../08-operations/01-the-health-monitor.md) will read is checked the same way and at the same gate. The numbers that comparison reads are emitted by the software the factory wrote, so a build emitting none of them is a build whose [analysis window](../../../08-operations/02-the-analysis-window.md) measures nothing while reporting that it watched — the reading [_The analysis window_](../../../08-operations/02-the-analysis-window.md) already refuses for an absent input, arriving one gate earlier. So the emission is an artifact of the item like the encoding is, derived from the build, and this gate rejects in both directions over it too: a service whose build stops emitting a number its windows were being decided on, and an emission naming a number nothing reads. It rejects on a third count in the first direction: a build in an area naming a [hazardous operation](../../../02-intent-into-items/03-decomposition/03-hazard-severity.md) whose emission does not count it. What that costs: a change to what a service measures is a change this gate can stop, a stop on work that is often the point of the item.

Not every encoding needs the environment. An encoding declares which of two places decides it, the build or the candidate environment. One deciding a criterion over the code alone, the unit test, is run by [the build runner](../../../05-environments/01-records-and-one-long-lived-branch.md) in the build's own process when it performs the [build](../../../05-environments/01-records-and-one-long-lived-branch.md), its result written onto the build beside the [resolved set](../../../05-environments/01-records-and-one-long-lived-branch.md) of packages. So this gate rejects on a criterion the build decided against, as it rejects a build that does not compile, and a human reading the diff here reads those results beside it. The candidate environment decides only the encodings declaring it.

What drives each screen into the states its [state machine](../02-spec/04-the-screen-state-machine.md) declares is authored here on the same terms. It is code in the build like the encoding, it is what [the run on the candidate environment](../../../05-environments/04-what-the-candidate-environment-decides/01-the-third-outcome.md) decides the [predicate-kind constraints](../../../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) over, and this gate rejects in both directions over it too: a state in force for the build that nothing drives, and a driver naming a state no machine in force declares. What it costs is a render per declared state at every run of that item's candidate.
