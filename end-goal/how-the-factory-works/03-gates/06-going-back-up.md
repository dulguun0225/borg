# Going back up

Every stage above moves an item toward a release; this is the one way back. An item goes back three ways — a gate rejects it, the author working the stage sends it, or [the merge queue](../05-environments/03-the-merge-queue.md) rejects a candidate that failed its own re-verification — and what happens to the work below is the same in each.

A reject names the stage the item returns to. By default that is the stage that fired — which is what a reject already meant: another attempt at the same artifact. At the two event gates that reject there is no stage of their own, so the default is the nearest authoring stage above, which is Implementation for both; the merge queue's rejection defaults there as well, and whichever of [its three readings](../05-environments/03-the-merge-queue.md) it found — a candidate that no longer passes against what it will actually ship beside, or an encoding that could not hold its answer — names no stage above it. Decomposition names nothing at all: its reject re-decomposes the set rather than sending an item anywhere, so the field its close event would carry stays unwritten there. Where what is wrong is upstream, the verdict names the stage that owns it and the item goes there directly: an implementation rejected because the spec says two things returns to Spec, and Implementation plan and Tasks are not visited on the way. Nothing limits the jump to one step: a walk back one stage at a time arrives at the same place having paid an attempt and a rejected artifact at every stage in between. The latest anything may be sent back from is the merge to master — the ceiling reject already has, and for its reason: after the merge the release number is assigned and the release exists, so what is left is [undoing the change after it shipped](../../what-humans-do.md) (10) and not a stage to re-author. Spec is the earliest of an item's own stages, and below it two things that are not among them may be named, because a defect above the item is not repairable inside it. [_Decomposition_](../02-intent-into-items/03-decomposition/README.md) is the first: an item that should have been three names it, decomposition runs again over the intent, and the set that comes out is decided at Decomposition like any other. [_The interview_](../02-intent-into-items/02-the-interview.md) is the second and the earliest thing reachable: a stage that cannot author because the request itself is underdetermined names the intent, which returns to the unrefined state an intent starts in and raises a question for whoever holds (3). That is where an ambiguity only the person who asked can settle belongs, and reaching it is the whole reason the floor is not Spec: re-authoring a spec four times against the same underdetermined request spends the limit and then asks that question anyway, one escalation later than needed.

The stage's agent can send an item back too, and that is where the defect is usually found first: the agent working from a spec is the one that discovers it says two things. It ends its attempt without authoring an artifact and writes a **rework request**, naming what owns the defect and the defect it found, and no gate fires, there being no artifact for one to decide over. The defect stated is the request's reason, the field a [reject](01-where-a-gate-is-and-what-decides-it.md)'s close event carries, and the stage it names is handed it the same way. A human [backstopping](../../what-humans-do.md) the stage (11, 12) sends one the same way, authorship being an attribute of the stage and the rework request being the stage's. It is written into the log by the log, with whoever was authoring as the actor, which is the arrangement the third kind of hold already takes for something that happened where no gate fired. A rework request is not a hold, which is the record it most resembles: it counts an attempt where a hold counts none, and where it names a stage it is an outcome on the author of that stage's artifact, which the [per-author prior](../04-risk-score/01-factors-at-least.md) reads like every other outcome on that author's work. Naming decomposition or the intent moves no prior at all: decomposition proposes a set rather than an artifact, and an intent is not an artifact either — the person who asked is not its author in the sense the prior keeps, and moving theirs would score an owner for having asked a question the factory could not answer. A rework request is never a reject, since no gate fired and no verdict was given, so no threshold learns from one either way.

The attempt is counted at what the item is sent to, and that is the rule for a reject naming a target as much as for a rework request: the rework is booked against the thing that was wrong. Against a stage that is the stage's own count on the item; against decomposition or the intent it is one of the two counts the intent keeps, its re-decompositions and its interview rounds, which is why neither target needs a counter of its own. The stages below the target then re-author counting nothing, the rule [_The merge queue_](../05-environments/03-the-merge-queue.md) already keeps for candidates re-verifying behind someone else's failure: they are being redone because of somebody else, and a count that rose for that would escalate the stage that noticed the defect rather than the one that made it. So a spec returned to four times escalates at Spec (12), and that is what ends the loop: an item cannot go around the pipeline indefinitely, because every rework request costs an attempt at the stage it names. The cost of not counting below: an item can spend four implementations and four builds while Implementation's count stands at one, so what a stage cost is answerable from the spend [_What an item names_](../02-intent-into-items/03-decomposition/02-what-an-item-names.md) keeps beside the count and never from the count itself, and [_Factory_](../11-screens/01-work-ops-factory-people.md)'s rework rate reports the stage that was wrong rather than the work that was redone.

What a rework request costs: an item's position stops being something anyone can recompute. Dispatch matches a stage against a [role](../01-one-pipeline.md) and writes the transition it is told about, so a rework request is the one thing that moves an item where neither a match nor a gate decided it: an agent decides that its own item goes backwards, and nothing decides over that. Nothing but the count limits it, so an agent that sends back every spec it is given spends that item's attempts at Spec and turns work the factory could have finished into an escalation (12) a human clears. Naming the intent is the same failure aimed at a person: an agent that finds every request underdetermined turns the factory into a questionnaire, and the rounds limit it the way they limit an interview going in circles.

An item sent back to a stage re-authors every stage below it. Sent past its stages it re-authors what the answer or the re-decomposition actually changed and no more: an item the re-decomposition left standing resumes where it was, and one it replaced is superseded and authors nothing again. What was already authored is not removed: the versions stay in the chain the artifact store keeps, so a decision naming one still points at what was decided over. But nothing below the target stands as approved, and a plan authored from a [spec version](07-what-particular-gates-decide/02-spec/README.md) since superseded is not this item's plan; leaving it approved would have the [_Implementation_](07-what-particular-gates-decide/05-implementation/README.md) gate decide a build against it. The gates below fire again on what is re-authored. What that costs is everything spent below the target, a build among it where the item had got that far: the same cost that gate already carries for a rejection of its own.

A spec version authored on a rework request introduces and withdraws [acceptance criteria](07-what-particular-gates-decide/02-spec/02-in-force-and-withdrawal.md) like any other, and an item returning to Spec to drop a behaviour has to withdraw its criterion explicitly. A criterion is a record of the service, written once and never written again, so one introduced by the version being replaced stays in force until a version withdraws it, and leaving it out of the new version withdraws nothing.

A rework request to a stage ends nothing. The item keeps its [branch](../05-environments/01-records-and-one-long-lived-branch.md) and its builds, which are freed for good when it merges, is dropped, or is superseded by a re-decomposition — the last of those being the one way a rework request ends an item rather than sending it back anywhere. Its [environment](../05-environments/02-an-environment-per-candidate/README.md), where it has one, is reclaimed while the item is stopped above Implementation and composed again when it next reaches the candidate deploy gate, which [_An environment per candidate_](../05-environments/02-an-environment-per-candidate/README.md) sets out. So an item sent from the Merge to master gate back to Spec pays a second composition when it returns, instead of holding an environment nothing is running on for as long as the spec, the plan, the tasks, and the implementation take.
