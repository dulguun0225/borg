# Overlapping windows

An open window blocks nothing. The next item builds, verifies on its own environment, merges, mints its number, and deploys while the window before it is still open — up to the **window limit**, which is how many windows one service may hold open at once. The window limit is authored with the rest of gate policy (8), and where an owner authors nothing the score supplies it, the same division the window's own parameters use. A safeguard on the window limit is a maximum on how many releases one rollback undoes — the score may ask for fewer open windows, never more — so a safeguard can only add safety here too. The drawback of authoring it appears late: the number has no visible effect until the first rollback, where it is how many releases are undone at once.

What the score supplies starts at 1 and rises only with evidence, because that evidence arrives one-sided — a service that has never rolled back has seen the throughput the window limit gives and none of the rollback size it causes. What moves it is stated exit by exit, the way the [per-author prior](../04-risk-score/01-factors-at-least.md)'s evidence is and for the same reason: a window closing `passed` raises it, a rollback that undid more than its target lowers it — unless a human marked it as not caused by the release, which is set out below — and `timed out` and `skipped` raise nothing. A release nothing ruled anything out on is not a release that behaved, and counting one would let a service whose instrumentation stopped ratchet its own window limit upward while measuring nothing at all; `skipped` is the plainer case still, the rollback that skipped the window being the same event that lowers the limit. That is the same shape as the prior, a position taken where there is no evidence and moved by what arrives, and it requires nothing of the score it does not already do. The drawback: a service that rarely rolls back rises slowly and gives up throughput it could have had, and the first rollback after a rise undoes more releases than it would have before. A service too quiet to close a window on evidence stays at 1 and is serial — not a cost this rule adds but the [weak protection](02-the-analysis-window.md) such a service already has: a limit rising on unresolved windows would enlarge the batch one rollback undoes on the one service that can measure neither the throughput gained nor the size risked.

That is what a started control makes possible. A found baseline made concurrency incoherent: with the comparison made against the release it replaced, a second deploy during an open window made the first release the second's baseline, so a regression the first introduced became part of what the second was measured against and was never detected. Serializing was the only way to keep the baseline single-valued. A control is started per release and never changes, so two open windows are two independent comparisons and neither is the other's baseline.

What a rollback targets has to change with it, and it is two things rather than one word doing two jobs. A service's **last known-good release** is the standing value — the release watched by the newest closed window whose exit is passed or timed out. It is what a rollback could return to at all and where [_declarations in force_](../07-contracts/06-what-a-consumer-declares.md) start. A **rollback's target** is computed for one rollback: the newest release *below the release being rolled back* whose window closed passed or timed out, descending past failed, past skipped, and past any window still open. The two coincide whenever windows close in the order they opened and differ exactly where they do not — stated per service alone, the query would return a release above the failed one and the factory would restore the change it had just failed, [master](../05-environments/01-records-and-one-long-lived-branch.md) being linear.

Nothing writes either: the release record is written once at the [fast-forward](../05-environments/03-the-merge-queue.md) and never again, so an outcome settled by a window closing long afterwards cannot be a field of it, and the fact is already implied by records that exist. Timing out counts: a release no window ever failed is one the factory can return to, and requiring a passed close would leave a service too quiet to ever reach one with no rollback's target at all. A release whose deploy [stopped before its build took traffic](../06-releases/05-the-deploy-record/README.md) (a schema change that failed to apply) does not count for either query, however its window closed. It never ran and its change never landed, so returning to it would redeploy a build over a store missing the change it shipped. Both queries read that from the deploy record, no target being marked complete, and descend past such a release the way the target descends past skipped. What this costs: every rollback path computes it rather than reading a field, and a window that fails to close leaves the rollback's target older than it should be — the rollback goes further back and undoes releases no window failed, up to the window limit, which is the safe direction and still a real loss.

Timing out counts only because a release that never served cannot time out. A release that deployed and then died, crash-looped, or emitted nothing is one arm silent beside a control that is serving, which [the health monitor](01-the-health-monitor.md) reads as a crossing on the request rate and [the window](02-the-analysis-window.md) closes failed. So neither query can name a build that took traffic and served none of it: a release the factory returns to is one whose arm served every request its control served, or one no request reached while nothing reached the control either. What that costs is the case the arm reading cannot see, both arms silent for the whole window, where the release is named on no evidence — the position a service too quiet to close a window on evidence is already in.

Closing skipped does not count, and that is what separates the two unresolved exits. A release a rollback undid was never failed either — its health monitor simply stopped, because master is linear and the release was above the rollback's target — but nothing is left running its build. Its own instances ended with the rollback, and nothing the rollback left running serves it, so there is nothing to return to. The release the rollback targeted is what runs afterwards and stays the rollback's target. A release the factory skipped over is not one it can return to.

Rollback is then a traffic shift onto the instances of the rollback's target, which are still running — long-lived, warm, and sized for all of production. They are, because a release's instances are kept at the capacity they had while any open window's rollback could return to that release, and torn down only when the last such window closes. On a [widening schedule](../03-gates/02-the-rollout-strategy.md) the release's share grows by routing and the instances it is taking traffic from are not scaled down as it does, so a release at ninety percent of traffic still has a full fleet of the build it replaces beside it; a fixed share and a second complete copy are the same rule at other shares. Not the control: a control is sized for the release's share, and shifting all of production onto it would saturate it, so the recovery would be the outage — which is what an earlier draft said, and release engineering and platform engineering each found it separately. Where the rollout was without a control there is nothing to shift traffic onto and the rollback is the slow one — the build of the rollback's target redeployed and waited for. So there are two ways a rollback reaches the same release, and which one applies is decided by the strategy and never by the order windows closed in.

What that costs is capacity, and it is stated here because it is the window limit's price in something other than rollback size. A rollout with a control costs a second full copy of the service for the window's length whatever the schedule: the three schedules differ in how much traffic the release is exposed to and not in what is provisioned. Windows open at once each keep the fleet of the release they could return to, so a service at its window limit runs one more full fleet than it has open windows. Two cheaper shapes were considered and refused. Scaling the target's instances out at the crossing and shifting once they are ready makes recovery take as long as a scale-out and a warm-up. It also makes recovery depend on a scale-out succeeding during the incident that caused the crossing, which is the moment one is likeliest to fail. The design's rollback is the fast path because it has no step that can fail, and that is worth a fleet. Returning traffic on the schedule the rollout used keeps the failed release serving part of production for the length of the shift and measures nothing by doing so; a rollback is immediate.

What an owner may author is the fraction of its fleet the build being replaced keeps while it is the rollback's target, on the [service record](../02-intent-into-items/03-decomposition/README.md) beside the window limit and the explicit threshold, and not one of [gate policy](../09-gate-policy/README.md)'s eleven rows. It is never supplied by the score: the factory [does not model a service's capacity](01-the-health-monitor.md), so it cannot know what fraction is enough, and the one value it can set without knowing is all of it. Below that the rollback scales the target's instances back to full before it shifts, and a scale-out that fails inside the window [pages](07-pages.md) with production still on the failed release — the owner bought the saving with that exposure, and the page names it.

Nothing shifts onto those instances until a rollback needs them, so a service's rollback path is otherwise first exercised at the moment it is needed, and the claim above that it has no step that can fail is a claim about a mechanism whose ordinary operation produces no evidence. The design already holds the pattern for that in [the sample the score holds out](../04-risk-score/02-how-it-learns.md), and applies it to the score and not to the recovery. So an owner may author a **proof test** on the [service record](../02-intent-into-items/03-decomposition/README.md) beside the fraction: how often the deployer, inside an open window, shifts a share of traffic onto the instances of the rollback's target and back again. It is authored outright with nothing supplied, for the reason the fraction is, that nothing the factory observes says what share of a service's traffic proves anything. A test that finds fewer instances than [the deploy record names](../06-releases/05-the-deploy-record/README.md) is already a [mismatch](08-drift-detection.md) by the comparison that reads that count, holding the service's production deploys; a test that finds the fleet there and cannot shift onto it stops nothing, and [Ops](../11-screens/01-work-ops-factory-people.md) reporting it is the whole of what happens. What a test costs is the traffic the release's arm does not receive while the share is away, which lengthens the window it runs inside. Where an owner authors none, the path is unexercised and what this section claims for it is an assumption about that service rather than a finding.

A safeguard may not suspend any of this. Every other safeguard adds a human or a constraint and removes no protection; one that held the traffic shift until a human acted would remove a recovery, which is the one direction a safeguard does not go. The rollback inside the window is the factory's own authority, limited by evidence and by nothing else, and the design's answer to a human having to decide is always a gate. A customer whose rules forbid an unattended change to what production serves adds a safeguard at the [production deploy gate](../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) instead — which costs them a human in front of every release on that service rather than only the ones that go wrong, and still rolls back without them when one does.

Nor may an operator pause it, on a service or anywhere. The case for a pause is a human who can see the comparison is confounded — a zone losing its network under the release's instances while the controls sit in another, every open window on the service crossing at once — and the rollbacks those crossings start were the right thing for production: the release's instances were failing, and shifting traffic back onto the instances of the release returned to is what restored service. What was wrong was the evidence and the revert, and the mark below answers both, ending the [revert item](../06-releases/06-rollback.md) the rollback raised and lifting the hold before the revert ships. So the mark gives that human everything a pause would except the rollback itself, and the rollback is the cheap part — a traffic shift onto instances already warm. A pause is the other thing: a state a human sets and walks away from, like an [acknowledgement](07-pages.md), that removes a recovery for as long as it lasts and does so in exactly the period a human is least available. What refusing it costs: a human watching a confounded comparison cleans up after it rather than preventing it, one mark per rollback.

The window limit's drawback is rollback granularity. Master is linear, so the release above a bad one includes it: a rollback inside overlapping windows undoes every release above its target, up to the window limit of them. That is the one place the factory ships more than one item at a time, and it is limited rather than unlimited — [_One item per release_](../06-releases/01-one-item-per-release.md) is still true for what ships, and for what a human undoes once the window has closed. A window limit of 1 is the serial factory, and every increment above it adds throughput on a high-frequency service, increases how many releases one rollback undoes, and keeps one more full fleet running.

A rollback still sets a [hold](../03-gates/04-what-a-gate-may-change.md), where an open window no longer does. Master keeps the change that was rolled back and the next item was built on master, so deploying it would redeliver the defect just removed. The hold stays until the revert item ships, and it does not hold the revert — a dependency hold that blocked its own dependency would never lift. The revert also deploys ahead of every release the hold is holding, which is the one place the release number does not order deploys: those releases cannot deploy until the revert ships, so making the revert wait behind them would be the same deadlock one step further out. Without both exceptions the mechanism stops working exactly when it is needed.

The revert's deploy is the largest batch the factory ships. Merging is not held while the hold stands, so the revert merges onto a master that already carries every release merged during it, and its one deploy delivers them all under one window. Holding the queue instead was refused: it stops the service's merges the moment any rollback holds, however small the pile, where a bound an owner authors stops them where the owner said — the same stop, begun where they set it rather than at once. What bounds the batch is the **backlog cap** — how many releases may wait behind a rollback hold, the ones the rollback [skipped](02-the-analysis-window.md) and the ones merged while it stands alike, every one the revert's deploy would deliver, before [_The merge queue_](../05-environments/03-the-merge-queue.md) stops fast-forwarding that service's candidates. No gate fires at that stop, so it is [a wait the factory could not compute at a firing](../03-gates/04-what-a-gate-may-change.md), written into [the log](../../deferred.md) by the log with the queue as caller and [actor](../../deferred.md), counting no attempt and teaching the score nothing, and it ends when the rollback hold lifts. The stop does not catch the revert's own candidate: the hold lifts only when the revert ships, so a stop that held it would never end — the deadlock the hold above already refuses, one step further in. It is a field on the [service record](../02-intent-into-items/03-decomposition/README.md) beside the window limit, and where an owner authors nothing it is the window limit, so both halves of [_the exception_](../06-releases/01-one-item-per-release.md) are bounded by one number until an owner separates them; a safeguard (9) may lower it and never raise it. Under a human operator the cap is a nicety; under the factory it is the only thing between a slow revert and a batch of a hundred, because nothing else notices the pile growing. What it costs: a revert taking a day stops the service's merges for most of it.

Where the batch's window fails, the rollback returns to the rollback's target as any rollback does, and the failure is attributed to nothing: the batch is one comparison over several changes, and marking every author in it would teach the [per-author prior](../04-risk-score/01-factors-at-least.md) from a label the evidence does not support. What recovers attribution is a **search**, the health monitor's own authority bounded by evidence the way the rollback is. The search calls [the build runner](../05-environments/01-records-and-one-long-lived-branch.md) to make one build at a time and the deployer to deploy that build with a [control](01-the-health-monitor.md); each such deploy is measured by a window of its own and ends with that window, whatever the exit. The exit is the answer, and traffic returns to the instances of the rollback's target, which the search never tears down. A search's build is nothing on master: the revert's change applied onto the commit of one release the batch delivered, because every release in the batch carries the failed change and a build of one of them alone would measure the defect just removed. The first applies the revert onto the rollback's target and answers whether the revert itself is at fault; the rest bisect the batch by release number. A search deploy's record names the build and no release, so the service's [current release](../06-releases/05-the-deploy-record/README.md) stays the rollback's target throughout, and the drift detector reads the target against the build the record names.

What a consumer admitted against that release then meets is a share of traffic on a later [contract](../07-contracts/README.md) form, which is what any rollout already shows it, and safe for the same reason: every form a search's build serves passed [the contract diff](../07-contracts/04-enforcement.md) at its own merge, and every contract promises backward compatibility. The search is not a wait on a human, and production running a build older than the newest release during it meets no [page](07-pages.md) condition — said here because it otherwise reads as meeting one. The builds are made from commits master keeps, so the search depends on no build being retained, which the slow rollback does, on the reachability floor [_Rollback_](../06-releases/06-rollback.md) states for the host.

Three limits, each there because the operator is a machine. The search runs only where each of its windows can close on evidence: where the service's traffic cannot rule out a regression of the size in force inside the window's cap, or cannot support [the power in force](02-the-analysis-window.md) at that size, no search runs, since a bisection over a signal that cannot conclude terminates anyway and names an innocent release. The second condition is the same test the window already applies to itself — a window that cannot exit passed clears no build the search deployed — so a service can support the search's size and still be refused a search on the rate its owner asked for. A null result is a result: a build that cannot be made because the revert does not apply onto that commit narrows the search no further, and a search that names no release marks nobody — a missing label slows the score's learning where a wrong one corrupts it, and a wrongly marked prior is carried by a [model version](../10-fleet/01-what-an-agent-runs-on.md) that cannot argue back. And a **search budget**, on the service record beside the cap: a maximum count of builds and a maximum total time production spends on them, each one putting a build that passed no gate in front of real traffic. Where an owner authors nothing the budget is what bisecting a batch of the cap's size needs, each build watched for one window, and a safeguard (9) may lower it. What the search costs is the one exception to [what was tested is what ships](../06-releases/04-the-release-number.md): its build is a commit on no branch and a build no gate decided, kept out of master by construction and in production for one window. Recovery from a bad batch takes several windows rather than one, so attribution is delayed where the search can run and lost where it cannot. The revert the batch's failed exit calls for is authored against the release the search names and never against the batch's own release, because that release is itself a revert and reverting it would redeliver the defect the first rollback removed; where the search runs and names nobody, or cannot run, the [intent](../02-intent-into-items/01-intake/README.md) the health monitor raised carries the null result as its evidence and [the interview](../02-intent-into-items/02-the-interview.md) asks a human (3) which change to remove.

A human can approve through it. The hold is the factory's own and the [emergency action](../01-one-pipeline.md) is approve now, not skip; the production deploy gate offers Approve regardless. What approving redelivers is the defect that was just removed — the most damaging thing in the factory to approve through, and the one most likely to be tried during an incident. So this hold is the one [_What a gate may change_](../03-gates/04-what-a-gate-may-change.md) gives a routing and a stated reason of its own. The verdict names this hold and no other, and the row waits on the duty that undoes a shipped change (10) rather than on whoever is at [Ops](../11-screens/01-work-ops-factory-people.md). What the record carries afterwards is who accepted redelivering a named defect and why.

A crossing is not proof that the release caused it. The comparison is confounded by whatever differs between the two arms besides the change — a zone losing its network under the release's instances while the control sits in another, a control that was itself unhealthy — and the authored confidence bounds only how often a release that is fine crosses on noise, never how often one crosses on a real difference that is not the change. So a named human at [Ops](../11-screens/01-work-ops-factory-people.md) may mark a rollback as not caused by the release, with the reason they state, the way a rollback on their own judgment names its [source](../06-releases/06-rollback.md). The mark is a record of its own, written once, pointing at the rollback's deploy record; it is read by everything that learns from outcomes and by nothing that acts. What it changes is the evidence and only the evidence: the rollback is excluded from the [per-author prior](../04-risk-score/01-factors-at-least.md) of every release it undid, from the [window's size and its power](02-the-analysis-window.md) alike — which of the two the event would otherwise have moved is the exit its window took, and a mark removes it from both — and from the window limit, the way a window whose comparison received no volume is — it is a rollback that measured something other than the release, which is evidence about nothing. It teaches the confidence nothing either, and that is deliberate: a confounded comparison says what crossed the boundary was not the change, and nothing about how confident the comparison should have been. The rollback stands, the [incident](06-incidents.md) stands — production was worse, whatever made it so — and nothing the factory did on its own is undone by the mark. What happens to the revert depends on when the mark is made. Before the revert ships, the mark ends the revert item — [dropped](../02-intent-into-items/03-decomposition/02-what-an-item-names.md), written by [dispatch](../02-intent-into-items/05-dispatch.md) with Ops as the caller — and lifts the hold the rollback set, there being no defect on master for the hold to keep off production: the next release from master carries the change, opens a window of its own, and is measured again, and until one comes the service stays on the release the rollback returned to, because a redeploy of a release already watched [opens no window](02-the-analysis-window.md). After the revert has shipped the change is gone from master and the mark corrects the evidence only; restoring it is a new intent the owner raises. What the mark costs is a judgment in a mechanism the design otherwise keeps to arithmetic, and the judgment can be wrong in the direction nothing checks — a human excusing a release that was at fault launders it out of the prior, and the [agent](../10-fleet/README.md) that wrote it — a model in a role — is scored as if it had been fine. That is why the mark is read by nothing that decides anything, so that a model cannot learn to be excused, and why it records the reason and the human beside the rollback it corrects, which is where a later reader argues with it. What it does not do is intervene: it comes after the rollback and suspends nothing, for the reason _Overlapping windows_ gives against a pause.
