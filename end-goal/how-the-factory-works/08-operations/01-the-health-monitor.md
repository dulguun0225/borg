# The health monitor

A [deploy record](../06-releases/05-the-deploy-record/README.md) says which [release](../06-releases/02-the-release-record.md) runs where, so the factory always knows which [build](../05-environments/01-records-and-one-long-lived-branch.md) it is measuring. The **health monitor** compares that release against a **control** — a set of instances running the build already in production, started alongside the release and taking comparable traffic. That comparison is what the factory reads to decide whether a [rollout](../03-gates/02-the-rollout-strategy.md) is failing — automated canary analysis, in the vocabulary of the field the `control` and the `baseline` below come from. Nothing has to be authored for a service to be measured this way, once there is a build in production to compare against.

The control is started rather than found, because a new process and a long-lived one differ before either serves a request: cold caches, empty pools, a compiler that has not yet seen the workload. Measured against the instances it is replacing, a release is slower for being new, and the factory reads that difference as a regression. Measured against a control of the same age, the only difference left is the change itself — for a change confined to the process. A control isolates nothing where the change is to shared state: both arms are instances of the same service reading and writing the same store, so a migration that slows every query degrades the two identically and the comparison stays flat. What reads it is the reading the health monitor takes against the service's own recent history, which has no second arm to move with it — and [_The analysis window_](02-the-analysis-window.md) takes passed away from a window whose control is crossing that reading, so the flat comparison does not close it on evidence while production is materially worse. **Baseline** stays the name for what the comparison is made against; what changed is that the factory now starts one instead of pointing at what is already running.

A control belongs to the deploy the rollout is part of and is not a deploy of the release it runs. It takes traffic so that it can be measured, and only that much: it is sized for the release's share and not for production, because it exists to be compared against and never to serve production on its own. What carries production if the release fails is the other thing the [strategy](../03-gates/02-the-rollout-strategy.md) keeps running — the instances of the build being replaced, serving the rest of the traffic throughout. The two are different instances with different jobs, the control started cold for the comparison and those long-lived. It mints no [release number](../06-releases/04-the-release-number.md), and the production deploy record of the release it was started beside names it: the build the control runs and the instances running it. It is named there by [the deployer](09-the-deployer.md), which is already writing that record at that event. There is no rollout component: the rollout is the deployer executing the [strategy](../03-gates/02-the-rollout-strategy.md) through [seam 4](../../deferred.md), starting the control, widening the release's share as it reads the comparison, and advancing its own deploy record's status target by target.

There is one control per production
[target](../05-environments/01-records-and-one-long-lived-branch.md) the release has
reached, started on that target when the rollout reaches it, and the deploy record names
each. Both arms of every comparison then sit in the same failure domain: a target losing
its network takes the release's instances and its control together, where one control on
another target would have crossed on a difference that was not the change. The comparison
is evaluated per target, each target's release instances against the control on it, and
never pooled across targets. Pooled, a regression confined to one target is diluted by
every target it is not on and can sit under a boundary sized for the whole service; per
target, it crosses on that target and starts the same rollback. How the boundary holds the
authored confidence over the set of targets is [_The analysis
window_](02-the-analysis-window.md)'s. The rollout reaches targets in the order the
environment record lists them, one at a time, each held until the ones before it have
served [the bake volume](../03-gates/02-the-rollout-strategy.md); that order and that hold
are the rollout strategy's and are stated there. What a control per target costs is one
started cold on every target rather than one for the deploy, and a target too quiet to
serve the bake volume holding every target after it to the window's cap.

The deployer's own stop takes [the merge queue](../05-environments/03-the-merge-queue.md)'s rule and not one of its own, the same operation restartable from either side. On every start, a crash and an upgrade of the self-hosted factory being the same stop, it reads its [deploy records](../06-releases/05-the-deploy-record/README.md) not marked failed that no target or only some targets have completed. It asks each of those targets which build it is running, and either completes the deploy in the target order or returns every target it reached to the release that was current before it. Keyed on the deploy record and the target, a repeat writes nothing and no target is deployed to twice. Two things are composed again rather than resumed. One is a rollout whose schedule the stop lost, the record carrying completion per target and never the share each build was taking. The other is a [candidate environment](../05-environments/02-an-environment-per-candidate.md) caught mid-composition, and composing one again is the work [reclamation](../05-environments/02-an-environment-per-candidate.md) already does. The one case the restart cannot decide is a [schema change](../06-releases/05-the-deploy-record/README.md) the record does not mark complete: the deploy is marked failed with the previous release left current, on the [store rule](../07-contracts/09-the-store-is-a-contract-too.md) rather than on the deployer knowing how far it got. What makes the stop readable while it lasts is the deployer's own [last check](08-drift-detection.md) record, which [_Drift detection_](08-drift-detection.md) reads against the rollout exemption below.

Teardown is ordered by what a [rollback](../06-releases/06-rollback.md) needs and not by
[the exit](02-the-analysis-window.md) alone. At passed and at timed out the health monitor
calls the deployer to tear the control down and then closes the window, the order
[_The analysis window_](02-the-analysis-window.md) states for every exit. A rollback closes
the window of every release it undoes, failed for the one whose analysis failed and skipped
for the rest, and no control survives it: every control ends with its window, and so do the
instances of every release the rollback undid. What the rollback shifts traffic onto is not
a control but [_the instances of the rollback's
target_](03-overlapping-windows.md), kept running at full capacity for as long as any open
window could return to that release. That is the ordering this paragraph exists to state:
those instances are torn down when the last window that could return to them closes, and
never at an exit of their own.

[_Drift detection_](08-drift-detection.md) is told about this, or it would page on every
rollout it sees. A build running on a production
[target](../05-environments/01-records-and-one-long-lived-branch.md) beside the [current
release](../06-releases/05-the-deploy-record/README.md) is a mismatch only where no open window
names it: as the release under watch, as the control that window's deploy record names, or
as the release a rollback of it would return to. It is never exempt on a target the [deploy
record](../06-releases/05-the-deploy-record/README.md) marks complete, that target being meant to
run the release under watch, so the old build on it is a mismatch whatever window is open.
The exemption covers the targets the rollout has not reached yet and nothing else. That
makes a control left running after its window closed a mismatch like any other, which is
how a failed teardown is caught — at the cost of the drift detector reading two factory
records to interpret one fact about the world. The exemption is bounded by the window's own
cap: a window open past it excuses nothing, because the record that suppresses the check is
written by the component whose failure the check exists to survive, and an exemption that
outlives the thing it describes is one a stopped health monitor holds open forever.

The measurement exists in production and nowhere else, and the reason is arithmetic rather than policy: it is computed from organic traffic, and a [candidate environment](../05-environments/02-an-environment-per-candidate.md) has none. A comparison computed from one human exercising a screen is noise that looks like evidence, and running a control beside it would double the compute spent on learning nothing. What a candidate environment decides is the [criteria](../03-gates/07-what-particular-gates-decide/02-spec/README.md), which need a test run rather than a population.

A rollout fails when the comparison crosses the [boundary](02-the-analysis-window.md), and the rollback follows automatically — except while a [mismatch](08-drift-detection.md) holds that service's production deploys, where [_Drift detection_](08-drift-detection.md) says what happens instead. The health monitor runs after every production deploy, and the strategy decides only how the factory acts on it. A rollout with a control moves its traffic back to the instances of the release it returns to, which are still running at full capacity whatever schedule the release was taking that traffic on, and a deploy [without a control](../03-gates/02-the-rollout-strategy.md), having no other instances running, has to redeploy the previous build and wait for it to start.

A control requires the old build to keep serving. So the real comparison is available only with the strategy that keeps one, and a deploy without a control falls back to reading the release against the recent history of the release [a rollback of it would return to](03-overlapping-windows.md) — the newest release below it whose window closed passed or timed out, descending past skipped as that query does, a release a rollback undid having no instances left to read a history off. Not against the ordinal predecessor, which is the reading this was until 2026-08-19: where windows overlap, the predecessor of a release under watch is itself under watch, so its history is not history yet and one release becomes the other's baseline — the exact incoherence a started control was introduced to remove, arriving by the back door in the one case that has no control. Not the [last known-good release](03-overlapping-windows.md) either, for the reason that query is not stated per service: it can be a release *above* the one being read, and a release measured against something that includes it is measured against itself. It is the rollback's target, computed for the release under watch rather than for a rollback of it, and it is single-valued and below whatever is open. What the fallback still has is the confound above, unanswered, which is what makes it the weak fallback. This is the second thing the [score](../04-risk-score/README.md) decides when it picks a strategy: the cheapest rollout is also the one that measures least, and where the score wants a measurement, it picks a strategy that keeps a control running.

The baseline is only as good as the build it runs, which is the argument for a safeguard: an owner can add a [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md) setting explicit thresholds for a service, the way they add one at a [gate](../03-gates/01-where-a-gate-is-and-what-decides-it.md) or on a strategy, and a service whose normal behaviour is already bad is where that is worth doing. An explicit threshold is absolute where the comparison is relative, and it applies in addition to the comparison rather than instead of it — the release passes both or neither, so a safeguard here can only add a check, like every other. Absolute is what the number is and not what the reading is. The quantity tested against it is counted from finite traffic, so the threshold is read against a boundary of its own, on the same terms as the reading against a service's own recent history below. [_The analysis window_](02-the-analysis-window.md) says why a fixed number read continuously is not a check that cannot fire wrongly. It is authored on the [service record](../02-intent-into-items/03-decomposition/README.md) beside the [window limit](03-overlapping-windows.md) and the window's parameters, and it is not one of [gate policy](../09-gate-policy/README.md)'s eleven rows: those are one closed set that one section gathers, and this is authored without being among them, the way [retention](../09-gate-policy/03-what-is-not-in-it/02-retention.md) is. What that costs is a value an owner authors that the [duty](../../what-humans-do.md)'s own line does not count, so an owner reading the eleven rows has not read everything they may set.

An explicit threshold names no [intent](../02-intent-into-items/01-intake/README.md) and no [criterion](../03-gates/07-what-particular-gates-decide/02-spec/03-the-six-patterns.md), and that is decided rather than missing. The link would outlive the item it was authored for, a withdrawn criterion would leave it pointing at history, and nothing would act on it — no gate fires on production's numbers after the fact. Validation at production's scale is post-production by design: the acceptance round (3) asks whether what shipped is what was asked for, and a screen still slow at that scale reaches the factory as a new intent, the way a [consumer's break](../07-contracts/01-two-versioned-things.md) already does. What that costs is stated where the criterion is decided: an intent can pass its criterion, ship, and be no faster at production's scale, the miss found by a human or a crossing and never by a link, and what motivated a threshold lives in the [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md) record that set it.

A comparison needs a control, and a control exists only while a window is open. Between rollouts there is no second arm, so the health monitor also reads each service against its own recent history — the same quantities, measured against what that service was doing before the deploy rather than against instances running beside it. It runs whether or not a window is open and nothing tears it down, so it is what the monitor is still reading [_After the analysis window_](04-after-the-analysis-window.md), what catches a change to shared state that moves both arms together, and what makes a service that is simply broken visible when no release is under watch at all. The rule it is read under is [_The analysis window_](02-the-analysis-window.md)'s and not a new one: a crossing inside an open window rolls the release back, and outside one it raises an [item](../01-one-pipeline.md). Carrying that authority, it is read against a boundary valid at every point it is read, for the reason the window gives for the comparison's: a threshold set for one look at a fixed sample is not the threshold for a reading taken continuously and forever. This reading never closes, so it has no last look to spend a rate against and cannot state one per reading.

What it states instead is the **average run length** — the mean volume of traffic a service whose behaviour has not changed runs before this reading crosses it once, which is what statistical process control asks of a detector over a stream with no horizon. Its size, one value per quantity as the [window](02-the-analysis-window.md)'s is and the smallest change in that quantity this reading has to detect, and its run length take the same division the window's own parameters use. They are authored on the [service record](../02-intent-into-items/03-decomposition/README.md) beside them, supplied by the score where an owner authors neither, and a [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md) may only shorten the run length, which adds a check rather than removing one.

An explicit threshold is read at a run length too, on the same division: the owner set its size when they set the number, and the run length is supplied where they authored none. What it costs is the confound a started control was introduced to remove: a release is slower for being new, and a reading against history carries that difference where the comparison does not. So its size is coarse by construction, finding a service failing and never the size worth catching, and a regression arriving gradually is absorbed into the history it is read against and crosses nothing. What the run length costs is what it admits: one crossing per run length of traffic on a service where nothing changed, rolling a release back inside a window and raising an item outside one. An item on a service with nothing wrong finds nothing to fix, exhausts the [attempt limit](../03-gates/05-the-attempt-limit.md), and becomes an escalation (12) that [pages](07-pages.md). That is a number and not an unknown, the service's traffic over the run length in force, so [Ops](../11-screens/01-work-ops-factory-people.md) reports it per service beside the size in force, which is what an owner shortening the run length reads before authoring it. More than one reading now runs on one service, the comparison, this one, and an explicit threshold where a safeguard set one, so what an [incident](06-incidents.md) records is which of them crossed, on which quantity, and at what boundary.

The quantities are the service's own: request rate, error rate, and latency, emitted because the factory instruments the software it writes, which is what makes a service measurable without an owner authoring anything. Availability is the error rate read over a period rather than a fourth quantity. Saturation is read by its effect and never modelled: a pool exhausted or a disk filling appears as errors or latency and nowhere else, because a picture of a service's capacity would put the factory in the business of planning spend on [substrate](../../what-humans-do.md) the owner hosts and the factory did not deploy. A [mitigation](../../deferred.md) changes the instance count of a release it did deploy, not that picture. What that costs is that the factory can report a service failing and never a service about to fail; a queue growing crosses nothing until it starts costing requests.

How the three are emitted is fixed, because a comparison over numbers two services emit differently is a comparison over the difference. The software emits two records per request or job: one when it arrives, naming the service, the [build](../05-environments/01-records-and-one-long-lived-branch.md) that emitted it, the [deploy](../06-releases/05-the-deploy-record/README.md) that placed the instance, and the [target](../05-environments/01-records-and-one-long-lived-branch.md) it ran on; and one when it completes, naming the same four, the outcome, and the duration. The build names the [release](../06-releases/04-the-release-number.md) through the release record, and where the deploy is [the search's](03-overlapping-windows.md), whose record names no release, the build stands alone. The instance is told its deploy at placement: the deployer hands it the deploy record's identity in its configuration, beside the token [the way in](../02-intent-into-items/01-intake/02-reports.md) calls with, so the record carries it and no reader joins it by time. The deploy is what tells the arms apart. The control and the long-lived instances of the build it runs are two sets of instances of one build on one target, and the build alone cannot separate them. The control was placed by the deploy it belongs to and those instances by an earlier one, so the release's records and the control's sit under one deploy and two builds, and the kept instances sit under a deploy of their own that never enters the comparison. What that costs is a series per deploy rather than per release, and a value passed at placement that a build cannot emit on its own.

Two records rather than one because a record written at completion alone is written only by the requests that completed. A process dying mid-request, a hang on a dependency, or a request queued behind an exhausted pool would then write nothing, and a release that hung a share of its requests would be measured on the ones it finished, which are the fast ones. So the outcome set holds `unfinished` beside the outcomes the software names: a request that arrived in an interval and has no completion counted against that interval once a deadline the instrumentation fixes for the service has passed since the interval ended, computed from the two counts and emitted by nothing. The request rate is counted over arrivals, the error rate over arrivals with `unfinished` among the failures, and the duration distribution over completions alone. What that costs is a second record per request, and a latency reading blind to a request that did not finish, which is why the hang lands in the error rate. The arm is named by the build and the deploy the record carries and never joined by time, so attributing a record to an arm of the comparison rests on no clock agreeing with any other. Nothing is sampled: a [window](02-the-analysis-window.md) is a volume condition, and a sampled count is a volume the window would rule things out on that never arrived.

The interval a record lands in is assigned when the store accepts it, by the store's clock, and the instance's clock names nothing. Every series in a comparison is then on one clock, which is what the request-rate reading needs: the two arms' volumes over the same interval are the same interval only if one clock says so, and a host skewed by an hour would otherwise read as an arm that went silent. The instrumentation writes each record at the event and holds none back, so what a slow emitter moves is bounded by how long a write takes and not by a buffer, and an instance that dies loses no record it had already written; its requests in flight are the `unfinished` ones. A completion is counted against the interval its request arrived in, which the store computes as the time it accepted the completion less the duration the record carries, a duration being measured on the instance's own clock and needing no other to agree. So `unfinished` for an interval is that interval's arrivals less the completions counted against it, read only once the deadline has passed since the interval ended; until then the interval is open, and the error rate over it is read as no volume rather than as a low one. What that costs is a write per record on the path a request takes, an error rate that lags the deadline where the other two quantities do not, and an arrival moved one interval by a write slower than the resolution, which moves it inside one arm and never between two.

The request rate is the one quantity the comparison also reads from the outside, because it is the one a release can move by emitting nothing. The control is sized for the release's share and takes comparable traffic, so the two arms should receive comparable volume over one interval. A release arm receiving materially fewer requests than its control over the same interval is a crossing on the request rate, at the boundary the [window](02-the-analysis-window.md) holds for every quantity, however few records the release emitted — and none is the plainest case. A release that is dead, crash-looping, black-holed by the [platform](../03-gates/02-the-rollout-strategy.md), or whose emission the new build broke is one arm silent beside one that is serving, and the window fails it. Without a control the fallback reads the same direction against the recent history it is read against. What that costs is a rollback on a release the platform routed less than its share to for a reason that was not the change, corrected afterwards by [the mark](03-overlapping-windows.md) as any confounded crossing is.

What is kept is not what is emitted. The store the outside row of [_What the factory does not build_](../../what-the-factory-does/04-what-the-factory-does-not-build.md) names keeps a count of arrivals for each interval per closed set of names (service, build, deploy, target), and a count and a histogram of durations per the same set with the outcome added, at one resolution the factory fixes for every service and ships with the instrumentation. The histogram is a count per bucket over a fixed set of bucket boundaries, one set for every service, fixed by the factory and shipped with the instrumentation the way the resolution is. A bucket count is a count, so histograms add across intervals, across instances, and across the two arms of a comparison, which a set of quantiles summarised per interval would not; that is what lets the comparison, the reading against a service's own recent history, and the [objective](05-service-level-objectives.md) all read one kept series. The latency the three quantities name is one quantile of that histogram, which quantile fixed with the boundaries, and it is read at the resolution the buckets give and no finer. So the finest latency size a window can be authored or learned to detect is the width of the bucket that quantile falls in: a floor under the size arithmetic [_The analysis window_](02-the-analysis-window.md) does, taken there as the coarser of that width and what the traffic reaches, and reported by [Ops](../11-screens/01-work-ops-factory-people.md) with the size in force. The three quantities are computed over those, and no reading in the factory opens a per-request record, so whether the host keeps one is the host's. A count per interval is the volume a window reads, so keeping the aggregate samples nothing.

The comparison reads the deploy the window was opened over: the release's series under its build against the control's under the control's build, and no series under any other deploy. The number of series grows with deploys and targets and never with users or requests, and the number of records grows with time at the fixed resolution; a record carries nothing of the request's content. What that costs: a regression confined to one customer's requests is read as a small change in the whole, and the resolution bounds how often a boundary read continuously is evaluated. How long the store keeps them is a requirement on the host and not a value an owner authors: at least the longest of the window's cap, the period of the service's [objective](05-service-level-objectives.md), and the span the reading against its own recent history is read over, stated as a shape the way [_An environment per candidate_](../05-environments/02-an-environment-per-candidate.md) states the platform's.

A fourth kind is kept on the same terms: a **failure record**, a count per interval per service, build, deploy, target, failure class, and code location, the point in the code the failure was raised from. Failure class and code location are two more names in that closed set, named by the software the way outcome and build already are, and no request content joins them. The number of distinct keys one release may hold open per interval is capped on the [service record](../02-intent-into-items/03-decomposition/README.md), the excess landing in a named overflow bucket rather than growing the store without bound, so the count stays true and where it was truncated stays visible. What that costs is a count and a site rather than an occurrence: the agent working the item a crossing raises reads how often and where, never the input that reached it. An `unfinished` request has a site by construction: the one the arrival record names, or the last one its own record was updated at — coarser than the site a normal failure names, since neither points at where the request actually stalled.

The shape of what is emitted and kept is versioned, because it is the one thing the factory ships into every service it wrote and cannot rewrite in place. The names on a record, the outcome set, the interval resolution, the histogram boundaries and the quantile, the failure record's key set, and the `unfinished` deadline are one shape, and the shape carries an **emission version** that every record names and the store keeps as one more name in the closed set. A build emits the version the factory that built it ships, so a service moves to a new version on its next build and never by an item raised for the purpose, and until then it emits the version it was built with. The [window](02-the-analysis-window.md) names the emission version each arm was read at, and a comparison whose arms differ in version is read over the quantities both carry, a quantity the newer alone carries being outside that window's set and recorded on it as such.

The health monitor reads every emission version the factory has shipped, on the promise [_One process_](../../one-process.md) makes for the factory's own store: a version adds a name or a quantity beside what the version before carried and removes nothing until the version after, so a series kept at an earlier version is read as it was. Where a change cannot be an addition, a resolution or a boundary set replaced, the version is a removal. Intervals kept at the version before are then read by the changed reading as a period the store does not cover, the side an absent input already lands on below, until the span the reading needs is covered at the new version. What that costs is a history that restarts at a removal, so an objective's period and the own-history reading are blind for that span on every service at once after such an upgrade. A service with no build since the upgrade is measured at the old version for as long as that lasts, which [Ops](../11-screens/01-work-ops-factory-people.md) reports per service beside the span the store holds.

The health monitor reads what the store holds and assumes nothing about it. On each pass it writes onto its [last check](08-drift-detection.md) for the service the newest time the store holds a record for, and a read whose newest record is older than the interval that last check carries, or whose period the store does not cover, is read as no volume and never as a low one. That is the side an absent input already lands on: a window over it cannot pass, and an objective over a period the store does not cover holds the way [_Service level objectives_](05-service-level-objectives.md) states. What that costs is that a store that stopped keeping records reads as every service gone quiet at once, the reading a stopped health monitor already produces, and [Ops](../11-screens/01-work-ops-factory-people.md) reports per service the span the store holds beside the span the service needs.

[_Ops_](../11-screens/01-work-ops-factory-people.md) is where the numbers are read and there is no other place: a screen of numbers with no setting beside them is what that screen refuses. A dependency outside the factory, a third-party API or a store the owner runs, is read the same way and in the calling service's own numbers. The item raised from it is one no change to the code the factory holds will fix; it exhausts the [attempt limit](../03-gates/05-the-attempt-limit.md) and becomes an escalation (12), which is where a failure the factory cannot end already goes.

A service's first release has no build in production to compare against, and the weak fallback is no answer there either: reading a release against its predecessor's own recent history requires a predecessor, and the reading against a service's own recent history is no answer either, a service shipping for the first time having none. So an explicit threshold is the only reading left, used alone rather than alongside a comparison for the one release where there is nothing to compare — and where no safeguard sets a threshold, the first release is unmeasured and nothing about it is discovered by watching. Where one does, its boundary still needs the volume its run length asks for, so a first release on a service too quiet to reach that volume inside [the cap](02-the-analysis-window.md) is unmeasured in effect as well: the threshold is set, the reading crosses nothing, and the window records what volume it actually received, which is what tells that case from a threshold the service passed. A control exists from the second release, and the measurement is complete from there. An adopted service differs, and [_A service that already exists_](../02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md) sets out how: software is already running, so where the [platform](../03-gates/02-the-rollout-strategy.md) can shift a share its first release has a control — the instances that were running — and the comparison is between two builds of one commit; where it cannot, the first release has the weak fallback at least, the service having a recent history of its own.
