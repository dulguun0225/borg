# The third outcome

A criterion has a third outcome and it is not a kind of pass. An encoding that produced a failure and a pass over the same build decided nothing, because what a repeated run measures is the repetition, so the criterion is **undecided** for that build and undecided rejects the way a failure does. For a criterion the disagreement has one place to appear: [the queue's confirming run](../03-the-merge-queue.md) is the only repeat over one build there is, a run over one build being otherwise something nothing performs twice. It runs after the Merge to master gate approved, so a criterion goes undecided at the queue and is rejected there. What still reads at that gate the way a failure does is a [consumer contract](../../07-contracts/06-what-a-consumer-declares.md) or a [store declaration](../../07-contracts/09-the-store-is-a-contract-too.md) undecided by a path the run never exercised, whose disagreement needs no repeat. Recording either as a pass is what would make the verdict rest on nothing, since a passing criterion is the whole of what that gate reads about the item's own behaviour. What it costs is that an encoding whose own defect has nothing to do with the change stops the item, and the way out is to author the encoding again rather than to run it again: retrying until green is available to nobody, the factory included, because the factory is what would otherwise do it at scale.

A predicate-kind [constraint](../../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) reads the same way, and the [screen state machines](../../03-gates/07-what-particular-gates-decide/02-spec/04-the-screen-state-machine.md) in force for the build enumerate where it is decided. Each of their states, in each condition the [design system](../../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md)'s content declares, an appearance, a viewport width, a text scale, a text direction, is a place the predicates are decided, the run driving the screen into it as [_Implementation_](../../03-gates/07-what-particular-gates-decide/05-implementation/README.md) authored. Within a render, each component the state shows is put in each state the design system's contents field lists for it, and the predicates are decided there too. A declared state the run did not render in every declared condition leaves every predicate over that screen undecided, and undecided rejects at Merge to master the way an unexercised consumer contract does. Each verdict names the state, the condition, and the component states it was decided in, so a pass is a pass at a named width and appearance and never at whichever the run happened to open. A build whose items declare no screen has no state to decide anything over, so an item on a service with no user interface is stopped by nothing. Reading an unexercised predicate as nothing gave away the states a happy path skips: the failed, the empty and the permission-denied, where a contrast floor, a focus order and a control's name fail in practice.

The enumeration costs a render per declared state per declared condition on every item touching a screen, multiplied again by the component states within each, and a state machine authored thin buys the weak check back. That is a defect the human confirming the criteria (6) can see, where an unexercised predicate was one nobody could. What it does not reach is a screen no state machine declares: the predicates decide nothing there, and what is left is the diff a [design system](../../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) arriving as code carries.

A run that could not be performed produced no outcome, this third one included, and what could not be performed is narrow: the environment failed to compose, or a dependency it needed was unreachable before the run began. A run that composed, started, and ended without the encodings finishing is not among them: the item's own service not answering is behaviour of the build, and its criteria fail as criteria. Reading a deterministic hang as an unperformed run would retry a real defect with nothing counting and nobody reaching it. For the narrow kind, nothing is recorded against any criterion, no attempt is counted, and the run is performed again: an absent input is not a failed check, the reading [an unavailable factor](../../04-risk-score/01-factors-at-least.md) already gets, recorded as absent rather than read as a result. Performing it again is not the retrying refused above, nothing having been decided that a second run could contradict. A run whose second attempt also could not be performed stops retrying and waits, [a wait no gate could compute](../../03-gates/04-what-a-gate-may-change.md), written into the log by the log with the deployer as caller and actor, counting no attempt and teaching the score nothing, read in [_Work_](../../11-screens/01-work-ops-factory-people.md) like any other wait. What ends it is the run performing. What it costs is that the wait is bounded by nothing but the dependency coming back, and at the queue it stands in that service's merge order while it lasts.
