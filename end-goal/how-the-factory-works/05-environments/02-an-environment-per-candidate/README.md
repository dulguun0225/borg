# An environment per candidate

Every item in progress gets an environment of its own, created from master plus that item's candidate and torn down when the item merges, is dropped, or is superseded by a [re-decomposition](../../02-intent-into-items/03-decomposition/README.md). It is the item's and not the candidate's, so a rebuild composes no second one: the three teardown events are the item's, as [_Records, and one long-lived branch_](../01-records-and-one-long-lived-branch.md) already has it, and one environment per candidate is what the arrangement looks like at any moment rather than what is counted. Nothing is shared, so nothing queues behind anything: a candidate being repaired delays nobody, and a candidate waiting on a human delays only itself. Nothing shares because nothing else is candidate-fed — the environments a customer defines receive master's releases alone, so no persistent slot exists for candidates to take turns on.

The environment is composed for the candidate running in it, from the [_current releases_](../../06-releases/05-the-deploy-record/README.md) of its dependencies: what is running rather than what is newest, never another service's candidate, and wherever those dependencies are, a service in another project included. Which services those are, [_Which producer a consumer reaches_](../../07-contracts/11-which-producer-a-consumer-reaches.md) derives. That is what makes a twelve-service project testing twelve items at once safe, and it is only safe because no item may break a contract. What it was composed from is a field the deployer writes at creation and rewrites when the environment is recomposed at a re-verification. It names each dependency and the release of it that was current then, and the versions of the seed and of the value set the store and the configuration were built from, as [_The store and the configuration_](01-the-store-and-the-configuration.md) states. No deploy record is written for a dependency put in place that way, a deploy record being what a gate decided and there being one gate here, over the item's own build. The cost is that a field the deployer writes about its own work can disagree with what is actually on that environment, and nothing checks it — the drift detector reads production targets only.

[Mutation of the build](../../03-gates/07-what-particular-gates-decide/05-implementation/03-what-the-encoding-rests-on.md), the check on whether an encoding could have failed, adds a cost of its own. Each mutant tested at [_Implementation_](../../03-gates/07-what-particular-gates-decide/05-implementation/README.md) is a build and a deploy onto the item's one environment, run serialised with the seeded store restored between them, so mutation multiplies composition and environment-hours by the mutant count. A **mutant cap** per item bounds it, authored on the [service record](../../02-intent-into-items/03-decomposition/README.md) with a fixed default.

The cost is infrastructure per item in progress rather than one shared environment per service. It is the factory's cost and not a human's: where the score or a safeguard puts a human on a candidate, that human's delay is that item's alone, where a single shared environment would have imposed it on every item behind them.
