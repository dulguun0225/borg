# The store and the configuration

Its [store](../../07-contracts/09-the-store-is-a-contract-too.md) is created with it, and what that store holds is stated. The deployer applies the service's schema to it the way a production deploy would: every change master carries plus the item's own, the same step and the same actor [the deploy record names](../../06-releases/05-the-deploy-record/README.md). So an item's schema change runs first where a failure costs a candidate and not an incident. What the store starts with is authored per service on the [service record](../../02-intent-into-items/03-decomposition/README.md), beside [the explicit threshold](../../08-operations/01-the-health-monitor.md) and at the same cost: a snapshot the owner has anonymised, or synthetic rows they supply, and where they author nothing it starts empty. Each authoring is a version, written beside the earlier ones with a content digest computed at the write and never editing one, so the version a run was composed from stays readable, and the composition a run's results carry names it. It is stated rather than silent because two checks read the store's state: the [criteria](../../03-gates/07-what-particular-gates-decide/02-spec/README.md), and the store [declarations in force](../../07-contracts/06-what-a-consumer-declares.md) decided against it. What a candidate's store cannot rehearse is production's scale: a change that completes in milliseconds over the seed can hold a lock for minutes over production's rows, and what catches that is [the reading against the service's own recent history](../../08-operations/01-the-health-monitor.md), not this run.

A check the run decided over no row is [undecided](../04-what-the-candidate-environment-decides/01-the-third-outcome.md), the reading [_The store is a contract too_](../../07-contracts/09-the-store-is-a-contract-too.md) gives a predicate no path exercised, and undecided rejects at Merge to master. Over an empty seed a backfill's second run copies nothing and a store declaration over rows nobody wrote is exercised by nothing, so each is undecided rather than a pass over zero rows; the schema change's double application is over the form and decides the same over an empty store as over a full one. What it costs is that a service whose owner authored no seed merges no backfill, and no schema change a row-reading check decides, until one is authored; what it buys is that a check over a store nobody seeded no longer decides over whatever the run happened to write. A seed or value set replaced between two runs is a composition that differs: [the queue](../03-the-merge-queue.md) reads it as it reads a moved release, and the criterion's [outcome history](../../03-gates/07-what-particular-gates-decide/02-spec/02-in-force-and-withdrawal.md) compares runs composed from one seed version and no other, so replacing a seed moves no criterion toward unreliable.

A non-production value set of the configuration is authored per service on the service record, beside what the store starts with, and the deployer writes it onto the candidate environment at composition, so a candidate never holds a production value. It is versioned as the seed is, and the composition names its version too. A service whose owner authors none runs its criteria against unset values, and the production value an item changes is exercised only by its window, never by its candidate.
