# What the queue reads before it mints

Two things guard [the number query](03-the-merge-queue.md) where the queue's ordering cannot, because the ordering lives only in a running queue. A second [release](../06-releases/02-the-release-record.md) naming one service and one number is refused where the records are kept, so a duplicate mint is a failed write and never two releases answering to one name. And the fast-forward and the record write are one operation restartable from either side: the record is keyed on the commit, so writing it again writes nothing, and on start the queue reads [master](01-records-and-one-long-lived-branch.md) before it mints, every start, a crash and an upgrade of the self-hosted factory being the same stop.

What it reads is master against the service's release records, and it reads the same way before every mint. Master's head being the commit the service's newest release names is the ordinary case. A commit on master past that one is compared against the [builds](01-records-and-one-long-lived-branch.md) the records hold. One that a build of a candidate approved at [Merge to master](../03-gates/07-what-particular-gates-decide/07-merge-to-master.md) names is the queue's own unfinished merge, and the queue completes it in master's order with the write the fast-forward already implied. One no such build names is a commit the queue did not put there: a human's push, an agent's, or a merge whose records a restore lost. It is told from the queue's own by the records and not by the queue's memory of its work. On that commit the queue mints nothing for the service and writes [a wait no gate could compute](../03-gates/04-what-a-gate-may-change.md) into [the log](../../deferred.md), naming the service and the commit. The wait has no holder, so it widens to the owner and goes out by mail or chat; it [pages](../08-operations/07-pages.md) nobody, since production is no worse for it, and it stops work rather than production the way [a fleet entry with no credential](../10-fleet/05-an-account-that-runs-out-is-a-hold.md) does.

The wait ends one of two ways. Master returned to the commit the newest release names is repository administration, outside the factory as [_What the factory does not build_](../../what-the-factory-does/04-what-the-factory-does-not-build.md) places it, and the queue reads it at its next pass. Or a human accepts the commit at [Work](../11-screens/01-work-ops-factory-people.md), a log row naming them as [actor](../../deferred.md), and the queue builds it, re-verifies it as it re-verifies a candidate, the [contract checks](../07-contracts/04-enforcement.md) included, and mints its release in master's order naming the build and no item. A re-verification that fails leaves the wait standing with the failure on it. A release naming no item is one no gate decided: no [consumer contract](../07-contracts/06-what-a-consumer-declares.md) is derived for it, since none is authored at a stage it never passed, its [authorship rollup](../06-releases/02-the-release-record.md) names nothing the factory wrote, no [prior](../04-risk-score/01-factors-at-least.md) moves, and every traversal from it ends at the acceptance rather than at an intent. That is what makes the claim that what was verified is what ships a claim a reader checks per release, instead of one resting on who holds write access. What it costs is a read a producer's [deprecation list](../07-contracts/08-deprecation.md) cannot see, an accepted commit reading a field no consumer contract protects, and a release on master that no score and no human at a gate ever saw.

The other direction is read at the same start. A release record naming a commit master does not hold is git restored behind the graph, the members of the [recovery unit](../../what-the-factory-does/04-what-the-factory-does-not-build.md) having landed apart. The queue mints nothing for the service and writes the same wait, naming the release and its commit, and the wait ends only when master holds the commit again, from the repository restored to a later point or from any clone that holds it, because a release is written once and cannot be unwritten to match. So the single recovery point the unit requires is checked at every start rather than assumed: members restored apart are a service held at the queue, and never a candidate branched from a master missing work already deployed.

A restore leaves the deploy targets and the artifact store where they were, both outside the unit, so production keeps running releases the restored records no longer hold. Every production [deploy record](../06-releases/05-the-deploy-record/README.md) falls behind what runs, which is a [mismatch](../08-operations/08-drift-detection.md) per service that pages and holds already, and the reading above finds master whole, git having been restored with the graph. What the number query cannot see is the numbers of the lost releases, and one above the highest record would reuse them. The [install event](../../deferred.md) says there was a restore, so the first mint on a service after one takes the higher of two readings and adds one: the highest number among the service's release records, and the highest number among the releases of that service the [health monitor](../08-operations/01-the-health-monitor.md)'s store names. That store is outside the unit and holds what production emitted while the records were behind. The mint writes the numbers it skipped into the log, so the gap stands beside the install event rather than as a puzzle on [Ops](../11-screens/01-work-ops-factory-people.md).

What this costs is that the queue reads two systems where it read one, git at every start and every mint, and a third once after a restore. The ordinals gap after every restore. And every merge to a service is held whenever master holds a commit the queue did not make or lacks one it did, until a human ends the wait or master is whole again. One case the reading cannot cover: a release that served no request between its deploy and the restore emitted nothing, so its number is taken by the next mint. Two builds then answer to one name until the drift detector's digest comparison, which reads bytes and not names, holds that service and a human reads the install event beside the mismatch.
