# Records, and one long-lived branch

Environments are records, not names in code. One record type with a **kind** fixed at creation and three values — production, one a customer defines, and a [candidate](../06-releases/03-what-a-build-is-called-and-when.md)'s own. [Gate](../03-gates/01-where-a-gate-is-and-what-decides-it.md) thresholds, credential references, and the targets an environment is reached at are fields of both persistent kinds; the strategy default is production's alone, because a [strategy](../03-gates/02-the-rollout-strategy.md) decides whether a [control](../08-operations/01-the-health-monitor.md) runs and a control exists only where [organic traffic](../03-gates/02-the-rollout-strategy.md) does. A candidate's environment holds nothing an owner authored, being created at the gate that decides its deploy and so unable to hold the threshold deciding it. What it does hold is what no deploy can happen without: the targets the [deployer](../08-operations/01-the-health-monitor.md) created for it and the credential reference it reaches them with, both written by the deployer at creation rather than authored by anybody. An environment with neither is one nothing can deploy into, and keeping the two facts on the record rather than implied by the creator is what lets the same readers read all three kinds. Production exists everywhere, every candidate gets one of its own, and customers define more per [project](../11-screens/01-work-ops-factory-people.md).

A service's non-secret configuration is a file in its repository, so a change to it is an ordinary [item](../01-one-pipeline.md): a diff, a build, a gate, a candidate environment, a release number, an [analysis window](../08-operations/02-the-analysis-window.md). It does not reopen the second path [the rollout strategy](../03-gates/02-the-rollout-strategy.md) refuses for a flag, since the value comes from the file at deploy and never from a branch left in the running build. Each address at which the service reaches another service's interface is an entry of that file naming the service and the interface, which is what [_Which producer a consumer reaches_](../07-contracts/11-which-producer-a-consumer-reaches.md) resolves a call site against and what the deployer writes per environment. Its secrets are the exception: held by name in the file and resolved to a value at deploy through the resolver that seam 3 of [_Deferred, but not designed out_](../../deferred.md) names, so no build and no diff ever carries one.

An environment names its **targets**, plural: the addresses a deploy is performed against. They are a field, not records of their own, so nothing holds a reference that must survive an address change. A target is never an environment and an environment is never a target: an environment of any kind holds targets, and the kind says which writer created the record, not how many addresses it holds, so a customer with four addresses has one environment naming four targets and not four environments. A [deploy record](../06-releases/05-the-deploy-record/README.md) is keyed by [service](../02-intent-into-items/03-decomposition/README.md) and environment rather than by target and carries completion per target as a field, a mismatch names the address that differs, and [_Drift detection_](../08-operations/08-drift-detection.md) reads each in turn. The field is ordered, and the order is the one a [rollout](../03-gates/02-the-rollout-strategy.md) reaches the targets in. The owner writes it when they declare the targets, and it is the only order there is: on a platform that serves no share, it is the whole of what limits how much of production a release reaches before anything has read it. The cost is that an owner declares every target before the factory can deploy into that environment, and a target added at the provider and never declared is deployed to by nothing and read by the drift detector as nothing — a real target running old software named by no mismatch.

Which of an environment's targets a service runs on is a field of the [service record](../02-intent-into-items/03-decomposition/README.md), owner-written at Factory beside the parameters, and where the owner writes none the service runs on every target of the environment. A project is not one placement: an edge-hosted front end, a batch host, and a regional backend are three services on three subsets of one environment's targets, and without the field every service in a project would have to run on every target or be a project of its own, a boundary drawn by hosting rather than by product. Every reader of targets reads the service's set. [Current release](../06-releases/05-the-deploy-record/README.md) is completion on the service's targets; the deploy record's completion per target, the [window](../08-operations/02-the-analysis-window.md)'s target set, and the [rollout](../03-gates/02-the-rollout-strategy.md)'s order are over them; [the drift detector](../08-operations/08-drift-detection.md) reads them and no other for that service; and the [score](../04-risk-score/README.md) picks the row with a control only where every target in the service's set serves a share. A target removed from the service's set is a [removal](../02-intent-into-items/03-decomposition/04-retirement.md) on that target first, as a target leaving the environment is. What it costs is one more owner-written field on the service record, a set every reader of targets joins through, and an owner who names a target the environment does not hold, which the write refuses.

An environment also declares its [platform](../03-gates/02-the-rollout-strategy.md): the credential the deployer composes a [candidate environment](02-an-environment-per-candidate/README.md) through, resolved by name through seam 3 of [_Deferred, but not designed out_](../../deferred.md), and whether that platform can compose an environment on demand. A production environment declaring one that cannot is refused at [adoption](../02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md) and at decomposition for its services, an environment per candidate being the shape [_What the factory does not build_](../../what-the-factory-does/04-what-the-factory-does-not-build.md) admits and nothing else. So which platform a candidate environment is composed on is the production environment record of the item's service, and the deployer's [last check](../08-operations/08-drift-detection.md) for a platform and the [maximum concurrent candidate environments](../03-gates/07-what-particular-gates-decide/06-deploy-to-candidate-environment.md) are keyed by that record, one of each per production environment, so an install whose projects run on two platforms sums nothing across them. What it costs is a platform an owner declares before the factory can compose anything for a project, and a ceiling authored per production environment rather than once.

An environment also declares, per target, whether the platform behind it serves a share: whether it can decide what fraction of arriving traffic reaches each of two builds. The owner writes it with the target, and it is the fact the [score](../04-risk-score/README.md) reads when it picks a [strategy](../03-gates/02-the-rollout-strategy.md). On an environment with a target that serves no share the row with a control is unavailable, so the score picks the other row rather than a rollout the deployer cannot perform, and a strategy the platform cannot perform stops being something the deployer discovers. The [deploy record](../06-releases/05-the-deploy-record/README.md) names the strategy performed beside the one picked, so a target declared as serving a share on a platform that moved instances instead shows there as a control that did not run. What it costs is what the targets already cost: one more thing an owner declares before the factory can deploy into the environment.

The kind is also the [seam](../../deferred.md), two writers never writing a record of the other's kind. An owner writes the persistent kinds on [_Factory_](../11-screens/01-work-ops-factory-people.md): production's at the creation of the project, which an owner does not choose because production exists everywhere, and each further one when they define it. The [deployer](../08-operations/01-the-health-monitor.md) writes a candidate's, creating it at the approval of [Deploy to candidate environment](../03-gates/07-what-particular-gates-decide/06-deploy-to-candidate-environment.md), tearing it down for good when the [item](../01-one-pipeline.md) merges, is dropped, or is superseded by a [re-decomposition](../02-intent-into-items/03-decomposition/README.md), and reclaiming one meanwhile as [_An environment per candidate_](02-an-environment-per-candidate/README.md) sets out. The only component that reaches a deploy target is the one that reaches environments, and a gate decides an event and edits nothing. What that costs is three creation paths for one record type, so every reader excludes the kinds it does not want, and a torn-down candidate record is kept rather than deleted because the deploy records naming it would otherwise point at nothing.

A persistent environment contains a whole project, every service in it, while a [release](../06-releases/02-the-release-record.md), a [release number](../06-releases/04-the-release-number.md), a master branch, and an [analysis window](../08-operations/02-the-analysis-window.md) are all per service. A deploy puts one service's build on one environment, so an environment fed by a twelve-service project has twelve independent promotion paths. A candidate's environment contains no project: it is composed for one candidate, which [_An environment per candidate_](02-an-environment-per-candidate/README.md) sets out. The [gate row](../03-gates/03-actions-at-each-gate.md) a customer's environment adds describes that environment; what fires is one [decision](../03-gates/01-where-a-gate-is-and-what-decides-it.md) per deploy into it. A customer's extra environments are places master's releases are deployed to and not ordered stops — nothing makes a release pass through one before production, and the [production deploy gate](../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) gains no [hold](../03-gates/04-what-a-gate-may-change.md) on another environment's deploy. An owner who wants a human to look at a release running somewhere first adds a [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md) putting one at that gate (9). What that costs is that a staging environment enforces nothing: a release can reach production having never been deployed there.

Its history is not a field. The deploys that name a record are inbound edges, the arrangement the release record already uses, and [incidents](../08-operations/06-incidents.md) and [rollbacks](../06-releases/06-rollback.md) exist on production environments alone, because the [health monitor](../08-operations/01-the-health-monitor.md) that opens an incident and the strategy that keeps a control both attach to a production deploy and to no other. The cost is that a pre-production environment where something misbehaves has no record of it — what is written there is a rejected candidate or nothing.

One long-lived branch is each service's promotion path: master. A candidate has a branch of its own until it merges, is dropped, or is superseded by a re-decomposition. Merging and deploying are separate events and so are separate gates — a merge admits a change to master, a deploy puts a build on an environment, and either can happen without the other. A deploy can be rerun; a merge cannot be unmerged the same way.

A candidate is not a record. It names an item and the build currently in force for it, and a build on a candidate branch belongs to one item, so the pair and the build pick out the same thing — a record per pair would repeat what the build and the item say already. The [criteria](../03-gates/07-what-particular-gates-decide/02-spec/02-in-force-and-withdrawal.md) results and the candidate deploy attach to the build. The branch and the environment are the item's and persist across a rebuild, the environment being a record already. What that costs is that [_The merge queue_](03-the-merge-queue.md)'s rejection has no record of its own: no gate fires, so it is written into [the log](../../deferred.md) by the log with the queue as caller and [actor](../../deferred.md), the way [a wait no gate could compute](../03-gates/04-what-a-gate-may-change.md) is, and not as a [decision](../03-gates/01-where-a-gate-is-and-what-decides-it.md). There is no firing to open a row at, the [Merge to master](../03-gates/07-what-particular-gates-decide/07-merge-to-master.md) gate's own having closed as an approval, and no [factor vector](../04-risk-score/01-factors-at-least.md) computed for it. It is counted as an attempt against [_the limit_](../03-gates/05-the-attempt-limit.md) at the [stage](../02-intent-into-items/03-decomposition/02-what-an-item-names.md) the item is sent back to. What that costs is that [_Factory_](../11-screens/01-work-ops-factory-people.md)'s gate rejection rate, being rejects over firings per gate row, does not see it: one of the three ways an item goes back is absent from the number an owner reads.

A **build** is a record, one per commit built. The **build runner**, the component that performs every build, reaches no deploy target, and never crosses [seam 4](../../deferred.md), writes it when called to build. Four callers. The first two: the implementation stage when it finishes, so that the [Implementation gate](../03-gates/07-what-particular-gates-decide/05-implementation/README.md) decides over a build that exists and the [score](../04-risk-score/README.md) has a diff to compute the [change factors](../04-risk-score/01-factors-at-least.md) from; and the candidate deploy where a rebuild is needed. The other two: the merge queue at [re-verification](03-the-merge-queue.md), which builds the candidate branch onto the master it will actually merge into; and the [search](../08-operations/03-overlapping-windows.md), whose builds are of commits on no branch, decided by no gate and bounded there rather than here. A rebuild is a new build, so an item holds one build per time it was built and the release names the last one. That the commit verified is the commit that merges is therefore a property of the queue, not of any build. Every record naming a build says which: a gate decision names the one in force at the firing, a factor vector is computed from that same build, a [consumer contract](../07-contracts/06-what-a-consumer-declares.md) names the one it was derived from. The commit is a field of the build and not a record, one commit per build and nothing pointing at a commit that has no build. A build also names the [shipped-bundle identity](../../deferred.md#the-products-release-channel) of the release of the product that made it, which is what says which [way in](../02-intent-into-items/01-intake/02-reports.md) the build carries.

So is what the build resolved: every third-party package, the version resolved to, and the licence the package declares, written by the build runner from the build it performed. That is because a commit resolving an unpinned range on two days is two builds shipping two things, and the [advisory](../02-intent-into-items/01-intake/03-advisories.md) detector reads a shipped build's set and nothing else could say what it holds. The same set, diffed against the [current release](../06-releases/05-the-deploy-record/README.md)'s build's, is the dependency change the score's [exposure](../04-risk-score/01-factors-at-least.md) factor reads, and a licence policy is decided against it as a build-kind [constraint](../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md); which services ship a package at a version is a query over current release, build, and set, and not an estimate. What the build costs is that an item rebuilt four times leaves three builds nothing points at.

An entry of the set is more than a name and a version, because a version is not an identity for bytes: a registry lets a version be republished, a mirror serves other content under the same name, and one name in two registries is two packages. Each entry therefore records the source it was resolved from, a registry or a repository named the way a deploy target is, the version, and the digest of the content the resolution produced, with the declared licence kept as the claim it is. The build names beside them the digest of the artifact the build runner produced from it, which is what a deploy puts on a target and what [_Drift detection_](../08-operations/08-drift-detection.md) and a [rollback](../06-releases/06-rollback.md)'s redeploy read it against.

Three readers change with the field. The [advisory](../02-intent-into-items/01-intake/03-advisories.md) match is keyed by source and name rather than name alone. The [exposure](../04-risk-score/01-factors-at-least.md) factor's diff reads a digest moved under an unchanged version as a package moved, which is what it is. And an owner may state as a build-kind [constraint](../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) which sources a service may resolve from, a package from any other rejecting at Implementation, which is the one mechanical answer to a package substituted from a registry nobody chose. Where the resolver produced no digest or no source for an entry, the entry says so. That is the resolver's coverage, which the build records beside the set per ecosystem and per entry: a constraint reaching such an entry resolves a human to the gate, and an advisory match over it is unassessed rather than clear. What it costs is a resolver that has to produce a digest per toolchain, an entry unassessed wherever it cannot, and a dependency change read on a version nobody moved because its bytes did.

Each entry also records what required it: the manifest in the repository that declares it, for a package the service names itself, or the entry that pulled it in, for one that arrived through another, so the set is a graph from the manifests down and not a flat list. That edge tells a package the change declared from one an upstream version move dragged along, which the diff of two sets cannot. The [advisory](../02-intent-into-items/01-intake/03-advisories.md) match at Implementation and the [exposure](../04-risk-score/01-factors-at-least.md) factor each name, for a package added or moved, whether the diff touched a manifest on its chain; a package the agent named itself, with no manifest on its chain, is how a registered look-alike name arrives. An advisory item's plan reads the same edge, and where an entry's chain reaches no manifest the service holds, the item moves the entry that requires it. What it costs is a resolver that has to produce the requiring edge per toolchain, and an entry whose edge it could not produce saying so the way one without a digest does, read by those two as added by the change.

Resolution and execution are two steps, in that order, because a package's install-time code would otherwise run before anything read the set. The build runner resolves and fetches first, with install-time scripts disabled where the toolchain allows it, writes the set, and reads the source constraint in force against it before it runs anything: a package from a source the constraint excludes stops the build there, recorded as a build that did not run, and Implementation rejects on that record. The licence constraint and the advisory match are decided at the gate as before, over a set the fetch produced and the build did not alter. Where a toolchain cannot separate fetching from running, the coverage says so, and a build on it resolves a human to Implementation the way a set without digests does. What it costs is a second pass over the manifests on every build, and a human on every change to a service whose package manager runs code as it fetches.

At [the queue's re-verification](03-the-merge-queue.md) the re-resolved set's digests are compared to the approved build's too, and a difference rejects there on the terms a candidate that fails its own merits already does: the item goes back up to Implementation and counts an attempt. What it costs is one comparison added to a resolution the re-verification was already performing.

The resolved set is a derivation and not a fact every build has. Recovering it is per toolchain, so a resolver is a component of the factory shipped with it, and which toolchains have one is published as a fact of the factory's version, the arrangement [_What a consumer declares_](../07-contracts/06-what-a-consumer-declares.md) gives its extractors. A lockfile names the declared ecosystem's packages and nothing else, so the build records what the resolver covered beside the set: which ecosystems it read, whether the base image's packages, vendored source and statically linked code were enumerated, and per entry whether the package is present at run time or only at build time. Where no resolver covers the build, or resolution fails outright, the field is **could not derive**, a record and not an empty set, because "nothing vulnerable was resolved" and "nothing resolved was visible" call for opposite responses.

Every reader of the set reads the coverage with it, and none reads an absence as clean. The [advisory](../02-intent-into-items/01-intake/03-advisories.md) detector matches only inside what was covered, and a service whose current release's set is could not derive or covers less than the feeds watched is listed as unassessed rather than clear. A licence [constraint](../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) over such a build cannot be decided mechanically and resolves a human to Implementation the way an [unavailable factor](../04-risk-score/01-factors-at-least.md) does, the vector naming what the resolver did not cover. The [exposure](../04-risk-score/01-factors-at-least.md) factor reads a could-not-derive set as that factor unavailable, resolving the same way, and never as no dependency change, which would lower the number on the build the factory knows least about. What it costs is a resolver per toolchain to ship and keep, a human at Implementation on every change to a service on a toolchain without one, and such a service standing as unassessed for as long as that holds. That is the pressure _What a consumer declares_ already builds, here aimed at the software an [adoption](../02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md) is most likely to bring in.

The build runner produces one more field from the resolved set, in the same write: a **notice file** naming every package's source, version and declared licence. Where the resolved set is could not derive, or its coverage leaves out what the file would list, the notice file is could not derive too, and the release naming this build reads the same at [Merge to master](../03-gates/07-what-particular-gates-decide/07-merge-to-master.md).

A build in a project with screens names one thing more: the [design system](../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) constraint record in force for that project when the build was performed, written by the build runner beside the resolved set and for the same reason. A constraint is never edited, so the record is the version. Without the field, which design system a shipped screen was built from is reconstructed by holding the build's time against constraint arrivals and withdrawals; with it, the question is answered by following a link. The [search](../08-operations/03-overlapping-windows.md)'s builds, which are of commits on no branch, are the exception: a search build names the record the release it was built from named, so what the search's exit isolates is the revert's change and not a design system that moved since. What it costs is a field on every build in a project with a user interface, none on a build in a project without one, and one caller that has to say which build it is performing.

What a run on a candidate environment produced attaches to the build, written by the deployer when the run finishes and not a record of its own: each criterion decided, and each consumer contract checked against the exchanges observed there. The composition in force at the run is copied onto the build with them, from the field [_An environment per candidate_](02-an-environment-per-candidate/README.md) has the deployer write, because that field is rewritten at a recomposition and what an earlier run ran against survives on the build or nowhere. Which environment the run happened on is the item's, which the build names — the build could not name one itself, being written when the implementation stage finishes, one gate above the approval that creates the environment.

The identity is the build, the run, and the criterion id. A run is one deploy of the build onto the item's environment, numbered per build by the deployer in the order it performed them, and the composition is copied per run and not per build. That is because one build is run more than once: [the queue's confirming run](03-the-merge-queue.md) repeats a re-verification over its own build, and an item whose environment was reclaimed resumes at [Deploy to candidate environment](../03-gates/07-what-particular-gates-decide/06-deploy-to-candidate-environment.md) on the build it already had, against a composition that may have moved. A gate reads the build's latest run, and every earlier run stands with the composition it was decided against, which is what [undecided](04-what-the-candidate-environment-decides/01-the-third-outcome.md), the queue's three readings, and the criterion's [outcome history](../03-gates/07-what-particular-gates-decide/02-spec/02-in-force-and-withdrawal.md) each compare. Keyed by build and criterion alone, a second run would overwrite the first, and the disagreement the third outcome is computed from would be gone before anything read it. What it costs is one more part to the key, and a build carrying as many result sets as it was run. The producer's own [contract diff](../07-contracts/04-enforcement.md) is not among them. It needs no run and no environment, and a verdict stored at run time is not a check made when the gate fires, which is what [_Two baselines, kept apart_](../07-contracts/06-what-a-consumer-declares.md) requires. What is written is what was observed; what is decided is decided at the gate.

The encodings that declare no environment are the exception on the other side: the build runner decides them in the build's own process when it performs the build, and writes their results onto the build beside the resolved set, so the [Implementation gate](../03-gates/07-what-particular-gates-decide/05-implementation/README.md) reads them before any environment exists. At [the queue's re-verification](03-the-merge-queue.md) the new build carries them again, and one failing there fails the candidate as a criterion failing on the recomposed environment does. The build runner performs a build in a process of its own holding nothing of the factory's: no target, no credential, no reach to the store, the log, or the resolver, and network reach to the sources the set names and to nothing else. Wherever the build runs, a container runtime or the host itself, that boundary is a requirement on the host, stated the way the artifact's reachability is. A package's install-time code and a build plugin run inside it, so a compromised dependency reaches the clone it was fetched for and the artifact it builds, and never the factory's records or another service's credential. That is what the boundary buys: a build compromise ships through the gates as any change does and rewrites nothing they read. An encoding declared for the build that needed an environment fails there rather than passing against nothing. What it costs is a build that is also a run, paid on every build the build runner performs. A criterion the build decided is never repeated over one build: [undecided](04-what-the-candidate-environment-decides/01-the-third-outcome.md) cannot arise for it, and an encoding of that kind that cannot hold its answer shows only as two builds disagreeing.
