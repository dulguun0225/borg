# Deferred, but not designed out

Two things are sequenced away rather than answered: security, and software the factory did not build. Both are decisions about order. What each has to satisfy is that waiting creates no requirement the factory cannot meet when it arrives, and the two satisfy it differently — security by leaving fields populated in the meantime, adoption by leaving nothing that has to be done in advance.

## Security comes last

The factory should be free and easy to play with at the start and tighten as the human world demands it. That is a sequencing decision, not permission to build something that cannot be secured later.

Four seams are nearly free now and expensive to retrofit:

1. **An actor on every record** — every gate decision, edit, approval, veto. No authentication, no enforcement, just the field, always populated. Identity cannot be added to a history that was written without it.
2. **One append-only decision log, each record chaining its predecessor.** It is the audit trail and the risk score's training data at once, and it must not become two systems. Append-only is a promise its writer makes about itself, and the chain is what makes it evidence instead — one field, populated from the first record. Where the head is anchored and who reads it can wait; the field cannot, because a chain laid over history written without one starts at the retrofit. The same record names the policy and the score version it was decided under, for the reason the actor is there: what a decision was made under is not recoverable from a history that recorded only the decision. One chain means one writer: every component that decides anything calls the log rather than writing into it, because five writers would be five implementations of the chain and five heads. The log holds three shapes and not one — a decision, a [_page event_](how-humans-do-it/08-operations.md#pages), and a wait the factory could not compute when a gate fired, an unreachable credential among them — and the last two name no policy version and no score version, being a delivery and a wait rather than a decision. What that costs is that every reader of the trail filters on which shape it has, and the score is told to ignore two of them the way it already ignores a hold. How long the log is kept is a setting an owner authors, stated with the rest of what they author in [_Gate policy_](how-humans-do-it/09-gate-policy.md#what-is-not-in-it).
3. **Secrets by reference.** Artifacts and specs contain names, never values — they get copied, diffed, and given to agents. So does every credential the factory records: the one an agent reaches its own model through, which is [_The fleet_](how-humans-do-it/10-fleet.md) using this seam before any artifact does, and the one on an [_environment record_](how-humans-do-it/05-environments.md#records-and-one-long-lived-branch) that seam 4 resolves at every deploy. One resolver answers both, and it can be a file on disk today. What that costs is that nothing separates the two: whoever can read the resolver reaches the models and the deploy targets alike, so until policy attaches at seam 4 this separates storage and not reach.
4. **A named seam between agents and deploy targets.** However it is implemented, an agent reaches an environment through a small set of named operations. That seam is where policy attaches later; without it, production access is spread through the codebase. What it attaches to on the other side is an agent's [_scope_](how-humans-do-it/01-one-pipeline.md), declared and enforced by nothing until this seam is built.

One pipeline is not a fifth seam — it is the architecture the four attach to, and it was chosen for coherence rather than safety: a single path is a single place to put policy. What makes that work is that nothing routes around it, including incidents — the emergency action [_One pipeline_](how-humans-do-it/01-one-pipeline.md) allows is approve now, not skip, so a rushed yes is a yes with an actor on it and not a gap in the record. That is where most single-path designs fail.

The drawback is that a single path is a single point of failure. Almost nothing outside the pipeline disagrees with the pipeline, so a subverted one ships a change with a valid approval on it. What replaces the second path is mostly downstream of the deploy and reads what the factory wrote: the log for detection, the actor for attribution, and veto after the fact (10) inside the [_watch window_](how-humans-do-it/08-operations.md#the-watch-window) for the undo. [_The reconciler_](how-humans-do-it/08-operations.md#the-reconciler) is the one thing that disagrees from outside, and it does so over a single fact — what is actually running against the record naming it — which is the whole of what a separate second path is worth.

## Adopting an existing codebase

Everything else in the tree assumes a factory that has always been there. A first run on software somebody else built has none of what that assumes, and how a factory takes such a codebase over is not designed here. What is settled is that it is sequenced away and what the wait costs, so that the section which eventually designs it starts from a known list rather than a discovery.

Five things a first run does not have, and what each costs until it does:

- **A deploy record for what is already running.** A service's [_current release_](how-humans-do-it/06-releases.md#the-deploy-record) is what its production deploy record names, and the factory made none of the deploys that are running. Until it ships that service once, the dependency holds at both deploy gates and [_The reconciler_](how-humans-do-it/08-operations.md#the-reconciler) have nothing to read: the first deploy the factory performs is what brings a service inside its own checks.
- **Declared meaning on the interfaces.** [_What a diff cannot see_](how-humans-do-it/07-contracts.md#what-a-diff-cannot-see) states this already — an interface adopted from outside arrives without it, and naming a field afterwards is a breaking change, which is three items for a rename no behaviour depends on. Until that work is done, a consumer's declarations are checked against what was never declared.
- **A design system a machine can read.** The screens exist and were drawn under no constraint the factory holds, so what enforces a look is a pin (9) putting a human at a gate — the cheap form [_Intake_](how-humans-do-it/02-intent-into-items.md#intake) sets out, which requires that human for as long as the pin lasts.
- **A build to start a control from.** The factory can take traffic from what is running; it cannot start an instance set of a build it never made. So the first release on an adopted service is measured the way a straight deploy is, on the weak fallback [_The health signal_](how-humans-do-it/08-operations.md#the-health-signal) names, and the second release is the first one that can be measured properly.
- **History behind the learned parameters.** The authorship prior starts wide, K starts at 1, the item-size target and the watch window's size come from the score. That is the design working, and adoption is where its drawback is most visible: a service that has shipped for ten years starts from the same floor as one that has never shipped at all.

None of those five becomes impossible by waiting — each takes the same work whenever adoption is designed, which is why this is deferred work and not a fifth seam. What no field populated on the first day recovers is behind the adoption rather than in front of it: every release links back to an item and its intent, and code the factory did not write links back to the day it arrived and stops there. That is not a deferred cost but one nothing could have avoided, and what it means in practice is that an incident in adopted code is worked as an item like any other, while following the links out of it ends where the factory's own history starts.
