# Operations

## The health signal

A deploy record says which release runs where, so the factory always knows which build it is measuring. It compares that release against a **control** — an instance set running the build already in production, started alongside the release and taking comparable traffic — and that comparison is the health signal. Nothing has to be authored for a service to have one, once there is a build in production to compare against.

The control is started rather than found, because a new process and a long-lived one differ before either serves a request: cold caches, empty pools, a compiler that has not yet seen the workload. Measured against the instances it is replacing, a release is slower for being new, and the factory reads that difference as a regression. Measured against a control of the same age, the only difference left is the change itself. **Baseline** stays the name for what the comparison is made against; what changed is that the factory now starts one instead of pointing at what is already running.

A control belongs to the rollout and is not a deploy of the release it runs. It takes traffic so that it can be measured, it mints no number, and it is torn down when the window closes.

The signal exists in production and nowhere else, and the reason is arithmetic rather than policy: it is computed from organic traffic, and a candidate environment has none. A comparison computed from one human exercising a screen is noise that looks like evidence, and running a control beside it would double the compute spent on learning nothing. What a candidate environment decides is the criteria, which need a test run rather than a population.

A rollout fails when the comparison crosses the boundary, and the rollback follows automatically. The comparison runs after every production deploy, and the strategy decides only how the factory acts on it: a rollout with a control moves its traffic back to the build still serving, whatever schedule it was taking that traffic on, and a straight deploy, having no other instances running, has to redeploy the previous build and wait for it to start.

A control requires the old build to keep serving, which is exactly what a straight deploy does not do. So the real comparison is available only with the strategy that keeps one, and a straight deploy falls back to reading the release against its predecessor's own recent history — the confound above, unanswered, which is what makes that fallback the weak one. This is the second thing the score decides when it picks a strategy: the cheapest rollout is also the one that measures least, and where the score wants a measurement, it picks a strategy that keeps a control running.

The baseline is only as good as the build it runs, which is the argument for pinning: an owner can pin explicit thresholds for a service the way they pin a gate or a strategy, and a service whose normal behaviour is already bad is where that is worth doing. An explicit threshold is absolute where the comparison is relative, and it applies in addition to the comparison rather than instead of it — the release passes both or neither, so a pin here can only add a check, like every other.

A service's first release has no build in production to compare against, and the weak fallback is no answer there either: reading a release against its predecessor's own recent history requires a predecessor. So the absolute reading is the only one left, used alone rather than alongside a comparison for the one release where there is nothing to compare — and where an owner has pinned no threshold, the first release is unmeasured and nothing about it is discovered by watching. A control exists from the second release, and the signal is complete from there. An adopted service differs in one way, set out in [_Deferred, but not designed out_](../deferred.md): software is already running, so its first release has the weak fallback even though it has no control.

## The watch window

The **watch window** is how long the factory may act on the comparison alone. Inside it, crossing the boundary rolls the release back with no human involved; outside it, the same crossing raises an item. It is the factory's own authority and is limited by evidence, where veto after the fact (10) is a human's and is limited by reversibility — a rollback while the control is still running, a revert once it is gone. That is why there is no second named window: what limits a human's undo is the control, which the strategy either keeps or does not, and a window with no parameter and no limit of its own is a second name for something already named. A rollback deploy opens no window of its own: the build being restored was the control, and a fresh window would compare it against the release just condemned and restore that one.

The window is a volume condition, not a clock — and not a volume computed in advance either. The comparison is evaluated as traffic arrives, against a boundary that is valid at every point it is read. That much is forced by what the factory already does: a threshold set for one look at a fixed sample is not the threshold for a thousand looks at a growing one, and reading a fixed-horizon test continuously is how a factory rolls back healthy releases all day. The boundary is what makes continuous reading legitimate rather than a fault nobody traces to its cause.

| Exit | What closes the window | What follows |
|---|---|---|
| **harm** | the comparison crosses the boundary against the release | rolled back, no human involved |
| **clean** | the comparison rules out a regression of the size worth catching | closed early, on evidence |
| **cap** | neither, by the cap | closed unresolved |
| **swept** | a rollback aimed below it undid this release | closed with the release neither condemned nor running |

What an owner authors is that size and the confidence required, with the rest of gate policy (8), pinned per service the way explicit thresholds are (9); where they author nothing the score supplies both. A pinned size is a minimum level of protection — the score may ask to catch something smaller, never something coarser, so a pin can only add protection, the way a pinned gate can only add a human.

The duration is measured and never set, and that is where the throughput comes from: a release that is plainly fine shows it early and its window closes. It gets there by being fine rather than by being watched against a coarser boundary, which is the change not to make — the traffic a comparison needs scales as the inverse square of what it must detect, so cutting the window tenfold makes the boundary three times coarser. Speed obtained that way runs out quickly. Speed obtained from evidence does not.

A boundary is not arguable the way a vector of factors is, and the score's own rule is that a number nobody can argue with is one nobody will trust. What an owner argues with is the size and the confidence, both authored and both pinnable; the boundary is arithmetic on those. That is the same shape as the score — a published formula over inputs a human can disagree with.

A cap limits it in elapsed time, authored the same way. The condition is a traffic-volume one, but what ends a window that will never reach its volume cannot be — so a service too quiet to receive that much traffic ends at the cap every time. There the window is weak protection and is reported as weak: a service called twice a night is not made safe by watching it until lunchtime. A service's first release ends there too and for a different reason: it has no comparison to rule anything out, so clean is not an exit available to it — a pinned threshold can still condemn it, but nothing can clear it early. With K at 1 on a service that has never shipped, that cap is also how long the second release waits. The sample the score holds out runs to the cap rather than stopping where the boundary would allow — auto-passing a change the score wanted gated is where the factory is most openly guessing, so it takes the longest watch available, which on a quiet service is not much.

The window reads the producer's own signal and nothing else. A consumer that breaks does so in its own error rate, on its own schedule, and what catches it is that service's own comparison raising an item — after the producer's window closed, with nothing rolling back automatically. Reading another service's signal would require every consumer's calls to be recorded and attributed across services, which is the recorded-usage approach [_What a diff cannot see_](07-contracts.md#what-a-diff-cannot-see) refuses; the window keeps that refusal rather than reopening it. The item is what replaces it, together with the contract rules that make the schema half mechanical, the producer's own per-field observables, and veto after the fact (10) while the change can still be undone.

The parameters are learned. How fast a problem would appear is already what the score reads to pick a strategy, and the same evidence sets the size wherever an owner has not. Only a rollback or veto traceable to the health signal counts as that evidence — a change vetoed for being the wrong feature says nothing about what the comparison should have caught, and feeding those back would shrink the size for owners who changed their minds and lengthen every window with it. The score learns from the signal it could have seen, the same way it learns from a reject and not from a hold.

## Overlapping windows

An open window blocks nothing. The next item builds, verifies on its own environment, merges, mints its number, and deploys while the window before it is still open — up to **K** of them at once per service. K is authored with the rest of gate policy (8), and where an owner authors nothing the score supplies it, the same division the window's own size and confidence use. A pinned K is a maximum on how many releases one rollback undoes — the score may ask for fewer open windows, never more — so a pin can only add safety here too. The drawback of authoring it appears late: the number has no visible effect until the first rollback, where it is how many releases are undone at once.

What the score supplies starts at 1 and rises only with evidence, because that evidence arrives one-sided — a service that has never rolled back has seen the throughput K gives and none of the rollback size it causes. Windows closing without harm raise it; a rollback that undid more than its target lowers it. That is the same shape as the authorship prior, a position taken where there is no evidence and moved by what arrives, and it requires nothing of the score it does not already do. The drawback is that a service which rarely rolls back rises slowly and gives up throughput it could have had, and the first rollback after a rise undoes more releases than it would have before.

That is what a started control makes possible. A found baseline made concurrency incoherent: with the comparison made against the release it replaced, a second deploy during an open window made the first release the second's baseline, so a regression the first introduced became part of what the second was measured against and was never detected. Serializing was the only way to keep the baseline single-valued. A control is started per release and never changes, so two open windows are two independent comparisons and neither is the other's baseline.

What a rollback targets has to change with it. The previous release is not single-valued while K windows are open, so the recovery target is the last release whose window closed without harm, recorded on the release record. Closing at the cap counts: a release that was never condemned is one the factory can return to, and requiring a clean close would leave a service too quiet to ever reach one with no target at all.

Closing swept does not count, and that is what separates the two unresolved exits. A release a rollback undid was never condemned either — its comparison simply stopped, because master is linear and the release was above the target — but it is not running and its control was torn down with its window, so there is nothing to return to. The release the rollback targeted is what runs afterwards and stays the target. A swept release is one the factory skipped over, not one it can return to.

Rollback is then a traffic shift onto the control of the oldest open window, which is already running that target — started, warm, and the instances the comparison was being made against. No control has to outlive its own window for this to work: each one runs the release below it, so the fallback is always provided by the window above the one that closed. Where the rollout was a straight deploy there is nothing to shift traffic onto, and the rollback is the slow one — the previous build redeployed and waited for.

K's drawback is rollback granularity. Master is linear, so the release above a bad one includes it: a rollback inside overlapping windows undoes every release above its target, up to K of them. That is the one place the factory ships more than one item at a time, and it is limited rather than unlimited — [_One item per release_](06-releases.md#one-item-per-release) is still true for what ships, and for what a veto undoes once the window has closed. K = 1 is the serial factory, and every increment above it adds throughput on a high-frequency service and increases how many releases one rollback undoes.

A rollback still sets a hold, where an open window no longer does. Master keeps the change that was rolled back and the next item was built on master, so deploying it would redeliver the defect just removed. The hold stays until the revert item ships, and it does not hold the revert — a dependency hold that blocked its own dependency would never lift. Without that exception the mechanism stops working exactly when it is needed.

A human can approve through it. The hold is the factory's own and the emergency action is approve now, not skip; the production deploy gate offers Approve regardless. What approving redelivers is the defect that was just removed — the most damaging thing in the factory to approve through, and the one most likely to be tried during an incident.

## After the watch window

The comparison keeps running after the window closes. What it finds then is not a rollback candidate — the change has been live for a week and the window's authority ended long before. It is an unrefined intent in [_Work_](11-surfaces.md#work-ops-factory-people), the same shape as an end-user complaint (4, 5), taking the same stages and the same gates. That is the whole of "finds issues and fixes bugs": detection writes an intent, and the pipeline does the rest.

## Incidents

An incident is a record on the environment. It points at the deploy, the deploy at the release, the release at its item and its intent — so what caused an incident is answered by following those links, the same links the release record answers from the other end.

The factory works the item it raised under the attempt bound like any other. Exceeding that bound turns it into an escalation (12), the same Work row a stuck feature produces: a bug the factory cannot fix is not a different kind of stuck.

## Pages

Mail and chat deliver everything waiting on a human out of the product. A **page** is the narrow channel: what qualifies for one is a wait where the deployed software is worse until a human ends it, and nothing else fires one.

That condition is already the document's, and two refusals above follow from it rather than being added to it. A declared dependency that is not its service's current release holds the production deploy, nothing is decided, and the hold lifts itself when the dependency is current again — there is no wait for a human to end. An owner's silence at [_The interview_](02-intent-into-items.md#the-interview) consumes no compute, which is why no bound applies to that wait; a page would be the same mistake made more loudly.

Three things meet that condition today, and the condition is what governs — the list follows from it and is not the test. An escalation (12) on an item the factory raised from an incident — the factory saying it cannot fix a defect that is live. A human deciding at a gate on a revert while the rollback that removed the defect still holds: the service is running the build that was restored, master still contains the defect, and nothing ships past that human. And a mismatch [_The reconciler_](#the-reconciler) found, which holds that service's production deploys until a human clears it. In all three, production is worse than it should be and no mechanism the factory has will improve it.

The first is not special for having come from an incident. An item [_After the watch window_](#after-the-watch-window) raises is not one, and takes the same shape as an end-user complaint (4, 5); an end-user bug report is that shape exactly. Any of the three stopped at the attempt bound is the factory giving up on a defect while the software containing it is live, so it meets the condition without being on the list. What separates these is never which of intake's three sources the intent came from: the refusal below — that an escalation on a feature item has nothing live that is worse — already separates on whether something live is worse, and that is the whole of the test.

A rollback the factory performed on its own is reported, not requested, and reporting is not paging — **the factory does not page to inform.** Nothing else waiting on a human meets the condition either: a UAT assignment (7) delays its own item and holds its own item's environment, an escalation on a feature item has nothing live that is worse, a deploy queued behind its service's K open windows is waiting on the factory, and a [_fleet entry with no credential to reach_](10-fleet.md#an-account-that-runs-out-is-a-hold) stops work rather than making anything live worse — the row most often mistaken for a page and still not one. Those wait in Work, and mail or chat delivers them.

A page has no duty of its own — inventing a thirteenth would be a mechanism where routing already exists. It reaches whoever holds the duty the row belongs to, the same routing that showed them the row in Work.

Not every row belongs to a duty. A mismatch [_The reconciler_](#the-reconciler) found holds the production deploy gate, which none of the twelve owns: confirming criteria (6) and performing UAT (7) are the duties at a gate, and [_What the candidate environment decides_](05-environments.md#what-the-candidate-environment-decides) puts the UAT one at the merge gate. Installing the reconciler is substrate outside the twelve, so the page reaches whoever [_People_](11-surfaces.md#work-ops-factory-people) records as having installed it, and widens to the owner where nobody is recorded. That is what [_What the fleet is not_](10-fleet.md#what-the-fleet-is-not) already does for a lent credential — routing needs a named human rather than a duty number — and it is why a thirteenth duty stays refused: a duty would score an obligation the twelve deliberately leave unscored, where a named human only has to be reachable.

A duty may be held by more than one human, and a page reaches all of them at once. There is no rotation naming which one it reaches first: a rotation would be a People declaration enforced by nothing, and what a stale one does — widen to every holder — is what happens here without it. The parameter's failure mode is the behaviour that replaces it, so the parameter is what can be dropped. Unanswered, a page widens once more, to the owner. The drawback is that a page nobody needed reaches everybody, accepted so that none is ever lost.

An unanswered page never makes the factory act alone, because the state it is paging about is stable. The service runs the last release whose window closed without harm, not the one just condemned, so the wait delays the fix and never the recovery.

A human may fire one on their own judgment, from [_Ops_](11-surfaces.md#work-ops-factory-people), which is the parallel veto after the fact (10) already has: the rollback the factory would perform, on a human's judgment instead of the comparison's. Nothing scores it and no bound applies to it. What limits it is that a page nobody needed makes its recipient slower to answer the next one.

A page is an event on the row it belongs to — who was reached, when it widened, who answered — each recording an actor, which is seam 1 of [_Deferred, but not designed out_](../deferred.md) and nothing new. None of it is authored: who holds a duty is a People declaration and the widening is the factory's own, so gate policy stays at the rows it has.

## The reconciler

Every check above reads a record the factory wrote. A service's [_current release_](06-releases.md#the-number) is what its production deploy record names, the health signal is measured against a control the factory started and recorded, and an incident points at a deploy the same log describes. So a factory whose records are wrong reports itself healthy, and nothing downstream of them contradicts it.

The **reconciler** is one process outside the pipeline that reads what is actually running on each production target and compares it against that service's current release. One fact, one comparison, read-only — no deploy privilege, and it writes nothing the factory reads back. The owner installs it beside the factory they already host, because a reconciler the factory deployed would be inside the trust domain it exists to check.

What it catches is the record that was wrong when it was written — a deploy that did not complete, an agent that recorded one that never happened, a target changed underneath. That is the common failure and it is a bug rather than malice. What it does not catch is a record rewritten afterwards; anchoring the log's chain head is what would, and seam 2 of [_Deferred, but not designed out_](../deferred.md) keeps that open for attribution rather than for this.

A mismatch holds that service's production deploys and [_pages_](#pages). The factory does nothing further, because every remedy it has reads the record in question — a rollback targets a release recorded on the release record, and using a record that has just been shown wrong repeats the fault with more traffic behind it. That hold does not lift itself, which is what makes the page necessary rather than informational: the service cannot receive its own fixes until a human ends it.

The drawback is a second process to run, and the cheaper alternatives were rejected rather than the reconciler being free. Anchoring the chain head is nearly free in the record, but it leaves the owner keeping a chain head the factory cannot reach for as long as the product runs, and custody that never ends is a duty. Installing the reconciler is done once and requires nothing after, so it stays outside the twelve the way hosting the factory does. Target-side attestation on seam 4 uses up that seam's "however it is implemented" early and creates the same custody duty anyway.

What the reconciler is not is a second opinion on whether the software is good. It compares one recorded fact to the world; the comparison, the score, and the criteria all stay where they are. One that acquired a judgment of its own would be the second path [_One pipeline_](01-one-pipeline.md) refuses, arriving indirectly.
