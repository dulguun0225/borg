# Operations

What happens after a deploy: how the factory measures the change, how long it may act on that measurement alone, and what it does when something is wrong.

## The health monitor

A [deploy record](06-releases.md#the-deploy-record) says which [release](06-releases.md#the-release-record) runs where, so the factory always knows which build it is measuring. The **health monitor** compares that release against a **control** — a set of instances running the build already in production, started alongside the release and taking comparable traffic — and that comparison is what the factory reads to decide whether a rollout is failing — automated canary analysis, in the vocabulary of the field the `control` and the `baseline` below come from. Nothing has to be authored for a service to be measured this way, once there is a build in production to compare against.

The control is started rather than found, because a new process and a long-lived one differ before either serves a request: cold caches, empty pools, a compiler that has not yet seen the workload. Measured against the instances it is replacing, a release is slower for being new, and the factory reads that difference as a regression. Measured against a control of the same age, the only difference left is the change itself — for a change confined to the process. A control isolates nothing where the change is to shared state: both arms are instances of the same service reading and writing the same store, so a migration that slows every query degrades the two identically and the comparison stays flat. What reads it is the reading the health monitor takes against the service's own recent history, which has no second arm to move with it — and [_The analysis window_](#the-analysis-window) takes passed away from a window whose control is crossing that reading, so the flat comparison does not close it on evidence while production is materially worse. **Baseline** stays the name for what the comparison is made against; what changed is that the factory now starts one instead of pointing at what is already running.

A control belongs to the deploy the rollout is part of and is not a deploy of the release it runs. It takes traffic so that it can be measured, and only that much: it is sized for the release's share and not for production, because it exists to be compared against and never to serve production on its own. What carries production if the release fails is the other thing the [strategy](03-gates.md#the-rollout-strategy) keeps running — the instances of the build being replaced, serving the rest of the traffic throughout — and the two are different instances with different jobs, the control started cold for the comparison and those long-lived. It mints no [release number](06-releases.md#the-release-number), and it is named on that production deploy record — the build it runs and the instances running it — by the **deployer** — the component that builds, creates and tears down [candidate environments](05-environments.md#an-environment-per-candidate), performs every deploy, applies [a build's schema change](06-releases.md#the-deploy-record) to its service's store before the build takes traffic, executes the rollout, and writes the deploy record — which is already writing that record at that event. There is no rollout component: the rollout is the deployer executing the [strategy](03-gates.md#the-rollout-strategy) through [seam 4](../deferred.md), starting the control, widening the release's share as it reads the comparison, and advancing its own deploy record's status target by target. What that costs is that the deployer is the largest component in [the graph](../what-the-factory-does.md#tight-integration), so one fault in it stops both deploying and undoing.

Teardown is ordered by what a [rollback](06-releases.md#rollback) needs and not by [the exit](#the-analysis-window) alone. At passed and at timed out the health monitor closes the window and calls the deployer to tear the control down. A rollback closes the window of every release it undoes — failed for the one whose analysis failed, skipped for the rest — and no control survives it: every control ends with its window, and so do the instances of every release the rollback undid. What the rollback shifts traffic onto is not a control but [_the instances of the rollback's target_](#overlapping-windows), kept running at full capacity for as long as any open window could return to that release, which is the ordering this paragraph exists to state: those instances are torn down when the last window that could return to them closes, and never at an exit of their own. [_Drift detection_](#drift-detection) is told about this, or it would page on every rollout it sees: a build running on a production [target](05-environments.md#records-and-one-long-lived-branch) beside the [current release](06-releases.md#the-deploy-record) is a mismatch only where no open window names it — as the release under watch, as the control that window's deploy record names, or as the release a rollback of it would return to — and never on a target the [deploy record](06-releases.md#the-deploy-record) marks complete: that target is meant to run the release under watch, so the old build on it is a mismatch whatever window is open. The exemption covers the targets the rollout has not reached yet and nothing else. That makes a control left running after its window closed a mismatch like any other, which is how a failed teardown is caught — at the cost of the drift detector reading two factory records to interpret one fact about the world. The exemption is bounded by the window's own cap: a window open past it excuses nothing, because the record that suppresses the check is written by the component whose failure the check exists to survive, and an exemption that outlives the thing it describes is one a stopped health monitor holds open forever.

The measurement exists in production and nowhere else, and the reason is arithmetic rather than policy: it is computed from organic traffic, and a [candidate environment](05-environments.md#an-environment-per-candidate) has none. A comparison computed from one human exercising a screen is noise that looks like evidence, and running a control beside it would double the compute spent on learning nothing. What a candidate environment decides is the [criteria](03-gates.md#spec), which need a test run rather than a population.

A rollout fails when the comparison crosses the boundary, and the rollback follows automatically. The health monitor runs after every production deploy, and the strategy decides only how the factory acts on it: a rollout with a control moves its traffic back to the instances of the release it returns to, which are still running at full capacity whatever schedule the release was taking that traffic on, and a deploy [without a control](03-gates.md#the-rollout-strategy), having no other instances running, has to redeploy the previous build and wait for it to start.

A control requires the old build to keep serving. So the real comparison is available only with the strategy that keeps one, and a deploy without a control falls back to reading the release against the recent history of the release [a rollback of it would return to](#overlapping-windows) — the newest release below it whose window closed without failing it. Not against the ordinal predecessor, which is the reading this was until 2026-08-19: where windows overlap, the predecessor of a release under watch is itself under watch, so its history is not history yet and one release becomes the other's baseline — the exact incoherence a started control was introduced to remove, arriving by the back door in the one case that has no control. Not the [last known-good release](#overlapping-windows) either, for the reason that query is not stated per service: it can be a release *above* the one being read, and a release measured against something that includes it is measured against itself. It is the rollback's target, computed for the release under watch rather than for a rollback of it, and it is single-valued and below whatever is open. What the fallback still has is the confound above, unanswered, which is what makes it the weak fallback. This is the second thing the [score](04-risk-score.md) decides when it picks a strategy: the cheapest rollout is also the one that measures least, and where the score wants a measurement, it picks a strategy that keeps a control running.

The baseline is only as good as the build it runs, which is the argument for a safeguard: an owner can add a [safeguard](09-gate-policy.md#one-shape-across-all-of-them) setting explicit thresholds for a service, the way they add one at a [gate](03-gates.md#where-a-gate-is-and-what-decides-it) or on a strategy, and a service whose normal behaviour is already bad is where that is worth doing. An explicit threshold is absolute where the comparison is relative, and it applies in addition to the comparison rather than instead of it — the release passes both or neither, so a safeguard here can only add a check, like every other. It is authored on the [service record](02-intent-into-items.md#decomposition) beside the [window limit](#overlapping-windows) and the window's parameters, and it is not one of [gate policy](09-gate-policy.md)'s eight rows: those are one closed set that one section gathers, and this is authored without being among them, the way [retention](09-gate-policy.md#what-is-not-in-it) is. What that costs is a value an owner authors that the [duty](../what-humans-do.md)'s own line does not count, so an owner reading the eight rows has not read everything they may set.

A comparison needs a control, and a control exists only while a window is open. Between rollouts there is no second arm, so the health monitor also reads each service against its own recent history — the same quantities, measured against what that service was doing before the deploy rather than against instances running beside it. It runs whether or not a window is open and nothing tears it down, so it is what the monitor is still reading [_After the analysis window_](#after-the-analysis-window), what catches a change to shared state that moves both arms together, and what makes a service that is simply broken visible when no release is under watch at all. The rule it is read under is [_The analysis window_](#the-analysis-window)'s and not a new one: a crossing inside an open window rolls the release back, and outside one it raises an [item](01-one-pipeline.md). Nothing is authored for it either — where an owner sets no explicit threshold the score supplies its size, the same division the window's own size and confidence use. What it costs is the confound a started control was introduced to remove: a release is slower for being new, and a reading against history carries that difference where the comparison does not. So its size is coarse by construction — it finds a service failing and never the size worth catching — and a regression arriving gradually is absorbed into the history it is read against and crosses nothing. Two readings of different sizes now run on one service, so what an [incident](#incidents) records is which of them crossed.

The quantities are the service's own: request rate, error rate, and latency, emitted because the factory instruments the software it writes, which is what makes a service measurable without an owner authoring anything. Availability is the error rate read over a period rather than a fourth quantity. Saturation is read by its effect and never modelled — a pool exhausted or a disk filling appears as errors or latency and nowhere else — because a picture of a service's capacity would put the factory in the business of planning spend on substrate the owner hosts. What that costs is that the factory can report a service failing and never a service about to fail: a queue growing crosses nothing until it starts costing requests. How the three are emitted is fixed, because a comparison over numbers two services emit differently is a comparison over the difference: one record per request served or job run, naming the service, the [release](06-releases.md#the-release-number) whose build emitted it, the [target](05-environments.md#records-and-one-long-lived-branch) it ran on, the outcome, and the duration — the three quantities being counts and a distribution over those records, computed where the outside row [_What the factory does not build_](../what-the-factory-does.md#what-the-factory-does-not-build) keeps them. The release is named by the build itself and never joined by time, so attributing a record to an arm of the comparison rests on no clock agreeing with any other, and what a skewed clock costs is the order of records inside one arm and never which arm they are in. Nothing is sampled: a [window](#the-analysis-window) is a volume condition, and a sampled count is a volume the window would rule things out on that never arrived. And the set of names is closed — service, release, target, outcome — so the store's size grows with releases and never with users or requests, and a record carries nothing of the request's content; what that costs is that a regression confined to one customer's requests is read as a small change in the whole. [_Ops_](11-screens.md#work-ops-factory-people) is where the numbers are read and there is no other place: a screen of numbers with no setting beside them is what that screen refuses. A dependency outside the factory — a third-party API, a store the owner runs — is read the same way and in the calling service's own numbers, and the item raised from it is one no change to the code the factory holds will fix; it exhausts the [attempt limit](03-gates.md#the-attempt-limit) and becomes an escalation (12), which is where a failure the factory cannot end already goes.

A service's first release has no build in production to compare against, and the weak fallback is no answer there either: reading a release against its predecessor's own recent history requires a predecessor, and the reading against a service's own recent history is no answer either, a service shipping for the first time having none. So an explicit threshold is the only reading left, used alone rather than alongside a comparison for the one release where there is nothing to compare — and where no safeguard sets a threshold, the first release is unmeasured and nothing about it is discovered by watching. A control exists from the second release, and the measurement is complete from there. An adopted service differs, and [_A service that already exists_](02-intent-into-items.md#a-service-that-already-exists) sets out how: software is already running, so where the [platform](03-gates.md#the-rollout-strategy) can shift a share its first release has a control — the instances that were running — and the comparison is between two builds of one commit; where it cannot, the first release has the weak fallback at least, the service having a recent history of its own.

## The analysis window

The **analysis window** is a record, one per production deploy of a release its service has not watched before, whichever attempt that is, and one per deploy [the search](#overlapping-windows) calls for, over a build nothing has watched — so a rollback opens none, the release it returns to having been watched already, and neither does a redeploy of one already watched. Watched rather than current, because a release that exits failed never completes its deploy and so never becomes [_current_](06-releases.md#the-deploy-record), and the window that failed it has to have been opened over something. The health monitor writes it, opened when that deploy record is written and closed once at exactly one of four exits, because the health monitor is what evaluates every exit and the deployer never advances that record again on the deploy's own account — a rollback does advance the records of every release it undid, and that is a later event the health monitor called for rather than the deploy finishing. It names the deploy it was opened over and through it the release — the build, where the deploy is [the search's](#overlapping-windows) and its record names no release — the service, and the control; whether passed is available to it; the size, confidence, and cap resolved at the open beside the [policy version](../what-the-factory-does.md#traceability) and [score version](04-risk-score.md#factors-at-least) in force, because a reading at an exit is not interpretable against anything but the boundary it was actually read against. What that costs is that the health monitor is the only thing that closes a window, so a monitor that stops running leaves windows open, reaches the window limit, and holds that service's production deploys. That is a wait on the factory while the monitor is running and something else while it is not, and the two are told apart the way [_Drift detection_](#drift-detection) already tells them apart for itself: a check that silently stops is worse than the bug it catches, so the health monitor writes a last check record per service and the deployer one per deploy target, the same record the drift detector keeps and overwritten the same way, read by [Ops](11-screens.md#work-ops-factory-people). Without it a stopped monitor and a service with nothing to report are the same row in [Work](11-screens.md#work-ops-factory-people), and the component that is stopped is the one whose stopping disarms the [rollback](06-releases.md#rollback) — the factory's only authority to act on production without a human — for every release after it. What the record costs is a write per pass on two components that otherwise write only at events.

The window is also how long the factory may act on the health monitor alone. Inside it, a **crossing** of the boundary — what sequential analysis calls a statistic reaching the stopping boundary set for it — rolls the release back with no human involved; outside it, the same crossing raises an [item](01-one-pipeline.md). It is the factory's own authority and is limited by evidence, where [undoing a change after it shipped](../what-humans-do.md) (10) is a human's and is limited by reversibility — a rollback while the build it would return to is still running, a revert once it is gone. That is why there is no second named window: what limits a human's undo is that build's instances, which the strategy either keeps or does not, and a window with no parameter and no limit of its own is a second name for something already named. A rollback deploy opens no window of its own: the build being restored has been watched already, and a fresh window would compare it against the release just failed and restore that one.

The window is a volume condition, not a clock — and not a volume computed in advance either. The comparison is evaluated as traffic arrives, against a boundary that is valid at every point it is read. That much is forced by what the factory already does: a threshold set for one look at a fixed sample is not the threshold for a thousand looks at a growing one, and reading a fixed-horizon test continuously is how a factory rolls back healthy releases all day. The boundary is what makes continuous reading legitimate rather than a fault nobody traces to its cause.

| Exit | What closes the window | What follows |
|---|---|---|
| **failed** | the comparison crosses the boundary against the release | rolled back, no human involved |
| **passed** | the comparison rules out a regression of the size worth catching | closed early, on evidence |
| **timed out** | neither, by the cap | closed unresolved |
| **skipped** | a rollback aimed below it undid this release | closed with the release neither failed nor running |

Passed is available only while the control is readable. A comparison rules out a regression relative to the control, so a control that is itself failing lets a bad release pass — the one reading nobody corrects afterwards, because nothing rolled back and nothing is left to mark. The health monitor already reads every service against its own recent history, and it reads the control the same way: a window whose control is crossing that reading cannot exit passed, and stays open until the control is readable again or the cap closes it timed out. That is also what closes the hole a shared-state change leaves, where both arms degrade together and the comparison stays flat. Failed stays available: a release worse than a failing control still improves production when rolled back, and the rollback's own confound is corrected afterwards by a human [marking it as not caused by the release](#overlapping-windows). What it costs is a second reading per window on instances the monitor is already measuring, and a service whose control is failing holding its next deploy to the cap — the safe direction, since what it has is a comparison that can say nothing.

What an owner authors is that size and the confidence required, with the rest of [gate policy](09-gate-policy.md) (8), safeguarded per service the way explicit thresholds are (9); where they author nothing the score supplies both. A safeguard on the size is a minimum level of protection — the score may ask to catch something smaller, never something coarser, so a safeguard can only add protection, the way one at a gate can only add a human.

The duration is measured and never set, and that is where the throughput comes from: a release that is plainly fine shows it early and its window closes. It gets there by being fine rather than by being watched against a coarser boundary, which is the change not to make — the traffic a comparison needs scales as the inverse square of what it must detect, so cutting the window tenfold makes the boundary three times coarser. Speed obtained that way runs out quickly. Speed obtained from evidence does not.

The confidence is over the set of quantities and not per quantity: what it bounds is how often a release that is fine is rolled back, because a crossing on any one of the three quantities [the health monitor reads](#the-health-monitor) starts the same rollback, the same [hold](03-gates.md#what-a-gate-may-change) on the service's deploys, and the same [incident](#incidents). Read per quantity, 95% authored means about one good release in seven rolled back over three quantities, and the figure moves every time a quantity is added without anything the owner wrote changing — a number whose meaning depends on arithmetic done somewhere else is the number nobody can argue with. So the health monitor reads each quantity at the stricter boundary that holds the authored confidence over the set, which is its arithmetic to do once rather than every owner's to do by hand. An explicit threshold a [safeguard](09-gate-policy.md#one-shape-across-all-of-them) sets stays outside that set: it is absolute, so it has no false-positive rate to budget, and folding it in would loosen the comparison to pay for a check that costs nothing. What it costs is traffic — a stricter boundary per quantity needs more of it, a fifth or so more over three — so a service near the edge of closing a window on evidence times out instead, and is watched at the coarser size the paragraphs below already resolve for a service whose traffic cannot reach what the evidence asks for. That cost lands as weak protection reported as weak, which the window already does, and not as a rate the owner did not author.

A boundary is not arguable the way a vector of factors is, and the score's own rule is that a number nobody can argue with is one nobody will trust. What an owner argues with is the size and the confidence, both authored and both open to a [safeguard](09-gate-policy.md#one-shape-across-all-of-them); the boundary is arithmetic on those. That is the same shape as the score — a published formula over inputs a human can disagree with.

A cap limits it in elapsed time, authored the same way. The condition is a traffic-volume one, but what ends a window that will never reach its volume cannot be — so a service too quiet to receive that much traffic times out every time. There the window is weak protection and is reported as weak: a service called twice a night is not made safe by watching it until lunchtime. Timing out on traffic too thin to rule anything out is weak evidence; timing out on traffic the comparison never received at all is none, and the two look alike from inside the factory because the volume the health monitor counts comes from the same emission it is measuring — a service whose instrumentation stopped reads as a service nobody called. So the window records what volume the comparison actually received, and where that is nothing the exit says nothing about the release. [The score](04-risk-score.md)'s own rule is what governs, and it was written for this: a factor that silently reads as absent reads as low risk, and the protection a failure would remove is the protection that failure is evidence for needing. Such a window stays admissible for one thing only, [a rollback's target](#overlapping-windows), which asks whether any window ever failed that release and not whether anything measured it. A service's first release ends there too and for a different reason: it has no comparison to rule anything out, so passed is not an exit available to it — an explicit threshold a safeguard set can still fail it, but nothing can clear it early. With a window limit of 1 on a service that has never shipped, that cap is also how long the second release waits. The [sample the score holds out](04-risk-score.md#how-it-learns) runs to the cap rather than stopping where the boundary would allow — [auto-passing](03-gates.md#where-a-gate-is-and-what-decides-it) a change the score wanted gated is where the factory is most openly guessing, so it takes the longest watch available, which on a quiet service is not much.

The window reads the [producer](07-contracts.md#two-versioned-things)'s own numbers and nothing else, one window excepted below. A [consumer](07-contracts.md#two-versioned-things) that breaks does so in its own error rate, on its own schedule, and what catches it is that service's own health monitor raising an item — after the producer's window closed, with nothing rolling back automatically. Reading another service's numbers would require every consumer's calls to be recorded and attributed across services, which is the recorded-usage approach [_What a diff cannot see_](07-contracts.md#what-a-diff-cannot-see) refuses; the window keeps that refusal rather than reopening it. The item is what replaces it, together with the [contract rules](07-contracts.md#enforcement) that make the schema half mechanical, the producer's own [per-field observables](07-contracts.md#what-a-diff-cannot-see), and a human undoing the change after it shipped (10) while it can still be undone.

The one window that reads more is a [brownout](07-contracts.md#deprecation)'s, and it does not reopen the refusal. A brownout's effect lands wherever the hidden read is: a disabled operation still called errs in the producer's own error rate, which the window already reads, but a field a consumer parses and now fails on errs in that consumer's numbers alone, and the producer's own never show it. So beside the producer's own numbers its window reads a reading already taken: the health monitor reads every service against its own recent history — the reading the control check above uses — with no call recorded and nothing attributed across services. Any service crossing that reading while a brownout's window is open fails it. What that costs is a false failure whose rate rises with the install's size — a service breaking for its own reasons fails a brownout that touched nothing of its — and it fails in the safe direction: an element restored that nobody read, and a removal blocked that a human must re-raise.

The parameters are learned. How fast a problem would appear is already what the score reads to pick a strategy, and the same evidence sets the size wherever an owner has not. Only a rollback or a human's undo traceable to the health monitor counts as that evidence, and not a rollback a human [marked as not caused by the release](#overlapping-windows) — a change undone for being the wrong feature says nothing about what the monitor should have caught, and feeding those back would shrink the size for owners who changed their minds and lengthen every window with it. The score learns from what the health monitor could have seen, the same way it learns from a [reject](03-gates.md#what-a-gate-may-change) and not from a hold.

That evidence sets what is worth catching, and one thing more is needed: whether anything can be caught. The size in force is the coarser of the two — what the evidence asks for, and the finest size this service's own traffic can rule anything out at inside the cap, which is arithmetic over the volume its windows have actually received. A size finer than that is a size nothing is ruled out at, so the window times out every time, protects nothing, and holds the next deploy for the whole cap; asking for it would be watching longer and catching less. The two are different questions and only the first is about harm, which is why reading the second does not reopen the restriction above. What it costs is that a service can be told, truthfully, that it is being watched for something coarser than the evidence asked for — so the size in force is reported with what the traffic reaches beside it, and a service whose traffic falls far enough is watched at the size it was installed with and no coarser, which is the weak protection [_The analysis window_](#the-analysis-window) already says such a service gets. This is also what keeps a learned size from ratcheting: every miss makes it finer and nothing makes it coarser, so without the second question a service that missed twice would need sixteen times the traffic it has and never close a window on evidence again.

## Overlapping windows

An open window blocks nothing. The next item builds, verifies on its own environment, merges, mints its number, and deploys while the window before it is still open — up to the **window limit**, which is how many windows one service may hold open at once. The window limit is authored with the rest of gate policy (8), and where an owner authors nothing the score supplies it, the same division the window's own size and confidence use. A safeguard on the window limit is a maximum on how many releases one rollback undoes — the score may ask for fewer open windows, never more — so a safeguard can only add safety here too. The drawback of authoring it appears late: the number has no visible effect until the first rollback, where it is how many releases are undone at once.

What the score supplies starts at 1 and rises only with evidence, because that evidence arrives one-sided — a service that has never rolled back has seen the throughput the window limit gives and none of the rollback size it causes. Windows closing without failing a release raise it; a rollback that undid more than its target lowers it, unless a human marked it as not caused by the release, which is set out below. A window whose comparison received no volume raises nothing, for the reason [_The analysis window_](#the-analysis-window) gives: a release nothing measured is not a release that behaved, and counting it would let a service whose instrumentation stopped ratchet its own window limit upward while measuring nothing at all. That is the same shape as the [per-author prior](04-risk-score.md#factors-at-least), a position taken where there is no evidence and moved by what arrives, and it requires nothing of the score it does not already do. The drawback is that a service which rarely rolls back rises slowly and gives up throughput it could have had, and the first rollback after a rise undoes more releases than it would have before.

That is what a started control makes possible. A found baseline made concurrency incoherent: with the comparison made against the release it replaced, a second deploy during an open window made the first release the second's baseline, so a regression the first introduced became part of what the second was measured against and was never detected. Serializing was the only way to keep the baseline single-valued. A control is started per release and never changes, so two open windows are two independent comparisons and neither is the other's baseline.

What a rollback targets has to change with it, and it is two things rather than one word doing two jobs. A service's **last known-good release** is the standing value — the release watched by the newest closed window whose exit is passed or timed out — and it is what a rollback could return to at all and where [_declarations in force_](07-contracts.md#what-a-consumer-declares) start. A **rollback's target** is computed for one rollback: the newest release *below the release being rolled back* whose window closed passed or timed out, descending past failed, past skipped, and past any window still open. The two coincide whenever windows close in the order they opened and differ exactly where they do not — stated per service alone, the query would return a release above the failed one and the factory would restore the change it had just failed, [master](05-environments.md#records-and-one-long-lived-branch) being linear. Nothing writes either: the release record is written once at the [fast-forward](05-environments.md#the-merge-queue) and never again, so an outcome settled by a window closing long afterwards cannot be a field of it, and the fact is already implied by records that exist. Timing out counts: a release no window ever failed is one the factory can return to, and requiring a passed close would leave a service too quiet to ever reach one with no rollback's target at all. A release whose deploy [stopped before its build took traffic](06-releases.md#the-deploy-record) — a schema change that failed to apply — does not count for either query, however its window closed: it never ran and its change never landed, so returning to it would redeploy a build over a store missing the change it shipped. Both queries read that from the deploy record, no target being marked complete, and descend past such a release the way the target descends past skipped. What this costs is that every rollback path computes it rather than reading a field, and a window that fails to close leaves the rollback's target older than it should be — the rollback goes further back and undoes releases no window failed, up to the window limit, which is the safe direction and still a real loss.

Closing skipped does not count, and that is what separates the two unresolved exits. A release a rollback undid was never failed either — its health monitor simply stopped, because master is linear and the release was above the rollback's target — but nothing is left running its build. Its own instances ended with the rollback, and nothing the rollback left running serves it, so there is nothing to return to. The release the rollback targeted is what runs afterwards and stays the rollback's target. A release the factory skipped over is not one it can return to.

Rollback is then a traffic shift onto the instances of the rollback's target, which are still running — long-lived, warm, and sized for all of production. They are, because a release's instances are kept at the capacity they had while any open window's rollback could return to that release, and torn down only when the last such window closes. On a [widening schedule](03-gates.md#the-rollout-strategy) the release's share grows by routing and the instances it is taking traffic from are not scaled down as it does, so a release at ninety percent of traffic still has a full fleet of the build it replaces beside it; a fixed share and a second complete copy are the same rule at other shares. Not the control: a control is sized for the release's share, and shifting all of production onto it would saturate it, so the recovery would be the outage — which is what an earlier draft said, and release engineering and platform engineering each found it separately. Where the rollout was without a control there is nothing to shift traffic onto and the rollback is the slow one — the build of the rollback's target redeployed and waited for. So there are two ways a rollback reaches the same release, and which one applies is decided by the strategy and never by the order windows closed in.

What that costs is capacity, and it is stated here because it is the window limit's price in something other than rollback size: a rollout with a control costs a second full copy of the service for the window's length whatever the schedule — the three schedules differ in how much traffic the release is exposed to and not in what is provisioned — and windows open at once each keep the fleet of the release they could return to, so a service at its window limit runs one more full fleet than it has open windows. Two cheaper shapes were considered and refused. Scaling the target's instances out at the crossing and shifting once they are ready makes recovery take as long as a scale-out and a warm-up, and makes it depend on a scale-out succeeding during the incident that caused the crossing, which is the moment one is likeliest to fail; the design's rollback is the fast path because it has no step that can fail, and that is worth a fleet. Returning traffic on the schedule the rollout used keeps the failed release serving part of production for the length of the shift and measures nothing by doing so; a rollback is immediate. What an owner may author is the fraction of its fleet the build being replaced keeps while it is the rollback's target, on the [service record](02-intent-into-items.md#decomposition) beside the window limit and the explicit threshold, and not one of [gate policy](09-gate-policy.md)'s eight rows. It is never supplied by the score: the factory [does not model a service's capacity](#the-health-monitor), so it cannot know what fraction is enough, and the one value it can set without knowing is all of it. Below that the rollback scales the target's instances back to full before it shifts, and a scale-out that fails inside the window [pages](#pages) with production still on the failed release — the owner bought the saving with that exposure, and the page names it.

A safeguard may not suspend any of this. Every other safeguard adds a human or a constraint and removes no protection; one that held the traffic shift until a human acted would remove a recovery, which is the one direction a safeguard does not go. The rollback inside the window is the factory's own authority, limited by evidence and by nothing else, and the design's answer to a human having to decide is always a gate. A customer whose rules forbid an unattended change to what production serves adds a safeguard at the [production deploy gate](03-gates.md#deploy-to-production) instead — which costs them a human in front of every release on that service rather than only the ones that go wrong, and still rolls back without them when one does.

Nor may an operator pause it, on a service or anywhere. The case for a pause is a human who can see the comparison is confounded — a zone losing its network under the release's instances while the controls sit in another, every open window on the service crossing at once — and the rollbacks those crossings start were the right thing for production: the release's instances were failing, and shifting traffic back onto the instances of the release returned to is what restored service. What was wrong was the evidence and the revert, and the mark [below](#overlapping-windows) answers both, ending the [revert item](06-releases.md#rollback) the rollback raised and lifting the hold before the revert ships. So the mark gives that human everything a pause would except the rollback itself, and the rollback is the cheap part — a traffic shift onto instances already warm. A pause is the other thing: a state a human sets and walks away from, like an [acknowledgement](#pages), that removes a recovery for as long as it lasts and does so in exactly the period a human is least available. What refusing it costs is that a human watching a confounded comparison cleans up after it rather than preventing it, one mark per rollback.

The window limit's drawback is rollback granularity. Master is linear, so the release above a bad one includes it: a rollback inside overlapping windows undoes every release above its target, up to the window limit of them. That is the one place the factory ships more than one item at a time, and it is limited rather than unlimited — [_One item per release_](06-releases.md#one-item-per-release) is still true for what ships, and for what a human undoes once the window has closed. A window limit of 1 is the serial factory, and every increment above it adds throughput on a high-frequency service, increases how many releases one rollback undoes, and keeps one more full fleet running.

A rollback still sets a [hold](03-gates.md#what-a-gate-may-change), where an open window no longer does. Master keeps the change that was rolled back and the next item was built on master, so deploying it would redeliver the defect just removed. The hold stays until the revert item ships, and it does not hold the revert — a dependency hold that blocked its own dependency would never lift. The revert also deploys ahead of every release the hold is holding, which is the one place the release number does not order deploys: those releases cannot deploy until the revert ships, so making the revert wait behind them would be the same deadlock one step further out. Without both exceptions the mechanism stops working exactly when it is needed.

The revert's deploy is the largest batch the factory ships. Merging is not held while the hold stands, so the revert merges onto a master that already carries every release merged during it, and its one deploy delivers them all under one window. Holding the queue instead was refused: it stops the service's merges the moment any rollback holds, however small the pile, where a bound an owner authors stops them where the owner said — the same stop, begun where they set it rather than at once. What bounds the batch is the **backlog cap** — how many releases may wait behind a rollback hold, the ones the rollback [skipped](#the-analysis-window) and the ones merged while it stands alike, every one the revert's deploy would deliver, before [_The merge queue_](05-environments.md#the-merge-queue) stops fast-forwarding that service's candidates. No gate fires at that stop, so it is [a wait the factory could not compute at a firing](03-gates.md#what-a-gate-may-change), written into [the log](../deferred.md) by the log with the queue as caller and [actor](../deferred.md), counting no attempt and teaching the score nothing, and it ends when the rollback hold lifts. The stop does not catch the revert's own candidate: the hold lifts only when the revert ships, so a stop that held it would never end — the deadlock the hold above already refuses, one step further in. It is a field on the [service record](02-intent-into-items.md#decomposition) beside the window limit, and where an owner authors nothing it is the window limit, so both halves of [_the exception_](06-releases.md#one-item-per-release) are bounded by one number until an owner separates them; a safeguard (9) may lower it and never raise it. Under a human operator the cap is a nicety; under the factory it is the only thing between a slow revert and a batch of a hundred, because nothing else notices the pile growing. What it costs is that a revert taking a day stops the service's merges for most of it.

Where the batch's window fails, the rollback returns to the rollback's target as any rollback does, and the failure is attributed to nothing: the batch is one comparison over several changes, and marking every author in it would teach the [per-author prior](04-risk-score.md#factors-at-least) from a label the evidence does not support. What recovers attribution is a **search**, the health monitor's own authority bounded by evidence the way the rollback is. The search calls the deployer to make and deploy one build at a time, each deployed with a [control](#the-health-monitor) and measured by a window of its own, and each deploy ending with its window whatever the exit: the exit is the answer, and traffic returns to the instances of the rollback's target, which the search never tears down. A search's build is nothing on master: the revert's change applied onto the commit of one release the batch delivered, because every release in the batch carries the failed change and a build of one of them alone would measure the defect just removed. The first applies the revert onto the rollback's target and answers whether the revert itself is at fault; the rest bisect the batch by release number. A search deploy's record names the build and no release, so the service's [current release](06-releases.md#the-deploy-record) stays the rollback's target throughout, and the drift detector reads the target against the build the record names. What a consumer admitted against that release then meets is a share of traffic on a later [contract](07-contracts.md) form, which is what any rollout already shows it, and safe for the same reason: every form a search's build serves passed [the contract diff](07-contracts.md#enforcement) at its own merge, and every contract promises backward compatibility. The search is not a wait on a human, and production running a build older than the newest release during it meets no [page](#pages) condition — said here because it otherwise reads as meeting one. The builds are made from commits master keeps, so the search depends on no build being retained, which the slow rollback does and [_Open_](../open.md) holds.

Three limits, each there because the operator is a machine. The search runs only where each of its windows can close: where the service's traffic cannot rule out a regression of the size in force inside the window's cap, no search runs, since a bisection over a signal that cannot conclude terminates anyway and names an innocent release. A null result is a result: a build that cannot be made because the revert does not apply onto that commit narrows the search no further, and a search that names no release marks nobody — a missing label slows the score's learning where a wrong one corrupts it, and a wrongly marked prior is carried by a [model version](10-fleet.md#what-an-agent-runs-on) that cannot argue back. And a **search budget**, on the service record beside the cap: a maximum count of builds and a maximum total time production spends on them, each one putting a build that passed no gate in front of real traffic. Where an owner authors nothing the budget is what bisecting a batch of the cap's size needs, each build watched for one window, and a safeguard (9) may lower it. What the search costs is the one exception to [what was tested is what ships](06-releases.md#the-release-number): its build is a commit on no branch and a build no gate decided, kept out of master by construction and in production for one window. Recovery from a bad batch takes several windows rather than one, so attribution is delayed where the search can run and lost where it cannot. The revert the batch's failed exit calls for is authored against the release the search names and never against the batch's own release, because that release is itself a revert and reverting it would redeliver the defect the first rollback removed; where the search runs and names nobody, or cannot run, the [intent](02-intent-into-items.md#intake) the health monitor raised carries the null result as its evidence and [the interview](02-intent-into-items.md#the-interview) asks a human (3) which change to remove.

A human can approve through it. The hold is the factory's own and the [emergency action](01-one-pipeline.md) is approve now, not skip; the production deploy gate offers Approve regardless. What approving redelivers is the defect that was just removed — the most damaging thing in the factory to approve through, and the one most likely to be tried during an incident.

A crossing is not proof that the release caused it. The comparison is confounded by whatever differs between the two arms besides the change — a zone losing its network under the release's instances while the control sits in another, a control that was itself unhealthy — and a boundary read against several quantities at once crosses more often than the confidence authored for one of them says. So a named human at [Ops](11-screens.md#work-ops-factory-people) may mark a rollback as not caused by the release, with the reason they state, the way a rollback on their own judgment names its [source](06-releases.md#rollback). The mark is a record of its own, written once, pointing at the rollback's deploy record; it is read by everything that learns from outcomes and by nothing that acts. What it changes is the evidence and only the evidence: the rollback is excluded from the [per-author prior](04-risk-score.md#factors-at-least) of every release it undid, from the [window's size](#the-analysis-window), and from the [window limit](#overlapping-windows), the way a window whose comparison received no volume is — it is a rollback that measured something other than the release, which is evidence about nothing. It teaches the confidence nothing either, and that is deliberate: a confounded comparison says what crossed the boundary was not the change, and nothing about how confident the comparison should have been. The rollback stands, the [incident](#incidents) stands — production was worse, whatever made it so — and nothing the factory did on its own is undone by the mark. What happens to the revert depends on when the mark is made. Before the revert ships, the mark ends the revert item — [dropped](02-intent-into-items.md#what-an-item-names), written by [dispatch](02-intent-into-items.md#dispatch) with Ops as the caller — and lifts the hold the rollback set, there being no defect on master for the hold to keep off production: the next release from master carries the change, opens a window of its own, and is measured again, and until one comes the service stays on the release the rollback returned to, because a redeploy of a release already watched [opens no window](#the-analysis-window). After the revert has shipped the change is gone from master and the mark corrects the evidence only; restoring it is a new intent the owner raises. What the mark costs is a judgment in a mechanism the design otherwise keeps to arithmetic, and the judgment can be wrong in the direction nothing checks — a human excusing a release that was at fault launders it out of the prior, and the [agent](10-fleet.md) that wrote it — a model in a role — is scored as if it had been fine. That is why the mark is read by nothing that decides anything, so that a model cannot learn to be excused, and why it records the reason and the human beside the rollback it corrects, which is where a later reader argues with it. What it does not do is intervene: it comes after the rollback and suspends nothing, for the reason [_Overlapping windows_](#overlapping-windows) gives against a pause.

## After the analysis window

The health monitor keeps running after the window closes, on the reading against the service's own recent history — the control was torn down with the window, so no comparison is left to run. What it finds then is not a rollback candidate — the change has been live for a week and the window's authority ended long before. It is an unrefined intent in [_Work_](11-screens.md#work-ops-factory-people), the same shape as the intent an end user's [_reports_](02-intent-into-items.md#reports) are grouped into (4, 5), taking the same stages and the same gates. That is the whole of "finds issues and fixes bugs": a [detector](02-intent-into-items.md#intake) writes an intent, and [the pipeline](01-one-pipeline.md) does the rest.

## Service level objectives

The reading against a service's own recent history says whether that service is failing now. It says nothing about how often it has failed, and a service that fails a fraction of its requests every day crosses nothing: those failures are in the history it is read against.

A **service level objective** is a target an owner authors on the [service record](02-intent-into-items.md#decomposition) — the proportion of a quantity that must be good over a stated period, 99.9% of requests served without error over thirty days being the ordinary shape. The factory computes what is left of it from the emission the health monitor already reads, and that remainder is the **error budget**. It does one thing: while the budget is exhausted, that service's production deploys are held, and the hold lifts itself when the period rolls forward far enough to restore it. Nothing is decided and no [_page_](#pages) fires, which is the shape the hold a [declared dependency that is not current](03-gates.md#deploy-to-production) sets already has.

It is authored and never supplied, which is the opposite of the division the window's size and the [window limit](#overlapping-windows) use, and the reason is that the score learns from the factory's own outcomes: a target inferred that way is set to whatever the service already achieves and never binds. What an objective states is what the customer promised the people using the software, and the factory observes nothing that says what that is. Where an owner authors none there is no budget and nothing is held — that reading and the window are the whole of what protects that service. It is authored on the service record beside the explicit threshold and is not one of [gate policy](09-gate-policy.md)'s eight rows, at the same cost that threshold carries.

What the hold costs is that the fix for whatever exhausted the budget is itself a production deploy. So two items pass the hold: a revert, which passes the hold [a rollback leaves](#overlapping-windows) for the same reason, and an item whose intent the health monitor raised on that service. Without them the budget would hold hardest exactly where production is worst. What the exception costs is that a fix making things worse takes the same path, so a service can spend what is left of its budget on its own repairs, bounded by the [attempt limit](03-gates.md#the-attempt-limit) and by nothing else.

## Incidents

An incident is a record on a production environment, written by the health monitor at the crossing — of its own boundary, or of a threshold an owner's safeguard set — against the release running there, whether or not that release's window is still open. The health monitor is the only component that reads production behaviour and knows which release and which deploy that behaviour belongs to, which is exactly what an incident points at; a human-written one would put a judgment where the design keeps arithmetic, and a human's judgment about live software already reaches production through the undo of a shipped change (10) and the page they may fire. A human's judgment about the incident's cause has a place too and it is not the incident: a rollback [marked as not caused by the release](#overlapping-windows) is a record beside it, and the incident stands, because production was worse whatever made it so. It points at the deploy, the deploy at the release and at [the schema change it applied](06-releases.md#the-deploy-record) where it applied one, the release at its item and its intent — so what caused an incident is answered by following those links, a change to the store included, the same links the release record answers from the other end. Its status advances to resolved when the crossing has stopped against what is running *and* what was raised from it has finished: a rollback stops the crossing and does not resolve the incident, production being still worse, which is what the hold and the page both say.

It is also what the health monitor keys its own deduplication on, before it calls [intake](02-intent-into-items.md#intake): an open incident on this service and this release makes a further crossing an observation on it and never a second intent. What that costs is that an incident points at the deploy that was running when it appeared and not always at the one that caused it — a consumer broken by its producer gets an incident on its own innocent deploy, and the item raised from it is what finds the producer.

The factory works the item it raised under the [attempt limit](03-gates.md#the-attempt-limit) like any other. Exceeding that limit turns it into an escalation (12), the same Work row a stuck feature produces: a bug the factory cannot fix is not a different kind of stuck.

## Pages

One **notifier** delivers everything waiting on a human out of the product, on three channels: mail, chat, and the page. It routes all three the same way — on the [_People_](11-screens.md#work-ops-factory-people) declaration, by the [duty](../what-humans-do.md) the row belongs to, or by the named human where the row belongs to none — so the routing is implemented once rather than beside each thing that waits. Its callers are the components that create a wait: the [gate component](01-one-pipeline.md) when it opens a decision a human must close, intake when it writes a round of [_interview_](02-intent-into-items.md#the-interview) questions or an intent escalated, [dispatch](02-intent-into-items.md#dispatch) when it writes an item escalated, and an owner firing one from [Ops](11-screens.md#work-ops-factory-people). The drift detector calls nothing, so the notifier reads its store itself. A **page** is the narrow channel: what qualifies for one is a wait where the deployed software is worse until a human ends it, and nothing else fires one. It is the only channel that widens and the only one that writes a record — mail and chat write nothing, a delivery that changes no state being no evidence, and a record per delivery would size [the log](../deferred.md) by how often the factory notifies. What one component costs is that a fault in it stops all three channels at once and the factory falls back to whoever remembers to open Work, which is the poll [push-not-poll](11-screens.md#three-properties-every-screen-needs) was written to remove. So the notifier writes a last check record too, beside the health monitor's and the deployer's, and nothing pages when the notifier is what stopped: the channel that would carry that page is the thing that stopped. What makes it visible instead is [Ops](11-screens.md#work-ops-factory-people) reading those records beside the drift detector's own — a poll, and the one place push-not-poll cannot reach, because a component cannot announce its own silence.

A page is not a record; it is the name for the sequence of page events on one row. A **page event** is one append to the log naming the row, the human reached, and which of four it is — reached, acknowledged, widened, answered — each with an [actor](../deferred.md). The first delivery reaches every human holding the duty at once; unacknowledged it widens exactly once, to the owner; there is no narrower first recipient and no second widening. Acknowledged is written when a human says they have the row, which is an act in the product and nothing else — it ends no wait, decides nothing, and stops only the widening. Answered is written when the row stops waiting, and the component that ends the wait calls the notifier at the same write it ends it with. Widening on unanswered instead would make a human already working the problem indistinguishable from one asleep, because every page whose remedy takes longer than the delay would widen — so the channel that exists to be rare would be loudest exactly where somebody is already on it. What acknowledgement costs is a state a human can set and then walk away from, which is why it stops the widening and never the page: the row still waits, still shows in [Work](11-screens.md#work-ops-factory-people), and still reads as production being worse until somebody ends it. A caller that fails to make the closing call leaves a page unanswered against a row already resolved, which Ops shows as a wait with nothing waiting on it.

One wait ends where nothing calls, and it is the one the notifier already reads for itself: a mismatch is cleared by a human inside [the drift detector](#drift-detection), which writes into a store no factory component may write and calls nothing. So that page's answered event is written by the notifier the next time it reads that store and finds the mismatch cleared, and its time is the time of that read rather than of the clearing. Every other caller makes the closing call.

That condition is already the document's, and two refusals above follow from it rather than being added to it. A [declared dependency](02-intent-into-items.md#decomposition) that is not its service's current release holds the production deploy, nothing is decided, and the hold lifts itself when the dependency is current again — there is no wait for a human to end. An owner's silence at [_The interview_](02-intent-into-items.md#the-interview) consumes no compute, which is why no limit applies to that wait; a page would be the same mistake made more loudly.

Six things meet that condition today, four of them here, one in [_Rollback_](06-releases.md#rollback), where a failed exit finds no release to return to and the failed release goes on serving, and the sixth in [_An account that runs out is a hold_](10-fleet.md#an-account-that-runs-out-is-a-hold), where a target credential cannot be reached while the health monitor is calling for a rollback; the condition is what governs — the list follows from it and is not the test. An escalation (12) on an item the factory raised from an incident — the factory saying it cannot fix a defect that is live. A human deciding at a gate on a revert while the rollback that removed the defect still holds: the service is running the build that was restored, master still contains the defect, and nothing ships past that human. And a mismatch [_Drift detection_](#drift-detection) found, which holds that service's production deploys until a human clears it. The fourth is a window past its cap that nothing has evaluated, which is what a stopped health monitor looks like from outside: the release under watch is unmeasured, the rollback that would undo it is not going to happen, the service's production deploys are held at the window limit, and no mechanism the factory has ends any of it — the component that would is the one that stopped. Its own last check record is what makes the state readable rather than inferred. In all four, production is worse than it should be and no mechanism the factory has will improve it.

The first is not special for having come from an incident. An item [_After the analysis window_](#after-the-analysis-window) raises is not one, and takes the same shape as an intent grouped from end-user [_reports_](02-intent-into-items.md#reports) (4, 5); a defect an end user reported is that shape exactly. An item from any of those three, stopped at the attempt limit, is the factory giving up on a defect while the software containing it is live, so it meets the condition without being on the list. What separates these is never which of intake's three sources the intent came from: the refusal that an escalation on a feature item has nothing live that is worse already separates on whether something live is worse, and that is the whole of the test.

One wait meets a condition of its own and is admitted beside these rather than under them: a deadline a [constraint](02-intent-into-items.md#constraints-and-the-design-system) put on an intent, where a law started a clock. The software is no worse for the hour, and the customer is — a breach notified late is a breach notified late whatever production is doing — so it pages whoever holds (2) for that constraint when the deadline is written, at any hour, and is answered when the intent ends or the human marks the obligation met. It is the one page the condition above does not cover, admitted because the condition was written for what the factory can make worse and a statutory period is worse on its own; what it costs is a page class whose remedy the factory cannot perform, so the page delays nothing the factory would otherwise have done, and every one of them reaches a human at whatever hour the trigger happened to arrive.

A rollback the factory performed on its own is reported, not requested, and reporting is not paging — **the factory does not page to inform.** Nothing else waiting on a human meets the condition either: a [UAT](../what-humans-do.md) assignment (7) delays its own item and holds its own item's environment, an escalation on a feature item has nothing live that is worse, a deploy queued behind its service's window limit is waiting on the factory, and a [_fleet entry with no credential to reach_](10-fleet.md#an-account-that-runs-out-is-a-hold) stops work rather than making anything live worse — the row most often mistaken for a page and still not one. Those wait in Work, and mail or chat delivers them.

A page has no duty of its own — inventing a thirteenth would be a mechanism where routing already exists. It reaches whoever holds the duty the row belongs to, the same routing that showed them the row in Work.

Not every row belongs to a duty. A mismatch [_Drift detection_](#drift-detection) found holds the production deploy gate, which none of [the twelve](../what-humans-do.md) owns: confirming criteria (6) and performing UAT (7) are the duties at a gate, and [_What the candidate environment decides_](05-environments.md#what-the-candidate-environment-decides) puts the UAT one at the [Merge to master](03-gates.md#merge-to-master) gate. Installing the drift detector is [substrate](../what-humans-do.md) outside the twelve, so the page reaches whoever [_People_](11-screens.md#work-ops-factory-people) records as having installed it, and widens to the owner where nobody is recorded. That is what [_What the fleet is not_](10-fleet.md#what-the-fleet-is-not) already does for a lent credential — routing needs a named human rather than a duty number — and it is why a thirteenth duty stays refused: a duty would score an obligation the twelve deliberately leave unscored, where a named human only has to be reachable.

A duty may be held by more than one human, and a page reaches all of them at once. There is no rotation naming which one it reaches first: a rotation would be a People declaration enforced by nothing, and what a stale one does — widen to every holder — is what happens here without it. The parameter's failure mode is the behaviour that replaces it, so the parameter is what can be dropped. Unacknowledged, a page widens once more, to the owner. The drawback is that a page nobody needed reaches everybody, accepted so that none is ever lost, and acknowledgement narrows it only where somebody is awake to send one.

An unanswered page never makes the factory act alone, because the state it is paging about is stable. Where a rollback has run, the service runs the last release whose window closed without failing it and not the one just failed, so the wait delays the fix and never the recovery; where none has, what is live is what was live when the page fired, and the wait delays the fix there too.

That split is also what decides whether a page waits for morning. Where production serves a release the health monitor has called for a rollback on and the rollback has not run — a failed exit with nothing to return to, a target credential that cannot be reached, a window past its cap with the health monitor stopped — the software is worse now and worse for every hour of the wait, and the page fires whenever the condition arises, on every service. Where the rollback has run, or nothing was live to remove — the revert at a gate, an escalation on an item raised from an incident, a mismatch the drift detector found — the software is worse until a human ends the wait and no worse for the hour at which they do. The factory tells the two apart from what it already holds, the release the production deploy record names and whether a rollback the health monitor called for on it has run, and nothing authors the urgency and nothing scores it; the score computes impact for every decision it makes, but which of the two a wait is turns on state and not on likelihood. For the second kind an owner authors on the [service record](02-intent-into-items.md#decomposition), beside the explicit threshold and the objective, the hours within which that service pages. A wait of the second kind arising outside them goes out by mail and chat at once, waits in [Work](11-screens.md#work-ops-factory-people) as every row does, and pages at the next hour the service allows; where an owner authors none, it pages at any hour, which is what every service did before there was anything to author. The hours are authored and never supplied, for the reason the [objective](#service-level-objectives) is: nothing the factory observes says which service the customer minds losing overnight, and a value inferred from outcomes would be set to whatever the service already gets. What it costs is another authored value that goes stale the way a People declaration does, and a page that waited until morning on a service whose hours were authored too narrow — the owner who authored them chose that over a page reaching every holder at 02:40 for work that could not have needed doing before morning, which is the thing that makes the next page slower to answer.

A human may fire one on their own judgment, from [_Ops_](11-screens.md#work-ops-factory-people), which is the parallel a human's undo (10) already has: the rollback the factory would perform, on a human's judgment instead of the health monitor's. Nothing scores it and no limit applies to it. What limits it is that a page nobody needed makes its recipient slower to answer the next one.

A page is an event on the row it belongs to — who was reached, when it widened, who answered — each recording an actor, which is seam 1 of [_Deferred, but not designed out_](../deferred.md) and nothing new. The hours are the one authored thing in it, and they are on the service record; who holds a duty is a People declaration and the widening is the factory's own, so gate policy stays at the rows it has.

## Drift detection

Every check above reads a record the factory wrote. A service's [_current release_](06-releases.md#the-deploy-record) is what its production deploy record marks complete on every target, the health monitor measures against a control the factory started and recorded, and an incident points at a deploy the same log describes. So a factory whose records are wrong reports itself healthy, and nothing downstream of them contradicts it.

The **drift detector** is one process outside the pipeline that reads what is actually running on each production target and compares it against what that service's production [deploy record](06-releases.md#the-deploy-record) marks for that target — the release it names where the target is marked complete, the previous one where it is not. The second comparison is [the log](../deferred.md)'s — the chain each of its records makes by naming its predecessor: each pass it reads the chain's head, verifies the chain still holds the head it recorded last pass — extended and nothing else — and records the new one. A chain its recorded head is no longer inside is a mismatch whose hold matches the record it impeaches: a deploy record reaches one service, so its mismatch holds that service's production deploys; the log reaches every decision, so this one holds every service's, cleared like any other by a human at the detector. A [truncation](09-gate-policy.md#what-is-not-in-it) removes the oldest records and never the head, so the check reads through one undisturbed — unless retention is shorter than the gap since the detector's last pass and the cut removed the recorded head, which is that same mismatch with the truncation row as the evidence the clearing human weighs, a real cut and a fabricated row reading the same. Two facts, two comparisons, read-only — no deploy privilege, and it writes into a store of its own that no factory component may write, the recorded head being the detector's own with nothing else reading it. It is not true that the factory reads nothing back: a mismatch holds a gate and pages, and both require reading it. What the independence actually requires is narrower and is the rule — nothing the drift detector writes is evidence about the software. It cannot cause anything to be built, deployed, scored, approved, or measured, and the one thing it can do is stop. The seam is two records and three readers: the **mismatch**, read by the gate component at the moment the production deploy gate fires and by the notifier; and the **last check** per production target, overwritten each pass, read by Ops so a stopped drift detector is visible rather than silent, and by the gate only where an owner's safeguard sets a maximum age on it. In the other direction it reads one factory record per comparison: each service's production deploy record with its completion per target, and the log's head row. Failing to reach a target is not a mismatch — a network blip would otherwise hold every production deploy — which is why the last check exists at all: a check that silently stops is worse than the bug it catches. The owner installs it beside the factory they already host, because a checker the factory deployed would be inside the trust domain it exists to check.

A mismatch remains until a human clears it at the drift detector, even where a later comparison agrees, which the drift detector records on it so the human clearing has the evidence. Clearing it from Ops is refused: it would make the factory a writer of the record that says the factory is wrong, and a deploy that did not complete is precisely the kind of bug that would clear it on retry. What that costs is two actions in two places at the moment production is worst — approve through at the gate, then clear at the drift detector — and one record with no [chain](../deferred.md) behind it, so the trail of what stopped a deploy is complete only when a second store is read beside the log.

Its store's life follows from its independence the way its installation does: a store no factory component may write is not the factory's to keep either, so keeping it — and with it the half of that trail only it holds — is part of installing the detector, the owner's as hosting the factory already is. And the one event that makes the detector loud on every service at once is the factory's own records restored from a backup, which is the mechanism working rather than failing: every deploy record falls behind what runs, every service that shipped since the backup mismatches, production deploys hold, and each mismatch is cleared by a human holding the evidence of what the restore lost — the same stop [_The merge queue_](05-environments.md#the-merge-queue) reaches from the other side when it refuses to mint over a history it cannot derive.

What the first comparison catches is the record that was wrong when it was written — a deploy that did not complete, the deployer recording one the target never received, a target changed underneath. That is the common failure and it is a bug rather than malice. A record rewritten afterwards is the other failure, and the head the detector records is what catches that one — the anchoring seam 2 of [_Deferred, but not designed out_](../deferred.md) places here, with what it is and is not evidence against stated there.

A mismatch holds that service's production deploys and [_pages_](#pages). The factory does nothing further, because every remedy it has reads the record in question — a rollback targets a release computed from the windows the factory itself closed, and using records that have just been shown wrong repeats the fault with more traffic behind it. That hold does not lift itself, which is what makes the page necessary rather than informational: the service cannot receive its own fixes until a human ends it.

The drawback is a second process to run, and the cheaper alternatives were rejected rather than the drift detector being free. Anchoring the chain head alone is nearly free in the record, but a head the owner keeps by hand is custody that never ends, a duty — which is why the head lives in the detector's store instead, kept by the process rather than the person. Installing the drift detector is done once and requires nothing after, so it stays outside the twelve the way hosting the factory does. Target-side attestation on seam 4 uses up that seam's "however it is implemented" early and creates the same custody duty anyway.

What the drift detector is not is a second opinion on whether the software is good. It compares what the factory recorded against what stands — a target's build, the chain's head — and judges neither; the health monitor, the score, and the criteria all stay where they are. One that acquired a judgment of its own would be the second path [_One pipeline_](01-one-pipeline.md) refuses, arriving indirectly.
