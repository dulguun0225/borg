# One item per release

**One item per release. Always, at every stage, permanently.** The single timeline of an [item](../01-one-pipeline.md) never splits: [rollout](../08-operations/01-the-health-monitor.md) stays item-scoped like everything before it, and a human's [undo of a shipped change](../../what-humans-do.md) (10) is the rollback of exactly one item rather than extracting one change from a set of ten. One exception, limited and named, and it runs in both directions: master is linear, so where analysis windows overlap a rollback undoes every release above its target, up to the [window limit](../08-operations/03-overlapping-windows.md) — and the revert release that follows redelivers the ones that were only [skipped](../08-operations/02-the-analysis-window.md), which were never failed and whose code is still on master. One deploy then delivers several items' changes, measured by one window against the restored build. What ships is still one item, and each half is bounded: the rollback by the window limit, and the revert's deploy by the [backlog cap](../08-operations/03-overlapping-windows.md), which counts every release that deploy would deliver — the skipped ones and the ones merged while the revert is authored alike, merging not being held — and is the window limit until an owner separates them.

The cost is [an environment per item in progress](../05-environments/02-an-environment-per-candidate.md), stated there. An environment added later follows the rule rather than changing it.
