# The deploy record

A service's **current release** is the one its production deploy record marks complete on every production [target](../05-environments/01-records-and-one-long-lived-branch.md) — what is running, not what is newest. Merged-and-never-deployed being normal is exactly what makes those different facts, and every cross-service check reads the current one: an environment composed from its dependencies is composed from what runs, and a promise is kept by what serves it.

A deploy record is written by the [deployer](../08-operations/01-the-health-monitor.md), the one component that reaches a deploy target, through seam 4 of [_Deferred, but not designed out_](../../deferred.md), when the deploy starts, and its status advances to complete or rolled back per target: the record names the release it puts on the environment once, and beside each of the environment's targets whether that target has it yet. A revert's deploy also lists the releases it delivers — the ones the [hold](../08-operations/03-overlapping-windows.md) was holding, whose code is in its build — a list beside the one release the record names, the shape [_Rollback_](06-rollback.md)'s record already keeps for the releases it undid, so a release delivered by a later release's deploy is on a deploy record and not only on master; without that, [Ops](../11-screens.md#work-ops-factory-people) reads those releases as merged and never deployed while their code is live. A deploy [the search](../08-operations/03-overlapping-windows.md) calls for names the build and no release, there being none. What it names as the thing deployed is the build it put there, and the release where it is deploying one: [_Deploy to candidate environment_](../03-gates/07-what-particular-gates-decide/06-deploy-to-candidate-environment.md) fires one gate before the release number exists, so a record naming a release there would name one nothing had minted. Naming the build on every deploy is also what makes what is running comparable to what the record says: a target reports the build it is running and not the name that build has on master, which is a fact of this store and not of the target. Every reader of what is running reads the records that name a release, a [candidate environment](../05-environments/02-an-environment-per-candidate.md) being a place where nothing is current. One rollout produces one, and [_Rollback_](06-rollback.md) is a deploy event and produces its own. No agent performs a deploy: deploying is not a stage an agent is dispatched to, so the record's [actor](../../deferred.md) is the deployer and never an agent — a program the factory runs and can check, where which model an agent is is only what its [fleet entry](../10-fleet.md) says. What that costs is that an agent's [scope](../01-one-pipeline.md) says nothing about a deploy target, so where a deploy may go is authored on the [environment record](../05-environments/01-records-and-one-long-lived-branch.md) and never on an entry. What the record does not say is what share of traffic each build takes — that is the rollout's and its [_control_](../08-operations/01-the-health-monitor.md)'s, and a deploy log recording every shift would scale with the schedule for a fact only the rollout reads while it runs.

A deploy that ships a schema change names it. The [store rule](../07-contracts/09-the-store-is-a-contract-too.md) makes a breaking change three items, so what one deploy carries is one item's change, applied by the deployer to the service's store before the build takes any traffic, through the credential the [environment's record](../05-environments/01-records-and-one-long-lived-branch.md) holds — the deployer is the only component that reaches a deploy target, and the store is reached the same way. The revert's deploy is the one deploy that can carry more: delivering releases that never deployed on their own, it applies each delivered release's schema change that no deploy applied, in release order, before its build takes traffic — without that, a migration's additive item delivered in the batch would leave its column on master and nowhere else, and the code shipped after it would write to a store that never gained it. The record says whether the change completed, so a schema change is on the trail an [incident](../08-operations/06-incidents.md)'s links walk and never an unrecorded act. A change that fails to apply stops the deploy before any traffic shifts: no target is marked complete, the previous release stays current, and the failure stands on the record for [Ops](../11-screens.md#work-ops-factory-people). That a change can stop halfway is survivable for the reason the store rule holds in both directions: of the three items, the added form is read by nothing until the code that migrates onto it ships, and the drop ran only once no [declaration in force](../07-contracts/06-what-a-consumer-declares.md) named the old form — so a store between two forms is one every release a rollback can restore still reads and writes.

It is keyed by service and environment and not by [target](../05-environments/01-records-and-one-long-lived-branch.md): one record names one release for the whole environment, and completion is a field per target on that record rather than a record per target. A record per target stays refused, because four records could each name a different release and each be right; one record with one release and completion per target cannot. What one record with completion per target expresses is the state the earlier shape could not: a deploy that reached three targets of four is a recorded partial deploy, the fourth target marked not yet complete, rather than an incomplete one caught as a mismatch after the fact. [_Drift detection_](../08-operations/08-drift-detection.md) reads each production target against what the record marks for that target, so a target marked complete and serving the old build is a mismatch whether or not a window is open. Every cross-service reader reads completion per target and needs a rule for what current means while they differ, and the rule is the strictest: a release is current only once every production target is marked complete, and until then the previous release is. A consumer whose [declared dependency](../02-intent-into-items/03-decomposition/README.md) is on three targets of four is held at [_Deploy to production_](../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) until the fourth lands, which is what stops one call in four reaching a producer without the [contract](../07-contracts/README.md) form the consumer verified against. The cost is the wait on the slowest target, and that every reader of current release evaluates a rule over targets instead of reading one field.

Current is the highest-numbered release whose deploy completed and was not rolled back, and not the most recently started; the two disagree exactly while a rollout runs. Composing a dependent's [_candidate environment_](../05-environments/02-an-environment-per-candidate.md) from the release still taking part of the traffic would verify it against a build that may roll back within the hour, and the dependency hold at [_Deploy to production_](../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) would admit a producer nothing is yet committed to. The number rather than the completion time is what orders them, because rollouts overlap and differ in length: the [strategies](../03-gates/02-the-rollout-strategy.md) run from minutes to hours and the [score](../04-risk-score/README.md) picks per release, so a short rollout completing while a longer one below it is still widening would make an older release current under a recency reading, and nothing later would move it — leaving every reader of that record wrong at once while production served something else.

A control started above a release runs the release [a rollback of it would return to](../08-operations/03-overlapping-windows.md) — the newest release below it whose window closed without [failing](../08-operations/02-the-analysis-window.md) it, past every release a rollback would descend past, and not the ordinal predecessor. The two coincide until something is failed and differ exactly after a rollback: master is linear, so the ordinal predecessor's build contains the change just failed, and a control on it would restart failed code onto organic traffic for the whole of the next window and measure the revert against the build it exists to remove. Defining both by one rule is what [_Overlapping windows_](../08-operations/03-overlapping-windows.md) needs so that the build the comparison is made against and the build a rollback returns to are the same one, and neither is something the factory has already ruled out. What that costs is a dependent whose producer is mid-rollout waiting for it, which on a [widening schedule](../03-gates/02-the-rollout-strategy.md) is the length of the rollout.
