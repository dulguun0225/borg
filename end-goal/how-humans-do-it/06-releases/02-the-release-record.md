# The release record

A release is a record, and it is where [the graph](../../what-the-factory-does.md#tight-integration) joins. It names what is known at the merge: the item that caused it, and the build and commit it is made of. The [contract versions](../07-contracts.md#two-versioned-things) it publishes are not a field of it — they name the release instead, each carrying that release's own number, because ordering versions is ordering releases and answering "the version in force at release N" by reading release records would make every reader of a contract a reader of releases. A version that names the release cannot also be a column here without the same fact standing in two places, written at one event by one writer. So "the release names the contract versions it publishes" is an inbound edge, which is what every deploy of a release already is, and the cost is the one this record's single writer already carries: a reader asking what a release publishes indexes that edge rather than reading a field. The [gate decisions](../03-gates/01-where-a-gate-is-and-what-decides-it.md) name the item and the build and never the release, whether they were written before it existed or, at the [production deploy gate](../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md), after; every deploy of it to every [environment](../05-environments/01-records-and-one-long-lived-branch.md) is written afterwards and names the release. Ask anything about a shipped change — from what [intent](../02-intent-into-items/01-intake/README.md), on whose approval, under which [policy](../09-gate-policy.md), running where, rolled back when — and the answer is reached by traversing edges at the release record, outbound or inbound. Traceability is not added to this; it is what the record is for.

[_The merge queue_](../05-environments/03-the-merge-queue.md) writes it and mints the release number with it. Master's only inbound path is the queue, so the fast-forward is the event and the queue is what performs it, and the serialization that stops two merges taking one number is the per-service ordering the queue keeps already. A writer of its own, called at the fast-forward, would be a component with one caller and that ordering implemented again inside it. What this costs is release identity inside the queue's component, and no release record for a commit that reached master by another path — which nothing does, the queue's exclusivity being what makes that true.

It is written once and never written again, which is what keeps that one writer. The alternative was five — a [gate component](../01-one-pipeline.md), the [deployer](../08-operations.md#the-health-monitor), and the rest writing their links into it — which is five writers on the record the whole graph joins on and a [seam](../../deferred.md) to declare between each pair, and writes to a release after it shipped. The cost of one is that where a release runs and which gates let it through are queries over the records that name it, so every reader asking either needs those inbound edges indexed.
