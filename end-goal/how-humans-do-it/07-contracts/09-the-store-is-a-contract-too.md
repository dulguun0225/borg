# The store is a contract too

A service's store is a contract too, and its consumer is the service's own past — the release that was running a minute ago, which a rollback can restore. That consumer is why a store promises **forward** as well: every rollback reads across the change in the direction backward alone does not cover, and it is the only kind of contract with a consumer of that kind. It is also a consumer that writes: a rollback makes the restored build the store's writer again, so its consumer contract is derived from writes as well as reads — the elements the code writes, and whether each is written populated and inside its domain, from the build like everything else — where an interface's consumer declares reads alone. The [declarations in force](06-what-a-consumer-declares.md) are the same range query, from the last known-good release up to the newest, which is exactly the set of releases a rollback can put back in front of the store.

The rule is the same there: **no single item may break the store.** A breaking schema change is three items — the store gains the new form beside the old, the code migrates onto it, the old form is dropped — and while it remains, the old form has the same deprecation obligation an old interface has. The schema change itself is a step of the deploy that ships it, applied by the [deployer](../08-operations.md#the-health-monitor) and named on the [deploy record](../06-releases/05-the-deploy-record.md), and a rollback undoes none: the schema moves only forward, which is what makes this promise the one a rollback rests on.

Enforcement requires nothing new: the factory diffs the schema a candidate declares against the one in production, and a diff the declarations in force forbid without the migration already shipped ahead of it is a rejection at the Merge to master gate. What the declarations forbid is read over writes as well as reads: dropping an element a declaration in force still names is destructive, and so is adding a constraint — a not-null constraint, a domain check, a uniqueness rule — that a write declared inside the range would violate, because the release that writes that way is one a rollback can restore, and an additive diff that condemns its inserts turns a recovery into a write outage. The middle item of a migration diffs empty by construction — both forms present, only the writes moving — so the diff alone would pass it unconditionally; what decides it is [the candidate environment](../05-environments/04-what-the-candidate-environment-decides.md), where the run's writes land in the environment's own store and every store declaration in force, read and write, is decided against the state it holds — the past release's predicate over a column the candidate stopped writing is exercised there or it is undecided, and undecided is read at the gate the way a failure is. The drawback falls on small work — renaming a column is three items and three trips through the pipeline. What it makes possible is the rollback in [_Releases_](../06-releases/06-rollback.md), which is otherwise a promise about code made over data that has already changed.
