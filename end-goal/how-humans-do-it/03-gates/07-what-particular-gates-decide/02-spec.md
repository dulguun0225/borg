# Spec

One duty, and one confirmation already made. [_The interview_](../../02-intent-into-items/02-the-interview.md) (3) refines intent and the spec is what it produces; the person who asked confirmed the factory's reading of the request at the interview's last round, which no score gates, so there is no interview gate and none is missing. A spec version names the acceptance criteria it introduces and the ones it withdraws, so approving it confirms that change to the set (6). What is confirmed is the criteria; the encoding that decides them against an observed run is authored at [_Implementation_](05-implementation.md) and is downstream of this approval, not the object of it.

A criterion is a record of the service and the spec does not restate it. A restated criterion would let the spec and the criterion disagree — the reason an item names no [project](../../11-screens.md#work-ops-factory-people) — and it would make ids stable and never reused a rule about nothing. The record is written exactly once, by the [artifact store](../../01-one-pipeline.md) in the same call that submits the spec version introducing it, and never written again: withdrawal is recorded on the withdrawing spec version, so a version the gate rejects takes its withdrawal down with it. Which criteria are in force for a build is then a query, and a build is a set of items — the ones merged into the repository it was made from, plus the item whose branch it is. A criterion is in force for a build where the item that introduced it is in that build and no spec version in that build withdraws it. That reading is right for master and for the withdrawing candidate at once, where a field written at either moment would be wrong for the other, and both halves have to read the same set: a criterion introduced by a sibling that has not merged is a promise this build's tree could not keep, so holding it in force would reject every candidate decomposed in parallel with the one that introduced it. What that costs is that the set in force differs between two candidates of one service at the same moment, so what a service promises is read from the build running in production and never from the criterion records alone. A human confirming (6) reads what the version changes and not the accumulated set; what a service promises now is the set in force for its current release, and [Factory](../../11-screens.md#work-ops-factory-people) reports how many are in force, how many were admitted as exceptions — sentences that fit no pattern — how many have never failed, and what share of them are unwanted conditions, so drift is visible rather than re-read. The cost: a set that drifted is never re-read unless an owner's safeguard puts a human here, and an item legitimately changing a behaviour has to withdraw the old criterion and remove its encoding in one item — the one edit that removes protection.

Criteria are predicates, not prose, for the reason a [consumer contract](../../07-contracts.md#what-a-consumer-declares) is: what cannot be decided against an observed run is checked by nobody, and in the steady state that is most of them — the factory drafts its own criteria and a human reads them only where the score or a safeguard (9) puts one there. Each states one testable behaviour in one of a closed set of six sentence patterns, drawn from EARS.

| Pattern | The sentence it makes |
|---|---|
| **always true** | `the system shall <response>` |
| **event** | `When <trigger>, the system shall <response>` |
| **state** | `While <state>, the system shall <response>` |
| **unwanted condition** | `If <condition>, then the system shall <response>` |
| **optional feature** | `Where <feature is included>, the system shall <response>` |
| **state with an event inside it** | `While <state>, when <trigger>, the system shall <response>` |

Ids are stable and never reused, the same rule the [release number](../../06-releases.md#the-release-number) keeps, and a criterion that is dropped stays withdrawn rather than freeing its id. The rule is the same and the mechanism is not: the release number is an ordinal because ordering builds is its job, and its position in master's linear history is what lets [_The merge queue_](../../05-environments/03-the-merge-queue.md) re-derive one after a stop or a restore from a backup, where a criterion id orders nothing and nothing outside the factory records it — so a criterion id is opaque, drawn so that minting cannot repeat one, and a restore that loses criterion records loses no counter a later mint would rewind. What opacity costs is an id a human reads nothing from, which the release number's whole job is to provide. A sentence fitting no pattern is admitted with a tagged reason and counted: a form everything can escape is not a form.

A criterion may state a quality of the behaviour as well as the behaviour — a latency, a property of the rendered screen — and the six patterns already carry one: the response clause holds the measurement, so `When the export is requested, the system shall respond within 200 ms under the stated load` is the event pattern like any other. What admits it is the rule that admits every criterion, decidability against an observed run, which for a quality criterion means its encoding produces the condition it measures on [the candidate environment](../../05-environments/04-what-the-candidate-environment-decides.md): load the encoding generates, stated in the criterion's sentence, or a render the encoding drives and reads. An encoding whose load is stated leaves no unloaded run to disagree with a loaded one, so it goes [undecided](../../05-environments/04-what-the-candidate-environment-decides.md) only the way any encoding does. What it establishes is bounded and named: behaviour on that environment's hardware under that load, which is not production's scale — production is read afterwards, by [the health monitor](../../08-operations.md#the-health-monitor)'s comparison and by [an explicit threshold](../../08-operations.md#the-health-monitor) a safeguard (9) sets, and [_Does the explicit health threshold link to what motivated it?_](../../../open.md#does-the-explicit-health-threshold-link-to-what-motivated-it) is the question that residue leaves open. What it costs is the most expensive encoding kind there is: generated load and a driven render spend candidate compute at every run, and an owner whose complaint was production's scale has bought a check that cannot see it.

The form is the whole of what this provides, and having it makes one failure worse: pattern-perfect criteria can describe an incomplete set, and the incompleteness is hidden behind a passing check. The unwanted conditions are where that happens — a set of only happy-path criteria is half a set, and nothing mechanical will ever ask for the other half.

What is available instead of a check is a count, which is why the share of criteria written in the unwanted-condition pattern is one of the numbers Factory reports. Nothing decides on it and no gate reads it: a set with none is visible without anything having judged that it should have some. The cost: the number means little against one item — an item genuinely has no unwanted condition sometimes — so it is worth reading across a service and over time rather than against a spec, and an agent that has learned it is counted can satisfy it with unwanted conditions nobody needed.

Where the item has a user interface, the spec version introduces a screen's **state machine** — the states a screen can be in, the events that move it between them, and what each state forbids, empty and loading and failed among them. It is part of what a human confirms here (6) and not one of the six patterns: the patterns are sentences and lose the transitions, and it is the transitions that make [_Implementation_](05-implementation.md)'s rejection mechanical. It is a record of the service like a criterion, written by the artifact store in the same call, and the screen's identity is the id of the state machine that introduced it — per service, stable, never reused, the rule the criterion id and the release number both keep, and opaque by the criterion id's mechanism rather than the release number's. A revision is a new state machine naming the one it supersedes, and the chain of supersessions is the screen; there is no screen record, because a screen with no state machine is nothing the factory can check. The cost is that nothing mechanical stops two items introducing two chains for what a human would call one screen, and what catches that is the owner confirming here — the one place the flow's enforcement rests on a human noticing rather than on a link.

The drawback is the authoring, the same one declared meaning has in [_What a diff cannot see_](../../07-contracts.md#what-a-diff-cannot-see) — a sketch is cheaper and checks nothing. What the screen looks like is not here: that is the design system the project chose as a [permanent constraint](../../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) (2), a screen design that arrived with the request and binds only what was decomposed from it, and, where neither answers, [_Implementation plan_](03-implementation-plan.md).
