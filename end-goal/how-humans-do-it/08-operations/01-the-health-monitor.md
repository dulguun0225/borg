# The health monitor

A [deploy record](../06-releases/05-the-deploy-record.md) says which [release](../06-releases/02-the-release-record.md) runs where, so the factory always knows which [build](../05-environments/01-records-and-one-long-lived-branch.md) it is measuring. The **health monitor** compares that release against a **control** — a set of instances running the build already in production, started alongside the release and taking comparable traffic — and that comparison is what the factory reads to decide whether a [rollout](../03-gates/02-the-rollout-strategy.md) is failing — automated canary analysis, in the vocabulary of the field the `control` and the `baseline` below come from. Nothing has to be authored for a service to be measured this way, once there is a build in production to compare against.

The control is started rather than found, because a new process and a long-lived one differ before either serves a request: cold caches, empty pools, a compiler that has not yet seen the workload. Measured against the instances it is replacing, a release is slower for being new, and the factory reads that difference as a regression. Measured against a control of the same age, the only difference left is the change itself — for a change confined to the process. A control isolates nothing where the change is to shared state: both arms are instances of the same service reading and writing the same store, so a migration that slows every query degrades the two identically and the comparison stays flat. What reads it is the reading the health monitor takes against the service's own recent history, which has no second arm to move with it — and [_The analysis window_](02-the-analysis-window.md) takes passed away from a window whose control is crossing that reading, so the flat comparison does not close it on evidence while production is materially worse. **Baseline** stays the name for what the comparison is made against; what changed is that the factory now starts one instead of pointing at what is already running.

A control belongs to the deploy the rollout is part of and is not a deploy of the release it runs. It takes traffic so that it can be measured, and only that much: it is sized for the release's share and not for production, because it exists to be compared against and never to serve production on its own. What carries production if the release fails is the other thing the [strategy](../03-gates/02-the-rollout-strategy.md) keeps running — the instances of the build being replaced, serving the rest of the traffic throughout — and the two are different instances with different jobs, the control started cold for the comparison and those long-lived. It mints no [release number](../06-releases/04-the-release-number.md), and it is named on that production deploy record — the build it runs and the instances running it — by the **deployer** — the component that builds, creates and tears down [candidate environments](../05-environments/02-an-environment-per-candidate.md), performs every deploy, applies [a build's schema change](../06-releases/05-the-deploy-record.md) to its service's store before the build takes traffic, executes the rollout, and writes the deploy record — which is already writing that record at that event. There is no rollout component: the rollout is the deployer executing the [strategy](../03-gates/02-the-rollout-strategy.md) through [seam 4](../../deferred.md), starting the control, widening the release's share as it reads the comparison, and advancing its own deploy record's status target by target. What that costs: the deployer is the largest component in [the graph](../../what-the-factory-does/01-tight-integration.md), so one fault in it stops both deploying and undoing.

Teardown is ordered by what a [rollback](../06-releases/06-rollback.md) needs and not by [the exit](02-the-analysis-window.md) alone. At passed and at timed out the health monitor closes the window and calls the deployer to tear the control down. A rollback closes the window of every release it undoes — failed for the one whose analysis failed, skipped for the rest — and no control survives it: every control ends with its window, and so do the instances of every release the rollback undid. What the rollback shifts traffic onto is not a control but [_the instances of the rollback's target_](03-overlapping-windows.md), kept running at full capacity for as long as any open window could return to that release, which is the ordering this paragraph exists to state: those instances are torn down when the last window that could return to them closes, and never at an exit of their own. [_Drift detection_](08-drift-detection.md) is told about this, or it would page on every rollout it sees: a build running on a production [target](../05-environments/01-records-and-one-long-lived-branch.md) beside the [current release](../06-releases/05-the-deploy-record.md) is a mismatch only where no open window names it — as the release under watch, as the control that window's deploy record names, or as the release a rollback of it would return to — and never on a target the [deploy record](../06-releases/05-the-deploy-record.md) marks complete: that target is meant to run the release under watch, so the old build on it is a mismatch whatever window is open. The exemption covers the targets the rollout has not reached yet and nothing else. That makes a control left running after its window closed a mismatch like any other, which is how a failed teardown is caught — at the cost of the drift detector reading two factory records to interpret one fact about the world. The exemption is bounded by the window's own cap: a window open past it excuses nothing, because the record that suppresses the check is written by the component whose failure the check exists to survive, and an exemption that outlives the thing it describes is one a stopped health monitor holds open forever.

The measurement exists in production and nowhere else, and the reason is arithmetic rather than policy: it is computed from organic traffic, and a [candidate environment](../05-environments/02-an-environment-per-candidate.md) has none. A comparison computed from one human exercising a screen is noise that looks like evidence, and running a control beside it would double the compute spent on learning nothing. What a candidate environment decides is the [criteria](../03-gates/07-what-particular-gates-decide/02-spec.md), which need a test run rather than a population.

A rollout fails when the comparison crosses the [boundary](02-the-analysis-window.md), and the rollback follows automatically. The health monitor runs after every production deploy, and the strategy decides only how the factory acts on it: a rollout with a control moves its traffic back to the instances of the release it returns to, which are still running at full capacity whatever schedule the release was taking that traffic on, and a deploy [without a control](../03-gates/02-the-rollout-strategy.md), having no other instances running, has to redeploy the previous build and wait for it to start.

A control requires the old build to keep serving. So the real comparison is available only with the strategy that keeps one, and a deploy without a control falls back to reading the release against the recent history of the release [a rollback of it would return to](03-overlapping-windows.md) — the newest release below it whose window closed without failing it. Not against the ordinal predecessor, which is the reading this was until 2026-08-19: where windows overlap, the predecessor of a release under watch is itself under watch, so its history is not history yet and one release becomes the other's baseline — the exact incoherence a started control was introduced to remove, arriving by the back door in the one case that has no control. Not the [last known-good release](03-overlapping-windows.md) either, for the reason that query is not stated per service: it can be a release *above* the one being read, and a release measured against something that includes it is measured against itself. It is the rollback's target, computed for the release under watch rather than for a rollback of it, and it is single-valued and below whatever is open. What the fallback still has is the confound above, unanswered, which is what makes it the weak fallback. This is the second thing the [score](../04-risk-score/README.md) decides when it picks a strategy: the cheapest rollout is also the one that measures least, and where the score wants a measurement, it picks a strategy that keeps a control running.

The baseline is only as good as the build it runs, which is the argument for a safeguard: an owner can add a [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md) setting explicit thresholds for a service, the way they add one at a [gate](../03-gates/01-where-a-gate-is-and-what-decides-it.md) or on a strategy, and a service whose normal behaviour is already bad is where that is worth doing. An explicit threshold is absolute where the comparison is relative, and it applies in addition to the comparison rather than instead of it — the release passes both or neither, so a safeguard here can only add a check, like every other. It is authored on the [service record](../02-intent-into-items/03-decomposition/README.md) beside the [window limit](03-overlapping-windows.md) and the window's parameters, and it is not one of [gate policy](../09-gate-policy/README.md)'s eight rows: those are one closed set that one section gathers, and this is authored without being among them, the way [retention](../09-gate-policy/03-what-is-not-in-it.md) is. What that costs is a value an owner authors that the [duty](../../what-humans-do.md)'s own line does not count, so an owner reading the eight rows has not read everything they may set.

A comparison needs a control, and a control exists only while a window is open. Between rollouts there is no second arm, so the health monitor also reads each service against its own recent history — the same quantities, measured against what that service was doing before the deploy rather than against instances running beside it. It runs whether or not a window is open and nothing tears it down, so it is what the monitor is still reading [_After the analysis window_](04-after-the-analysis-window.md), what catches a change to shared state that moves both arms together, and what makes a service that is simply broken visible when no release is under watch at all. The rule it is read under is [_The analysis window_](02-the-analysis-window.md)'s and not a new one: a crossing inside an open window rolls the release back, and outside one it raises an [item](../01-one-pipeline.md). Nothing is authored for it either — where an owner sets no explicit threshold the score supplies its size, the same division the window's own size and confidence use. What it costs is the confound a started control was introduced to remove: a release is slower for being new, and a reading against history carries that difference where the comparison does not. So its size is coarse by construction — it finds a service failing and never the size worth catching — and a regression arriving gradually is absorbed into the history it is read against and crosses nothing. Two readings of different sizes now run on one service, so what an [incident](06-incidents.md) records is which of them crossed.

The quantities are the service's own: request rate, error rate, and latency, emitted because the factory instruments the software it writes, which is what makes a service measurable without an owner authoring anything. Availability is the error rate read over a period rather than a fourth quantity. Saturation is read by its effect and never modelled — a pool exhausted or a disk filling appears as errors or latency and nowhere else — because a picture of a service's capacity would put the factory in the business of planning spend on [substrate](../../what-humans-do.md) the owner hosts. What that costs: the factory can report a service failing and never a service about to fail: a queue growing crosses nothing until it starts costing requests. How the three are emitted is fixed, because a comparison over numbers two services emit differently is a comparison over the difference: one record per request served or job run, naming the service, the [release](../06-releases/04-the-release-number.md) whose build emitted it, the [target](../05-environments/01-records-and-one-long-lived-branch.md) it ran on, the outcome, and the duration — the three quantities being counts and a distribution over those records, computed where the outside row [_What the factory does not build_](../../what-the-factory-does/04-what-the-factory-does-not-build.md) keeps them. The release is named by the build itself and never joined by time, so attributing a record to an arm of the comparison rests on no clock agreeing with any other, and what a skewed clock costs is the order of records inside one arm and never which arm they are in. Nothing is sampled: a [window](02-the-analysis-window.md) is a volume condition, and a sampled count is a volume the window would rule things out on that never arrived. And the set of names is closed — service, release, target, outcome — so the store's size grows with releases and never with users or requests, and a record carries nothing of the request's content; what that costs: a regression confined to one customer's requests is read as a small change in the whole. [_Ops_](../11-screens/01-work-ops-factory-people.md) is where the numbers are read and there is no other place: a screen of numbers with no setting beside them is what that screen refuses. A dependency outside the factory — a third-party API, a store the owner runs — is read the same way and in the calling service's own numbers, and the item raised from it is one no change to the code the factory holds will fix; it exhausts the [attempt limit](../03-gates/05-the-attempt-limit.md) and becomes an escalation (12), which is where a failure the factory cannot end already goes.

A service's first release has no build in production to compare against, and the weak fallback is no answer there either: reading a release against its predecessor's own recent history requires a predecessor, and the reading against a service's own recent history is no answer either, a service shipping for the first time having none. So an explicit threshold is the only reading left, used alone rather than alongside a comparison for the one release where there is nothing to compare — and where no safeguard sets a threshold, the first release is unmeasured and nothing about it is discovered by watching. A control exists from the second release, and the measurement is complete from there. An adopted service differs, and [_A service that already exists_](../02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md) sets out how: software is already running, so where the [platform](../03-gates/02-the-rollout-strategy.md) can shift a share its first release has a control — the instances that were running — and the comparison is between two builds of one commit; where it cannot, the first release has the weak fallback at least, the service having a recent history of its own.
