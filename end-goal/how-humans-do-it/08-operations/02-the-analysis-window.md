# The analysis window

The **analysis window** is a record, one per production deploy of a release its service has not watched before, whichever attempt that is, and one per deploy [the search](03-overlapping-windows.md) calls for, over a build nothing has watched — so a rollback opens none, the release it returns to having been watched already, and neither does a redeploy of one already watched. Watched rather than current, because a release that exits failed never completes its deploy and so never becomes [_current_](../06-releases/05-the-deploy-record.md), and the window that failed it has to have been opened over something. The health monitor writes it, opened when that deploy record is written and closed once at exactly one of four exits, because the health monitor is what evaluates every exit and the deployer never advances that record again on the deploy's own account — a rollback does advance the records of every release it undid, and that is a later event the health monitor called for rather than the deploy finishing. It names the deploy it was opened over and through it the release — the build, where the deploy is [the search's](03-overlapping-windows.md) and its record names no release — the service, and the control; whether passed is available to it; the size, confidence, and cap resolved at the open beside the [policy version](../../what-the-factory-does/02-traceability.md) and [score version](../04-risk-score/01-factors-at-least.md) in force, because a reading at an exit is not interpretable against anything but the boundary it was actually read against. What that costs: the health monitor is the only thing that closes a window, so a monitor that stops running leaves windows open, reaches the window limit, and holds that service's production deploys. That is a wait on the factory while the monitor is running and something else while it is not, and the two are told apart the way [_Drift detection_](08-drift-detection.md) already tells them apart for itself: a check that silently stops is worse than the bug it catches, so the health monitor writes a last check record per service and the deployer one per deploy target, the same record the drift detector keeps and overwritten the same way, read by [Ops](../11-screens/01-work-ops-factory-people.md). Without it a stopped monitor and a service with nothing to report are the same row in [Work](../11-screens/01-work-ops-factory-people.md), and the component that is stopped is the one whose stopping disarms the [rollback](../06-releases/06-rollback.md) — the factory's only authority to act on production without a human — for every release after it. What the record costs is a write per pass on two components that otherwise write only at events.

The window is also how long the factory may act on the health monitor alone. Inside it, a **crossing** of the boundary — what sequential analysis calls a statistic reaching the stopping boundary set for it — rolls the release back with no human involved; outside it, the same crossing raises an [item](../01-one-pipeline.md). It is the factory's own authority and is limited by evidence, where [undoing a change after it shipped](../../what-humans-do.md) (10) is a human's and is limited by reversibility — a rollback while the build it would return to is still running, a revert once it is gone. That is why there is no second named window: what limits a human's undo is that build's instances, which the strategy either keeps or does not, and a window with no parameter and no limit of its own is a second name for something already named. A rollback deploy opens no window of its own: the build being restored has been watched already, and a fresh window would compare it against the release just failed and restore that one.

The window is a volume condition, not a clock — and not a volume computed in advance either. The comparison is evaluated as traffic arrives, against a boundary that is valid at every point it is read. That much is forced by what the factory already does: a threshold set for one look at a fixed sample is not the threshold for a thousand looks at a growing one, and reading a fixed-horizon test continuously is how a factory rolls back healthy releases all day. The boundary is what makes continuous reading legitimate rather than a fault nobody traces to its cause.

| Exit | What closes the window | What follows |
|---|---|---|
| **failed** | the comparison crosses the boundary against the release | rolled back, no human involved |
| **passed** | the comparison rules out a regression of the size worth catching | closed early, on evidence |
| **timed out** | neither, by the cap | closed unresolved |
| **skipped** | a rollback aimed below it undid this release | closed with the release neither failed nor running |

Passed is available only while the control is readable. A comparison rules out a regression relative to the control, so a control that is itself failing lets a bad release pass — the one reading nobody corrects afterwards, because nothing rolled back and nothing is left to mark. The health monitor already reads every service against its own recent history, and it reads the control the same way: a window whose control is crossing that reading cannot exit passed, and stays open until the control is readable again or the cap closes it timed out. That is also what closes the hole a shared-state change leaves, where both arms degrade together and the comparison stays flat. Failed stays available: a release worse than a failing control still improves production when rolled back, and the rollback's own confound is corrected afterwards by a human [marking it as not caused by the release](03-overlapping-windows.md). What it costs is a second reading per window on instances the monitor is already measuring, and a service whose control is failing holding its next deploy to the cap — the safe direction, since what it has is a comparison that can say nothing.

What an owner authors is that size and the confidence required, with the rest of [gate policy](../09-gate-policy/README.md) (8), safeguarded per service the way explicit thresholds are (9); where they author nothing the score supplies both. A safeguard on the size is a minimum level of protection — the score may ask to catch something smaller, never something coarser, so a safeguard can only add protection, the way one at a gate can only add a human.

The duration is measured and never set, and that is where the throughput comes from: a release that is plainly fine shows it early and its window closes. It gets there by being fine rather than by being watched against a coarser boundary, which is the change not to make — the traffic a comparison needs scales as the inverse square of what it must detect, so cutting the window tenfold makes the boundary three times coarser. Speed obtained that way runs out quickly. Speed obtained from evidence does not.

The confidence is over the set of quantities and not per quantity: what it bounds is how often a release that is fine is rolled back, because a crossing on any one of the three quantities [the health monitor reads](01-the-health-monitor.md) starts the same rollback, the same [hold](../03-gates/04-what-a-gate-may-change.md) on the service's deploys, and the same [incident](06-incidents.md). Read per quantity, 95% authored means about one good release in seven rolled back over three quantities, and the figure moves every time a quantity is added without anything the owner wrote changing — a number whose meaning depends on arithmetic done somewhere else is the number nobody can argue with. So the health monitor reads each quantity at the stricter boundary that holds the authored confidence over the set, which is its arithmetic to do once rather than every owner's to do by hand. An explicit threshold a [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md) sets stays outside that set: it is absolute, so it has no false-positive rate to budget, and folding it in would loosen the comparison to pay for a check that costs nothing. What it costs is traffic — a stricter boundary per quantity needs more of it, a fifth or so more over three — so a service near the edge of closing a window on evidence times out instead, and is watched at the coarser size the paragraphs below already resolve for a service whose traffic cannot reach what the evidence asks for. That cost lands as weak protection reported as weak, which the window already does, and not as a rate the owner did not author.

A boundary is not arguable the way a vector of factors is, and the score's own rule is that a number nobody can argue with is one nobody will trust. What an owner argues with is the size and the confidence, both authored and both open to a [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md); the boundary is arithmetic on those. That is the same shape as the score — a published formula over inputs a human can disagree with.

A cap limits it in elapsed time, authored the same way. The condition is a traffic-volume one, but what ends a window that will never reach its volume cannot be — so a service too quiet to receive that much traffic times out every time. There the window is weak protection and is reported as weak: a service called twice a night is not made safe by watching it until lunchtime. Timing out on traffic too thin to rule anything out is weak evidence; timing out on traffic the comparison never received at all is none, and the two look alike from inside the factory because the volume the health monitor counts comes from the same emission it is measuring — a service whose instrumentation stopped reads as a service nobody called. So the window records what volume the comparison actually received, and where that is nothing the exit says nothing about the release. [The score](../04-risk-score/README.md)'s own rule is what governs, and it was written for this: a factor that silently reads as absent reads as low risk, and the protection a failure would remove is the protection that failure is evidence for needing. Such a window stays admissible for one thing only, [a rollback's target](03-overlapping-windows.md), which asks whether any window ever failed that release and not whether anything measured it. A service's first release ends there too and for a different reason: it has no comparison to rule anything out, so passed is not an exit available to it — an explicit threshold a safeguard set can still fail it, but nothing can clear it early. With a window limit of 1 on a service that has never shipped, that cap is also how long the second release waits. The [sample the score holds out](../04-risk-score/02-how-it-learns.md) runs to the cap rather than stopping where the boundary would allow — [auto-passing](../03-gates/01-where-a-gate-is-and-what-decides-it.md) a change the score wanted gated is where the factory is most openly guessing, so it takes the longest watch available, which on a quiet service is not much.

The window reads the [producer](../07-contracts/01-two-versioned-things.md)'s own numbers and nothing else, one window excepted below. A [consumer](../07-contracts/01-two-versioned-things.md) that breaks does so in its own error rate, on its own schedule, and what catches it is that service's own health monitor raising an item — after the producer's window closed, with nothing rolling back automatically. Reading another service's numbers would require every consumer's calls to be recorded and attributed across services, which is the recorded-usage approach [_What a diff cannot see_](../07-contracts/05-what-a-diff-cannot-see.md) refuses; the window keeps that refusal rather than reopening it. The item is what replaces it, together with the [contract rules](../07-contracts/04-enforcement.md) that make the schema half mechanical, the producer's own [per-field observables](../07-contracts/05-what-a-diff-cannot-see.md), and a human undoing the change after it shipped (10) while it can still be undone.

The one window that reads more is a [brownout](../07-contracts/08-deprecation.md)'s, and it does not reopen the refusal. A brownout's effect lands wherever the hidden read is: a disabled operation still called errs in the producer's own error rate, which the window already reads, but a field a consumer parses and now fails on errs in that consumer's numbers alone, and the producer's own never show it. So beside the producer's own numbers its window reads a reading already taken: the health monitor reads every service against its own recent history — the reading the control check above uses — with no call recorded and nothing attributed across services. Any service crossing that reading while a brownout's window is open fails it. What that costs is a false failure whose rate rises with the install's size — a service breaking for its own reasons fails a brownout that touched nothing of its — and it fails in the safe direction: an element restored that nobody read, and a removal blocked that a human must re-raise.

The parameters are learned. How fast a problem would appear is already what the score reads to pick a strategy, and the same evidence sets the size wherever an owner has not. Only a rollback or a human's undo traceable to the health monitor counts as that evidence, and not a rollback a human [marked as not caused by the release](03-overlapping-windows.md) — a change undone for being the wrong feature says nothing about what the monitor should have caught, and feeding those back would shrink the size for owners who changed their minds and lengthen every window with it. The score learns from what the health monitor could have seen, the same way it learns from a [reject](../03-gates/04-what-a-gate-may-change.md) and not from a hold.

That evidence sets what is worth catching, and one thing more is needed: whether anything can be caught. The size in force is the coarser of the two — what the evidence asks for, and the finest size this service's own traffic can rule anything out at inside the cap, which is arithmetic over the volume its windows have actually received. A size finer than that is a size nothing is ruled out at, so the window times out every time, protects nothing, and holds the next deploy for the whole cap; asking for it would be watching longer and catching less. The two are different questions and only the first is about harm, which is why reading the second does not reopen the restriction above. What it costs: a service can be told, truthfully, that it is being watched for something coarser than the evidence asked for — so the size in force is reported with what the traffic reaches beside it, and a service whose traffic falls far enough is watched at the size it was installed with and no coarser, which is the weak protection _The analysis window_ already says such a service gets. This is also what keeps a learned size from ratcheting: every miss makes it finer and nothing makes it coarser, so without the second question a service that missed twice would need sixteen times the traffic it has and never close a window on evidence again.
