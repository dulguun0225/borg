# Decomposition

One intent becomes one item or several — none only for the conformance intent [_Constraints and the design system_](../01-intake/01-constraints-and-the-design-system.md) raises, whose decomposition may find nothing departing, attach that finding, and write no item, no gate firing over an empty set — and an item names exactly one service. How many go to one service is a floor and not a cap: a service the work changes gets at least one item, and gets more where one item would be larger than decomposition is aiming at, or where a change cannot ship as one. Decomposition is where [_No single item may break a contract_](../../07-contracts/02-no-single-item-may-break-a-contract.md) is applied rather than discovered: "an item that cannot ship by itself was decomposed wrong" is a statement about this stage, and a migration with one consumer is four items over two services, three of them on the producer, which adds the new form in one item, runs the [brownout](../../07-contracts/08-deprecation.md) of the old one in a second, and removes it in a third — the last two the factory raises itself, the brownout when the derived list empties and the removal on the brownout's evidence, the way [_Deprecation_](../../07-contracts/08-deprecation.md) sets out, not written here ahead of conditions nobody can schedule. Until decomposition got a gate of its own, nothing ratified what it produced.

A service the work changes may not exist yet, and nothing about decomposition changes: one item creates it, and whatever calls it is a second item declared to wait on the first. Decomposition writes the service record in the same write as that item, because an item names one service and the record has to exist for the item's only outbound link to point at anything. Its other writer is an owner at [_Factory_](../../11-screens/01-work-ops-factory-people.md), putting the [window limit](../../08-operations/03-overlapping-windows.md) and the [analysis window](../../08-operations/02-the-analysis-window.md)'s parameters on it (8), and the seam between the two is the field: decomposition writes the service's identity and never a parameter, an owner writes parameters and never creates a service. A service is one repository with one long-lived branch inside it, and no repository holds two: [master](../../05-environments/01-records-and-one-long-lived-branch.md), [the release number](../../06-releases/04-the-release-number.md), and the queue's ordering are all per service, and two services sharing a repository would give it two divergent trunks, so a build of either would be made from a tree that contains the other's stale code. The drawback is that a twelve-service project is twelve repositories, and a customer arriving with a monorepo has a split to perform that nothing in the factory does for them. Master itself does not exist until the first release: the [implementation role](../../01-one-pipeline.md) commits the [candidate branch](../../05-environments/01-records-and-one-long-lived-branch.md) with no base, and the queue's first fast-forward is what creates master. Nothing writes the service's place in an environment either — a [deploy record](../../06-releases/05-the-deploy-record.md) is keyed by service and environment, so a service is in an environment by having been deployed there. The item ships by itself, a service nothing calls yet being exactly the kind of thing that can. The drawback is that the factory's weakest measurement applies to the release the rest of the work waits on: a first release is [_without a control_](../../03-gates/02-the-rollout-strategy.md) whatever the score would prefer, nothing can close its window [_passed_](../../08-operations/02-the-analysis-window.md), where no safeguard sets a threshold (9) it is [_unmeasured altogether_](../../08-operations/01-the-health-monitor.md), and it has no [_rollback target_](../../06-releases/06-rollback.md). Each of those is stated where it arises, and this is where they arrive together. How long they last is stated too: until the second release closes a [window](../../08-operations/02-the-analysis-window.md) on evidence, which a service with organic traffic — requests real users are already making — reaches at its second release and a service with none does not reach at all. What the customer has meanwhile is a factory gating on the prior the product shipped for each model version rather than on a wide one, which [_A model under a name_](../../10-fleet/02-a-model-under-a-name.md) supplies, and no measurement of what it ships. A customer whose software is already running and already has traffic is past that state at the second release, which is why [_A service that already exists_](01-a-service-that-already-exists.md) is the ordinary way a factory starts and not the exception.

Shipping by itself is a minimum and not a size — it admits an item that touches forty files and one that changes a string. What sizes an item between them is a target the score supplies, which an owner authors, or safeguards per area (9), with the rest of gate policy (8). It learns from what a bad size does in each direction, and both are already among the numbers [_Factory_](../../11-screens/01-work-ops-factory-people.md) reports: a decomposition too coarse shows as attempt-limit escalations (12), with everything spent on the item thrown away, and one too fine shows as cost per feature and rework rate — an environment, a spec, four gates, and a release number for a one-line change. What that number reaches is model spend and nothing the host bills — the environment and the fleet a release keeps are hosting the factory does not read, and the spend ceiling does not reach them either — so the target can be learned finer than the install can afford while Factory shows the number falling. That is stated as a cost and not repaired: the owner's lever is to author the target over what the score learned (8). The minimums do not move with the target. It ships by itself, and no single item may break a contract, which is four items for an interface and three for a store, however small the target. What the target is not is a definition: an item is not one feature. A feature that changes a contract is several items by the rule above, so a definition of that shape is broken by the case [_A service that already exists_](01-a-service-that-already-exists.md) works through, and Factory computes cost per feature as what the intent and its items spent, which already makes a feature an intent. What refusing it costs is that the target has two named failure directions and no stated unit, and [_In what unit is the item-size target authored?_](../../../open.md#in-what-unit-is-the-item-size-target-authored) is that question.

Decomposition also records the order. Where one item cannot be verified until another has shipped — the producing release of a migration — that dependency is declared here, and both deploy gates hold on it: [_Deploy to candidate environment_](../../03-gates/07-what-particular-gates-decide/06-deploy-to-candidate-environment.md) until the dependency is live, [_Deploy to production_](../../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) if it has stopped being. Ordering is a property of decomposition, not something discovered at deploy time.

The declared order is checked where the set is decided: a set whose dependencies form a cycle is rejected at [the Decomposition gate](../../03-gates/07-what-particular-gates-decide/01-decomposition.md) mechanically, the way a forbidden transition is at [_Implementation_](../../03-gates/07-what-particular-gates-decide/05-implementation.md), because two items each holding a deploy gate on the other is a wait nothing lifts and no instrument shows — a factory hold over an existing record writes nothing, counts no attempt, and pages nobody. A re-decomposition also repoints what stands: an item left standing that waited on one now superseded waits on the replacements, written by decomposition in the same write that creates them — the inverse of the pointer a superseded item already carries — and an item left waiting on one replaced by nothing has that wait resolved in the set the gate decides, what waits on what being part of what is approved. Without the repointing, an item waiting on a superseded sibling waits on something that will never be current, forever, and every instrument reads it as an ordinary dependency hold about to lift itself.

Decomposition has a gate of its own, named for the stage and scored like every other, and it fires where the stage yielded more than one item. What is approved is the set: how many items, which service each changes, and what waits on what. A rejection re-decomposes the set rather than sending one item back, because what the gate decides on is the decomposition and not an item, and each round counts against the attempt limit on the intent rather than on an item — the items of a rejected round are superseded and their replacements start at nothing, so a count kept on them would never reach a limit however many rounds were spent. It is the parameter the interview already counts its rounds against, one stage later and on the same record, in a field of its own beside the rounds and never the same field: the two are different stretches of work, an owner answering an escalated interview clears that count alone, and one field would spend an interview's rounds out of decomposition's budget. Intake writes it, called by decomposition, which is the one write decomposition makes to an intent rather than to items. While rounds remain, a human re-decomposes by hand with [Edit in place](../../03-gates/03-actions-at-each-gate.md), the gate still deciding and the set still editable. An intent that exceeds the limit gets **escalated** written on it and appears in Work as an escalation (12) — the second of the two things that write that value, and the two are told apart by which of the intent's counts exceeded the limit rather than by the value itself.

Decomposition also runs again on an intent in progress, which is what three other sections send a problem to: a group [_Reports_](../01-intake/02-reports.md) says the grouper preferred to make, a spec that comes back too large, and a change [_No single item may break a contract_](../../07-contracts/02-no-single-item-may-break-a-contract.md) says cannot ship as one. A [rework request](../../03-gates/06-going-back-up.md) naming decomposition re-decomposes the set, as does a gate's reject naming it, and what either produces is decided at this gate whatever it yields — the one-item condition is the first decomposition's, and a re-decomposition of work in progress always fires, because what it decides is which existing items are superseded rather than how many are proposed. The intent goes to re-decomposing and every unmerged item of it stops while that firing is open, the way they stop while the interview is: without it a sibling merges between the rework request and the verdict, and the set approved would supersede a release. The item that sent it back stops with them, its stage unchanged and its attempt booked on the intent, so it resumes where it was if the re-decomposition does not replace it. The items it replaces are superseded and point at their replacements, the record shape a rejected round already uses; what differs is that an item in progress has spent artifacts, a build, and an environment, and superseding it throws all of them away. A merged item is out of reach — a rework request may be raised no later than the merge to master — so the re-decomposition leaves shipped work alone and declares the new set's order against it, which is what [_When an intent's items do not all ship_](../04-when-an-intents-items-do-not-all-ship.md) already says about the siblings that got there first. Each round counts against the same re-decomposition count, so a set that keeps being re-decomposed escalates the intent rather than dividing forever, and its items stop there rather than resuming — they appear in Work under it until a human takes one over (12) or drops them, the factory not going on to build a decomposition it has just said it cannot make. Against a decomposition that fires once per intent this costs a gate every builder implements as re-firing and a set that can change under work already approved; what it buys is that a wrong decomposition is repaired on the intent that caused it rather than restarted as a new one with the interview, the grouped reports, and the timeline left behind.

One verdict covers the whole decomposition, however many services it changes. Splitting it up — one verdict per service, each holder deciding only the items in theirs — would rebuild here the wait [_Who owns a contract_](../../07-contracts/07-who-owns-a-contract.md) refused: approvals that must all arrive before anything proceeds, in a graph where a four-service decomposition is ordinary, and the attempt limit turning a long enough wait into escalations (12). A holder who wants to decide at decomposition for their own service gets that with a safeguard (9) on their area, which is what a safeguard does everywhere else. The drawback is that they first see the work one stage down, with the authoring already done — never blind, since the item links back to its intent and Work shows the sibling timelines under the same decision, but reading a spec rather than a proposal.

Decomposition writes the items, and the gate decides over records that already exist. Every other [artifact gate](../../03-gates/01-where-a-gate-is-and-what-decides-it.md) does — Spec, [Implementation plan](../../03-gates/07-what-particular-gates-decide/03-implementation-plan.md), [Tasks](../../03-gates/07-what-particular-gates-decide/04-tasks.md), and Implementation each decide over an artifact already written — and the alternative gives the Decomposition decision fields describing the set it proposes, which is what an item already records. It would also split one record's writer in two: a decomposition yielding one item fires no gate, so items would appear at approval where a gate fired and at decomposition where none did.

A rejected set is superseded rather than discarded. Each rejected item points at the items of the re-decomposition that replaced it — a list, since a re-decomposition may replace four items with two — written by decomposition in the same write that creates the replacements, so what was decomposed wrong is readable beside what replaced it rather than only in the decision's feedback. Where a re-decomposition replaced an item with nothing the pointer stays unwritten, and what says why is the item's superseded stage beside the decision that rejected the set. What the pair of choices costs is item records that no gate approved, a superseded set per rejected round, and a service record decomposition wrote for an item the re-decomposition did not replace, which no item in progress then names: every reader of items — [_Work_](../../11-screens/01-work-ops-factory-people.md) first — has to tell an item in progress from one of those.

The Spec gate cannot do this job — it is per item, so approving one item's spec never ratifies the decomposition that produced four. Without a gate here, a wrong decomposition is discovered several specs later and re-decomposing means abandoning items that were already approved. So the gate fires where there is a set to ratify and nowhere else: a decomposition that yields one item produced none, and putting a gate in front of every intent — most of them single-item — would be a decision about nothing. Scoring it was the cheaper defence and it is the wrong one: a gate the score auto-passes is still a gate every builder implements and every intent passes through. What the condition costs is the decomposition that should have yielded four and yielded one, which now reaches a human one stage down as a spec too large, at [_Spec_](../../03-gates/07-what-particular-gates-decide/02-spec.md) rather than here.
