# A service that already exists

Most software a customer brings has been running for years, and it is adopted through the same pipeline as anything else: an owner raises an intent (1) naming a repository and the environment it is running in, and the interview asks what it does — the criteria a human can state for behaviour nobody wrote down, which may be none. Decomposition writes the service record for it, the repository already existing, and yields one item, whose implementation stage authors nothing: the repository's head is the implementation, the candidate branch is its trunk, and the [deployer](../../08-operations/01-the-health-monitor.md) builds it as it builds any commit, so the item has a [build](../../05-environments/01-records-and-one-long-lived-branch.md), the [consumer contracts](../../07-contracts/06-what-a-consumer-declares.md) the factory derives from one, and the resolved set the [advisory](../01-intake/03-advisories.md) detector reads. Every gate fires as it fires on any item, the [Implementation](../../03-gates/07-what-particular-gates-decide/05-implementation.md) gate's diff being the whole tree against nothing, and the queue's first fast-forward makes the head master and the item release one. Its production deploy is where adoption differs from a first release the factory built: the software is already running, so where the [platform](../../03-gates/02-the-rollout-strategy.md) can shift a share, the release takes traffic [with a control](../../03-gates/02-the-rollout-strategy.md) — the instances already running are the control, kept serving as any control is — and the window compares the factory's build of the head against the customer's, which is a comparison between two builds of one commit and establishes that the factory builds and deploys this service the way its owner did. From that deploy the service is inside the factory's checks: it has a current release for [a deploy gate's hold on a dependency](../../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) to read, a deploy record for [_Drift detection_](../../08-operations/08-drift-detection.md) to compare, and a build for the next release's control to start from, so the second release is measured completely — on a service with organic traffic, sooner than a service the factory built from nothing is ever measured. The [design system](../01-intake/01-constraints-and-the-design-system.md) an owner picks for the project reaches it through the [conformance raise](../01-intake/01-constraints-and-the-design-system.md), an item per screen that departs.

What adoption does not give a service is stated rather than promised. Release one has no [rollback target](../../06-releases/06-rollback.md) — what ran before it is not a release — so a window that fails on it finds nothing to return to and takes the [page](../../08-operations/07-pages.md) that [exit](../../08-operations/02-the-analysis-window.md) already has. The interfaces arrive without [declared meaning](../../07-contracts/05-what-a-diff-cannot-see.md), a consumer's contracts are checked against what was never declared, and naming a field afterwards is a breaking change and a migration's four items. Every parameter of the service starts where a new service's does — the [window limit](../../08-operations/03-overlapping-windows.md) at one, the window's size supplied — because nothing the factory can read says what ten years of shipping taught. And the service is one repository with one trunk: a customer arriving with a monorepo splits it before adoption, the split being work nothing in the factory does for them, for the reason [_Decomposition_](README.md) states. What adoption costs the factory is one item that changes nothing and pays for an environment, a run, and a release number anyway, and a first window whose passed exit says only that the factory reproduced what was running. Following the links out of an incident in adopted code ends at the adoption item, which is where the factory's history of that service starts, and nothing recovers what was behind it.
