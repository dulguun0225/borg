# Reports

An end user's bug report (4) or complaint (5) is a **report**, and a report is not an intent. The way in is thin and embedded in the deployed software: what it writes is a report, into the **report store**, one of its own sized for what a population of end users sends rather than for what a graph joins on. A **grouper** reads that store and calls intake once per group, so five hundred reports of one slow button are one intent and not five hundred.

The grouper is an [agent](../../01-one-pipeline.md), because deciding whether two free-text reports are one problem is model work, and model work outside [the fleet](../../10-fleet/README.md) would run on words no gate ever decided. It runs under a [fleet entry](../../10-fleet/README.md) like any other agent — a model, an [effort](../../10-fleet/01-what-an-agent-runs-on.md), a credential — in a role put on neither an intent nor an item: its scope is a project, and it reads the reports that arrived under that project and nothing else. Its [role prompt](../../10-fleet/03-what-an-agent-is-told/README.md) is versioned and decided at [a gate of its own](../../03-gates/07-what-particular-gates-decide/09-a-role-prompt-or-a-skill.md), so a safeguard (9) at that gate reaches the words it works from — words [_What a version is authored from_](../../10-fleet/03-what-an-agent-is-told/01-what-a-version-is-authored-from.md) keeps a report out of. What grouping does not do is move the [per-author prior](../../04-risk-score/01-factors-at-least.md): no gate decides a grouping and no artifact carries one, so its two failure directions surface one stage down — a group [decomposition](../03-decomposition/README.md) has to split, and duplicates linked as recurrences — where they are repaired rather than scored.

This source alone has a record in front of the intent. An owner's request is one thing because one person typed it, and a factory finding is keyed by its evidence. Only an end user's report arrives in a quantity nobody upstream has collapsed, in words the factory has to read to know whether two of them are one problem.

A report raises an intent on arrival rather than waiting for a batch: the first of a group raises it, and later matching ones attach. Nothing waits for a count, because grouping is deduplication and not triage — one report from one end user is an intent, and the count is evidence on it rather than a rank: nothing orders work by it on its own, though a human reordering a queue can read it. A batch would group better and delay every fix by the length of the interval.

A report is marked with the intent it was grouped into and kept. Deleting one on grouping would cost the measurement this store makes possible — the rate of reports before and after the release meant to fix what they describe — so what removes a report is a retention setting an owner authors, and never the grouping. That setting is a field of the one policy list the factory owns, which [_Gate policy_](../../09-gate-policy/03-what-is-not-in-it.md) sets out, and its only reader is the report store — the component that writes a report is the only one that may remove one. Where an owner authors nothing, reports are kept for the life of the install: no outcome teaches a retention period, so there is nothing for the [score](../../04-risk-score/README.md) to supply.

Grouping takes no gate. The interview, decomposition, and [_Spec_](../../03-gates/07-what-particular-gates-decide/02-spec.md) all read what it produced, which is the argument [_Dispatch_](../05-dispatch.md) makes for itself. The two ways it goes wrong are not symmetric, so the grouper prefers to group: two problems in one intent are separated one stage down, where decomposition yields an item each or a spec comes back too large, while duplicates that were never grouped are separated by nobody — each takes its own interview, its own [timeline](../../11-screens.md#work-ops-factory-people), and its own item, several of them on the same code and serialized behind each other in [_The merge queue_](../../05-environments/03-the-merge-queue.md).

A later report attaches to the intent and never rewrites it. What refines an intent is attached to it and every reader reads both, so the five hundredth report changes what is built by being read rather than by editing the record — which is what keeps an approval pointing at what was approved. Decomposition is the boundary. Before it, the grouper may still split a group it got wrong; after it, a report matching work already decomposed attaches and raises the count, and one that does not is a new intent, linked to the first as a recurrence. A report arriving after the fix shipped is that same rule: the timeline is finished, so evidence that the fix did not work is a new intent and never a reopening. What the boundary costs is a run of reports just after a narrow decomposition showing as two linked timelines where a human would call it one problem.

For an intent grouped from reports, the reports are what the interview and the spec are authored against and the intent's own **statement** — the field holding what was asked for — summarizes them; for an owner's request the statement is the thing itself.

An intent grouped from reports never auto-passes the [Spec](../../03-gates/07-what-particular-gates-decide/02-spec.md) gate. The source intake wrote is a context factor the [score](../../04-risk-score/01-factors-at-least.md) reads, and reports is the value that is resolved rather than weighed: it takes the treatment [a factor the score cannot compute](../../04-risk-score/01-factors-at-least.md) takes — toward the gate — so a human confirms the criteria (6) whatever the rest of [the vector](../../04-risk-score/01-factors-at-least.md) says, and the [held-out sample](../../04-risk-score/02-how-it-learns.md) cannot select past them, never selecting what a resolved factor put there. This is the one part of the channel's safety that does not rest on how good any reader is. That an agent treats a report as content and never as instruction stays [an instruction to the agent](../../01-one-pipeline.md), worth what an instruction is worth — a reason to hand report text onward quoted rather than folded into anything an agent is told, and not what stops an injected report from shipping code; the human at Spec is. What the floor costs: the source that arrives in the greatest volume is the one whose items cost the most human attention, the opposite direction from the rest of the design, and taken because the alternative is an anonymous sentence reaching production with nobody on the path.

Arrival is bounded at the channel. Two rates are fields of the [factory-wide settings record](../../09-gate-policy/02-one-shape-across-all-of-them.md) beside [retention](../../09-gate-policy/03-what-is-not-in-it.md) — one applied per service, one over the whole channel — and the report store enforces them at the way in: a report over either rate is refused rather than queued without bound. A report also carries an opaque key where the deployed software supplies one, derived from its own session and salted, so that it marks a session's reports as one source's and carries nobody's identity; the store rates a source by it, and a bad actor is limited through it. The key is not a reporter handle — nothing joins it to a person, it cannot be added to reports already written, and it is the most the channel can carry without trading away the anonymity it exists to offer, which is why the two authored rates stay coarse: what they bound is arrival, never any individual. A surge therefore drops real reports, a real loss preferred to an unbounded one — unbounded, the channel's volume is linear in what a stranger sends at no cost, read by the grouper report by report against [a quota](../../10-fleet/05-an-account-that-runs-out-is-a-hold.md) every stage shares and whose exhaustion pages nobody. The factory-wide rate authored to zero closes the channel, and a safeguard (9) narrowing the per-service rate to zero closes one service's. This is protection at the channel and not a ceiling on spend: what admitted reports go on to cost is bounded, where an owner authored one, by [the spend ceiling](../../10-fleet/08-a-spend-ceiling.md) and by nothing else.

An owner who wants a human before the pipeline spends anything on a report adds a safeguard (9) whose subject is the report store: with one in force a report-derived intent arrives and waits, [dispatch](../05-dispatch.md) putting no agent on it and no interview round running, until a human admits it at [_Work_](../../11-screens.md#work-ops-factory-people) — one action per group, the group already being one intent. It is a safeguard rather than the default because a regulated install wants it and an ordinary one should not have to pay it, and what it buys over the floor at Spec is that nothing is spent refining what a human would never admit.

Retention removes reports in bulk and on age; what removes one report's words is a **redaction** — a second record naming a report, the statement summarizing it, or an [artifact version](../../01-one-pipeline.md) quoting it, and the spans removed. The bytes named are destroyed, every reader reads the target through its redactions, and the redaction carries the actor and the reason and never the words. No link breaks, because what is erased is text inside a record and never the record: the report row, its grouping link, its count, and the before-and-after measurement all stand with the words gone. It is the correction idiom a [constraint](01-constraints-and-the-design-system.md) already uses — a second record, never an edit — pointed at content, with one difference: the original is destroyed rather than superseded, so this is the one mechanism in the factory that removes information a decision was made on. The decision still names its versions, and what those versions can no longer show, the redaction record says why. An owner performs one erasure as one action, and the factory walks the links that exist — the report to its intent, the statement, the artifact versions authored against them, which is the query the intent's source already marks out. What it costs is a read-through on every reader of stored text, and an auditor reading a decision back meeting a stated gap where words were.

What a redaction reaches ends at the install's edge, and both halves of that edge are on the record. Which providers received the words is answerable: report-derived work spends through named credentials — the field every [interview](../02-the-interview.md) round and every stage writes — and [_People_](../../11-screens.md#work-ops-factory-people) records who lent each, so the recipients are enumerable without a provider being named anywhere in the factory. What a provider retained is a residue the factory does not reach: recalling anything from one is the owner's agreement with that provider, which is [substrate](../../../what-humans-do.md) the way hosting is. And nobody — the factory included — can list a person's reports, because the channel carries no identity by design: an access request is answered by that fact, and an erasure request needs what every redaction needs, content pointed at.

Three things stay refused here, each for a reason already on the record. A subject key — indexing reports by the people their text mentions — would have the factory identify people in free text, building exactly the join the opaque key refuses to be; whoever the words are about is served by the redaction and not by an index. Screening content before an agent or a screen reads it is a moderation pipeline a one-customer install does not carry: the admission safeguard above is that screen where an owner wants one, an agent takes report text as [content and never instruction](../../01-one-pipeline.md), and the human the Spec floor keeps is the backstop. And a reporter still gets nothing back — no acknowledgment, no status, no way to contest a grouping — because each would need the reporter handle the channel refuses; the residue is that a misgrouped report is contested by nobody outside, and what repairs it is [decomposition](../03-decomposition/README.md) splitting the group and a recurrence link joining what it missed.

A report that is never grouped is work nobody sees, which is how a store in front of a pipeline fails wherever it is built. So every report is either linked to the intent it was grouped into or counted as ungrouped, and that count is a number on [_Factory_](../../11-screens.md#work-ops-factory-people). One report appears in [_Work_](../../11-screens.md#work-ops-factory-people) under its intent and nowhere else: a browsable list of reports would put end-user volume on the screen that is one item per timeline, and make the grouping a human's job again.
