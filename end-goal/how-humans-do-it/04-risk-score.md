# Risk score

A vector of named factors, reduced to one number by a published formula. Both halves matter — the number is what a [gate](03-gates/01-where-a-gate-is-and-what-decides-it.md) compares against a threshold, the vector is what a human reads while deciding, and the number is what they see beside their [verdict](03-gates/01-where-a-gate-is-and-what-decides-it.md) once written, for the reason [_Where a gate is, and what decides it_](03-gates/01-where-a-gate-is-and-what-decides-it.md) gives. A score nobody can argue with is a score nobody will trust.

## Factors, at least

Four groups of factor, named so a human can argue with them, and the set is open.

- **The change** — size, how much of the system it can affect, area churn, reversibility. Test coverage is deliberately not among them: it would be computed from the [encodings](03-gates/07-what-particular-gates-decide/05-implementation.md) the scored agent authored in the same stage as the code, so the scored author would set the factor — assertions piled on accessors beside an untested payment path read as high coverage — and it would lower the number exactly when it was gamed, with the [analysis window](08-operations.md#the-analysis-window) then closing `cleared` — its no-failure exit — on a quiet service, and the manoeuvre narrowing the prior of the author that performed it. It returns if something ever derives it independently of the author, the same condition [_Implementation_](03-gates/07-what-particular-gates-decide/05-implementation.md) states for making the encoding itself mechanical. Leaving it out costs this: the change group reads a tested change and an untested one alike; what carries that information instead is the run — a [criterion](03-gates/07-what-particular-gates-decide/02-spec.md) in force with no encoding naming it is already a rejection at [_Implementation_](03-gates/07-what-particular-gates-decide/05-implementation.md).
- **The author** — the **per-author prior**, one per human and per AI model version, computed from that author's own work with the changes a human [undid after they shipped](../what-humans-do.md) (10) and the [rollbacks](06-releases.md#rollback) marked. A [revert's deploy](08-operations.md#overlapping-windows) delivers several releases under one window, and that window's close moves no prior in either direction: one comparison over several changes is a label the evidence does not support, toward fault and toward trust alike. Only the release the [search](08-operations.md#overlapping-windows) names takes a failed batch's outcome, and where no search runs or it names nobody, the batch teaches nothing — the reading an absent input already gets. A deploy has no author: the [deployer](08-operations.md#the-health-monitor), the component that performs every deploy, is not one, so a deploy accrues no [attempt](03-gates/05-the-attempt-limit.md) and moves no prior, and the outcome that does move one — the [window](08-operations.md#the-analysis-window) closing on the release — is read against the artifact's author and never against what deployed it. A prior read as a list of only the bad outcomes could never narrow toward trust: what narrows it is the work nobody undid, so every outcome on that author's [artifact](01-one-pipeline.md) moves it, a [window](08-operations.md#the-analysis-window) closing without failing the release included — except a window whose comparison received no volume at all, evidence about nothing and narrowing nothing, the reading [_The analysis window_](08-operations.md#the-analysis-window) already sets for an absent input; a rollback a human [marked as not caused by the release](08-operations.md#overlapping-windows), evidence about something other than the author; and [a queue rejection whose repeated failure came with a moved dependency](05-environments.md#the-merge-queue) — the two runs' compositions differing — evidence about the dependency and not the author. It is kept per model version and not per family, which is how a new version accumulates a prior of its own; the cost: moving a [fleet entry](10-fleet.md) to a newer version starts its evidence over, and keeping the old name for a new version reads the old version's outcomes as the new one's. The [effort](10-fleet.md#what-an-agent-runs-on) an entry runs at and the [role prompt](10-fleet.md#what-an-agent-is-told) an agent works from change how one model behaves under one name too, and both are deliberately left out of the key — [_Paid for is not authored by_](10-fleet.md#paid-for-is-not-authored-by) refuses the split and states what refusing it costs. Both are recorded on the vector a gate firing writes instead, which is where a fact a human argues with belongs. It starts wide for an author the factory has not seen and narrows with evidence — or starts at the prior the product shipped for that model version where it shipped one, which [_A model under a name_](10-fleet.md#a-model-under-a-name) sets out with what a name pinned at the provider is worth, and with the one instrument the factory holds on a version that is not an outcome. A version that instrument finds departed from its own earlier results reads as an unfamiliar author, toward the gate — the treatment a drifted factor takes below. The restriction [_The analysis window_](08-operations.md#the-analysis-window) keeps — that only a rollback or a human's undo traceable to the [health monitor](08-operations.md#the-health-monitor) counts — is that window's parameters' rule and not this one's: the window learns from what the [health monitor](08-operations.md#the-health-monitor) could have seen, the prior from every outcome on that author's work, a change undone for being the wrong feature included, because building the wrong thing well says something about the author and nothing about the health monitor.
- **Exposure** — what the change reaches that the service did not reach before, read from the same diff: an outbound call added, a credential named or read, an authorization check removed or weakened, and a dependency change — the [build](05-environments.md#records-and-one-long-lived-branch)'s resolved set diffed against the set of the service's [current release](06-releases.md#the-deploy-record)'s build, each package added or moved named with its version and its declared licence, which reads an unpinned range resolving differently with nothing in the manifest changed as the change it is. Three things separate it from the change group. It only ever raises the number: a diff adding none of that reads as nothing, and nothing in this group lowers a score, its absence not being evidence of safety. It does not learn from outcomes: the signals [_How it learns_](#how-it-learns) reads are misbehaviour signals, and a change that posts credentials outward moves neither error rate nor latency, so a [window](08-operations.md#the-analysis-window) closing `cleared` on it says nothing about it — its weight is published and calibrated like the rest, and the only outcome that ever speaks to it is a later [advisory](02-intent-into-items/01-intake/03-advisories.md), report, or undo, arriving on the prior and not on this factor. And it reads the diff and never the intent: an injected change and a mistaken one add the same call, which is what makes it the one factor a stranger's sentence in a [report](02-intent-into-items/01-intake/02-reports.md) cannot talk its way past. Its evidence is a list on the vector — each call, each credential name, each check, each package with its version and licence, and the file and line of each — so what the human at [_Implementation_](03-gates/07-what-particular-gates-decide/05-implementation.md) argues with is that list beside the diff [Work](11-screens.md#work-ops-factory-people) renders. The list is not the diff, and where the two disagree the human decides over the code, the disagreement being what the list's derivation missed. It is derived by the factory from the diff and the build record, independent of the author, which is the condition test coverage failed above. What extracts a call or a credential read is per toolchain, as [_What a consumer declares_](07-contracts.md#what-a-consumer-declares)'s derivation is, so where no extractor runs for a toolchain the factor is unavailable and resolves the way an unavailable factor does below — a human at the gate, the vector naming why — and never as nothing. What it costs: an extractor per toolchain to ship and keep, a human at Implementation on every change on a toolchain without one, and a residue the list states rather than closes — what an extractor misses is decided by nobody, and a change whose harm nothing observed narrows its author's prior like any other clean window.
- **Context** — what this change touches in this customer's business, and which sibling services consume what it publishes. The same diff is a different risk in a payments path than on a marketing page. The [intent](02-intent-into-items/01-intake/README.md)'s source is here too, and one value of it is resolved rather than weighed: an intent grouped from [reports](02-intent-into-items/01-intake/02-reports.md) takes, at the [Spec](03-gates/07-what-particular-gates-decide/02-spec.md) gate, the treatment an unavailable factor takes below — a human at the gate whatever the formula returns, one the [held-out sample](#how-it-learns) may not select past, resolution being what it already never overrides — because that channel is the one way in the factory cannot authenticate, which [_Reports_](02-intent-into-items/01-intake/02-reports.md) states and owns.

A version of what an agent is told is scored on a set of its own, because the change group is computed from a diff and a [role prompt](10-fleet.md#what-an-agent-is-told) has no code to have sized and no area to have churned. Three factors replace that group at [_A role prompt or a skill_](03-gates/07-what-particular-gates-decide/09-a-role-prompt-or-a-skill.md) — the share of the factory working from this version; **departure**, how far it differs from the version in force; and reversibility, which is high for every version, [withdrawal](10-fleet.md#what-an-agent-is-told) being a second record and nothing having been deployed. The author and context groups are unchanged, the author being the agent that wrote the version. That the set is different here rather than partly unavailable is the point: a factor the score cannot compute puts a human at the gate, and treating area churn as missing rather than as inapplicable would put one at every version forever — a decision nobody made, arriving as a side effect. One version has no author at all — the [shipped entry](10-fleet.md#what-an-agent-is-told) an upgrade's first start enters, install's own firing no gate — and that absence is resolved rather than classed: a human at the gate whatever the formula returns, decided here so that a narrow shipped skill cannot auto-pass at an upgrade as a side effect. What it costs: a second factor set to publish, calibrate, and argue with, on a row that fires far less often than the eight of the [default path](03-gates/03-actions-at-each-gate.md).

Likelihood and impact stay separate until the last step. They answer different questions and call for different responses: likely-wrong but cheap to undo should ship and let rollback handle it; unlikely but catastrophic should be gated regardless. This is also why one score decides three things about a change: the gate reads mostly likelihood against impact, the [rollout strategy](03-gates/02-the-rollout-strategy.md) reads mostly impact against reversibility and how fast a problem would appear, and the boundary of the [_analysis window_](08-operations.md#the-analysis-window) reads mostly impact. Reading different halves is what keeps them from weakening together: a change misjudged on likelihood, which is what a per-author prior and an unfamiliar area affect, loses its gate and keeps its watch.

Cost is not a factor and not a strategy input. A cost term would have the score trade a gate or a control for money, which [_How it learns_](#how-it-learns) already refuses for the threshold: loosening it on cost alone is a judgment about what the factory is for, and the design hands that to the owner (8). The strategy is the same case: what a control costs is the owner's to weigh, and the levers are theirs — the [window limit](08-operations.md#overlapping-windows), the [fraction of its instances a release keeps](08-operations.md#overlapping-windows), and a [safeguard](09-gate-policy.md#one-shape-across-all-of-them) on the strategy — where model spend has a lever of its own in the [spend ceiling](10-fleet.md#a-spend-ceiling) an owner authors on a credential, which reaches nothing a control costs. The second reason is that there is nothing to calibrate a cost factor on: spend is recorded in the provider's units, which differ per model, so a factor over a fleet of two models would weigh units that do not add. What it costs: a large low-risk service pays a full control for every release the score gives one, and only a value an owner authored reduces it.

The defaults the score supplies where an owner authored nothing are not a fourth factor: [_Gate policy_](09-gate-policy.md#one-shape-across-all-of-them)'s eight parameters are each a field of the record its scope names — a service, an area, an environment, or the factory-wide settings record — and seven of them move as outcomes arrive, where the three factors are computed from one change. They are fields of a **score version** — a row of the [decision log](../deferred.md), appended by the log when the score calls for it and chained like every row there, naming the published formula, the factor set, and every value the score supplies, with a supplied value for seven of the eight rows and none for the [list of allowed predicate kinds](07-contracts.md#what-a-consumer-declares), which no outcome teaches. Every decision names the version in force. Keeping the supplied value here rather than in the record that holds the authored one is what leaves both single-writer, and it keeps a [safeguard](09-gate-policy.md#one-shape-across-all-of-them)'s floor distinguishable from the value moving inside it — one field two components wrote could not express that. The cost: a long sequence of versions, most differing in one number the decisions naming them never read, and a [value in force](09-gate-policy.md#one-shape-across-all-of-them) that is a read of three things rather than one.

A version that differs in a supplied value having moved takes effect as it is appended — gating each would gate the learning itself. A version that changes the published formula or the factor set is a different event, because what an owner authors is compared against the number the published formula returns: under a changed formula the same change gets a different number, so the authored value would go on being displayed while meaning something else, and an owner who set a [risk threshold](09-gate-policy.md#what-is-in-it) after an [incident](08-operations.md#incidents) would hold a number the score had silently redefined under them. So such a version does not decide a gate an authored threshold binds until the owner has confirmed or re-authored that threshold against it (8), the version in force at those gates staying the prior one meanwhile — the arrangement [_A role prompt or a skill_](03-gates/07-what-particular-gates-decide/09-a-role-prompt-or-a-skill.md) already gives a version nobody approved, which simply is not in force. What it costs: two score versions deciding at once while confirmations arrive, and an owner's silence keeping an improved formula out of force at their own gates indefinitely — the direction [_The interview_](02-intent-into-items/02-the-interview.md) already accepts for a silence that spends nothing.

The vector is recorded where it was computed and never recomputed. A gate firing writes it onto that firing's [_decision_](03-gates/01-where-a-gate-is-and-what-decides-it.md) beside the number, the score version, and the [policy version](../what-the-factory-does.md#traceability), so every firing produces a vector of its own. Where an agent authored what is under decision, the vector also names the effort its entry ran at and the versions of the role prompt and the [skills](10-fleet.md#what-an-agent-is-told) it worked from — the two facts the prior deliberately averages over, put where a human arguing with the number can see them, and where a query can group decisions by the version in force without any of it moving the prior. Recomputing one later reads today's prior, today's factor set, and today's formula — not the vector the decision was made on — and the vector a human argues with has to exist while they are deciding, which is why the decision is opened at the firing rather than at the verdict. At the four [artifact gates](03-gates/01-where-a-gate-is-and-what-decides-it.md) the change factor is computed from the artifact under decision and at [Decomposition](03-gates/07-what-particular-gates-decide/01-decomposition.md) from the set [decomposition](02-intent-into-items/03-decomposition/README.md) proposed, so it is weakest exactly where the decision is cheapest to get wrong.

A factor the score cannot compute resolves to the value that puts a human at the gate, and the vector records which factor was unavailable and why rather than leaving a gap a reader has to interpret. That covers an input the score could not read, a [build](05-environments.md#records-and-one-long-lived-branch) whose diff it could not take, and an evaluation that failed outright. The reason: the number is compared against a threshold, so a factor that silently reads as absent reads as low risk, and the gate a failure would remove is the gate that failure is evidence for needing. Nothing here decides how far the resolved value moves the number — that is the formula's, published like the rest of it — only its direction, which is the one thing that must not depend on a component being up. What it costs: a fault in whatever supplies a factor puts humans at gates across the factory at once, and from [_Work_](11-screens.md#work-ops-factory-people) that looks like the score having changed its mind rather than an outage; what says otherwise is the vector on each decision naming the same unavailable factor, which is why the naming is not optional.

## How it learns

The score is learned, not fixed. Every bad decision feeds back and refines it: an [auto-passed](03-gates/01-where-a-gate-is-and-what-decides-it.md) change that a human undoes (10), a low-risk change its analysis window rolled back, a gate the factory would have passed but a human rejected. Outcome feedback is the sharpest signal but not the only one — any source that improves the score is admissible, and the input set stays open.

A supplied value moves on both ends of its own row, and [gate policy](09-gate-policy.md#what-is-in-it)'s table is what says where the second end is: every row there states what goes wrong at each end, and both are evidence. One end is something going wrong — a rollback, a human's undo, a [crossing](08-operations.md#the-analysis-window) of the boundary the [health monitor](08-operations.md#the-health-monitor) could have seen and did not, an [item](01-one-pipeline.md) the [attempt limit](03-gates/05-the-attempt-limit.md) gave up on. The other is the parameter costing more than it returns, which is observable for most of them: attempts nothing has ever needed, a [cap](08-operations.md#the-analysis-window) far longer than any window of that service takes to resolve, a [window's size](08-operations.md#the-analysis-window) finer than its traffic can rule anything out at. Reading only the first end would make every value move one way and stay there, and a value that only tightens ends up costing what it was set to protect against — the clearest case being an [analysis window](08-operations.md#the-analysis-window) so fine it never resolves, watching every release for the whole cap and catching nothing.

Calibration also reads each factor's distribution over the decisions that named it, against that factor's own history. A factor whose distribution has moved is measuring something other than what the formula was calibrated on — an agent that learned what the factor rewards, an area whose shape changed, a fault in what supplies it — and outcomes alone discover that slowly, one release at a time against hundreds of decisions already taken. A factor found drifted takes the treatment [an unavailable factor](#factors-at-least) takes, resolved toward the gate and named on the vector, until the formula is recalibrated over it. What it costs is what that treatment always costs: a drifted factor puts humans at gates across the factory at once, and the vector naming it is what tells that apart from the score changing its mind.

Two of them have no second end here and are stated as such rather than left to be discovered. No outcome says [the confidence a comparison must reach](08-operations.md#the-analysis-window) was too high: what would show it is a rollback that turned out unnecessary, and the one thing that establishes a failed release was fine — a human [marking the rollback as not caused by the release](08-operations.md#overlapping-windows) — says the comparison was confounded, nothing about how confident it should have been, so it excludes the rollback from what learns and teaches the confidence nothing. And the other end of the [item-size target](02-intent-into-items/03-decomposition/README.md) is cost per feature and rework rate, both of which are [_Factory_](11-screens.md#work-ops-factory-people)'s to report and neither of which anything measures yet. Both are allowed to move one way because neither compounds — the traffic a comparison needs grows as the log of the confidence, where it grows as the inverse square of the size — so an owner may have to author over one of them, which [authoring being an override](09-gate-policy.md#one-shape-across-all-of-them) is exactly the case for.

The [risk threshold](09-gate-policy.md#what-is-in-it) is a third exception and not for want of an observable. Its own row states the loose end plainly — gate more and the human work the factory exists to remove comes back — and how often a row puts a human at it is a count, needing no outcome and no counterfactual. What it is not is evidence about safety, and the difference from the two above is the difference between protection gone worthless and protection gone expensive: a window too fine to resolve rules nothing out, so loosening it gives up nothing, where a human at a gate really does read the change and really does stop some of them. Loosening the threshold on its cost alone would be the score deciding that human review is not worth its price, which is a judgment about what the factory is for rather than a reading of what happened — and the design already answers a cost complaint the other way, by having the owner author the value (8). So the threshold moves down on outcomes and up on one thing only, which is the next paragraph.

Scoring on the author reinforces itself if left alone: a distrusted author is gated more, gated work draws more scrutiny, more scrutiny finds more faults, and distrust is confirmed. The factory holds out a random sample — auto-passing what it would have gated, under the longest analysis window there is — to keep unbiased signal on the authors and areas it has stopped trusting. How much it holds out is the **held-out sample rate**, authored with the rest of [gate policy](09-gate-policy.md#what-is-in-it) (8) rather than chosen by the score, for the reason every other bound there exists: the rate decides how often a change the score wanted gated reaches production with nobody at the gate, and a mechanism that sets its own rate of doing so is bounded by nothing. Where an owner authors none the score supplies it, the same division the [window's size](08-operations.md#the-analysis-window) uses, and a [safeguard](09-gate-policy.md#one-shape-across-all-of-them) (9) is a ceiling over it — sampling less is a human kept at a gate.

A held-out window that timed out is not evidence for raising a threshold. The sample exists to produce an outcome, and the exit that reports no outcome reports none here either: counting it as good would put back exactly what the sample was built to remove — an outcome recorded only for what the factory let through, this time as silence read as success. What that costs is the direction it leaves: a quiet service produces held-out releases that teach nothing, so on a service too quiet to close a window on evidence the threshold can fall and cannot rise — the ratchet [_How it learns_](#how-it-learns) already names in the other parameters, and the reason an owner may have to author over it.

The sample is also the only evidence there is for raising a threshold, which is more than the paragraph above asks of it. A change that was gated and turned out well is consistent with three things at once: it was never risky, the human at the gate caught what would have made it risky, or its author was more careful for knowing a human would read it — and no record tells those apart, so none of them is evidence the gate was unnecessary. What does tell them apart is a change the score wanted gated and did not gate, and the sample is the only thing that produces one. So a factory whose sample never selects has a threshold that can fall and cannot rise: it tightens on every outcome it gets wrong and never loosens on one it gets right, the same shape as a [window](08-operations.md#the-analysis-window) whose size only ever narrows. That is worth saying because the sample reads like a fairness mechanism for authors the factory has stopped trusting, and it is also the only reason half the calibration is possible at all.

The sample is the score's own to hold out of, and it reaches nothing an owner safeguarded. A safeguard (9) can only add, and a gate held always-on is a human added; a sample that could pass one would be the single mechanism in the design that removes a human from a gate — exactly what a safeguard exists to prevent. So what the sample may auto-pass is what the score itself would have gated on a vector it could compute — never the human [an unavailable factor](#factors-at-least) resolved to, the score being in no position to auto-pass what it could not read. The drawback: the areas an owner distrusts most are the ones it learns least about.

The selection is recorded on the decisions rather than as a set of its own, in two fields that must not be one. **Held out** says the score selected this [item](01-one-pipeline.md), written on every decision on it from the selection onward, so an item selected once auto-passes every gate the score itself would have gated — never one [an unavailable factor](#factors-at-least) resolved to a human — and reaches production with a human removed at each of them. **Why it auto-passed** says, at this firing, whether the auto-pass came from the number being under the threshold or from the selection, and reads threshold at a gate the score would have passed anyway. The health monitor runs the window to the [cap](08-operations.md#the-analysis-window) on the selection and not on the provenance, because what the sample is evidence about is a [release](06-releases.md#the-release-record) reaching production with a human removed somewhere above it. A held-out release also takes a strategy that keeps a [control](08-operations.md#the-health-monitor) wherever there is a build to start one from, whatever the vector's impact half would have picked: the sample exists to produce outcome evidence, and a deploy [without a control](03-gates/02-the-rollout-strategy.md) leaves only [the weak fallback](08-operations.md#the-health-monitor). What that costs: a second set of instances for a window that runs to the longest [exit](08-operations.md#the-analysis-window) there is, and a sample measured better than the population it represents — so its evidence supports that a comparison was available, not that an unsampled release on the same author would have shown the same. A service's first release has no control whatever the score prefers, so the sample cannot usefully select one.
