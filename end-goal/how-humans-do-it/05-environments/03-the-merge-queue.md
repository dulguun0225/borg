# The merge queue

Candidates verified in parallel cannot all fast-forward, because each was built on a master that has since moved. So merging is a queue: a candidate entering it re-verifies against master plus every candidate ahead of it, and fast-forwards only if that passes. A failure invalidates the speculation behind it, and those candidates re-verify against the master that actually resulted.

A candidate that fails its own re-verification — against the master that actually resulted, not against a speculation ahead of it — is rejected by the queue: the item [goes back up](../03-gates/06-going-back-up.md) [the pipeline](../01-one-pipeline.md) to Implementation, the queue naming no other stage and there being none between, and counts an attempt there against [_the limit_](../03-gates/05-the-attempt-limit.md) — the rework is real work, which is what the limit bounds. That is the stop the [Merge to master](../03-gates/07-what-particular-gates-decide/07-merge-to-master.md) gate can no longer give, having already approved, and without it a candidate failing here would have no path. Candidates behind a failure count nothing, for the same reason they re-verify without an attempt counted against them: they failed because of someone else.

That it failed on its merits is established rather than assumed, because a re-verification is never a repeat of the run that passed: the build is new and the environment recomposed, so a criterion that passed on the candidate environment and fails here changed its answer between two runs that differ, and what differed is on the record — each run's results name [the composition it was performed against](01-records-and-one-long-lived-branch.md), and each build its commit. Such a criterion is run once more, over the re-verification's own build and composition — once, and never until green. A repeat that disagrees is the disagreement over one build that makes a criterion [undecided](04-what-the-candidate-environment-decides.md), and the way back is authoring the criterion's encoding — the check [_Implementation_](../03-gates/07-what-particular-gates-decide/05-implementation.md) authors beside the code to decide it — again: the score learns from it the way it learns from a [reject](../03-gates/04-what-a-gate-may-change.md), an encoding that cannot hold its answer being a defect of the item's own build. A failure that repeats is real, and what the score learns turns on the two compositions. Where they match, the candidate failed against the master it will actually merge into, which is the queue doing its job, and the score learns as from a reject. Where a dependency's release moved between the runs, the score learns as from a [hold](../03-gates/04-what-a-gate-may-change.md) and the [per-author prior](../04-risk-score/01-factors-at-least.md) does not move: what changed is a release the author's work never saw, and a prior kept per model version and factory-wide would carry one moved dependency's noise onto every item that model authors. The rejection the queue writes into the log names which reading it was, and the moved release where there is one, so the one rejection [_Factory_](../11-screens.md#work-ops-factory-people)'s gate rejection rate cannot see is legible on the item's timeline in [_Work_](../11-screens.md#work-ops-factory-people). What this costs is one more run per disagreeing criterion and three exits where one stood. The attempt counts on every exit, so an item a moving dependency keeps rejecting still walks toward an [escalation](../03-gates/05-the-attempt-limit.md) — deliberately: work the environment will not let finish is work a human should see, and the limit bounds spend, which the rework is. What the three exits remove is the booking of that movement as the author's defect. On the third reading the attempt and the prior part ways — counted like a reject, taught like a hold, a combination no gate produces — because the two record different things: the limit what was spent, the prior who authored what failed, and here what failed is not what was authored.

The queue restores what one shared environment used to provide — the commit that was verified is the commit that merges. It costs compute on speculative runs that a failure ahead of them throws away, which is the better of the two: the shared environment imposed the same serialization on human time, and this imposes it on machine time.

Its order is settable, like the queue at any gate. Reordering changes when a candidate re-verifies, never what it has to pass. The settable order is one priority field of the item, written through [dispatch](../02-intent-into-items/05-dispatch.md) with [Work](../11-screens.md#work-ops-factory-people) as the caller, and it orders every queue an item waits in as an item — this one and the queues at the gates up to and including Merge to master. It orders nothing after the merge: numbered releases waiting to deploy are ordered by the release number and by nothing else, [_the revert a rollback is waiting on_](../08-operations/03-overlapping-windows.md) excepted. So an owner who rushes an item to the front here has rushed it at every gate it has left, and has no way to reorder a deploy — an urgent fix behind three numbered releases waits for them.

The queue is a component and not a record. Its membership is the items whose [stage](../02-intent-into-items/03-decomposition/02-what-an-item-names.md) says Merge to master approved them and whose fast-forward has not happened, its order is that priority and then the time of the approval in [the log](../../deferred.md), and its speculative re-verifications are its own state, read by nothing outside it. The two outcomes that outlast a run are records already: a fast-forward writes the release record, and a failure on the candidate's own merits is the rejection the queue writes into the log, with the queue as caller and actor and no decision opened — the arrangement stated where the candidate is said not to be a record. What that costs is that nothing records how long a candidate waited, so why something took a day is reconstructed from the approval time against the release record's own.

Master's head the queue reads from git, the system that holds it. Deriving it from the highest-numbered release record was refused because the two systems move at one event with nothing spanning them: a queue that stops between the fast-forward and the record write leaves a derived head one commit stale, and the next candidate would merge a change no release names inside its own release. The next number is a query and not a field — one above the highest among that service's release records, numbers never reused and a rolled-back release keeping its own, the queue's per-service ordering being what stops two candidates reading one — because a counter beside the records would be the same fact written twice at one event, and a lost counter write mints a duplicate.

Two things guard that query where the ordering cannot, because the ordering lives only in a running queue. A second release naming one service and one number is refused where the records are kept, so a duplicate mint is a failed write and never two releases answering to one name. And the fast-forward and the record write are one operation restartable from either side: the record is keyed on the commit, so writing it again writes nothing, and on start — every start, a crash and an upgrade of the self-hosted factory being the same stop — the queue reads master before it mints. A commit on master with no release record is the queue's own unfinished merge, and the queue completes it in master's order with the write the fast-forward already implied. The same reading is what makes records restored from a backup safe to start on, when every record since the backup is a lost write at once while git and the deploy targets roll back with nothing: the queue completes the records master's order still derives — master is linear, so the number a commit takes is its position — and mints nothing for any service while a commit's record cannot be derived, the item or build it named being among what the restore lost. That wait ends at a human, and what reaches one is not a page of the queue's own: the same restore leaves every deploy record behind what runs, which is a [mismatch](../08-operations/08-drift-detection.md) per service, and the mismatch pages and holds already. What this costs is that the queue reads two systems where it read one — git at every start and every mint — and that a restore holds every merge on a service until that service's history is whole again.
