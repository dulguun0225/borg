# What the candidate environment decides

[The graph](../../what-the-factory-does.md#tight-integration) is not uniform. Up to the merge, what moves is a candidate and deploys are plain — no strategy, no rollout, and no [_analysis window_](../08-operations/02-the-analysis-window.md), because a candidate environment has no organic traffic and a comparison computed from one human exercising a screen is noise that looks like evidence. What is not that comparison is a [quality criterion](../03-gates/07-what-particular-gates-decide/02-spec.md) decided under load its own encoding generates — an absolute reading under a condition the criterion states, decided here with the rest of the criteria and establishing nothing past this environment's hardware. What the environment decides is the criteria: the candidate runs on production-like infrastructure against the current releases of its dependencies, and every consumer contract is checked against it there, with the predicate-kind [constraints](../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md) in force decided against what the same run shows. A [store's](../07-contracts/09-the-store-is-a-contract-too.md) is checked the same way and against a state rather than an exchange — the store the run leaves behind, seeded as [_An environment per candidate_](02-an-environment-per-candidate.md) states and carrying the item's own schema change — so the reads and writes of every release a rollback could restore are decided here, before production rather than at the rollback. Deciding them is running the encoding [_Implementation_](../03-gates/07-what-particular-gates-decide/05-implementation.md) authored beside the code, and a criterion that fails is a rejection at the Merge to master gate on the same terms a consumer contract failing there is.

A criterion has a third outcome and it is not a kind of pass. An encoding that produced a failure and a pass over the same build decided nothing — what a repeated run measures is the repetition — so the criterion is **undecided** for that build, and undecided rejects the way a failure does. For a criterion the disagreement has one place to appear: [the queue's confirming run](03-the-merge-queue.md) is the only repeat over one build there is — a run over one build is otherwise something nothing performs twice — and it runs after the Merge to master gate approved, so a criterion goes undecided at the queue and is rejected there. What still reads at that gate the way a failure does is a [consumer contract](../07-contracts/06-what-a-consumer-declares.md) or a [store declaration](../07-contracts/09-the-store-is-a-contract-too.md) undecided by a path the run never exercised, whose disagreement needs no repeat. A predicate-kind constraint the run never exercised reads as nothing instead — it is a bound over what a run shows, never a claim every item must demonstrate, so an item whose run renders no screen is not stopped on a contrast floor it never touched. What that costs is that a departure no run has shown ships unchecked, caught at the first item whose run reaches it. Recording either as a pass is what would make the verdict rest on nothing, since a passing criterion is the whole of what that gate reads about the item's own behaviour. What it costs is that an encoding whose own defect has nothing to do with the change stops the item, and the way out is to author the encoding again rather than to run it again: retrying until green is available to nobody, the factory included, because the factory is what would otherwise do it at scale.

A run that could not be performed produced no outcome, this third one included, and what could not be performed is narrow: the environment failed to compose, or a dependency it needed was unreachable before the run began. A run that composed, started, and ended without the encodings finishing is not among them — the item's own service not answering is behaviour of the build, and its criteria fail as criteria — because reading a deterministic hang as an unperformed run would retry a real defect with nothing counting and nobody reaching it. For the narrow kind, nothing is recorded against any criterion, no attempt is counted, and the run is performed again: an absent input is not a failed check, the reading [an unavailable factor](../04-risk-score/01-factors-at-least.md) already gets, and performing it again is not the retrying refused above, nothing having been decided that a second run could contradict. A run that cannot be performed twice over stops retrying and waits — [a wait no gate could compute](../03-gates/04-what-a-gate-may-change.md), written into the log by the log with the deployer as caller and actor, counting no attempt and teaching the score nothing, read in [_Work_](../11-screens/01-work-ops-factory-people.md) like any other wait — and what ends it is the run performing. What it costs is that the wait is bounded by nothing but the dependency coming back, and at the queue it stands in that service's merge order while it lasts.

Merge to master is where a candidate becomes a release and gets its number. Everything from there is machine: numbering, strategy selection, rollout, monitoring, rollback.

The verdict is score-gated like every other gate, so it is not the last place a human decides and there is no last one: the same score decides at each gate whether a human decides there, and a safeguard (9) puts one back. Where one is there, what they are doing is [UAT](../../what-humans-do.md) (7) — the environment is no longer named for it, because in the steady state nobody is there. Where it auto-passes, the verdict is the factory's own, taken against acceptance criteria authored from a reading of the [intent](../02-intent-into-items/01-intake/README.md) that the person who asked confirmed at [the interview's last round](../02-intent-into-items/02-the-interview.md) — and confirmed as criteria by a human (6) only where the score or a safeguard put one at [Spec](../03-gates/07-what-particular-gates-decide/02-spec.md), which in the steady state it does not.

The alternative was to separate that verdict by origin — permanent for human-originated features, auto-passable for factory-originated fixes — and that is the second, invisible path the pipeline forbids, separated by a worse predictor than the score's own factors. Scoring it costs this: a change can reach production with nobody having watched it run. The analysis window covers half of that and says so: it catches a change that misbehaves, never one that behaves perfectly and is the wrong thing. What catches a wrong thing built well is the person who asked confirming the factory's reading of the intent at [the interview's last round](../02-intent-into-items/02-the-interview.md), which is not score-gated; the criteria, where the score or a safeguard put a human at the [Spec gate](../03-gates/07-what-particular-gates-decide/02-spec.md) to confirm them (6); end users (4, 5); and [a human undoing the change after it shipped](../../what-humans-do.md) (10) — and an owner who wants more adds it back per service or per area with a safeguard. Of the four, only the first is present on every item: the second is absent in the steady state, and the last two are after production.
