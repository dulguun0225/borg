# Records, and one long-lived branch

Environments are records, not names in code. One record type with a **kind** fixed at creation and three values — production, a deploy target a customer defines, and a [candidate](../06-releases/03-what-a-build-is-called-and-when.md)'s own. [Gate](../03-gates/01-where-a-gate-is-and-what-decides-it.md) thresholds, credential references, and the targets it is reached at are fields of both persistent kinds; the strategy default is production's alone, because a [strategy](../03-gates/02-the-rollout-strategy.md) decides whether a [control](../08-operations/01-the-health-monitor.md) runs and a control exists only where [organic traffic](../03-gates/02-the-rollout-strategy.md) does. A candidate's environment holds nothing an owner authored, being created at the gate that decides its deploy and so unable to hold the threshold deciding it. What it does hold is what no deploy can happen without: the targets the [deployer](../08-operations/01-the-health-monitor.md) created for it and the credential reference it reaches them with, both written by the deployer at creation rather than authored by anybody. An environment with neither is one nothing can deploy into, and keeping the two facts on the record rather than implied by the creator is what lets the same readers read all three kinds. Production exists everywhere, every candidate gets one of its own, and customers define more per [project](../11-screens/01-work-ops-factory-people.md).

An environment names its **targets**, plural — the addresses a deploy is performed against — and they are a field, not records of their own, so nothing holds a reference that must survive an address change: a [deploy record](../06-releases/05-the-deploy-record.md) is keyed by [service](../02-intent-into-items/03-decomposition/README.md) and environment rather than by target and carries completion per target as a field, a mismatch names the address that differs, and [_Drift detection_](../08-operations/08-drift-detection.md) reads each in turn. The cost is that an owner declares every target before the factory can deploy into that environment, and a target added at the provider and never declared is deployed to by nothing and read by the drift detector as nothing — a real target running old software named by no mismatch.

The kind is also the [seam](../../deferred.md), two writers never writing a record of the other's kind. An owner writes the persistent kinds on [_Factory_](../11-screens/01-work-ops-factory-people.md): production's at the creation of the project, which an owner does not choose because production exists everywhere, and each further one when they define it. The [deployer](../08-operations/01-the-health-monitor.md) writes a candidate's, creating it at the approval of [Deploy to candidate environment](../03-gates/07-what-particular-gates-decide/06-deploy-to-candidate-environment.md), tearing it down for good when the [item](../01-one-pipeline.md) merges, is dropped, or is superseded by a [re-decomposition](../02-intent-into-items/03-decomposition/README.md), and reclaiming one meanwhile as [_An environment per candidate_](02-an-environment-per-candidate.md) sets out — the only component that reaches a deploy target is the one that reaches environments, and a gate decides an event and edits nothing. What that costs is three creation paths for one record type, so every reader excludes the kinds it does not want, and a torn-down candidate record is kept rather than deleted because the deploy records naming it would otherwise point at nothing.

A persistent environment contains a project — every service in it — while a [release](../06-releases/02-the-release-record.md), a [release number](../06-releases/04-the-release-number.md), a master branch, and an [analysis window](../08-operations/02-the-analysis-window.md) are all per service. A deploy puts one service's build on one environment, so an environment fed by a twelve-service project has twelve independent promotion paths. A candidate's environment contains no project: it is composed for one candidate, which [_An environment per candidate_](02-an-environment-per-candidate.md) sets out. The [gate row](../03-gates/03-actions-at-each-gate.md) a customer's environment adds describes that environment; what fires is one [decision](../03-gates/01-where-a-gate-is-and-what-decides-it.md) per deploy into it. A customer's extra environments are deploy targets and not ordered stops — nothing makes a release pass through one before production, and the [production deploy gate](../03-gates/07-what-particular-gates-decide/08-deploy-to-production.md) gains no [hold](../03-gates/04-what-a-gate-may-change.md) on another environment's deploy. An owner who wants a human to look at a release running somewhere first adds a [safeguard](../09-gate-policy/02-one-shape-across-all-of-them.md) putting one at that gate (9). What that costs is that a staging environment enforces nothing: a release can reach production having never been deployed there.

Its history is not a field. The deploys that name a record are inbound edges, the arrangement the release record already uses, and [incidents](../08-operations/06-incidents.md) and [rollbacks](../06-releases/06-rollback.md) exist on production environments alone, because the [health monitor](../08-operations/01-the-health-monitor.md) that opens an incident and the strategy that keeps a control both attach to a production deploy and to no other. The cost is that a pre-production environment where something misbehaves has no record of it — what is written there is a rejected candidate or nothing.

One long-lived branch is each service's promotion path: master. A candidate has a branch of its own until it merges, is dropped, or is superseded by a re-decomposition. Merging and deploying are separate events and so are separate gates — a merge admits a change to master, a deploy puts a build on an environment, and either can happen without the other. A deploy can be rerun; a merge cannot be unmerged the same way.

A candidate is not a record. It names an item and the build currently in force for it, and a build on a candidate branch belongs to one item, so the pair and the build pick out the same thing — a record per pair would repeat what the build and the item say already. The [criteria](../03-gates/07-what-particular-gates-decide/02-spec.md) results and the candidate deploy attach to the build. The branch and the environment are the item's and persist across a rebuild, the environment being a record already. What that costs is that [_The merge queue_](03-the-merge-queue.md)'s rejection has no record of its own: no gate fires, so it is written into [the log](../../deferred.md) by the log with the queue as caller and [actor](../../deferred.md), the way [a wait no gate could compute](../03-gates/04-what-a-gate-may-change.md) is, and not as a [decision](../03-gates/01-where-a-gate-is-and-what-decides-it.md) — there is no firing to open a row at, the [Merge to master](../03-gates/07-what-particular-gates-decide/07-merge-to-master.md) gate's own having closed as an approval, and no [factor vector](../04-risk-score/01-factors-at-least.md) computed for it. It is counted as an attempt against [_the limit_](../03-gates/05-the-attempt-limit.md) at the [stage](../02-intent-into-items/03-decomposition/02-what-an-item-names.md) the item is sent back to. What that costs is that [_Factory_](../11-screens/01-work-ops-factory-people.md)'s gate rejection rate, being rejects over firings per gate row, does not see it: one of the three ways an item goes back is absent from the number an owner reads.

A **build** is a record, one per commit built, written by the deployer when it is called to build. Four callers: the implementation stage when it finishes, so the [Implementation gate](../03-gates/07-what-particular-gates-decide/05-implementation.md) decides over a build that exists and the [score](../04-risk-score/README.md) has a diff to compute the [change factors](../04-risk-score/01-factors-at-least.md) from; the candidate deploy where a rebuild is needed; the merge queue at [re-verification](03-the-merge-queue.md), which builds the candidate branch onto the master it will actually merge into; and the [search](../08-operations/03-overlapping-windows.md), whose builds are of commits on no branch, decided by no gate and bounded there rather than here. A rebuild is a new build, so an item has as many builds as it was built and the release names the last one — which is what makes the commit that was verified being the commit that merges a property of the queue. Every record naming a build says which: a gate decision names the one in force at the firing, a factor vector is computed from that same build, a [consumer contract](../07-contracts/06-what-a-consumer-declares.md) names the one it was derived from. The commit is a field of the build and not a record, one commit per build and nothing pointing at a commit that has no build. So is what the build resolved: every third-party package, the version resolved to, and the licence the package declares, written by the deployer from the build it performed, because a commit resolving an unpinned range on two days is two builds shipping two things, and the [advisory](../02-intent-into-items/01-intake/03-advisories.md) detector reads a shipped build's set and nothing else could say what it holds. The same set, diffed against the [current release](../06-releases/05-the-deploy-record.md)'s build's, is the dependency change the score's [exposure](../04-risk-score/01-factors-at-least.md) factor reads, and a licence policy is decided against it as a build-kind [constraint](../02-intent-into-items/01-intake/01-constraints-and-the-design-system.md); which services ship a package at a version is a query over current release, build, and set, and not an estimate. What the build costs is that a component named for reaching an environment is called once per item where no environment is reached, and that an item rebuilt four times leaves three builds nothing points at.

What a run on a candidate environment produced attaches to the build — each criterion decided, each consumer contract checked against the exchanges observed there, and the composition in force at the run, copied from the field [_An environment per candidate_](02-an-environment-per-candidate.md) has the deployer write, because that field is rewritten at a recomposition and what an earlier run ran against survives on the build or nowhere — written by the deployer when the run finishes, and not a record of its own: the identity is the build plus the criterion id, and which environment the run happened on is the item's, which the build names. The build could not name one itself — it is written when the implementation stage finishes, one gate above the approval that creates the environment. The producer's own [contract diff](../07-contracts/04-enforcement.md) is not among them. It needs no run and no environment, and a verdict stored at run time is not a check made when the gate fires, which is what [_Two baselines, kept apart_](../07-contracts/06-what-a-consumer-declares.md) requires. What is written is what was observed; what is decided is decided at the gate.
