# Releases

What ships, what it is called at each point, and how it is undone.

## One item per release

**One item per release. Always, at every stage, permanently.** The single timeline of an [item](01-one-pipeline.md) never splits: [rollout](08-operations.md#the-health-monitor) stays item-scoped like everything before it, and a human's [undo of a shipped change](../what-humans-do.md) (10) is the rollback of exactly one item rather than extracting one change from a set of ten. One exception, limited and named, and it runs in both directions: master is linear, so where analysis windows overlap a rollback undoes every release above its target, up to the [window limit](08-operations.md#overlapping-windows) — and the revert release that follows redelivers the ones that were only [skipped](08-operations.md#the-analysis-window), which were never failed and whose code is still on master. One deploy then delivers several items' changes, measured by one window against the restored build. What ships is still one item, and each half is bounded: the rollback by the window limit, and the revert's deploy by the [backlog cap](08-operations.md#overlapping-windows), which counts every release that deploy would deliver — the skipped ones and the ones merged while the revert is authored alike, merging not being held — and is the window limit until an owner separates them.

The cost is [an environment per item in progress](05-environments.md#an-environment-per-candidate), stated there. An environment added later follows the rule rather than changing it.

## The release record

A release is a record, and it is where [the graph](../what-the-factory-does.md#tight-integration) joins. It names what is known at the merge: the item that caused it, and the build and commit it is made of. The [contract versions](07-contracts.md#two-versioned-things) it publishes are not a field of it — they name the release instead, each carrying that release's own number, because ordering versions is ordering releases and answering "the version in force at release N" by reading release records would make every reader of a contract a reader of releases. A version that names the release cannot also be a column here without the same fact standing in two places, written at one event by one writer. So "the release names the contract versions it publishes" is an inbound edge, which is what every deploy of a release already is, and the cost is the one this record's single writer already carries: a reader asking what a release publishes indexes that edge rather than reading a field. The [gate decisions](03-gates.md#where-a-gate-is-and-what-decides-it) name the item and the build and never the release, whether they were written before it existed or, at the [production deploy gate](03-gates.md#deploy-to-production), after; every deploy of it to every [environment](05-environments.md#records-and-one-long-lived-branch) is written afterwards and names the release. Ask anything about a shipped change — from what [intent](02-intent-into-items/01-intake/README.md), on whose approval, under which [policy](09-gate-policy.md), running where, rolled back when — and the answer is reached by traversing edges at the release record, outbound or inbound. Traceability is not added to this; it is what the record is for.

[_The merge queue_](05-environments.md#the-merge-queue) writes it and mints the release number with it. Master's only inbound path is the queue, so the fast-forward is the event and the queue is what performs it, and the serialization that stops two merges taking one number is the per-service ordering the queue keeps already. A writer of its own, called at the fast-forward, would be a component with one caller and that ordering implemented again inside it. What this costs is release identity inside the queue's component, and no release record for a commit that reached master by another path — which nothing does, the queue's exclusivity being what makes that true.

It is written once and never written again, which is what keeps that one writer. The alternative was five — a [gate component](01-one-pipeline.md), the [deployer](08-operations.md#the-health-monitor), and the rest writing their links into it — which is five writers on the record the whole graph joins on and a [seam](../deferred.md) to declare between each pair, and writes to a release after it shipped. The cost of one is that where a release runs and which gates let it through are queries over the records that name it, so every reader asking either needs those inbound edges indexed.

## What a build is called, and when

What the same build is called at each point, and what is versioned beside it.

| Name | What it is | When it applies |
|---|---|---|
| **candidate** | an item plus its build — identity enough to deploy, test, and reject | from build until merge to master |
| **release** | the name a build has on master | from merge to master onward |
| **contract version** | semver, one per published interface — a compatibility promise | moves when the form that interface publishes moves — an element added, removed, or redeclared, and a [deprecation mark](07-contracts.md#deprecation) on one |

A build [the search](08-operations.md#overlapping-windows) calls for is not a third row: made by the deployer from commits master keeps, on no branch, it is never a candidate and never merges, so it takes neither name and is named only by the deploy record that carries it. A rejected candidate never needed a release number, and that is not a third row here either: it is a field of the release, minted at the same event, and [_The release number_](#the-release-number) is where it is set out. A build has one name at a time and the vocabulary stays at two, however many environments it runs on: a customer who defines five pre-production environments still has candidate and release, one build, and five deploy records — the names do not multiply with the environments.

## The release number

The **release number** is an ordinal, per service, assigned at merge to master. It orders builds and names rollback targets, and does no more; compatibility is the contract's business, not the release's. Numbers are never reused. A release that is rolled back keeps its number, and the fix that follows takes the next one. Never reused is enforced where the records are kept and not only by the queue: a second release naming one service and one number is a refused write, and how a number is minted — and re-derived where the queue stopped mid-merge or the records were restored from a backup — is stated at [_The merge queue_](05-environments.md#the-merge-queue).

A numbered release that has never run anywhere is normal, not an anomaly. The release number is minted at merge, one gate before production, so it records that a change was accepted — not that it is live. A [hold](03-gates.md#what-a-gate-may-change) at the production deploy gate produces exactly this. Where a release is running is a deploy record and never the release number.

Master's only inbound path is [_The merge queue_](05-environments.md#the-merge-queue), and a candidate fast-forwards only after re-verifying against the master it will actually merge into. The commit that was verified is the commit on master. What was tested is what ships — a structural property of the queue, not a discipline anyone has to keep.

## The deploy record

A service's **current release** is the one its production deploy record marks complete on every production [target](05-environments.md#records-and-one-long-lived-branch) — what is running, not what is newest. Merged-and-never-deployed being normal is exactly what makes those different facts, and every cross-service check reads the current one: an environment composed from its dependencies is composed from what runs, and a promise is kept by what serves it.

A deploy record is written by the [deployer](08-operations.md#the-health-monitor), the one component that reaches a deploy target, through seam 4 of [_Deferred, but not designed out_](../deferred.md), when the deploy starts, and its status advances to complete or rolled back per target: the record names the release it puts on the environment once, and beside each of the environment's targets whether that target has it yet. A revert's deploy also lists the releases it delivers — the ones the [hold](08-operations.md#overlapping-windows) was holding, whose code is in its build — a list beside the one release the record names, the shape [_Rollback_](#rollback)'s record already keeps for the releases it undid, so a release delivered by a later release's deploy is on a deploy record and not only on master; without that, [Ops](11-screens.md#work-ops-factory-people) reads those releases as merged and never deployed while their code is live. A deploy [the search](08-operations.md#overlapping-windows) calls for names the build and no release, there being none. What it names as the thing deployed is the build it put there, and the release where it is deploying one: [_Deploy to candidate environment_](03-gates.md#deploy-to-candidate-environment) fires one gate before the release number exists, so a record naming a release there would name one nothing had minted. Naming the build on every deploy is also what makes what is running comparable to what the record says: a target reports the build it is running and not the name that build has on master, which is a fact of this store and not of the target. Every reader of what is running reads the records that name a release, a [candidate environment](05-environments.md#an-environment-per-candidate) being a place where nothing is current. One rollout produces one, and [_Rollback_](#rollback) is a deploy event and produces its own. No agent performs a deploy: deploying is not a stage an agent is dispatched to, so the record's [actor](../deferred.md) is the deployer and never an agent — a program the factory runs and can check, where which model an agent is is only what its [fleet entry](10-fleet.md) says. What that costs is that an agent's [scope](01-one-pipeline.md) says nothing about a deploy target, so where a deploy may go is authored on the [environment record](05-environments.md#records-and-one-long-lived-branch) and never on an entry. What the record does not say is what share of traffic each build takes — that is the rollout's and its [_control_](08-operations.md#the-health-monitor)'s, and a deploy log recording every shift would scale with the schedule for a fact only the rollout reads while it runs.

A deploy that ships a schema change names it. The [store rule](07-contracts.md#the-store-is-a-contract-too) makes a breaking change three items, so what one deploy carries is one item's change, applied by the deployer to the service's store before the build takes any traffic, through the credential the [environment's record](05-environments.md#records-and-one-long-lived-branch) holds — the deployer is the only component that reaches a deploy target, and the store is reached the same way. The revert's deploy is the one deploy that can carry more: delivering releases that never deployed on their own, it applies each delivered release's schema change that no deploy applied, in release order, before its build takes traffic — without that, a migration's additive item delivered in the batch would leave its column on master and nowhere else, and the code shipped after it would write to a store that never gained it. The record says whether the change completed, so a schema change is on the trail an [incident](08-operations.md#incidents)'s links walk and never an unrecorded act. A change that fails to apply stops the deploy before any traffic shifts: no target is marked complete, the previous release stays current, and the failure stands on the record for [Ops](11-screens.md#work-ops-factory-people). That a change can stop halfway is survivable for the reason the store rule holds in both directions: of the three items, the added form is read by nothing until the code that migrates onto it ships, and the drop ran only once no [declaration in force](07-contracts.md#what-a-consumer-declares) named the old form — so a store between two forms is one every release a rollback can restore still reads and writes.

It is keyed by service and environment and not by [target](05-environments.md#records-and-one-long-lived-branch): one record names one release for the whole environment, and completion is a field per target on that record rather than a record per target. A record per target stays refused, because four records could each name a different release and each be right; one record with one release and completion per target cannot. What one record with completion per target expresses is the state the earlier shape could not: a deploy that reached three targets of four is a recorded partial deploy, the fourth target marked not yet complete, rather than an incomplete one caught as a mismatch after the fact. [_Drift detection_](08-operations.md#drift-detection) reads each production target against what the record marks for that target, so a target marked complete and serving the old build is a mismatch whether or not a window is open. Every cross-service reader reads completion per target and needs a rule for what current means while they differ, and the rule is the strictest: a release is current only once every production target is marked complete, and until then the previous release is. A consumer whose [declared dependency](02-intent-into-items/03-decomposition/README.md) is on three targets of four is held at [_Deploy to production_](03-gates.md#deploy-to-production) until the fourth lands, which is what stops one call in four reaching a producer without the [contract](07-contracts.md) form the consumer verified against. The cost is the wait on the slowest target, and that every reader of current release evaluates a rule over targets instead of reading one field.

Current is the highest-numbered release whose deploy completed and was not rolled back, and not the most recently started; the two disagree exactly while a rollout runs. Composing a dependent's [_candidate environment_](05-environments.md#an-environment-per-candidate) from the release still taking part of the traffic would verify it against a build that may roll back within the hour, and the dependency hold at [_Deploy to production_](03-gates.md#deploy-to-production) would admit a producer nothing is yet committed to. The number rather than the completion time is what orders them, because rollouts overlap and differ in length: the [strategies](03-gates.md#the-rollout-strategy) run from minutes to hours and the [score](04-risk-score.md) picks per release, so a short rollout completing while a longer one below it is still widening would make an older release current under a recency reading, and nothing later would move it — leaving every reader of that record wrong at once while production served something else.

A control started above a release runs the release [a rollback of it would return to](08-operations.md#overlapping-windows) — the newest release below it whose window closed without [failing](08-operations.md#the-analysis-window) it, past every release a rollback would descend past, and not the ordinal predecessor. The two coincide until something is failed and differ exactly after a rollback: master is linear, so the ordinal predecessor's build contains the change just failed, and a control on it would restart failed code onto organic traffic for the whole of the next window and measure the revert against the build it exists to remove. Defining both by one rule is what [_Overlapping windows_](08-operations.md#overlapping-windows) needs so that the build the comparison is made against and the build a rollback returns to are the same one, and neither is something the factory has already ruled out. What that costs is a dependent whose producer is mid-rollout waiting for it, which on a [widening schedule](03-gates.md#the-rollout-strategy) is the length of the rollout.

## Rollback

Rollback is a deploy event, not a version event: it shifts traffic onto the instances of [_the release it returns to_](08-operations.md#overlapping-windows), still running at full capacity, and writes a deploy record, minting and retiring no number. It applies no schema change either — the schema moves only forward, staying at the newest release's form however far traffic moves back, which is what the store's [forward promise](07-contracts.md#the-store-is-a-contract-too) exists to make survivable. It is not a record of its own — every field is on the deploy record already, and a second writer on the fact of what is running is the fact the drift detector exists to check. That record names the failed release as a field distinct from the list of releases the rollback undid, whose own deploy records the same event advances to rolled back on every target, a target the release never reached included, because the hold and the one-revert-per-failed-release rule both need the two apart. It also names a **source** beside its [actor](../deferred.md), the shape [intake](02-intent-into-items/01-intake/README.md) already uses: the [health monitor](08-operations.md#the-health-monitor) at the [failed](08-operations.md#the-analysis-window) exit, or the named human at [Ops](11-screens.md#work-ops-factory-people) with the reason they state. The actor stays the deployer that performed it. Which release that is is [_the rollback's target_](08-operations.md#overlapping-windows), and it is not always the ordinal predecessor — where windows overlap, the release below a bad one may still be under watch itself. Where the rollout kept no control, the same target is reached the slow way, by redeploying the build. That the restored build still works is not luck: [no item may break the store](07-contracts.md#the-store-is-a-contract-too) it runs on, and that rule applies in both directions and over writes as well as reads — what the newer release wrote while it was live is still readable by the one being restored, and what the restored one writes still lands, a constraint its declared writes would violate being a diff [the declarations in force](07-contracts.md#what-a-consumer-declares) rejected at the merge.

A revert is an ordinary item [decomposition](02-intent-into-items/03-decomposition/README.md) writes, from an intent intake wrote at the rollback — the health monitor calling intake at the failed exit, the named human at Ops calling it when they ask for one; "revert" names what raised its intent and nothing about the record. Nothing on the item says it is one, on the precedent that [the project is not a field](02-intent-into-items/03-decomposition/02-what-an-item-names.md) — the release it reverts is reachable through the intent's evidence, and a field would let the two disagree. One failed release is one revert item, and an owner undoing a whole [partly delivered intent](02-intent-into-items/04-when-an-intents-items-do-not-all-ship.md) asks for one intent decomposed into one revert item per shipped sibling. Where a failed exit finds no release to return to, no deploy record is written and the failed release keeps serving: the health monitor raises the revert intent itself and [pages](08-operations.md#pages) at that exit. Production is running a release the factory has just failed, and no mechanism the factory has will improve it — the [page condition](08-operations.md#pages) word for word, and the same one a target credential unreachable during a rollback already meets. The [escalation page](08-operations.md#pages) on the revert item is then a second reach on a state a human already knows about, rather than the first thing to reach anybody. It matters most where the owner bought the only detection there was: a service's first release cannot be [passed](08-operations.md#the-analysis-window) and is measured only where a [safeguard](09-gate-policy.md#one-shape-across-all-of-them) set an explicit threshold, so without this the human who authored that threshold gets no page from the crossing it caught.

Undoing a release whose window has closed is not a rollback. The instances of the release it would return to are gone, master keeps the change, and the correction is a revert — a new item, its own timeline, its own number. That is what the second phase of a human's undo (10) costs; the first is the rollback above, on a human's judgment instead of the health monitor's.

A service's first release has no target: nothing below it closed passed or timed out, no earlier build is running under it, and there is none to redeploy. A human's undo (10) begins at its second phase there, so the correction is a revert with no rollback before it. The drawback is that the cheapest undo the factory has is missing on the one release its [score](04-risk-score.md) knows least about.
