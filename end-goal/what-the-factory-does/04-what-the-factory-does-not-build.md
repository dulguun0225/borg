# What the factory does not build

The two properties above say what the factory is; this says what it is made of, and the record divides the two halves. Where a thing writes or keeps a record the factory has to be the only writer of, it is the factory's and this document describes it. Where a thing stores bytes, runs a process, moves traffic, or counts requests, it comes from outside and the factory reaches it. So nothing here reimplements a repository, a container runtime, a scheduler, or a store of numbers, and nothing outside decides anything the factory records.

| What comes from outside | What the factory does with it |
|---|---|
| **git** — one repository per [service](../how-the-factory-works/02-intent-into-items/03-decomposition/README.md), and the transport an agent clones and pushes through | Names the repository on the [service record](../how-the-factory-works/02-intent-into-items/03-decomposition/README.md), commits a candidate branch into it, and fast-forwards [master](../how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md) at [the merge queue](../how-the-factory-works/05-environments/03-the-merge-queue.md) |
| Somewhere to run a build or a test — a container runtime, or the host itself | Calls [the builder](../how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md) to build, and decides a [criterion](../how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/03-the-six-patterns.md) by running its encoding |
| Whatever runs instances on a [deploy target](../how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md) — a scheduler, or a host | Reaches it only through the named operations of seam 4 of [_Deferred, but not designed out_](../deferred.md), which is where policy attaches later, and reads back each pass how many [candidate environments](../how-the-factory-works/05-environments/02-an-environment-per-candidate.md) it holds against how many the records say |
| Whatever decides what fraction of arriving traffic reaches each of two builds | Picks [a rollout strategy](../how-the-factory-works/03-gates/02-the-rollout-strategy.md) the platform can perform, read from what the [environment record](../how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md) declares per target, every deploy going [without a control](../how-the-factory-works/03-gates/02-the-rollout-strategy.md) where none can, and names on the [deploy record](../how-the-factory-works/06-releases/05-the-deploy-record/README.md) the strategy it performed |
| Wherever the numbers [the health monitor](../how-the-factory-works/08-operations/01-the-health-monitor.md) reads are kept — a count and a histogram of durations per interval per closed set of names, the bucket boundaries fixed by the factory, and a count of [failure records](../how-the-factory-works/08-operations/01-the-health-monitor.md) per interval whose name set adds a failure class and a code location, every series naming the [emission version](../how-the-factory-works/08-operations/01-the-health-monitor.md) it was written at, all held for at least the span that section states | Instruments the software it writes so that it emits them, computes the comparison over them, and records on each pass the newest time the store holds |
| Wherever a build stays reachable after it was made | Names the artifact by digest on the [build](../how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md), and requires it reachable at least while its release could be a rollback's target — the floor [_Rollback_](../how-the-factory-works/06-releases/06-rollback.md) states as a shape |
| A store of published [advisories](../how-the-factory-works/02-intent-into-items/01-intake/03-advisories.md) against third-party packages, one per registry the services resolve from | Reads it on a pass of its own and matches each entry against what every service's current release resolved, raising an intent per advisory that matches |
| The models an agent runs on, the [effort](../how-the-factory-works/10-fleet/01-what-an-agent-runs-on.md) each runs at, and the credential each is reached with | Reads a [fleet](../how-the-factory-works/10-fleet/README.md) entry an owner wrote, and writes none back — where [what the agent is told](../how-the-factory-works/10-fleet/03-what-an-agent-is-told/README.md) is a record on this side of the division, written by the factory alone |

Everything on the factory's side of that division is what the rest of this document describes: the graph and the [append-only decision log](../deferred.md), [dispatch](../how-the-factory-works/02-intent-into-items/05-dispatch.md), the [gate component](../how-the-factory-works/01-one-pipeline.md), the queue's ordering and [the release number](../how-the-factory-works/06-releases/04-the-release-number.md), the score, [the analysis window](../how-the-factory-works/08-operations/02-the-analysis-window.md), the drift detector, and the [four screens](../how-the-factory-works/11-screens/01-work-ops-factory-people.md). No product supplies that set, and every part of it writes a record or decides one.

A host requirement crosses that division: the graph, the [report store](../how-the-factory-works/02-intent-into-items/01-intake/02-reports.md), and git make one **recovery unit**, backed up and restored together to a single **recovery point**. Restored apart, they would raise an ordering question: the graph could name a commit git does not yet hold, or git could hold a commit the graph has not yet recorded. One unit closes that question, since nothing in it is ever restored ahead of anything else it names. That the members landed at one point is checked rather than assumed: [_What the queue reads before it mints_](../how-the-factory-works/05-environments/05-what-the-queue-reads-before-it-mints.md) reads master against the release records at every start, and a service whose members landed apart is held there until master is whole. The store the health monitor reads stays outside the unit: it is read by time range and names nothing the graph has to hold first, so the ordering question never arises for it. Restoring it would also discard numbers production emitted while the factory was down, which the first mint after a restore reads to skip the numbers the restore lost. The drift detector's own store stays outside too, the owner's to keep separately or not at all, because a store no factory component may write is not the factory's to restore either. A restore that leaves its recorded head ahead of the graph is the mismatch [_Drift detection_](../how-the-factory-works/08-operations/08-drift-detection.md) already names, cleared there by a human. The start after a restore is the [install event](../deferred.md) the log already records, naming the actor who ran it. The snapshot [_One process_](../one-process.md) has an upgrade's first start take before it removes anything from the factory's own store is not a recovery point of the unit: an upgrade touches that store alone, and what a restore to that snapshot costs is stated there.

A forge — one product that is repository host, review tool, pipeline, and registry at once — has parts on both sides of that division, which is why the factory neither adopts one nor rewrites one. Two of its parts are rows above: the repository, and somewhere to run a build. Its other parts are records here — a review is a gate decision with an actor, a policy version, and a score version on it; what may reach master is the queue's exclusivity rather than a rule configured per repository; and what a [stage](../how-the-factory-works/01-one-pipeline.md) does is the pipeline. Taking those would put a decision in two stores, which the log refuses for the reason it has one writer, and the two would disagree the first time either was read alone.

What that costs is that everything a forge supplies around a repository is neither built nor bought, with one exception. [_Work_](../how-the-factory-works/11-screens/01-work-ops-factory-people.md) shows an item's artifacts on a timeline, so a human confirming criteria (6) or performing [UAT](../what-humans-do.md) (7) reads those and not code. At the one gate whose artifact is the code, [_Implementation_](../how-the-factory-works/03-gates/07-what-particular-gates-decide/05-implementation/README.md), Work renders the build's diff against master, read from the repository and written nowhere: a diff is bytes the repository already holds, outside the division above, and rendering it is a read like the clone an agent makes. It is built because the alternative was a human deciding over material the product would not show them, approving or rejecting with feedback they had no basis to write, and the actor field recording a human decision over what no human read. What it costs is one part of a forge built after all. Nothing administers a repository either — creating one and holding write access to it is part of hosting the factory, [substrate](../what-humans-do.md) rather than one of [the twelve duties](../what-humans-do.md).

What the factory reads about that is one field. An owner marks the service [provisioned](../how-the-factory-works/02-intent-into-items/03-decomposition/README.md) once the repository exists with the factory holding write access and the service's store exists on every persistent environment, and until then an item on that service waits at dispatch and at both deploy gates rather than failing a stage against a repository that is not there.

Master's only inbound path being the queue rests on how the repository is administered, not on a record. What refuses another push to a plain repository is who holds write access to it, where a forge would refuse one by configured rule, and the factory refuses none itself. What it reads is the evidence: [_What the queue reads before it mints_](../how-the-factory-works/05-environments/05-what-the-queue-reads-before-it-mints.md) compares master against the release records at every start and before every mint, and a commit there that no build of an approved candidate names is one the queue did not make, told from its own unfinished merge by the records. Such a commit holds the service's merges until a human returns master or accepts the commit, and an accepted one ships as a release naming no item, so the claim that what was verified is what ships is read off each release rather than off who holds write access. On a repository where humans can also push, the exclusivity holds by convention, and what the factory can tell is whether it held.

Where a service runs also differs per install, so two installs of one product do not measure alike. [_The rollout strategy_](../how-the-factory-works/03-gates/02-the-rollout-strategy.md) states one half of that already — which strategies a service can take is bounded by where it runs — and the health monitor is the other half: numbers reaching no store the factory can read leave a pipeline that ships changes and measures none of them.

The factory is for services of one shape: instances on a deploy target the deployer reaches, taking [organic traffic](../how-the-factory-works/03-gates/02-the-rollout-strategy.md), emitting one record per request served, replaceable one at a time, returnable by shifting traffic. A mobile or desktop application, a firmware image, a library, a CLI, and a scheduled pipeline are refused at [adoption](../how-the-factory-works/02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md) and at decomposition, the refusal stated with its reason: the operations half is the product, and a deliverable it cannot measure would be reported as shipped and measured. What that costs is a customer bringing one of those shapes told no at the door, which is the cheaper place to hear it.
