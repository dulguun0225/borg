# Traceability

**Traceability is the second**, the testable form of the first: every artifact links back to the intent that caused it and forward to what it produced, under the [policy](../how-the-factory-works/09-gate-policy/README.md) and score in force at the time.

Testable is what keeps it from being a discipline anyone has to maintain: it holds where a question is answered by following links, and fails where an answer has to be reconstructed. Two records supply those links — the [intent](../how-the-factory-works/02-intent-into-items/01-intake/README.md) every item points back to, and the [release record](../how-the-factory-works/06-releases/02-the-release-record.md) linking the item, the build, the gate decisions, the [contract versions](../how-the-factory-works/06-releases/03-what-a-build-is-called-and-when.md), and every deploy. An [incident](../how-the-factory-works/08-operations/06-incidents.md) is the same links followed from the other end.

A link back to the intent does not say which part of a request went unanswered. A third link runs the other way and does: the intent carries the reading the requester confirmed as a set of [requirements](../how-the-factory-works/02-intent-into-items/02-the-interview.md), one statement each, and every [acceptance criterion](../how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/03-the-six-patterns.md) names the requirement it answers. Which criteria answer a statement is then a query, and so is which statements no criterion answers, which is what an intent's completeness is read from. [_Decomposition_](../how-the-factory-works/02-intent-into-items/03-decomposition/README.md) and [_Spec_](../how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/03-the-six-patterns.md) are where that second query is a rejection rather than a reading.

_In force at the time_ is the harder part, because policy and score both change: an owner re-authors [gate policy](../how-the-factory-works/09-gate-policy/README.md), and the score is [learned from every outcome that arrives](../how-the-factory-works/04-risk-score/02-how-it-learns.md). A decision read back against today's values is not the decision that was made, so each decision record names the [policy version](../how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md) and the [score version](../how-the-factory-works/04-risk-score/01-factors-at-least.md) it was decided under, next to [the actor](../deferred.md) and for the same reason — no such field can be added to a history written without it. Both versions are rows of the [log](../deferred.md) the decision is a row of, chained like it, so a version rewritten after the fact breaks the chain rather than silently moving what every decision naming it is read against.

What traceability rules out is any action that skips a record. A human who wants different code [authors it upstream](../how-the-factory-works/03-gates/04-what-a-gate-may-change.md) rather than patching one at a gate, an emergency is [approve now rather than skip](../how-the-factory-works/01-one-pipeline.md), and undoing something already shipped is a [rollback](../how-the-factory-works/06-releases/06-rollback.md) while its [control](../how-the-factory-works/08-operations/01-the-health-monitor.md) is still running or a [revert item](../how-the-factory-works/06-releases/06-rollback.md) after. Every shortcut is an item — that is what keeps the links unbroken.
