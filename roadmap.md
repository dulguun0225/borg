# Roadmap

The order the factory is built in — milestones from an empty repository to the state [`end-goal/`](end-goal/README.md) describes. Each milestone is named by what becomes true when it is done, and each states its demonstration, which is what makes it a milestone rather than a phase. This file records order and never progress: nothing here says which milestone is current or how far along it is — the commit history is the record of what has been built. A milestone's section grows task-level detail only while it is the next one; every later milestone stays a paragraph, because a detailed plan for the sixth is guesswork.

The factory is built as ordinary software and does not run its own pipeline over itself, so no milestone below is the factory building the factory. M9 is not an exception: what an agent is told is a record decided at a gate, never an [item](end-goal/how-the-factory-works/01-one-pipeline.md) with a build and a release, so the factory authoring its own role prompts is the factory writing a record and not the factory shipping software to itself.

Two facts from the design set the order. The five seams of [_Deferred, but not designed out_](end-goal/deferred.md) — an actor on every record, one append-only decision log with each record chaining its predecessor, secrets by reference, a named seam between the deployer and deploy targets, and a principal on every call — cannot be added to a history written without them, so they come before anything that writes a record. And tight integration is the product — [one graph](end-goal/what-the-factory-does/01-tight-integration.md), not a bundle — so the first shipping milestone is the thinnest end-to-end path through the whole loop, every part shallow, rather than one subsystem built deep. What that order costs: the first milestone ships nothing a user can see, and every part the thin path touches is rebuilt deeper in a later milestone.

Security hardening is not a milestone here: [_Deferred, but not designed out_](end-goal/deferred.md) sequences it away, and this file inherits that. Adopting an existing codebase is not one either, for the opposite reason — it is not a mechanism of its own but the pipeline run on a service that already exists, per [_A service that already exists_](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md), so the first service M1 ships is an adopted one and M4 measures an adopted service's first release against what was running.

## M0 — The graph and the log

The record graph exists and the five seams are in it from the first record: the actor field on every record, the append-only decision log with its chain, one resolver behind which every secret is a name, the named operations a deploy target is reached through, and a principal on every call that reaches the resolver or those operations. One writer per record. Demonstrated by writing records through each seam and reading the chain back unbroken. This milestone ships no software; it exists because none of the five can be retrofitted.

M0 through M4 carry task-level detail; the sections below them stay a paragraph each. M0's is kept rather than trimmed once it is built, because the reason the rule gives for holding detail back — a detailed plan for the sixth milestone is guesswork — is not a reason to delete a plan that was carried out, and removing it is the one edit here that would say which milestones are done.

The stack, decided 2026-08-17: Go, because an import cycle is a compile error and the ecosystem leans on neither reflection nor DI containers; PostgreSQL from the first record, because the owner expects the project to need it and starting there means the chained log is never migrated; `pgx` directly, with no abstraction layer between the code and the SQL. Code lives in `factory/` under the rules the root [`CLAUDE.md`](CLAUDE.md)'s _Code_ section sets. Already in place: `mise.toml` pinning the toolchain, `factory/go.mod`, and `factory/docker-compose.yml` running the dev database on port 5433.

One package per seam, each owning its schema, its writer, and its `doc.go`:

| Package | What it owns |
|---|---|
| `record` | The graph's conventions: the actor — kind human or component, plus a name, never empty — ID generation, and the columns every record table carries |
| `decisionlog` | The chained log: one table, one writer type, three explicit append methods for the three shapes, and a `Verify` that walks the chain and names the first break |
| `secretref` | A reference type and a resolver reading one file on disk; nothing downstream stores a value |
| `targetseam` | The named operations an agent reaches a deploy target through — `Deploy`, `Stop`, `ReadRunning` to start, each later addition explicit — as an interface plus a fake; nothing real behind it yet |
| `postgres` | Opening the pool and applying each package's DDL; no ORM and no migration framework |
| `cmd/depscheck` | Failing the build on a package dependency `factory/deps.txt` does not allow |

Decisions inside `decisionlog`, taken so the demonstration holds: the payload column is text rather than JSONB, because JSONB normalises what it stores and the chain hashes exact bytes; the timestamp is text for the same reason — RFC 3339 UTC, written by the writer, because a hashed field has to read back byte-identical. A decision row names the policy version and score version it was decided under, the other two shapes refuse both, and a CHECK constraint enforces it in the store as well as in the methods. Appends serialise on one advisory lock, which is the one-writer rule enforced rather than assumed. How a verdict joins the chain is not decided here: M0 appends whole records, and the shape a decision takes belongs to the milestone whose first gate fires.

The demonstration is `go test ./...` against the compose database: append all three shapes and read the chain back unbroken; tamper with a middle row by raw SQL and `Verify` names the broken link; every record carries an actor; a resolved secret's value appears in no record; the fake target records the named operations called on it. CI (`.github/workflows/factory.yml`) runs `go vet`, `depscheck`, and the tests against a PostgreSQL service. M0 is done when all of that passes on a fresh clone.

## M1 — One change ships

The thinnest end-to-end path through the whole loop, every part the shallowest version that completes it. An [intent](end-goal/how-the-factory-works/02-intent-into-items/01-intake/README.md) is taken in, a minimal [interview](end-goal/how-the-factory-works/02-intent-into-items/02-the-interview.md) refines it, [decomposition](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md) yields one [item](end-goal/how-the-factory-works/01-one-pipeline.md), an agent produces the change against a [spec](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/README.md) of one criterion, one [gate](end-goal/how-the-factory-works/03-gates/01-where-a-gate-is-and-what-decides-it.md) fires with a human deciding — the [score](end-goal/how-the-factory-works/04-risk-score/README.md) is a stub whose answer is always that a human decides — merge assigns the [release](end-goal/how-the-factory-works/06-releases/03-what-a-build-is-called-and-when.md) its ordinal, a deploy [without a control](end-goal/how-the-factory-works/03-gates/02-the-rollout-strategy.md) ships it, and the [release record](end-goal/how-the-factory-works/06-releases/02-the-release-record.md) links all of it. Demonstrated by following the links from the deploy back to the intent with no step reconstructed. The service is one that already exists — a repository with software running from it — so the thin path is also the first run on software the factory did not build, per [_A service that already exists_](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/01-a-service-that-already-exists.md). The interface the human decides through is whatever is cheapest — the four screens come at M7, and a crude interface until then is what deferring them costs.

How a verdict joins the chain was the one question gating this milestone, and it is decided: a [decision](end-goal/how-the-factory-works/03-gates/01-where-a-gate-is-and-what-decides-it.md) is two rows, an open event appended when the gate fires so the human has the [factor vector](end-goal/how-the-factory-works/04-risk-score/01-factors-at-least.md) to argue with, and a close event naming it and carrying the verdict. So `decisionlog` gains what M0 did not need — a field saying which of the two a row is, the versions required on an open event and refused on a close event, and the CHECK constraint that enforces it in the store — and that is the first task of the gate, not a change to a milestone already built.

One package per record, each owning its schema, its writer, and its `doc.go`, and each the shallowest thing that completes the path:

| Package | What it owns |
|---|---|
| `intent` | The intent, its source and statement, the refinement state and the round count, and the questions attached to it — intake being the one writer of all of them |
| `service` | A service's identity and its repository, written at decomposition and by nothing else |
| `item` | The item — its intent, service, and branch — written once by decomposition, and the stage, attempts, and spend that dispatch writes after |
| `artifact` | The artifact store: an artifact's version chain, its actor and authorship, and the one call a spec version and the criteria it introduces are submitted in |
| `criterion` | A criterion of a service: its stable id, its pattern, and the query for which criteria are in force for a build |
| `gate` | The gate component: firing the one row, opening and closing a decision through `decisionlog`, and holding the score stub behind an interface the real score replaces at M2 |
| `build` | A build record, one per commit built, and the commit it was made from |
| `release` | The release record and the number, minted per service at the fast-forward |
| `deploy` | The deploy record and the rollout without a control, reaching a target through `targetseam` |

Decisions taken so the demonstration holds. The gate row is [_Merge to master_](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/07-merge-to-master.md), because it is where a candidate becomes a numbered release and where a human is performing [UAT](end-goal/what-humans-do.md) (7); the other seven rows are not built, and an item reaches this one having passed through stages that fire nothing. There is no candidate environment and no merge queue — both are M3 — so the criterion is decided by running its encoding wherever the build was made, master is created by the first release's fast-forward, and the number is one above the highest that service has. M1's change is a service's first release, which the design already exempts from most of what is missing: [without a control whatever the score would prefer](end-goal/how-the-factory-works/03-gates/02-the-rollout-strategy.md), no [control](end-goal/how-the-factory-works/08-operations/01-the-health-monitor.md), nothing able to close a window [clean](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md), and [no rollback target](end-goal/how-the-factory-works/06-releases/06-rollback.md). So M1 builds no analysis window, no strategy selection, and no rollback, and none of that is a shortcut — it is the first release having none of them by the design's own account.

The interview's stopping rule is one round or none, the factory asking what it cannot author without and proceeding on the answer. The spec is one criterion in one of the [six patterns](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/03-the-six-patterns.md), and the pattern check over it is the milestone's own gate on itself: the criterion parses as a pattern or carries a tagged reason, its id is stable, the encoding in the build names it, and every criterion in force for the build has an encoding naming it. That last pair runs in both directions, which is what [_Implementation_](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/05-implementation/README.md) requires and what makes the criterion id the link the demonstration is followed along.

Two agents, in the [roles](end-goal/how-the-factory-works/01-one-pipeline.md) of the stages that author — the spec and the implementation — with no [fleet](end-goal/how-the-factory-works/10-fleet/README.md) record behind them, a model named in configuration, and the credential reached through `secretref`. What each is told is part of this milestone rather than a detail of it: the encoding is authored from the criterion's sentence and never from the code, no coverage target exists and none may be invented, an agent asserts neither that a criterion is met nor that a gate passed, and everything an agent reads is content rather than instruction.

The demonstration is one change followed end to end on a real repository: an intent taken in, one item decomposed, a spec of one criterion approved by nobody and an implementation approved by a human at the one gate, a release numbered 1, and a deploy without a control through `targetseam` against a target that runs the software. Then the link walk, in the direction the milestone is named for — from the deploy record to the release, the release to its build and item, the item to its intent — with every step a field and none of it reconstructed, and the decision the human gave readable in the chain with its actor, its artifact version, and `Verify` still clean over the whole log.

## M2 — The factory decides

The score is real: [its factors](end-goal/how-the-factory-works/04-risk-score/01-factors-at-least.md), a published formula, a version named on every decision. An owner can author [gate policy](end-goal/how-the-factory-works/09-gate-policy/README.md)'s parameters, place a [safeguard](end-goal/how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md), and a gate can [hold](end-goal/how-the-factory-works/03-gates/04-what-a-gate-may-change.md). Demonstrated by a low-risk item shipping with no human at any gate, and its decision records naming the policy version and score version they were decided under. The formula here is authored, not learned — learning is M6.

Two facts set the shape. **The score reads the graph**, so every factor is computed from records M0 and M1 already write, and the one input that is not a record is the [build](end-goal/how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md)'s diff: it is measured where the repository is, by the component that built, and handed to the score with the ids. It is not stored, because the [vector](end-goal/how-the-factory-works/04-risk-score/01-factors-at-least.md) computed from it is — a diff re-taken later, against a repository other items have merged into, is not the diff the decision was made on, and the design already forbids recomputing a vector. **Every value an owner authors is a field of the record its scope names**, so this milestone creates the records those fields need before it can claim a parameter is authorable: the [area](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/02-what-an-item-names.md), the [environment](end-goal/how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md), and the [factory-wide settings](end-goal/how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md) records all arrive here, ahead of the milestones whose mechanisms read what is on them.

Seven packages, each owning its schema, its writer, and its `doc.go` — `gatepolicy` owning no table, the way `record` owns none:

| Package | What it owns |
|---|---|
| `gatepolicy` | The vocabulary of everything an owner authors: the parameters, what each value means, the record its scope names, and the direction a safeguard on it points. It is what `safeguard` and `policy` would otherwise each keep a copy of, and it is where the seven rows are eight parameters — the window's size and confidence being one row bounded in opposite directions |
| `score` | The score version — one append-only record naming the published formula, the factor set, and every value the score supplies — the eight factors of the design's three groups, and the assessment a [gate](end-goal/how-the-factory-works/03-gates/01-where-a-gate-is-and-what-decides-it.md) fires with: the vector, the likelihood and impact halves kept apart until the last step, and the number the formula reduces them to |
| `policy` | The one writer every authored value and every safeguard goes through, which is [Factory](end-goal/how-the-factory-works/11-screens/01-work-ops-factory-people.md)'s; the policy version it appends in the same transaction as the write; the seven parameters and the safeguard direction each takes; and the effective value as a read of three things — what an owner authored, what the score supplies, and the safeguards in force |
| `safeguard` | The safeguard record — its subject, the parameter it binds, its direction, its bound, and whether it has been withdrawn — and the query by subject that every mechanism a safeguard binds now runs |
| `area` | The area record: an owner's grouping, the area it lies inside, and the [item-size target](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md) authored on it |
| `environment` | The environment record — production alone here, the [candidate](end-goal/how-the-factory-works/06-releases/03-what-a-build-is-called-and-when.md) kind being M3 — its targets, and the [risk threshold](end-goal/how-the-factory-works/04-risk-score/README.md) authored on it per gate row |
| `factorysettings` | The factory-wide settings record: the [attempt limit](end-goal/how-the-factory-works/03-gates/05-the-attempt-limit.md) per stage, the [list of allowed predicate kinds](end-goal/how-the-factory-works/07-contracts/06-what-a-consumer-declares.md), and the threshold [_A role prompt or a skill_](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/09-a-role-prompt-or-a-skill.md) reads |

Five packages M1 built change, and each change is what the score or the policy needs from a record it does not own. `gate` gains its second row — Deploy to production, which is where [hold](end-goal/how-the-factory-works/03-gates/04-what-a-gate-may-change.md) is an action — the real score behind both rows, the threshold read through `policy`, and an open event naming the values actually applied. `service` gains the four parameters an owner authors on it, written by an owner and never by decomposition, which is the seam the record already declares. `item` gains the area decomposition writes, because a safeguard drawn on an area reaches the item and the item-size target is per area. `artifact` gains the author — the model version for a version an agent wrote, the human's name for one a human wrote — because a [per-author prior](end-goal/how-the-factory-works/04-risk-score/01-factors-at-least.md) is kept per model version and is computed from that author's own work, which is not answerable from a record that names the role and not the model; that is the one edit this milestone makes to `end-goal/`, in [_One pipeline_](end-goal/how-the-factory-works/01-one-pipeline.md). `deploy` names the environment by the record's id rather than by the name M1 wrote there, the record now existing.

Decisions taken so the demonstration holds.

**What each factor reads, and what it costs.** The change group is computed from the diff and the records around the build: **size** from the lines the diff changes, **reach** from the share of the service's files it touches, **area churn** from the [releases](end-goal/how-the-factory-works/06-releases/02-the-release-record.md) minted in the item's area lately, **test coverage** from the criteria in force for the build and their results, and **reversibility** from whether the service has a release to return to. The authorship **prior** and the context group's **business area** are computed from the outcomes in [the log](end-goal/deferred.md) on that author's artifacts and on that area's items, and **consumers** is a query over what other services declare they consume, which returns none because nothing declares anything until M5. Two of those are thin in ways worth stating rather than hiding: reach reads the share of one service's files and knows nothing of the sibling services M5 introduces, and a coverage figure in the sense of lines executed is measured by nothing here — what the factor reads is how many criteria decided the build, which is the protection the factory actually has. None of the eight is unavailable on the path this milestone walks, which is what makes the demonstration reachable at all: a factor the score cannot compute resolves to the value that puts a human at the gate, and the published formula is what carries that direction — a vector with any factor unavailable reduces to the top of the scale, so one absent input gates the change however low the rest of it reads.

**Empty evidence is a wide value and not an unavailable factor.** The prior and the business area both start wide for an author or an area the factory has not seen and narrow as outcomes arrive, which is what the design says the prior does, and treating an empty history as unavailable instead would put a human at every gate of a new install forever — a decision nobody made arriving as a side effect. What narrows them here is a human's verdict and nothing else: a [window](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) closing without failing a release is M4, and an auto-passed decision is the factory agreeing with itself rather than evidence about the author. That is also the milestone's sharpest cost — a prior narrowed by human verdicts stops moving once the factory stops putting humans at gates, which is the self-reinforcement [_How it learns_](end-goal/how-the-factory-works/04-risk-score/02-how-it-learns.md) holds out a random sample to break, and the sample is M6. Nothing here records a held-out selection, because nothing selects one.

**The formula is published, authored, and calibrated so that the first item on a service is not the one that auto-passes.** Each factor resolves to a level between nothing and one against breakpoints written in the source; the likelihood half is the weighted mean of size, churn, coverage, and the prior; the impact half is the weighted mean of reach, business area, and consumers; reversibility discounts impact rather than joining either half, because the [rollout strategy](end-goal/how-the-factory-works/03-gates/02-the-rollout-strategy.md) reads impact against reversibility and reading them separately is what keeps the two from weakening together; and the last step scales the discounted impact by the likelihood without letting a low likelihood dissolve a high impact. The calibration is authored to a factory that has just been installed, where a service's first release has no release to return to, an author nobody has approved yet, and an area with no history — that item reads high and a human decides it, and the item after it, on an author one human has approved, reads low and nobody does. So the demonstration is two items rather than one, and it says something the design says about itself: the factory earns the autonomy rather than starting with it.

**Two append-only version records, one per side of what a decision is decided under.** The score version names the published formula, the factor set, and the value the score supplies for six of the seven parameters — none for the list of allowed predicate kinds, which no outcome teaches — and the score appends a version when what it publishes stops matching the newest one, which is one row here and the mechanism M6 moves. The policy version is Factory's, appended in the same transaction as every authoring write and every safeguard, and the version in force is the newest row. It names the parameter, the subject, and what was done rather than restating the value: the value is the field on the record the subject names, one fact in two places could disagree, and what a decision was decided under is the effective values its own open event carries. What that costs is that reading a policy version back tells a reader which write it was and not what the whole policy said, which is answerable only by replaying the writes.

**The effective value is a read of three things, and four of the seven parameters have no reader yet.** An owner authors on the record the scope names, the score supplies where the field is empty, and a [safeguard](end-goal/how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md) clamps the result — a ceiling caps it, a floor raises it, a safeguard never replaces a value already narrower than itself, and a safeguard on the risk threshold is a human added rather than a number changed. All seven resolve and all seven are tested that way. Only two are read by a mechanism this milestone builds: the risk threshold, at both gate rows, and the attempt limit, by the stages that retry. The item-size target waits for a decomposition that sizes anything, the list of allowed predicate kinds for M5, and the window limit and the window's parameters for M4 — so an owner can author four values that change nothing yet, which is the cost of the parameter being a field of a record that has to exist before its mechanism does.

**Two gate rows, and the hold that comes with the second.** Merge to master is M1's; Deploy to production is added because hold is an action at the deploy rows and nowhere else, and the candidate deploy row needs the environment per candidate that is M3. Both rows read production's environment record for their threshold, which is the rule the design gives for all eight. A hold a human sets is that firing's verdict, leaves the event queued with the change still good, counts no attempt, and teaches the score nothing — the three things that separate it from a reject. The factory's own hold has no condition to compute here: an open window, a dependency that is not current, a rollback whose revert has not shipped, and a [checker](end-goal/how-the-factory-works/08-operations/08-drift-detection.md) mismatch are all records later milestones write. Safeguard the strategy, the row's third action, is refused with its reason: a target that runs a release as a local process moves a process rather than traffic, so the strategy that keeps a [control](end-goal/how-the-factory-works/08-operations/01-the-health-monitor.md) is unavailable on this substrate and every deploy goes without a control — the exemption the design already states for a substrate of that kind, arriving here for the whole install rather than for one release.

**There is no project record, so a safeguard may not name one.** A project is what groups services, the [screens](end-goal/how-the-factory-works/11-screens/01-work-ops-factory-people.md) are M7, and the area chain terminates at an area rather than at a project until then. A safeguard here names a service, an area, a gate row, or the factory-wide settings record, and a subject the factory has no record for is refused rather than stored as a dangling name. Reading the design's stage as the gate at that stage's boundary is what lets a safeguard reach a deploy row at all, the eight rows each sitting at one and there being no other subject that names one.

The demonstration is three runs of the path against one service, and what each is for. The first is M1's, re-run under a real score: the item reads high, the gate puts a human at Merge to master and again at Deploy to production, and both decisions name a score version and a policy version that are records rather than the names M1 wrote. The second is the milestone's own: the same path on the same service with the prior and the area narrowed by the first run's verdicts, the number under the threshold at both rows, both verdicts the factory's own with no human anywhere, and the release deployed — with the open events naming the number, every factor, the threshold applied, and where that threshold came from. The third is the safeguard: an owner places one on the service, the deploy row puts a human back at a gate the score would have passed, the human holds, and the run stops with the release minted, nothing deployed, no attempt counted, and the item where it was. Then, over all three, `Verify` clean, the link walk from the last deploy back to its intent, and the effective value of each of the seven parameters printed with which of the three reads it came from.

## M3 — A candidate gets an environment

A [candidate](end-goal/how-the-factory-works/06-releases/03-what-a-build-is-called-and-when.md) runs on an [environment](end-goal/how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md) of its own, composed from the [current releases](end-goal/how-the-factory-works/06-releases/05-the-deploy-record/README.md) of its dependencies, and the [merge queue](end-goal/how-the-factory-works/05-environments/README.md) orders merges, with every pre-merge check decided against the candidate-environment run. Demonstrated by two candidates on one service proceeding at once, neither reading the other's environment.

Two facts set the shape. **Nothing is shared, so nothing queues behind anything**, which is the whole of what [_An environment per candidate_](end-goal/how-the-factory-works/05-environments/02-an-environment-per-candidate.md) buys — so the milestone's unit is two items in progress at once rather than one item walking further, and every record the path touches is read for whether two items can be inside it at the same time. Two could not: the environment, whose kind CHECK listed production alone, and the [item](end-goal/how-the-factory-works/01-one-pipeline.md)'s stage, which had no value for a candidate whose merge is approved and whose fast-forward has not happened — which is exactly the membership [_The merge queue_](end-goal/how-the-factory-works/05-environments/03-the-merge-queue.md) defines itself by. And **master's only inbound path is the queue**, so the [release record](end-goal/how-the-factory-works/06-releases/02-the-release-record.md) and [the release number](end-goal/how-the-factory-works/06-releases/04-the-release-number.md) move into it: the design names the queue as their writer, and M1 minted them in the crude interface beside a `git fetch` because there was no queue to put them in.

One package, and it owns no table — the queue is a component, its membership a query over items and its order a query over the log:

| Package | What it owns |
|---|---|
| `mergequeue` | The queue: its membership as the items whose stage says [Merge to master](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/07-merge-to-master.md) approved them and whose fast-forward has not happened, its order as the item's priority and then the time of that approval in [the log](end-goal/deferred.md), the fast-forward and the release it mints with it, and the rejection of a candidate that failed its own re-verification — a wait row the log writes with the queue as caller and actor, an attempt counted at Implementation, and the item sent back there |

Eleven packages change, and each change is what an environment per candidate or the queue needs from a record it does not own. `environment` gains the candidate kind, a second writer for it — the [deploy agent](end-goal/how-the-factory-works/08-operations/01-the-health-monitor.md), the kind being the seam between the two — the item it belongs to, what it was composed from, and the teardown that keeps the record and stops the software. `item` gains the queued stage, the priority an owner reorders a queue with, what decomposition declared it waits on, and a way back up the pipeline: `Dispatch` could only advance one stage forward, and the queue's rejection and a gate's reject both send an item back and count the attempt at what it is sent to. `gate` gains its third row — Deploy to candidate environment, where [hold](end-goal/how-the-factory-works/03-gates/04-what-a-gate-may-change.md) and reject are both actions and the threshold is still production's, a candidate's environment holding nothing an owner authored — and the read of when each item's merge approval closed, the shape of both a decision's payloads being its. `criterion` gains the outcome of deciding one against a build, [undecided](end-goal/how-the-factory-works/05-environments/04-what-the-candidate-environment-decides/01-the-third-outcome.md) among the three, written by the deploy agent when the run finishes; `artifact` changes only to pass the item through to it. `deploy` gains the build a deploy names, on every record rather than a release alone. `release` gains master's head as a query, which is the commit of the service's highest-numbered release, and `build` the query that answers which build a commit already has — a rebuild being a new build, so a re-verification that produced the commit already built produced none. `targetseam` renames the one field a deploy carries across it from the release to the build, and `localtarget` becomes one target per environment rather than one per install, a candidate environment being a place of its own. `cmd/factory`'s `run` takes an intent per candidate rather than one, `priority` joins the four subcommands that are duty 8 and duty 9, and the crude interface is also the deploy agent the queue reaches its repository and its candidate environments through.

Three edits to `end-goal/` come with it, each a defect building found rather than a decision this milestone took on its own. [_The deploy record_](end-goal/how-the-factory-works/06-releases/05-the-deploy-record/README.md) said a deploy record names the release, and a candidate deploy fires one gate before the number exists — so it names the build it put there and the release where it is deploying one. [_Records, and one long-lived branch_](end-goal/how-the-factory-works/05-environments/01-records-and-one-long-lived-branch.md) said the build names the environment a run happened on, which it cannot: the build is written when the implementation stage finishes, one gate above the approval that creates the environment, so what names it is the item. And [_Spec_](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/02-spec/02-in-force-and-withdrawal.md) said which criteria are in force for a build by filtering withdrawals alone, which two candidates at once break: a criterion introduced by a sibling that has not merged is a promise this build's tree could not keep, and holding it in force rejects every candidate decomposed in parallel with the one that introduced it. Both halves of that query now read the same set — the items in the build.

Decisions taken so the demonstration holds.

**A candidate's environment is a record with a second writer, and the kind is what keeps the two apart.** An owner writes the persistent kinds and never a candidate's; the deploy agent writes a candidate's at the approval of Deploy to candidate environment and never a persistent one. So `environment.Writer` refuses the candidate kind and the new `Candidates` writer refuses every other, and authoring a threshold on a candidate's record is refused where it is authored rather than left to a reader to notice — the record cannot hold the threshold that decided its own creation. A candidate's record names its item, which is what makes it findable and what says the environment is the item's rather than the build's: it persists across a rebuild. Teardown writes the time and keeps the row, because the deploy records naming it would otherwise point at nothing, and it stops the software before it does — the record and the process are two facts, and this is the one place the factory is allowed to make them agree without the [checker](end-goal/how-the-factory-works/08-operations/08-drift-detection.md).

**What it was composed from is a field, and on this path the field is empty.** The environment is composed from the current releases of the candidate's dependencies, a dependency here being what decomposition declared the item waits on — the only dependency the factory has a record of until [contracts](end-goal/how-the-factory-works/07-contracts/README.md) arrive at M5. Decomposition yields one item per intent at this milestone, so no run declares one and every composition on the demonstrated path names nothing. The mechanism is built rather than deferred because the field is written at creation and rewritten at each re-verification, and a field added later would be absent from every environment the factory had already composed. What it costs is the milestone's thinnest claim: two candidates are demonstrated not to read each other's environment, and neither of them reads a dependency's release either.

**The hold both deploy rows read is computed at the firing and writes nothing.** A declared dependency that is not live holds the candidate deploy until it is and holds the production deploy if it has stopped being, live meaning that the dependency's release is the one its service's production deploy record names. It is recomputed at every firing and written nowhere, which is what the design requires of a hold over a record that already exists — a record for it would be a decision where nothing is decided. It is computed by the caller rather than inside `gate`, which imports neither the item nor the deploy record and would need both; what `gate` owns is the vocabulary, and the condition is named there. Being untestable through a run that declares no dependency, it is tested directly against an item waiting on one that has not shipped.

**The other hold at that row does write, and it is the substrate's.** A substrate with no room for another environment is the one condition decomposition could not have declared, it is not a record, and no parameter of an owner's limits it — so it is a wait row the log writes with the deploy agent as caller and actor, the shape the design gives a wait no gate could compute. The ceiling is a number in the source and not gate policy, because it is the factory's own infrastructure limit rather than something an owner authors, and it is a field of what the crude interface composes so a test can set it to one. What that costs is the cost the design already states: an item stopped for a reason no artifact of it explains, visible only as a wait.

**The criteria are decided on the candidate environment, and undecided is the reason a second run happens at all.** The encodings run twice against the same build, and a criterion whose two runs disagree is undecided for that build rather than passed — a repeated run measures the repetition, and recording it as a pass would rest the merge verdict on nothing. Undecided is read at the Merge to master gate the way a failure is, and the way out is to author the encoding again rather than to run it again, so nothing here retries to green. Two coarsenesses are worth stating rather than hiding: the run's result is one exit status for the whole suite, so every criterion in force takes the same outcome from one run, and the second run doubles what a build's verification costs to catch a class of defect that a deterministic suite does not have. The results attach to the build and the criterion and are a table of the two, not a record with an identity of its own.

**The score is asked at three rows now, and coverage reads different things at two of them.** At the candidate deploy row no criterion has been decided yet, so the coverage factor reads the set in force and no failure; at the merge row it reads the same set with the outcomes the candidate-environment run produced, which is the reading M2 built. Neither is unavailable, so neither puts a human at a gate for the absence of a measurement — and what the candidate row's number is therefore blind to is exactly the thing that row exists to arrange, which is the run itself.

**The queue re-verifies serially, and the speculation is deliberately absent.** A candidate entering the queue re-verifies against the master that actually resulted — master merged into the candidate branch, a build written for the commit that produced, the environment recomposed, the build deployed to it, and the criteria decided there — and fast-forwards only if that passes. The design's speculative re-verification against master plus every candidate ahead is what makes the queue fast, and it is the queue's own state read by nothing outside it, so it can arrive later without changing a record: what a serial queue already provides is the property the design asks of it, that the commit that was verified is the commit that merges. What it costs is wall-clock — a queue of ten waits ten re-verifications where a speculating queue overlaps them — and it costs the demonstration nothing, a failure ahead invalidating a speculation there is none of.

**A candidate with no base is merged with unrelated histories allowed, and a conflict is a rejection.** Master does not exist until the first release, and the implementation role commits a candidate branch with no base, so two candidates decomposed before that first release have no common commit and the re-verification of the second is a merge of two roots. The merge is performed with unrelated histories allowed rather than special-cased, which is a flag with no effect where the histories are related; where the two trees then conflict, the candidate failed its own re-verification and the queue rejects it, which is the right answer and not a workaround. What it costs is that a git conflict and a failing criterion arrive at the same disposition with different reasons, and the reason is in the wait row rather than in the verdict.

**A merge is three writes, and two of the three windows between them close here.** The fast-forward, the mint, and the item's advance to merged cross a repository and two transactions, and nothing makes them atomic. The queue holds a per-service advisory lock across all of them, so two queue runs cannot interleave and two candidates cannot read one number — the serialization [_The release number_](end-goal/how-the-factory-works/06-releases/04-the-release-number.md) already requires. A member that already has a release is then finished rather than re-verified, which closes the advance's window: an advance that failed is repaired by the next run, and one merge never mints two numbers — which it otherwise would, a release being unique on the service and the number and not on the item, so nothing in the store refuses a second. What stays open is a mint that failed after the fast-forward, leaving master at a commit no release names: M1 stated that as the half-write the queue would close, and closing it is the drift detector's, which is M4. The direction is the one M1 chose for the same reason — a release numbering a commit that never reached master is worse, because a deploy could put it live.

**The queue's membership is the service's and not the run's.** Its members are every item of the service at the queued stage, which is what the design says and is not the same set as the candidates one run authored: a run that stops after one Merge to master gate has approved leaves that item queued, and nothing in the crude interface clears one. So a re-verification reads what it needs from the store rather than from what its process happens to remember, and a run that finds an item another one left behind finishes it — tears its environment down and deploys its release beside its own. The alternative was for a run to re-verify only what it authored, and that wedges the service: every later run would spend its model calls, compose an environment, fire two gates, and then fail on somebody else's item, with one more stuck item added each time.

**A reject counts its attempt where the item is sent, at every row that rejects.** M1 and M2 left an item at Implementation on a reject and counted nothing, there being nowhere to send it and no second stage below. With a stage between Implementation and merged, going back up is a real move, so `Dispatch` gains it and the two rows that reject and the queue's rejection all use it — the attempt booked against the stage the item returns to, which is the rule the design gives for a reject, a rework request, and the queue alike. What that changes for the milestones already built is that a rejected item's Implementation count is one higher than it was, which is the count the attempt limit was always meant to be compared against.

The demonstration is three runs and what each is for, all on one service. The first is M1's, walked along the path M3 builds: one candidate, its own environment created at the candidate deploy gate and named for the item, its build deployed there, the criteria decided by two runs on it, a human at each of the three rows because nothing about the service has been seen before, the queue re-verifying against a repository with no master, fast-forwarding to create one, minting number 1, tearing the environment down, and the production deploy putting it live. The second is the milestone's own, run after that one: two intents at once, two items decomposed on the same master, two candidate environments live together with different targets and different deploy records, each criteria run attaching to its own build, both Merge to master gates approving with nobody at either, and the queue merging them in its order — the second re-verifying against the master the first one created, which is a build the implementation stage never made — then two releases numbered 2 and 3, two environments torn down, and two production deploys. The third is the queue's rejection: the two candidates write to one file, so the second one's re-verification against the master the first created is a merge that conflicts, and the run ends with the first item merged and deployed, the second back at Implementation with an attempt counted there, its environment still its own and not torn down, no release minted for it, and a wait row in the log naming the queue as its actor. Three more things are demonstrated beside the runs, none of them reachable through one. The settable order: an owner writes a priority between the Merge to master gates and the queue, which one run performs in a single call, so the steps are driven one at a time and the candidate pushed to the front merges while the one behind it is the one whose merge now conflicts. The substrate's ceiling, lowered to a single environment so the second candidate of a run waits and that wait is written. And the dependency hold, driven against an item that waits on one nothing has shipped, because decomposition here yields one item per intent and no run declares a dependency. Then, over all of it, `Verify` clean, the link walk from the last deploy back to its intent, and the effective value of each of the seven parameters printed with which of the three reads it came from.

## M4 — The factory watches what it ships

Everything downstream of a deploy: the [health monitor](end-goal/how-the-factory-works/08-operations/01-the-health-monitor.md) and the control, the [analysis window](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) and the [window limit](end-goal/how-the-factory-works/08-operations/03-overlapping-windows.md), [rollback](end-goal/how-the-factory-works/06-releases/06-rollback.md) while a control is still running and a revert item after, [pages](end-goal/how-the-factory-works/08-operations/07-pages.md) and escalation, [incidents](end-goal/how-the-factory-works/08-operations/06-incidents.md), [the drift detector](end-goal/how-the-factory-works/08-operations/08-drift-detection.md), and the health monitor finding a problem [after its window closed](end-goal/how-the-factory-works/08-operations/04-after-the-analysis-window.md) and writing an intent at the start of the pipeline. Demonstrated by a deliberately bad deploy: shipped, caught by its window, rolled back, and the whole episode readable as links.

Two facts set the shape. **This substrate moves a process rather than traffic, so no control is ever started** — the [strategy that keeps one](end-goal/how-the-factory-works/03-gates/02-the-rollout-strategy.md) has been refused here since M2, and everything downstream of that refusal follows: the comparison is the weak fallback the design names rather than a release read against a control of the same age, every rollback is the slow one with the target's build redeployed and waited for, and no window this milestone opens names a control. So the milestone builds the whole mechanism and demonstrates its confounded half. And **the window is the first thing the factory decides with no human anywhere and no gate to put one at** — a [reject](end-goal/how-the-factory-works/03-gates/04-what-a-gate-may-change.md) needs an approval and a [hold](end-goal/how-the-factory-works/03-gates/04-what-a-gate-may-change.md) needs a firing, where a rollback inside the window needs neither — so what makes it legitimate is that the boundary is valid at every point it is read, which is arithmetic and not architecture. The milestone's largest single risk is there and not in the record graph.

Four edits to `end-goal/` come with it, each a defect building found rather than a decision this milestone took on its own. [_The health monitor_](end-goal/how-the-factory-works/08-operations/01-the-health-monitor.md) said an owner may set an explicit threshold per service with a safeguard and never said what that safeguard binds — gate policy's seven rows hold no such parameter, so it is authored on the service record and is not one of the seven, the way [retention](end-goal/how-the-factory-works/09-gate-policy/03-what-is-not-in-it/02-retention.md) already is. The same section made the weak fallback read a release against **its predecessor's own recent history**, which two open windows break: the predecessor of a release under watch is itself under watch, so its history is not history yet and one release becomes the other's baseline — the exact incoherence a started control was introduced to remove. The baseline is a rollback's target instead, computed for the release under watch rather than for a rollback of it: the newest release below it whose window closed without failing it, which is single-valued across overlapping windows and never above the release it is the baseline for. Not the last known-good release, which is where this edit started and is wrong for the reason that query is not stated per service — it can be a release above the one being read, and a release measured against something that includes it is measured against itself. [_The analysis window_](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) gave the health monitor sole authority to close a window because "the deploy agent never advances its own record again", which [_Rollback_](end-goal/how-the-factory-works/06-releases/06-rollback.md) contradicts — a rollback advances the deploy records of every release it undid — so the clause is narrowed to the deploy's own account. And [_Pages_](end-goal/how-the-factory-works/08-operations/07-pages.md) said the component that ends a wait calls the notifier at the same write, which cannot hold for the one wait a human ends inside the drift detector: that store calls nothing, so the answered event is written by the notifier at the pass that finds the mismatch cleared.

Decisions taken so the demonstration holds.

**The boundary is two one-sided tests, and the confidence is what each of them crosses at.** The quantity is a count of units of work and how many of them failed. The baseline rate is the target release's own rate, smoothed so that a baseline with no failure does not make a ratio infinite. The alternative is that rate **plus** the size rather than that rate raised by it, the size being a share of the work and not a share of the baseline: ruling out a tenth more of a baseline near nothing takes traffic no install has, and ruling out a tenth of the work failing takes a few hundred units. What that costs is at the other end — on a service failing a fifth of the time the same number is a much finer question, so an owner reading the size has to know which of the two it is. Harm is then the likelihood ratio between the alternative and the baseline; clean is that ratio inverted. Each is a non-negative martingale under the hypothesis it tests, so the chance of either ever crossing one over one-minus-confidence, however often it is read, is at most one-minus-confidence — which is what makes reading it continuously legitimate rather than a fault nobody traces to its cause. Two costs are stated rather than hidden. The baseline rate is estimated and then treated as known, so the confidence is the boundary's and not the pair's: that is the confound a control removes and this substrate does not have. And the units either side needs before it crosses grows as the inverse square of the size, which is the design's own claim about this arithmetic and is a property of this boundary rather than an assertion beside it.

**The quantity is emitted by the software the factory wrote, and the target is what wires it.** The implementer is told, in one standing instruction beside [the four rules](end-goal/how-the-factory-works/01-one-pipeline.md), to append a line per unit of work to the file its environment names. `localtarget` starts each process with that file named for the build it is running, so production's directory holds one file per build that ran there and a release's own counts are told apart from the last known-good release's. What it costs: a service the factory did not write emits nothing and cannot be watched, which is the adopted-service case [_Deferred, but not designed out_](end-goal/deferred.md) already sequences away; the health monitor reads a file rather than an observability system, so the quantity is behind an interface and is exactly as trustworthy as the build that wrote it; and the traffic is the release exercising itself, so a window passed here says the boundary works and not that the service is well.

**The four holds that lift themselves stop the deploy before a decision is opened; the one that does not lift itself fires the gate.** A declared dependency that is not live, the substrate with no room, the window limit reached, and a rollback whose revert has not shipped all lift themselves, and a gate fired for one of them would ask a human to approve through something the factory is about to clear on its own — so the deploy waits, nothing is decided, and the next firing recomputes. A mismatch the drift detector found is the other kind and the only one of it: no evidence the factory can gather lifts it, so the row fires with the mismatch on its open event, a human decides, and the notifier pages. Approving through the other four is then a human's action rather than an absent one — `approve <item-id>` fires the row with the hold named and takes the verdict, which is the emergency action the design keeps at that gate: approve now, not skip. What that closes is a gap M3 left: its dependency hold could be waited out and never approved through, which the design offers at every hold the factory sets.

**The window limit writes nothing, the rollback's hold writes nothing, and the substrate's ceiling still writes.** The open windows are records and so is the rollback's deploy record, so both new holds are computed from records that already exist and the design's rule gives them no row; the substrate's ceiling stays the one wait at a deploy row that is written, being neither a record nor a parameter of an owner's. What that costs is the cost the design already states: how long the factory has been holding is answerable for the written one alone, and a deploy queued behind open windows at the window limit is a wait on the factory visible only to a reader who asks.

**A rollback is always the slow one, and the revert is an ordinary item nothing marks.** With no control there is no traffic to shift, so every rollback redeploys the target's build and waits for it to start. The revert is an intent intake wrote with the detector as its source and decomposition turns into an item like any other; nothing on the item says it is one, on the precedent that [the project is not a field](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/02-what-an-item-names.md). What makes the hold computable without such a field is the link on the other end: the rollback's deploy record names the intent it raised, which is what "revert names what raised its intent" already says, put where the raising happened. So the hold reads the newest rollback of the service and asks whether the item decomposed from that intent has a release running, and the revert deploys ahead of every release the hold is holding — the one place the number does not order deploys, and without it the same deadlock one step out.

**An escalation pages where the intent was not an owner's.** The attempt limit is built and what M4 adds is who hears about it. An item whose intent came from a detector or from end-user reports is a defect that is live, so the factory giving up on it is the [page's condition](end-goal/how-the-factory-works/08-operations/07-pages.md) met; an item an owner asked for has nothing live that is worse. That is the whole of the test, read off the intent's source rather than off the list of three the design enumerates — which is what that section says of its own list.

**The drift detector is a second binary and a second store, and the factory reaches it through one interface and one read.** Its schema is applied by its own process, it is pointed at its store by an environment variable of its own, and for the demonstration that store is a second schema on the same PostgreSQL — which is where the independence is weakest and is stated: a store the owner installs elsewhere is this code with a different URL, and nothing in the factory writes either way. The gate asks it through an interface rather than importing it, so a factory composed without an drift detector decides exactly as it did at M3 and the absence shows in what `policy` prints rather than as a failure.

**The People declaration is a record now and the owner is not a row in it.** Routing needs the record, so it arrives with the notifier rather than with the screen that writes it — the arrangement the four window parameters already had, one milestone earlier. Who the owner is stays what the install knows and the notifier is composed with the name, because a page widening "to the owner" needs one name and the design gives the owner no record. What that costs is that an install with two owners cannot say so, and every widening reaches one of them.

**The window limit above one buys throughput here and no concurrent measurement.** A deploy without a control replaces the process, so the lower release stops emitting the moment the upper one deploys: two windows are open, two releases are recorded, and only the newest one is really being read. What the design gets from a started control is two independent comparisons running at once, and that is the half of the window limit this substrate cannot have — so the demonstration of a sweep drives the two deploys a step apart rather than through one run, which is the pause a control would make unnecessary. The window limit is still worth authoring above one, because what it changes about the merge and the number is real and what it changes about a rollback's reach is exactly what the design says it changes.

**A revert reaches the pipeline by its statement, because the crude interface has no other handle.** The health monitor takes the revert's intent in at the rollback, and `run` is given a statement rather than an intent id — so a run whose statement matches an unrefined intent already waiting works that one rather than taking in a second saying the same thing, which would leave the rollback's hold pointing at an intent nothing was decomposed from and never lifting. What it costs is a false match where an owner types a statement character for character equal to one already waiting, and the screen that replaces this shows an owner the intents that are waiting and has them pick one.

**A revert introduces a criterion nobody asked for, and the reason is M1's protocol.** The spec author's reply protocol requires exactly one criterion per spec version; the design makes it a set a version introduces and withdraws, which may be empty. A revert restores a behaviour the service already promises, so the honest version introduces none. Widening that protocol is a change to a milestone already built and is not made here — what is recorded is that the next thing to touch it should, and that until then every revert leaves one criterion behind it.

**Mail, chat, and the page are three channels of one component and one implementation here.** The crude interface writes all three to the terminal, distinguished by the channel they went out on, because there is nothing to deliver to. The page stays the only one that writes a record, which is what a test asserts over, and a fault in the one implementation stops all three at once — the cost the design states for having one notifier.

**The health monitor closes a window and nothing else does, so a run that ends mid-window leaves it open and the next run finishes it.** That is the merge queue's property for the merge queue's reason: what a pass needs is in the store rather than in what a process remembers. `run` watches to a close after its production deploys, and `watch <service>` is the pass alone against an existing database — which is also how a window left open by a run that stopped is closed.

The demonstration is three runs and four things not reachable through one, all on one service. The first is M3's, walked along the path M4 builds: one candidate released as number 1 and deployed, a window opened over that deploy naming no control, `passed` not available to it because there is nothing below it to compare against, the window ending at the cap, and nothing about that release discovered by watching — which is what the design says of a first release where no safeguard set a threshold. The second is the milestone's own: a candidate whose implementation fails a share of the units it serves, which passes every criterion in force because the failure is in no criterion's path, ships as number 2, and is caught — its window opens with release 1's rate as the baseline, the boundary crosses against it, and the exit is failed. That episode is an incident on production naming the release and the deploy, the window closed failed, the target computed as release 1 because its window timed out and timing out counts, release 1's build redeployed and waited for, the failed deploy advanced to rolled back with the health monitor as its source, a revert intent raised through intake, the rollback reported on mail and chat and not paged — the factory does not page to inform — and a hold now standing over every production deploy of that service. The third is the window limit: an owner authors two, two candidates merge, and their production deploys are driven a step apart so the lower one has something for its own comparison to read — the pause a substrate keeping a control would not need. Both windows are open at once, the lower one's boundary crosses, and the rollback undoes both: the failed one, and the one above it closed skipped, with the target still release 1 and both deploys advanced to rolled back. Four more things, none of them reachable through a run. The hold lifting: the revert item authored and shipped, deploying ahead of the release the hold was holding, after which that release deploys. Approving through: `approve` on the held release before the revert ships, which redelivers the defect that was just removed and is the most damaging thing in the factory to approve through. The crossing after the window closed, which writes an intent rather than rolling anything back, and a second crossing on the same release and service that is an observation on the open incident and never a second intent. And the drift detector: a target changed underneath the factory, a mismatch written in the drift detector's own store, the production deploy row firing with it on the open event and a human at it, page events in the log — reached, then widened to the owner — and the answered event written by the notifier at the pass that finds the mismatch cleared, because clearing it happens where nothing calls. Then, over all of it, `Verify` clean over a log holding page events beside the decisions and the waits, the link walk from the rollback's deploy record back to its intent, and the effective value of all eight parameters printed with which of the three reads it came from and what reads it — where four of the eight now name a reader.

## M5 — Contracts bind services

Two services exist, and what a consumer assumes is [derived from its build](end-goal/how-the-factory-works/07-contracts/06-what-a-consumer-declares.md) rather than entered by hand; [enforcement](end-goal/how-the-factory-works/07-contracts/04-enforcement.md) answers what a change breaks by query; [work that spans services](end-goal/how-the-factory-works/07-contracts/10-work-that-spans-services.md) needs no record type of its own. Demonstrated by a breaking change stopped at the [Merge to master gate](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/07-merge-to-master.md) naming the consumer it would break, and by the [three items](end-goal/how-the-factory-works/07-contracts/02-no-single-item-may-break-a-contract.md) that get the same change through. This is the first milestone that needs a second service, which is why it sits after operations; the order of M4 and M5 is the one ordering here that could go either way.

Three facts set the shape. **A contract is derived and never declared, so this milestone is a program analysis before it is a record graph** — what a service publishes and what a consumer reads are both read out of a checkout, and [_What a consumer declares_](end-goal/how-the-factory-works/07-contracts/06-what-a-consumer-declares.md) says outright that how much of a consumer's reading is visible is a property of that interface's toolchain rather than of the factory. So the derivation here is Go's, written against `go/parser` in the standard library, and a second toolchain replaces it rather than extending it. **The milestone's stopped change is a rejection and not a hold**: the merge row [offers no hold](end-goal/how-the-factory-works/03-gates/03-actions-at-each-gate.md), and a breaking diff without its migration shipped ahead of it is a rejection there — so "held at a gate", which is how this line read until 2026-08-20, is loose and the demonstration is the factory rejecting. And **one intent now yields more than one item**, which fires [Decomposition](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/01-decomposition.md) for the first time: every run before this one decomposed one item per intent and so fired none. That row arrives here because a contract migration is what makes decomposition yield a set, and it arrives thin — the [re-decomposition](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md) that a rejection asks for is not built.

Three packages, two of them records:

Beside the records, the vocabulary of a form and the diff between two of them, and the derivation of a form out of a checkout. `cmd/factory` becomes an interface over two services rather than one — a repository per service, the service each statement is decomposed on named with it, the merge queue run once per service — and gains the contract checks at the merge row, the same checks again inside the queue's re-verification, the deprecation detector as a pass, and `contracts` as the subcommand every query in this Decisions taken so the demonstration holds.

**The form is Go source, and the derivation reads it rather than a built artifact.** A service publishes one contract per exported struct type declared under `contract/` in its repository, and one store contract per type under `store/`; the type's name is the interface's name and its exported fields are the elements, each with the field's type, whether it is always populated, and whether it is marked deprecated, taken from a `borg` struct tag. The unit stays in the element's name — `SendTimeMillis` and never a tag — which is the design's own rule and is what makes a change of units a rename, a rename a breaking diff, and the [three items](end-goal/how-the-factory-works/07-contracts/02-no-single-item-may-break-a-contract.md) the whole of what handles it. Two costs are stated rather than hidden. The derivation parses source and does not type-check it, so a form the compiler would reject is still a form here — which nothing acts on, the build having to compile one step earlier. And the kind follows the directory rather than anything the toolchain states: `contract/` is a published interface and `store/` is a store, which is a convention in a path where the design has a fact about the thing. What the convention buys is that [nothing is declared](end-goal/how-the-factory-works/07-contracts/03-what-a-contract-promises.md) — the promise is still derived from the kind, and there is still no third case.

**A consumer contract is the mirror it holds and the fields its own code reads.** A consumer that reads a producer's interface declares a Go type mirroring it under `consume/`, named for the producer's service and interface, and the derivation is the fields of that mirror which the consumer's source actually selects — found syntactically, with `go/parser`, over the whole checkout. A field in the mirror that nothing reads is not declared, so a consumer that stops reading a field stops declaring it with nobody remembering to, which is the mechanism the [deprecation list](end-goal/how-the-factory-works/07-contracts/08-deprecation.md) rests on. Both of the design's blind cases are real here and neither is silent: a read the derivation misses is a field read through reflection or through a name the parser cannot resolve, and a read it invents is a field name the mirror shares with another type. The first is what a [safeguard's predicate](end-goal/how-the-factory-works/07-contracts/06-what-a-consumer-declares.md) covers, the second is what withdrawing one does, and the printed consumer contract is where an owner sees either.

**A predicate is decided twice, against two different things, because the design's two baselines are two different questions.** The five kinds are the four sentences [_What a consumer declares_](end-goal/how-the-factory-works/07-contracts/06-what-a-consumer-declares.md) lists, with "the field is read at all" and "it arrives populated" told apart: read, populated, unit, domain, range. Against a **form** — which is what a consumer's own merge row checks its newly derived consumer contract against, the form being the one its producer's newest release publishes — three of the five are decidable: the element exists, it is always populated, its name carries the unit. Against one **observed exchange** — which is what a producer's merge row checks every consumer contract against, on the candidate's own environment — all five are. A predicate the form cannot decide is not a failure there and is decided on the producer's side alone, so a domain a consumer narrowed is caught at the producer's next candidate and not at the consumer's own. What that costs is one kind of assumption protected one gate later than the other four.

**The exchange is emitted by the software the factory wrote, beside the quantity it already emits.** Each program appends one JSON document per unit of work to the file `BORG_EXCHANGE` names, and `localtarget` starts each process with that file named for the build, in the environment's own directory — the arrangement the signal file has had since M4, and for the same reason: a release's own documents are told apart from the ones the build before it wrote. A check with a consumer contract to decide and no document to decide it against is a failure and not a pass, because a producer that emits nothing has not shown that a consumer's assumption holds; a check with no consumer contract to decide reads nothing and passes. The costs are M4's, one milestone on: a service the factory did not write emits nothing and cannot be checked this way, which is the adopted-service case [_Deferred, but not designed out_](end-goal/deferred.md) already sequences away; and the documents are exactly as trustworthy as the build that wrote them. The form is flat — a nested value is not a scalar and every predicate on one fails — which is this substrate's limit and not the design's.

**A breaking diff is refused unless the deprecation list for what it breaks is empty, which is the one place enforcement and deprecation join.** The producer's own diff runs against the version its [current release](end-goal/how-the-factory-works/06-releases/05-the-deploy-record/README.md) publishes: an element removed, an element whose type changed, and an element that was always populated becoming optional are breaking; an element added and a mark placed are not. "Without the migration already shipped ahead of it" is then not a second mechanism — it is the list [_Deprecation_](end-goal/how-the-factory-works/07-contracts/08-deprecation.md) keeps having emptied, so a removal passes exactly when no consumer contract in force and no safeguard's predicate names the element. What that costs is that a producer with no consumer the factory can read may remove anything at once, which is the outside consumer the design says gets no warning but the major version.

**A store breaks on a fourth change, and it is the one no list empties.** A store promises [forward](end-goal/how-the-factory-works/07-contracts/03-what-a-contract-promises.md) as well, so an element added and always populated is breaking there: the [build being restored](end-goal/how-the-factory-works/06-releases/06-rollback.md) does not write it, so the newer build's own reads of it find nothing. What blocks that one is not a list but the release a rollback would restore, which exists whenever there is a form to diff against at all — its consumer is the service's own past, and a release that has already shipped cannot migrate. So the rejection is unconditional and what clears it is a form the restored build can read, which is why the first item of a store migration adds the new form beside the old and adds it optional. That is the same three items the design gives an interface, with the reason for the first one made mechanical.

**The version moves where the form moves, and the third number never moves.** A version is minted at the fast-forward of any release whose form differs from the version in force below it: major where the diff is breaking, minor where it is not, and patch never — nothing in a form is a patch-level change, and the number is there because semver has three. A mark mints a minor, which is a consumer seeing a bump for an annotation nothing breaks on and is the cost the design already states for the version tracking the form. Most releases publish no new version at all, and a release that publishes none writes nothing here.

**The contract and its versions are the queue's write, inside the mint's transaction, and the form reaches it from the deploy agent.** The queue reaches no checkout, so what the re-verification produced now carries the forms it derived, and the queue writes the contract where the first release publishing it is this one and the version in every case — inside the transaction [`release`](end-goal/how-the-factory-works/06-releases/02-the-release-record.md)'s mint holds, so one merge cannot leave a number with no version or a version under a number nothing minted. Nothing is on the release record: the version names the release and copies its number, so "the release names the contract versions it publishes" is the inbound edge every [deploy record](end-goal/how-the-factory-works/06-releases/05-the-deploy-record/README.md) of a release already is, and the number is copied for the reason `criterion` copies its item — the ordering of versions is the ordering of releases, and a package answering it by reading release records would make every reader of a contract a reader of releases.

**Consumer contracts in force is a range over releases, and the last known-good release is computed where it is read.** For one service the consumer contracts in force are the predicates derived by the items of every release from the [last known-good release](end-goal/how-the-factory-works/08-operations/03-overlapping-windows.md) to the newest, and a service none of whose windows closed passed or timed out has none, so the range is every release it has. It is computed in `contractcheck` and not in `healthmonitor`, which computes a [rollback's target](end-goal/how-the-factory-works/08-operations/03-overlapping-windows.md) from the same windows for a different question, and not in `window`, which cannot read a release's number. What the range costs is the design's own: it is as wide as the windows a service has open and wider wherever a release has merged and not deployed, so a producer is held to the assumptions of releases that are not running.

**The deprecation list is a query and the detector is a pass.** For one marked element the list is the consumers whose consumer contracts in force still name it plus any safeguard's predicate naming it, and nothing writes it. Where it is empty and the element is still in the newest version's form, the detector takes an intent in with itself as the source, asking for the removal — one per element, deduplicated by an unrefined intent with that statement already being there, which is the handle a [revert](end-goal/how-the-factory-works/06-releases/06-rollback.md) already reaches the pipeline by and costs what that costs: an owner who types the statement character for character gets the detector's intent.

**A safeguard's predicate takes a direction that is derived and not read off the list.** [_One shape across all of them_](end-goal/how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md) names ten safeguards and their directions and does not name this one, while the same section's argument for a safeguard being a record rests on it — a safeguard's predicate names a contract element as its subject, whose writer is the merge queue. So the direction is taken from the rule the whole list is an instance of: a safeguard's predicate adds a consumer contract and removes none, which is a floor. Its parameter is a ninth in `gatepolicy`, set by a safeguard and authored by nobody, so the printer's list of eight gains a line saying that nothing authors it — which is where a reader finds out that gate policy is seven rows and the safeguards are eleven.

**The unauthored value of the list of allowed predicate kinds is the factory's five kinds and not nothing.** [Gate policy](end-goal/how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md) has an owner extend the list and a safeguard only add to it, which presupposes something to extend; the score supplies none, having no outcome that teaches one. So the value in force is the five kinds this factory can decide, plus what an owner authored, plus what a safeguard adds, and the source a printer reports for an unauthored list is the factory's own — a third source, for this parameter alone. A consumer contract drawing on a kind in the list that the factory has no decider for is refused at the derivation, naming the kind, which is where [_the list wide enough to admit an undecidable assertion_](end-goal/how-the-factory-works/09-gate-policy/01-what-is-in-it.md) actually lands on this substrate. This is the first reader that parameter has had since M2 authored it.

**Decomposition arrives thin, and what is missing is the re-decomposition.** The row fires where decomposition yielded more than one item, over the set that already exists — how many items, which service each changes, and what waits on what — with one verdict for the whole decomposition however many services it changes, which is the design's refusal of a per-service approval. Approving lets the items proceed. Rejecting supersedes every item of the set, writes the re-decomposition count on the intent through intake, and stops there: the [re-decomposition](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md) itself needs a stage that decides the decomposition rather than one told what to produce, and this interface is told. Edit in place is refused with the same reason — the design's Edit at this row is a human re-decomposing by hand. What that leaves is a gate that can stop a bad decomposition and cannot repair one, and the next thing to touch decomposition owes the repair.

**The consumers factor counts what the graph says and not what enforcement asks.** The [context factor](end-goal/how-the-factory-works/04-risk-score/01-factors-at-least.md) counts the other services whose consumer contracts name a contract this service publishes, over consumer contracts derived by items that have a release. It is deliberately not the in-force range: that range is enforcement's question about one candidate at one moment, and the factor is a reading about the service, computed at every firing over the whole graph the way every other factor here is.

**The producer's own observables are not built, and they are the layer that rejects nothing.** [_What a diff cannot see_](end-goal/how-the-factory-works/07-contracts/05-what-a-diff-cannot-see.md) answers a semantic break three ways, and two of them are here: meaning declared so the diff can see it, which is the unit in the element's name, and a consumer's assumptions checked against the candidate. The third — per field, on the producer's own traffic, population rate and enum spread and the distribution of numbers, each against the release this one replaced — raises an item and rejects nothing, and every quantity in it is a distribution over the same exchange documents this milestone reads one at a time. Building it is M4's boundary applied per element rather than per release, over a quantity nothing emits per element yet. So the two layers that reject are built and the one that reports is not, and what that costs is exactly what the design says it costs: a field that quietly stops being populated where no consumer declared it populated is invisible until the consumer breaks in its own error rate.

The demonstration is four episodes and four things not reachable through a run. The first episode is the pair: one intent decomposed into two items — one on a producer, which creates the service and publishes an interface of two elements, and one on a consumer, which reads both and is declared to [wait on](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md) the producer's item. Decomposition fires over that set for the first time in this repository and one verdict covers it. Both items ship, and the run takes them in dependency order: the producer's release publishes the contract at 1.0.0, written by the queue inside the mint that gave that release its number; the consumer's candidate environment is then composed from the producer's current release, which is the first composition any run here has performed with something in it; and the consumer's release derives a consumer contract naming the elements its own code reads, ratified at the gates its item already passed. The second is the milestone's own: an intent on the producer alone whose implementation removes an element the consumer declares. It passes every criterion in force, because the removal is in no criterion's path, and the merge row rejects it before a verdict is asked for — the diff against the version production runs is breaking, the deprecation list for that element names the consumer, and the close event is the factory's own reject with the consumer on it. The item goes back to Implementation with an attempt counted there. The third is the migration, three intents and three items over two services: the producer adds the new element beside the old and marks the old deprecated, which mints 1.1.0 and breaks nothing; the consumer migrates onto the new element, and its next consumer contract stops naming the old one, which empties the list with nobody removing anything; and the producer removes the old element, which mints 2.0.0 and passes the same check that rejected the second episode. The fourth is the store, and it is where [_the store is a contract too_](end-goal/how-the-factory-works/07-contracts/09-the-store-is-a-contract-too.md) is demonstrated rather than asserted: the kind read off the file name and the promise read off the kind, an always-populated element added to the store rejected because the release a rollback restores does not write it — the one break no list empties to allow — and the same element added optional passing, which is what the first item of a store migration does.

Four more things, none reachable through a run. The detector: the pass that finds the emptied list and takes the removal intent in, which is what the third episode's last item is decomposed from, and a second pass that takes in nothing because the first one's intent is still unrefined. The safeguard's predicate: an owner supplies a predicate with a safeguard on an element the derivation cannot see, the removal candidate is rejected at its merge row on the safeguard with the safeguard and its author on the row, an attempt is counted, and withdrawing it lets the next candidate through. A rejected decomposition: the set superseded, a re-decomposition counted on the intent in a field of its own beside the interview's rounds, and nothing authored below decomposition. And the queries: `factory contracts` printing every contract, the versions and their elements and marks, which version production runs and so which one a producer's own diff is against, the consumer contracts in force per service with the release range they were derived over, the deprecation list per marked element, and, for one candidate, what it would break and whom — which is [_Enforcement_](end-goal/how-the-factory-works/07-contracts/04-enforcement.md)'s claim that "what does this break" is a query rather than an estimate, read off the graph in front of an owner. Then, over all of it, the walk from either release of the first episode back to the one intent that joins them — [_Work that spans services_](end-goal/how-the-factory-works/07-contracts/10-work-that-spans-services.md) needing no record type of its own, demonstrated as the query it says it is — and `Verify` clean over a log now holding a Decomposition decision, two mechanical rejections, and the detector's intake beside everything M4 left in it.

## M6 — The score learns

The loop [_How it learns_](end-goal/how-the-factory-works/04-risk-score/02-how-it-learns.md) describes: learning over the [decision log](end-goal/deferred.md), calibration against outcomes, the [per-author prior](end-goal/how-the-factory-works/04-risk-score/01-factors-at-least.md), and the parameters the score supplies wherever an owner authors nothing — the [window limit](end-goal/how-the-factory-works/08-operations/03-overlapping-windows.md), the [item-size target](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md), the [window](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md)'s size. Demonstrated by a supplied parameter moving because outcomes moved it, and by the [held-out sample](end-goal/how-the-factory-works/04-risk-score/02-how-it-learns.md) auto-passing a change the score wanted gated.

"With the movement readable in the log", which is how that line read until 2026-08-20, is wrong about where the movement is. A supplied value is a field of a [score version](end-goal/how-the-factory-works/04-risk-score/01-factors-at-least.md), which is a record of the score's own and not a row of the log; what the log makes readable is which version each decision was decided under. So the movement is read by following a decision to its version and that version to the one it superseded, and the log is what makes it readable rather than where it is. A log row for the movement is refused: the log's three shapes are a decision, a page event, and a wait, a supplied value moving is none of them, and the score version is already append-only and ordered. What that leaves is a residual [`end-goal/open.md`](end-goal/open.md) now carries — the log is defended by each record chaining its predecessor and the two version tables are not, so a row rewritten in either moves what every decision naming it is read against while the chain still verifies. It is this milestone's to raise because the values the score supplies were constants until it learned them, and a constant could be checked against what the factory would supply on its own where a learned value cannot.

Three facts set the shape. **Every outcome the score learns from arrives after the decision it judges, so learning is a pass over records that already exist and never a write at a firing** — nothing at a gate could compute one, and a version that moved mid-process would leave two decisions of one run naming different numbers. The pass runs where a process starts and as a subcommand of its own; what that costs is that a run acts on what the store said when it started, and an outcome arriving during a run is learned from by the next one. **A supplied value is per subject, so the version holds a table and not a number** — the window limit and the window's three per service, the item-size target per area, the [attempt limit](end-goal/how-the-factory-works/03-gates/05-the-attempt-limit.md) per stage, the threshold per [gate row](end-goal/how-the-factory-works/03-gates/03-actions-at-each-gate.md) — because what the score supplies is what stands where an authored field is empty, and that field is per subject already. That is the design's stated cost arriving in full: a long sequence of versions, most differing in one number the decisions naming them never read. And **the sample is the only thing here that changes what the factory decides rather than what it supplies**, which is why it is the one mechanism in [the design](end-goal/README.md) that takes a human off a row — and why what makes it legitimate is whose human it is.

No new package. The loop is the score's own: the values it supplies are fields of its own record, so a package for the learning would be a second writer of that record, and the six rules read records six other packages own through the readers those packages expose. This is the first milestone that adds no table and the first that changes none of `postgres`.

Eleven packages change. `score` gains the whole loop: one read of every outcome in the store — the closed decisions, the closed [analysis windows](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md), the [rollbacks](end-goal/how-the-factory-works/06-releases/06-rollback.md) and what each swept, the [incidents](end-goal/how-the-factory-works/08-operations/06-incidents.md), the items with their per-stage attempts, and the releases — the six rules over it, the supplied table on the version beside a fifth column holding the published rules those values move by, the widened prior, and the sample with the draw behind an interface its caller implements. `policy` is composed with the score version rather than reading the newest per answer, because the supplied half of a value in force is a field of that version and a reader that re-read it could hand one firing a threshold its own decision row does not name. `gate` asks the sample after the policy has answered and before the human test, carries the selection on both rows of the decision, and says which of two things auto-passed a firing — the number being under the threshold, or the sample. `window` gains the held-out mark on the record, because a window that runs to the [cap](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) because the factory is measuring what it guessed at is not the window that runs to the cap for want of a baseline; the read it closed on, so an exit can be recomputed from the numbers it was decided on; and a read of every closed window, which is what the score learns from. `healthmonitor` takes the selection at the open, the exit a window may take being a fact of the open. `deploy`, `item`, `release`, `incident`, and `artifact` gain one reader each, each of them the whole table or the whole of one author's work: the rollbacks, every item and every per-stage row, every release, every incident, and the items one author wrote a version of. `cmd/factory` gains `learn` — the pass alone against an existing database, printing the table, what moved, and what moved it — composes the score version before the policy reader, and prints the evidence behind a supplied threshold at every firing and behind every supplied value in `policy`.

The rules, one per parameter — seven parameters across the six rows the score supplies a value for — each a function of the whole graph rather than a step from the value in force, so a pass that runs twice moves nothing twice:

| Parameter | What moves it | Which way |
|---|---|---|
| [risk threshold](end-goal/how-the-factory-works/04-risk-score/README.md), per gate row | a change the score auto-passed on the number whose item turned out badly; a held-out firing whose item turned out well | down to one band below the number it got wrong; up one band per three held-out firings, and by nothing else |
| [attempt limit](end-goal/how-the-factory-works/03-gates/05-the-attempt-limit.md), per stage | the highest attempt at which that stage produced work that got past it, once three items have reported there | one above it, both ways, floored at one retry |
| [item-size target](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md), per area | a stall — an item that reached the limit at a stage and never shipped | halved per stall, floored at fifty lines; one way only |
| [window size](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md), per service | a miss — a window closed passed or timed out over a release an incident was later raised against — against what the service's traffic can resolve | halved per miss, then held at the finest size the traffic reaches |
| [window confidence](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md), per service | a false pass — a miss whose window closed passed | half the remaining distance to one, per false pass; one way only |
| [window cap](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md), per service | the longest a window of that service took to close on evidence | twice that, both ways, floored at a minute |
| [window limit](end-goal/how-the-factory-works/08-operations/03-overlapping-windows.md), per service | windows closing without failing a release; a rollback that swept a release | up one per three, down one per rollback, folded in order |

Decisions taken so the demonstration holds.

**Both ends of each parameter are the evidence, which is what keeps a learned value from ratcheting.** The first pass at this read the harm end of each row and nothing else, and five of the six then moved one way and stayed there — which on the window's size ends in a service watched longer and protected less, the traffic a comparison needs going as the inverse square of the size. What answers it is already in the design: [gate policy's own table](end-goal/how-the-factory-works/09-gate-policy/01-what-is-in-it.md) states what goes wrong at *each* end of every row, and both ends are inputs. One end is something going wrong; the other is the parameter costing more than it returns, which is observable for five of the seven — attempts nothing has ever needed, a cap far longer than any window of that service takes to resolve, a size finer than its traffic can rule anything out at. So the attempt limit and the cap move both ways, the size takes a second input, the threshold has the sample, and the window limit was two-sided already. Two move one way, each with the reason stated where the rule is published: no outcome here says a confidence was too high, and nothing measures the other end of an item-size target. Neither compounds — the units a window needs grow as the log of one over one-minus-confidence where they grow as the inverse square of the size — so what an owner may have to do is author over one of them, which authoring being an override is exactly the case for.

**The window's size is the coarser of what harm asks for and what the traffic reaches.** Halved per miss and never coarsened by anything, against the finest size on that same lattice whose [units to clean](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) this service's newest closed window read supplies inside the cap in force. The second number is arithmetic over volume rather than a claim about harm, so reading it does not reopen the restriction that only evidence traceable to the [health monitor](end-goal/how-the-factory-works/08-operations/01-the-health-monitor.md) sets the size — that restriction governs what is worth catching, and this governs whether anything can be caught. The units come from `boundary` and not from a second copy of the arithmetic, this being the one number whose whole purpose is to match what the health monitor actually does. Two costs. A service can be told, truthfully, that it is watched at something coarser than the signal asked for, so the number in force is printed with what the traffic reaches beside it. And the score never asks for anything coarser than the value it starts at, so a service too quiet for even that ends every window at the cap — the weak protection the design already describes, rather than the factory quietly agreeing to catch less than it was installed to catch.

**The read a window closed on is now on the window.** Four counts — what the release served and failed, and what its baseline did — written by the health monitor at the close, and none at the skipped exit, that close being the one that is not a reading. Without it the record held the boundary a window was read against and no reading to read against it, so an exit could not be recomputed from the numbers it was decided on, which is the rule the boundary's own reading keeps one level down. It is also what makes the traffic a service receives arithmetic, and so what makes the paragraph above computable.

**Only the sample raises a threshold, and that is what the sample is for.** A change the score gated and a human approved is consistent with three things at once — that it was never risky, that the human at the gate caught what would have made it risky, and that its author was more careful for knowing a human would read it — and no record tells those apart, so none of them is evidence that the gate was unnecessary. What does tell them apart is a change the score wanted gated and did not gate, which is exactly what the [held-out sample](end-goal/how-the-factory-works/04-risk-score/02-how-it-learns.md) produces — so the design's self-reinforcement argument, which reads as a fairness point about authors, turns out to be the mechanism without which one of the two directions is unobtainable. Lowering needs no sample and outranks raising: it names a number the score is known to have got wrong. What that costs is that a factory whose sample never selects has a threshold that can fall and cannot rise, which is what a composition with no draw is and what every test here but one runs as — so the pass says so where nothing has been held out, rather than leaving it to be deduced from an empty list.

**The threshold is the one exception to reading both ends, and its loose end is observable.** How often a row puts a human at it is a count, and it is exactly what [that row's loose end](end-goal/how-the-factory-works/09-gate-policy/01-what-is-in-it.md) costs — the human work the factory exists to remove coming back. It is deliberately not read, and the difference from the size and the cap is the difference between protection that has become worthless and protection that has become expensive: a window too fine to resolve rules nothing out, so loosening it gives up nothing, where a human at a gate reads the change and stops some of them. Loosening on cost alone would be the score deciding that human review is not worth its price, which is a judgment about what the factory is for rather than a reading of what happened — and the design answers a cost complaint the other way, by having an owner author the value. Stating it is the point: the rule above says every value moves on both ends, and a rule with an unstated exception is one the next thing to touch this will apply in the one place it is wrong.

**The sample selects an item, is read forward off the decisions, and passes nothing a safeguard put a human at.** The two fields the design keeps apart are kept apart: **held out** is on the open event of every decision on the item from the selection onward, and **why it auto-passed** says, per firing, whether the number or the selection passed it — reading the threshold at a gate the score would have passed anyway. The stickiness is a read of the log rather than a field on the item, because the design records the selection on the decisions and a second place holding it would be two able to disagree. A safeguard is refused first: a human a safeguard added at a gate is a human an owner added, and a sample that could pass one would be the single mechanism in the design that removes a human an owner put at a gate. [Decomposition](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/01-decomposition.md) is never sampled, one draw over a set being a selection of several items on a number that is none of theirs — so that row's threshold can fall and never rise.

**The sample gets half of what the design gives it, and the half it loses is the control.** A held-out release should take a [strategy](end-goal/how-the-factory-works/03-gates/02-the-rollout-strategy.md) that keeps a control whatever the vector's impact half would have picked; this substrate moves a process rather than traffic and every deploy goes without a control, which M4 already refused and M6 does not reopen. What it can have is the other half: the window runs to the [cap](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) rather than stopping where the boundary would allow, which is the longest watch there is. So a held-out release is watched by the same confounded comparison as every other one, and what its evidence supports is that a comparison was available rather than that an unsampled release on the same author would have read the same. The rate is the score's own and not an owner's — gate policy is seven rows and the sample is not one of them — and an owner who wants a row never sampled adds a safeguard at it.

**A miss is an incident after a window closed without failing a release, and a rollback can never be one.** [_The analysis window_](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) says the size is learned from a rollback or a human's undo traceable to the [health monitor](end-goal/how-the-factory-works/08-operations/01-the-health-monitor.md), and on this factory that set is empty by construction: the health monitor rolls a release back at the failed exit and nowhere else, so every rollback the factory performs has a failed window under it and a failed exit is the health monitor catching what it was watching for. What the design means is the crossing the health monitor could have seen and did not, and after a window closes that is an [incident](end-goal/how-the-factory-works/08-operations/06-incidents.md) and an item. So the miss is an incident raised against a release whose own window closed passed or timed out, and a human's undo is not one: a human's reason is prose, the factory does not judge prose, and an undo for the wrong feature says nothing about what the health monitor should have caught. It moves the prior instead, which is that factor's own rule.

**The prior counts every outcome on the author's work, which is what lets it keep moving.** A human's verdict on a version that author wrote, a window closing over a release of an item it wrote — without failing it for, failing it against — and a human undoing one of those releases after it shipped, against. A swept window is neither: a rollback aimed below the release undid it, so its health monitor stopped before deciding anything, which is the same reading [_Overlapping windows_](end-goal/how-the-factory-works/08-operations/03-overlapping-windows.md) gives that exit. A release failed by its window and then rolled back is one outcome and not two, so an undo counts only where the window did not already fail it. That closes what `score`'s own doc.go has called the sharpest cost in the package since M2: a prior narrowed by human verdicts alone stops moving once the factory stops putting humans at gates, and this one moves on outcomes nobody was asked about.

**A stall is what an escalation is readable as, and the score reads it against its own limit.** The design has the item-size target learn from [attempt-limit escalations](end-goal/how-the-factory-works/03-gates/05-the-attempt-limit.md), and an escalation is not a record: it is a wait, and only the ones the [page's condition](end-goal/how-the-factory-works/08-operations/07-pages.md) qualifies reach the log at all. What is a record is the item's per-stage attempts and whether it ever shipped, so what the score counts is an item that reached the limit at a stage and has no release — work spent and thrown away, which is what that parameter's own cell says a decomposition too coarse shows as. The limit it reads is the one the score itself supplies, not the one in force: reading the authored value would make this package a reader of what an owner wrote, and [gate policy](end-goal/how-the-factory-works/09-gate-policy/02-one-shape-across-all-of-them.md) has the score supply a value and never read one. The two agree wherever nobody authored a limit, and where an owner authored one the score is counting against its own default — which the evidence on the moved row says.

**The unit of the item-size target is settled in the design and not yet here.** [_Decomposition_](end-goal/how-the-factory-works/02-intent-into-items/03-decomposition/README.md) authors it in the count of its intent's requirements an item answers; M5 supplied a number in lines and this milestone halves that number, so the stored value moves to the design's unit when a decomposition first reads it. Nothing reads it either way — no decomposition sizes anything yet — so what moves is a value with one reader and no unit, which is the honest state and not an answer. What a later decomposition reads is the movement; what an owner sees today is that the score thinks an area's items are too large.

**The supplied values are stored as structure and the other four columns stay prose.** `policy` reads a number out of the supplied table at every gate firing and no reader of prose can, so that column holds the JSON encoding of the table and the printer renders it. The other four — the formula, the factor set, the rules, and the formula's name — stay the text a reader reads. What it costs is a column a human reading the row sees as JSON, and what it buys is that the supplied value in force is a read of a record rather than a parse of a paragraph.

**Nothing refuses two versions that say the same thing, and with a learned value that is ordinary.** The window limit rises to two on a service and falls back to one at the next rollback that sweeps, which is a table equal to one two versions down. What would be wrong is a version saying what the one immediately below it says, and only the lock the append holds can refuse that — in the store it could only be a trigger, a comparison between two rows made at the insert, which is logic the source does not show. `score`'s schema comment has claimed a unique index over the version's columns since M2 and no statement there ever created one: the claim was wrong and the absence was right, and building this found it.

**What the store did not refuse is a sequence that is not one, and that was a real gap in two packages.** Both `score_version` and `policy_version` say that `supersedes` makes the sequence readable without a column that orders it, and neither enforced it: two versions could name one predecessor, so the chain could fork, and two could name none, so it could have two beginnings. A unique constraint over `supersedes` says both at once, which is the arrangement [`decisionlog`](end-goal/how-the-factory-works/03-gates/01-where-a-gate-is-and-what-decides-it.md)'s one-close-per-open index already had. `policy` then needed the advisory lock `score` has held since M2, because a constraint alone turns a silent fork into an error on whichever owner authored second — the constraint refuses the fork and the lock is what means nobody meets the refusal. Found by looking for the index the comment above used to claim, which is the argument for reading a comment against the statements under it.

**The formula stays authored, and its name moves because one line of it changed.** What learning moves is the seven values the score supplies; an owner authors what the number is compared against and never how it is computed, which is [gate policy](end-goal/how-the-factory-works/09-gate-policy/03-what-is-not-in-it/README.md)'s own division. The prior's line in the published formula now reads over every outcome on an author's work rather than over human verdicts alone, which is a different number from the same arithmetic, so the formula's name moves with it and the rules the supplied values move by carry a name of their own beside it.

**Learning happens where a process starts, and `learn` is a command because the movement is worth reading on its own.** A run appends the version at composition and prints two lines about it; the pass prints the whole table, each row that has moved against the version in force, the evidence behind it, a value that has moved *back* — which the learned table holds no row for at all — and the items the sample has selected. That is what an owner disagreeing with a learned number has to see, and it is the same shape [`watch`](end-goal/how-the-factory-works/08-operations/02-the-analysis-window.md) already has: a pass against an existing database, needing nothing a process remembers.

The demonstration is the rules as arithmetic, the same rules over a real graph, and two episodes through the crude interface. The rules are tested over outcomes a test assembles and indexes the way a read of the store does — the window limit's fold in order, so that three windows closing without failing a release after a rollback are not the same as three before it; a miss halving the size and a false pass also raising the confidence; a failed exit moving neither, the health monitor having caught what it watched for; the cap tracking the longest a window actually needed in both directions; the limit one above the highest attempt that ever got past a stage and below the starting value where nothing ever needed a second; a size finer than a service's traffic can resolve not being asked for; and a stall halving its area's target. Over a real graph: three windows of one service closed through the writer that owns them, the window limit rising on the third and not the second, the row naming the service and the evidence, the version appended by the ordinary path naming the one it superseded, the superseded version still saying what it said, a second pass appending nothing, and `policy` reading the moved value in force with the evidence under it.

The two episodes are the milestone's own. The first is the calibration end to end: [M4](#m4--the-factory-watches-what-it-ships)'s deliberately bad release, auto-passed on the number at three rows and failed by its own window, lowers the threshold each of those rows supplies below the number it passed it at — so the run after it is decided by a human where the run before it was not, and what says why is the evidence printed beside the threshold at the firing. That episode also changed three tests M4 and M5 already had, which is the loop working rather than the tests fighting it. The second is the sample: an item held out of a gate the score would have gated, no human at the row, the close event naming the sample and not the threshold, every row below it held out because the selection is the item's, the window over its release running to the cap with `clean` unavailable to it for a reason a reader can tell from having no baseline, a row a safeguard reached keeping its human however the draw falls, and the prior narrowing on a window that closed without failing a release and widening again on one that failed a release. Then, over all of it, `Verify` clean over a log now holding held-out decisions beside everything M5 left in it, and the score version sequence read from either end — every decision naming the version it was decided under, and every version naming the one it replaced.

## M9 — The factory improves its own agents

[What an agent is told](end-goal/how-the-factory-works/10-fleet/03-what-an-agent-is-told/README.md) becomes a record the factory writes: a role prompt per [role](end-goal/how-the-factory-works/01-one-pipeline.md) and skills per subject, versioned through the [artifact store](end-goal/how-the-factory-works/01-one-pipeline.md), authored from what the [decision log](end-goal/deferred.md) records and never from a [report](end-goal/how-the-factory-works/02-intent-into-items/01-intake/02-reports.md), each version decided at [a gate of its own](end-goal/how-the-factory-works/03-gates/07-what-particular-gates-decide/09-a-role-prompt-or-a-skill.md) and undone by withdrawal. Beside it, [_A fleet proposal_](end-goal/how-the-factory-works/10-fleet/07-a-fleet-proposal.md): the factory arguing for a fleet it may not write.

It is last because it needs everything before it. There is nothing to author a role prompt from until the log holds decisions with reasons on them (M0, M2), nothing to judge a version by until [_Factory_](end-goal/how-the-factory-works/11-screens/01-work-ops-factory-people.md) reports rates over a real span (M7), and no reason to trust the [score](end-goal/how-the-factory-works/04-risk-score/README.md) with the gate that decides one until the score has been learning for a while (M6). Building it earlier would have the factory rewriting what its agents are told on evidence it had not yet collected.

Demonstrated by a skill the factory wrote from its own rejects going into force and an item being authored under it, and by a role prompt version reaching the gate and stopping there — the second half being the point, since reach is what puts a human at that row.
