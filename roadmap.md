# Roadmap

The order the factory is built in — milestones from an empty repository to the state [`end-goal/`](end-goal/README.md) describes. Each milestone is named by what becomes true when it is done, and each states its demonstration, which is what makes it a milestone rather than a phase. This file records order and never progress: nothing here says which milestone is current or how far along it is — the commit history is the record of what has been built. A milestone's section grows task-level detail only while it is the next one; every later milestone stays a paragraph, because a detailed plan for the sixth is guesswork.

The factory is built as ordinary software and does not run its own pipeline over itself, so no milestone below is the factory building the factory. M9 is not an exception: what an agent is told is a record decided at a gate, never an [item](end-goal/how-humans-do-it/01-one-pipeline.md) with a build and a release, so the factory authoring its own briefs is the factory writing a record and not the factory shipping software to itself.

Two facts from the design set the order. The four seams of [_Deferred, but not designed out_](end-goal/deferred.md) — an actor on every record, one append-only decision log with each record chaining its predecessor, secrets by reference, and a named seam between agents and deploy targets — cannot be added to a history written without them, so they come before anything that writes a record. And tight integration is the product — [one graph](end-goal/what-the-factory-does.md#tight-integration), not a bundle — so the first shipping milestone is the thinnest end-to-end path through the whole loop, every part shallow, rather than one subsystem built deep. What that order costs: the first milestone ships nothing a user can see, and every part the thin path touches is rebuilt deeper in a later milestone.

Security hardening and adopting an existing codebase are not milestones here: [_Deferred, but not designed out_](end-goal/deferred.md) sequences both away, and this file inherits that.

## M0 — The graph and the log

The record graph exists and the four seams are in it from the first record: the actor field on every record, the append-only decision log with its chain, one resolver behind which every secret is a name, and the named operations an agent reaches a deploy target through. One writer per record. Demonstrated by writing records through each seam and reading the chain back unbroken. This milestone ships no software; it exists because none of the four can be retrofitted.

M0, M1, M2, and M3 carry task-level detail; the sections below them stay a paragraph each. M0's is kept rather than trimmed once it is built, because the reason the rule gives for holding detail back — a detailed plan for the sixth milestone is guesswork — is not a reason to delete a plan that was carried out, and removing it is the one edit here that would say which milestones are done.

The stack, decided 2026-08-17: Go, because an import cycle is a compile error and the ecosystem leans on neither reflection nor DI containers; PostgreSQL from the first record, because the owner expects the project to need it and starting there means the chained log is never migrated; `pgx` directly, with no abstraction layer between the code and the SQL. Code lives in `factory/` under the rules the root [`CLAUDE.md`](CLAUDE.md)'s _Code_ section sets. Already in place: `mise.toml` pinning the toolchain, `factory/go.mod`, and `factory/docker-compose.yml` running the dev database on port 5433.

One package per seam, each owning its schema, its writer, and its `doc.go`:

| Package | What it owns |
|---|---|
| `record` | The graph's conventions: the actor — kind human or component, plus a name, never empty — ID generation, and the columns every record table carries |
| `decisionlog` | The chained log: one table, one writer type, three explicit append methods for the three shapes, and a `Verify` that walks the chain and names the first break |
| `secretref` | A reference type and a resolver reading one file on disk; nothing downstream stores a value |
| `targetseam` | The named operations an agent reaches a deploy target through — `Deploy`, `Stop`, `ReadRunning` to start, each later addition explicit — as an interface plus a fake; nothing real behind it yet |
| `postgres` | Opening the pool and applying each package's DDL; no ORM and no migration framework |
| `cmd/depscheck` | Failing the build on a package dependency `factory/deps.txt` does not allow |

Decisions inside `decisionlog`, taken so the demonstration holds: the payload column is text rather than JSONB, because JSONB normalises what it stores and the chain hashes exact bytes; the timestamp is text for the same reason — RFC 3339 UTC, written by the writer, because a hashed field has to read back byte-identical. A decision row names the policy version and score version it was decided under, the other two shapes refuse both, and a CHECK constraint enforces it in the store as well as in the methods. Appends serialise on one advisory lock, which is the one-writer rule enforced rather than assumed. How a verdict joins the chain is not decided here: M0 appends whole records, and the shape a decision takes belongs to the milestone whose first gate fires.

The demonstration is `go test ./...` against the compose database: append all three shapes and read the chain back unbroken; tamper with a middle row by raw SQL and `Verify` names the broken link; every record carries an actor; a resolved secret's value appears in no record; the fake target records the named operations called on it. CI (`.github/workflows/factory.yml`) runs `go vet`, `depscheck`, and the tests against a PostgreSQL service. M0 is done when all of that passes on a fresh clone.

## M1 — One change ships

The thinnest end-to-end path through the whole loop, every part the shallowest version that completes it. An [intent](end-goal/how-humans-do-it/02-intent-into-items.md#intake) is taken in, a minimal [interview](end-goal/how-humans-do-it/02-intent-into-items.md#the-interview) refines it, [the cut](end-goal/how-humans-do-it/02-intent-into-items.md#the-cut) yields one [item](end-goal/how-humans-do-it/01-one-pipeline.md), an agent produces the change against a [spec](end-goal/how-humans-do-it/03-gates.md#spec) of one criterion, one [gate](end-goal/how-humans-do-it/03-gates.md#where-a-gate-is-and-what-decides-it) fires with a human deciding — the [score](end-goal/how-humans-do-it/04-risk-score.md) is a stub whose answer is always that a human decides — merge assigns the [release](end-goal/how-humans-do-it/06-releases.md#what-a-build-is-called-and-when) its ordinal, a [straight](end-goal/how-humans-do-it/03-gates.md#the-rollout-strategy) deploy ships it, and the [release record](end-goal/how-humans-do-it/06-releases.md#the-release-record) links all of it. Demonstrated by following the links from the deploy back to the intent with no step reconstructed. The interface the human decides through is whatever is cheapest — the four surfaces come at M7, and a crude interface until then is what deferring them costs.

How a verdict joins the chain was the one question gating this milestone, and it is decided: a [decision](end-goal/how-humans-do-it/03-gates.md#where-a-gate-is-and-what-decides-it) is two rows, an opening row appended when the gate fires so the human has the [factor vector](end-goal/how-humans-do-it/04-risk-score.md#factors-at-least) to argue with, and a closing row naming it and carrying the verdict. So `decisionlog` gains what M0 did not need — a field saying which of the two a row is, the versions required on an opening row and refused on a closing one, and the CHECK constraint that enforces it in the store — and that is the first task of the gate, not a change to a milestone already built.

One package per record, each owning its schema, its writer, and its `doc.go`, and each the shallowest thing that completes the path:

| Package | What it owns |
|---|---|
| `intent` | The intent, its source and statement, the refinement state and the round count, and the questions attached to it — intake being the one writer of all of them |
| `service` | A service's identity and its repository, written at the cut and by nothing else |
| `item` | The item — its intent, service, and branch — written once by the cut, and the stage, attempts, and spend that dispatch writes after |
| `artifact` | The artifact store: an artifact's version chain, its actor and authorship, and the one call a spec version and the criteria it introduces are submitted in |
| `criterion` | A criterion of a service: its stable id, its pattern, and the query for which criteria are in force for a build |
| `gate` | The gate component: firing the one row, opening and closing a decision through `decisionlog`, and holding the score stub behind an interface the real score replaces at M2 |
| `build` | A build record, one per commit built, and the commit it was made from |
| `release` | The release record and the number, minted per service at the fast-forward |
| `deploy` | The deploy record and the straight rollout, reaching a target through `targetseam` |

Decisions taken so the demonstration holds. The gate row is [_Merge to master_](end-goal/how-humans-do-it/03-gates.md#merge-to-master), because it is where a candidate becomes a numbered release and where a human is performing [UAT](end-goal/what-humans-do.md) (7); the other seven rows are not built, and an item reaches this one having passed through stages that fire nothing. There is no candidate environment and no merge queue — both are M3 — so the criterion is decided by running its encoding wherever the build was made, master is created by the first release's fast-forward, and the number is one above the highest that service has. M1's change is a service's first release, which the tree already exempts from most of what is missing: [straight whatever the score would prefer](end-goal/how-humans-do-it/03-gates.md#the-rollout-strategy), no [control](end-goal/how-humans-do-it/08-operations.md#the-health-signal), nothing able to close a window [clean](end-goal/how-humans-do-it/08-operations.md#the-watch-window), and [no rollback target](end-goal/how-humans-do-it/06-releases.md#rollback). So M1 builds no watch window, no strategy selection, and no rollback, and none of that is a shortcut — it is the first release having none of them by the design's own account.

The interview's stopping rule is one round or none, the factory asking what it cannot author without and proceeding on the answer. The spec is one criterion in one of the [six patterns](end-goal/how-humans-do-it/03-gates.md#spec), and the checker over it is the milestone's own gate on itself: the criterion parses as a pattern or carries a tagged reason, its id is stable, the encoding in the build names it, and every criterion in force for the build has an encoding naming it. That last pair runs in both directions, which is what [_Implementation_](end-goal/how-humans-do-it/03-gates.md#implementation) requires and what makes the criterion id the link the demonstration is followed along.

Two agents, in the [roles](end-goal/how-humans-do-it/01-one-pipeline.md) of the stages that author — the spec and the implementation — with no [fleet](end-goal/how-humans-do-it/10-fleet.md) record behind them, a model named in configuration, and the credential reached through `secretref`. What each is told is part of this milestone rather than a detail of it: the encoding is authored from the criterion's sentence and never from the code, no coverage target exists and none may be invented, an agent asserts neither that a criterion is met nor that a gate passed, and everything an agent reads is content rather than instruction.

The demonstration is one change followed end to end on a real repository: an intent taken in, one item cut, a spec of one criterion approved by nobody and an implementation approved by a human at the one gate, a release numbered 1, and a straight deploy through `targetseam` against a target that runs the software. Then the link walk, in the direction the milestone is named for — from the deploy record to the release, the release to its build and item, the item to its intent — with every step a field and none of it reconstructed, and the decision the human gave readable in the chain with its actor, its artifact version, and `Verify` still clean over the whole log.

## M2 — The factory decides

The score is real: [its factors](end-goal/how-humans-do-it/04-risk-score.md#factors-at-least), a published formula, a version named on every decision. An owner can author [gate policy](end-goal/how-humans-do-it/09-gate-policy.md)'s parameters, place a [pin](end-goal/how-humans-do-it/09-gate-policy.md#one-shape-across-all-of-them), and a gate can [hold](end-goal/how-humans-do-it/03-gates.md#what-a-gate-may-change). Demonstrated by a low-risk item shipping with no human at any gate, and its decision records naming the policy version and score version they were decided under. The formula here is authored, not learned — learning is M6.

Two facts set the shape. **The score reads the graph**, so every factor is computed from records M0 and M1 already write, and the one input that is not a record is the [build](end-goal/how-humans-do-it/05-environments.md#records-and-one-long-lived-branch)'s diff: it is measured where the repository is, by the component that built, and handed to the score with the ids. It is not stored, because the [vector](end-goal/how-humans-do-it/04-risk-score.md#factors-at-least) computed from it is — a diff re-taken later, against a repository other items have merged into, is not the diff the decision was made on, and the design already forbids recomputing a vector. **Every value an owner authors is a field of the record its scope names**, so this milestone creates the records those fields need before it can claim a parameter is authorable: the [area](end-goal/how-humans-do-it/02-intent-into-items.md#what-an-item-names), the [environment](end-goal/how-humans-do-it/05-environments.md#records-and-one-long-lived-branch), and the [factory policy](end-goal/how-humans-do-it/09-gate-policy.md#one-shape-across-all-of-them) records all arrive here, ahead of the milestones whose mechanisms read what is on them.

Seven packages, each owning its schema, its writer, and its `doc.go` — `gatepolicy` owning no table, the way `record` owns none:

| Package | What it owns |
|---|---|
| `gatepolicy` | The vocabulary of everything an owner authors: the parameters, what each value means, the record its scope names, and the direction a pin on it points. It is what `pin` and `policy` would otherwise each keep a copy of, and it is where the seven rows are eight parameters — the window's size and confidence being one row pinned in opposite directions |
| `score` | The score version — one append-only record naming the published formula, the factor set, and every value the score supplies — the eight factors of the design's three groups, and the assessment a [gate](end-goal/how-humans-do-it/03-gates.md#where-a-gate-is-and-what-decides-it) fires with: the vector, the likelihood and impact halves kept apart until the last step, and the number the formula reduces them to |
| `policy` | The one writer every authored value and every pin goes through, which is [Factory](end-goal/how-humans-do-it/11-surfaces.md#work-ops-factory-people)'s; the policy version it appends in the same transaction as the write; the seven parameters and the pin direction each takes; and the effective value as a read of three things — what an owner authored, what the score supplies, and the pins in force |
| `pin` | The pin record — its subject, the parameter it binds, its direction, its bound, and whether it has been withdrawn — and the query by subject that every mechanism a pin binds now runs |
| `area` | The area record: an owner's grouping, the area it lies inside, and the [item-size target](end-goal/how-humans-do-it/02-intent-into-items.md#the-cut) authored on it |
| `environment` | The environment record — production alone here, the [candidate](end-goal/glossary.md) kind being M3 — its targets, and the [risk threshold](end-goal/how-humans-do-it/04-risk-score.md) authored on it per gate row |
| `factorypolicy` | The factory policy record: the [attempt bound](end-goal/how-humans-do-it/03-gates.md#the-attempt-bound) per stage, the [predicate catalog](end-goal/how-humans-do-it/07-contracts.md#what-a-consumer-declares), and the threshold [_A brief or a skill_](end-goal/how-humans-do-it/03-gates.md#a-brief-or-a-skill) reads |

Five packages M1 built change, and each change is what the score or the policy needs from a record it does not own. `gate` gains its second row — Deploy to production, which is where [hold](end-goal/how-humans-do-it/03-gates.md#what-a-gate-may-change) is an action — the real score behind both rows, the threshold read through `policy`, and an opening row naming the values actually applied. `service` gains the four parameters an owner authors on it, written by an owner and never by the cut, which is the seam the record already declares. `item` gains the area the cut writes, because a pin drawn on an area reaches the item and the item-size target is per area. `artifact` gains the author — the model version for a version an agent wrote, the human's name for one a human wrote — because an [authorship prior](end-goal/how-humans-do-it/04-risk-score.md#factors-at-least) is kept per model version and is computed from that author's own work, which is not answerable from a record that names the role and not the model; that is the one edit this milestone makes to `end-goal/`, in [_One pipeline_](end-goal/how-humans-do-it/01-one-pipeline.md). `deploy` names the environment by the record's id rather than by the name M1 wrote there, the record now existing.

Decisions taken so the demonstration holds.

**What each factor reads, and what it costs.** The change group is computed from the diff and the records around the build: **size** from the lines the diff changes, **reach** from the share of the service's files it touches, **area churn** from the [releases](end-goal/how-humans-do-it/06-releases.md#the-release-record) minted in the item's area lately, **test coverage** from the criteria in force for the build and their results, and **reversibility** from whether the service has a release to return to. The authorship **prior** and the context group's **business area** are computed from the outcomes in [the log](end-goal/deferred.md) on that author's artifacts and on that area's items, and **consumers** is a query over what other services declare they consume, which returns none because nothing declares anything until M5. Two of those are thin in ways worth stating rather than hiding: reach reads the share of one service's files and knows nothing of the sibling services M5 introduces, and a coverage figure in the sense of lines executed is measured by nothing here — what the factor reads is how many criteria decided the build, which is the protection the factory actually has. None of the eight is unavailable on the path this milestone walks, which is what makes the demonstration reachable at all: a factor the score cannot compute resolves to the value that puts a human at the gate, and the published formula is what carries that direction — a vector with any factor unavailable reduces to the top of the scale, so one absent input gates the change however low the rest of it reads.

**Empty evidence is a wide value and not an unavailable factor.** The prior and the business area both start wide for an author or an area the factory has not seen and narrow as outcomes arrive, which is what the design says the prior does, and treating an empty history as unavailable instead would put a human at every gate of a new install forever — a decision nobody made arriving as a side effect. What narrows them here is a human's verdict and nothing else: a [window](end-goal/how-humans-do-it/08-operations.md#the-watch-window) closing without harm is M4, and an auto-passed decision is the factory agreeing with itself rather than evidence about the author. That is also the milestone's sharpest cost — a prior narrowed by human verdicts stops moving once the factory stops putting humans at gates, which is the self-reinforcement [_How it learns_](end-goal/how-humans-do-it/04-risk-score.md#how-it-learns) holds out a random sample to break, and the sample is M6. Nothing here records a held-out selection, because nothing selects one.

**The formula is published, authored, and calibrated so that the first item on a service is not the one that auto-passes.** Each factor resolves to a level between nothing and one against breakpoints written in the source; the likelihood half is the weighted mean of size, churn, coverage, and the prior; the impact half is the weighted mean of reach, business area, and consumers; reversibility discounts impact rather than joining either half, because the [rollout strategy](end-goal/how-humans-do-it/03-gates.md#the-rollout-strategy) reads impact against reversibility and reading them separately is what keeps the two from weakening together; and the last step scales the discounted impact by the likelihood without letting a low likelihood dissolve a high impact. The calibration is authored to a factory that has just been installed, where a service's first release has no release to return to, an author nobody has approved yet, and an area with no history — that item reads high and a human decides it, and the item after it, on an author one human has approved, reads low and nobody does. So the demonstration is two items rather than one, and it says something the design says about itself: the factory earns the autonomy rather than starting with it.

**Two append-only version records, one per side of what a decision is decided under.** The score version names the published formula, the factor set, and the value the score supplies for six of the seven parameters — none for the predicate catalog, which no outcome teaches — and the score appends a version when what it publishes stops matching the newest one, which is one row here and the mechanism M6 moves. The policy version is Factory's, appended in the same transaction as every authoring write and every pin, and the version in force is the newest row. It names the parameter, the subject, and what was done rather than restating the value: the value is the field on the record the subject names, one fact in two places could disagree, and what a decision was decided under is the effective values its own opening row carries. What that costs is that reading a policy version back tells a reader which write it was and not what the whole policy said, which is answerable only by replaying the writes.

**The effective value is a read of three things, and four of the seven parameters have no reader yet.** An owner authors on the record the scope names, the score supplies where the field is empty, and a [pin](end-goal/how-humans-do-it/09-gate-policy.md#one-shape-across-all-of-them) clamps the result — a ceiling caps it, a floor raises it, a pin never replaces a value already narrower than itself, and a pin on the risk threshold is a human added rather than a number changed. All seven resolve and all seven are tested that way. Only two are read by a mechanism this milestone builds: the risk threshold, at both gate rows, and the attempt bound, by the stages that retry. The item-size target waits for a cut that sizes anything, the predicate catalog for M5, and K and the window's parameters for M4 — so an owner can author four values that change nothing yet, which is the cost of the parameter being a field of a record that has to exist before its mechanism does.

**Two gate rows, and the hold that comes with the second.** Merge to master is M1's; Deploy to production is added because hold is an action at the deploy rows and nowhere else, and the candidate deploy row needs the environment per candidate that is M3. Both rows read production's environment record for their threshold, which is the rule the design gives for all eight. A hold a human sets is that firing's verdict, leaves the event queued with the change still good, counts no attempt, and teaches the score nothing — the three things that separate it from a reject. The factory's own hold has no condition to compute here: an open window, a dependency that is not current, a rollback whose revert has not shipped, and a [reconciler](end-goal/how-humans-do-it/08-operations.md#the-reconciler) mismatch are all records later milestones write. Pin strategy, the row's third action, is refused with its reason: a target that runs a release as a local process moves a process rather than traffic, so the strategy that keeps a [control](end-goal/how-humans-do-it/08-operations.md#the-health-signal) is unavailable on this substrate and every deploy is straight — the exemption the design already states for a substrate of that kind, arriving here for the whole install rather than for one release.

**There is no project record, so a pin may not name one.** A project is what groups services, the [surfaces](end-goal/how-humans-do-it/11-surfaces.md#work-ops-factory-people) are M7, and the area chain terminates at an area rather than at a project until then. A pin here names a service, an area, a gate row, or the factory policy record, and a subject the factory has no record for is refused rather than stored as a dangling name. Reading the design's stage as the gate at that stage's boundary is what lets a pin reach a deploy row at all, the eight rows each sitting at one and there being no other subject that names one.

The demonstration is three runs of the path against one service, and what each is for. The first is M1's, re-run under a real score: the item reads high, the gate puts a human at Merge to master and again at Deploy to production, and both decisions name a score version and a policy version that are records rather than the names M1 wrote. The second is the milestone's own: the same path on the same service with the prior and the area narrowed by the first run's verdicts, the number under the threshold at both rows, both verdicts the factory's own with no human anywhere, and the release deployed — with the opening rows naming the number, every factor, the threshold applied, and where that threshold came from. The third is the pin: an owner places one on the service, the deploy row puts a human back at a gate the score would have passed, the human holds, and the run stops with the release minted, nothing deployed, no attempt counted, and the item where it was. Then, over all three, `Verify` clean, the link walk from the last deploy back to its intent, and the effective value of each of the seven parameters printed with which of the three reads it came from.

## M3 — A candidate gets an environment

A [candidate](end-goal/glossary.md) runs on an [environment](end-goal/how-humans-do-it/05-environments.md#records-and-one-long-lived-branch) of its own, composed from the [current releases](end-goal/how-humans-do-it/06-releases.md#the-deploy-record) of its dependencies, and the [merge queue](end-goal/how-humans-do-it/05-environments.md) orders merges, with every pre-merge check decided against the candidate-environment run. Demonstrated by two candidates on one service proceeding at once, neither reading the other's environment.

Two facts set the shape. **Nothing is shared, so nothing queues behind anything**, which is the whole of what [_An environment per candidate_](end-goal/how-humans-do-it/05-environments.md#an-environment-per-candidate) buys — so the milestone's unit is two items in progress at once rather than one item walking further, and every record the path touches is read for whether two items can be inside it at the same time. Two could not: the environment, whose kind CHECK listed production alone, and the [item](end-goal/how-humans-do-it/01-one-pipeline.md)'s stage, which had no value for a candidate whose merge is approved and whose fast-forward has not happened — which is exactly the membership [_The merge queue_](end-goal/how-humans-do-it/05-environments.md#the-merge-queue) defines itself by. And **master's only inbound path is the queue**, so the [release record](end-goal/how-humans-do-it/06-releases.md#the-release-record) and [the number](end-goal/how-humans-do-it/06-releases.md#the-number) move into it: the design names the queue as their writer, and M1 minted them in the crude interface beside a `git fetch` because there was no queue to put them in.

One package, and it owns no table — the queue is a component, its membership a query over items and its order a query over the log:

| Package | What it owns |
|---|---|
| `mergequeue` | The queue: its membership as the items whose stage says [Merge to master](end-goal/how-humans-do-it/03-gates.md#merge-to-master) approved them and whose fast-forward has not happened, its order as the item's priority and then the time of that approval in [the log](end-goal/deferred.md), the fast-forward and the release it mints with it, and the rejection of a candidate that failed its own re-verification — a wait row the log writes with the queue as caller and actor, an attempt counted at Implementation, and the item sent back there |

Eleven packages change, and each change is what an environment per candidate or the queue needs from a record it does not own. `environment` gains the candidate kind, a second writer for it — the [deploy agent](end-goal/how-humans-do-it/08-operations.md#the-health-signal), the kind being the seam between the two — the item it belongs to, what it was composed from, and the teardown that keeps the record and stops the software. `item` gains the queued stage, the priority an owner reorders a queue with, what the cut declared it waits on, and a way back up the pipeline: `Dispatch` could only advance one stage forward, and the queue's rejection and a gate's reject both send an item back and count the attempt at what it is sent to. `gate` gains its third row — Deploy to candidate environment, where [hold](end-goal/how-humans-do-it/03-gates.md#what-a-gate-may-change) and reject are both actions and the threshold is still production's, a candidate's environment holding nothing an owner authored — and the read of when each item's merge approval closed, the shape of both a decision's payloads being its. `criterion` gains the outcome of deciding one against a build, [undecided](end-goal/how-humans-do-it/05-environments.md#what-the-candidate-environment-decides) among the three, written by the deploy agent when the run finishes; `artifact` changes only to pass the item through to it. `deploy` gains the build a deploy names, on every record rather than a release alone. `release` gains master's head as a query, which is the commit of the service's highest-numbered release, and `build` the query that answers which build a commit already has — a rebuild being a new build, so a re-verification that produced the commit already built produced none. `targetseam` renames the one field a deploy carries across it from the release to the build, and `localtarget` becomes one target per environment rather than one per install, a candidate environment being a place of its own. `cmd/factory`'s `run` takes an intent per candidate rather than one, `priority` joins the four subcommands that are duty 8 and duty 9, and the crude interface is also the deploy agent the queue reaches its repository and its candidate environments through.

Three edits to `end-goal/` come with it, each a defect building found rather than a decision this milestone took on its own. [_The deploy record_](end-goal/how-humans-do-it/06-releases.md#the-deploy-record) said a deploy record names the release, and a candidate deploy fires one gate before the number exists — so it names the build it put there and the release where it is deploying one. [_Records, and one long-lived branch_](end-goal/how-humans-do-it/05-environments.md#records-and-one-long-lived-branch) said the build names the environment a run happened on, which it cannot: the build is written when the implementation stage finishes, one gate above the approval that creates the environment, so what names it is the item. And [_Spec_](end-goal/how-humans-do-it/03-gates.md#spec) said which criteria are in force for a build by filtering withdrawals alone, which two candidates at once break: a criterion introduced by a sibling that has not merged is a promise this build's tree could not keep, and holding it in force rejects every candidate cut in parallel with the one that introduced it. Both halves of that query now read the same set — the items in the build.

Decisions taken so the demonstration holds.

**A candidate's environment is a record with a second writer, and the kind is what keeps the two apart.** An owner writes the persistent kinds and never a candidate's; the deploy agent writes a candidate's at the approval of Deploy to candidate environment and never a persistent one. So `environment.Writer` refuses the candidate kind and the new `Candidates` writer refuses every other, and authoring a threshold on a candidate's record is refused where it is authored rather than left to a reader to notice — the record cannot hold the threshold that decided its own creation. A candidate's record names its item, which is what makes it findable and what says the environment is the item's rather than the build's: it persists across a rebuild. Teardown writes the time and keeps the row, because the deploy records naming it would otherwise point at nothing, and it stops the software before it does — the record and the process are two facts, and this is the one place the factory is allowed to make them agree without the [reconciler](end-goal/how-humans-do-it/08-operations.md#the-reconciler).

**What it was composed from is a field, and on this path the field is empty.** The environment is composed from the current releases of the candidate's dependencies, a dependency here being what the cut declared the item waits on — the only dependency the factory has a record of until [contracts](end-goal/how-humans-do-it/07-contracts.md) arrive at M5. The cut yields one item per intent at this milestone, so no run declares one and every composition on the demonstrated path names nothing. The mechanism is built rather than deferred because the field is written at creation and rewritten at each re-verification, and a field added later would be absent from every environment the factory had already composed. What it costs is the milestone's thinnest claim: two candidates are demonstrated not to read each other's environment, and neither of them reads a dependency's release either.

**The hold both deploy rows read is computed at the firing and writes nothing.** A declared dependency that is not live holds the candidate deploy until it is and holds the production deploy if it has stopped being, live meaning that the dependency's release is the one its service's production deploy record names. It is recomputed at every firing and written nowhere, which is what the design requires of a hold over a record that already exists — a record for it would be a decision where nothing is decided. It is computed by the caller rather than inside `gate`, which imports neither the item nor the deploy record and would need both; what `gate` owns is the vocabulary, and the condition is named there. Being untestable through a run that declares no dependency, it is tested directly against an item waiting on one that has not shipped.

**The other hold at that row does write, and it is the substrate's.** A substrate with no room for another environment is the one condition the cut could not have declared, it is not a record, and no parameter of an owner's limits it — so it is a wait row the log writes with the deploy agent as caller and actor, the shape the design gives a wait no gate could compute. The ceiling is a number in the source and not gate policy, because it is the factory's own infrastructure limit rather than something an owner authors, and it is a field of what the crude interface composes so a test can set it to one. What that costs is the cost the design already states: an item stopped for a reason no artifact of it explains, visible only as a wait.

**The criteria are decided on the candidate environment, and undecided is the reason a second run happens at all.** The encodings run twice against the same build, and a criterion whose two runs disagree is undecided for that build rather than passed — a repeated run measures the repetition, and recording it as a pass would rest the merge verdict on nothing. Undecided is read at the merge gate the way a failure is, and the way out is to author the encoding again rather than to run it again, so nothing here retries to green. Two coarsenesses are worth stating rather than hiding: the run's result is one exit status for the whole suite, so every criterion in force takes the same outcome from one run, and the second run doubles what a build's verification costs to catch a class of defect that a deterministic suite does not have. The results attach to the build and the criterion and are a table of the two, not a record with an identity of its own.

**The score is asked at three rows now, and coverage reads different things at two of them.** At the candidate deploy row no criterion has been decided yet, so the coverage factor reads the set in force and no failure; at the merge row it reads the same set with the outcomes the candidate-environment run produced, which is the reading M2 built. Neither is unavailable, so neither puts a human at a gate for the absence of a measurement — and what the candidate row's number is therefore blind to is exactly the thing that row exists to arrange, which is the run itself.

**The queue re-verifies serially, and the speculation is deliberately absent.** A candidate entering the queue re-verifies against the master that actually resulted — master merged into the candidate branch, a build written for the commit that produced, the environment recomposed, the build deployed to it, and the criteria decided there — and fast-forwards only if that passes. The design's speculative re-verification against master plus every candidate ahead is what makes the queue fast, and it is the queue's own state read by nothing outside it, so it can arrive later without changing a record: what a serial queue already provides is the property the design asks of it, that the commit that was verified is the commit that merges. What it costs is wall-clock — a queue of ten waits ten re-verifications where a speculating queue overlaps them — and it costs the demonstration nothing, a failure ahead invalidating a speculation there is none of.

**A candidate with no base is merged with unrelated histories allowed, and a conflict is a rejection.** Master does not exist until the first release, and the implementation role commits a candidate branch with no base, so two candidates cut before that first release have no common commit and the re-verification of the second is a merge of two roots. The merge is performed with unrelated histories allowed rather than special-cased, which is a flag with no effect where the histories are related; where the two trees then conflict, the candidate failed its own re-verification and the queue rejects it, which is the right answer and not a workaround. What it costs is that a git conflict and a failing criterion arrive at the same disposition with different reasons, and the reason is in the wait row rather than in the verdict.

**A merge is three writes, and two of the three windows between them close here.** The fast-forward, the mint, and the item's advance to merged cross a repository and two transactions, and nothing makes them atomic. The queue holds a per-service advisory lock across all of them, so two queue runs cannot interleave and two candidates cannot read one number — the serialization [_The number_](end-goal/how-humans-do-it/06-releases.md#the-number) already requires. A member that already has a release is then finished rather than re-verified, which closes the advance's window: an advance that failed is repaired by the next run, and one merge never mints two numbers — which it otherwise would, a release being unique on the service and the number and not on the item, so nothing in the store refuses a second. What stays open is a mint that failed after the fast-forward, leaving master at a commit no release names: M1 stated that as the half-write the queue would close, and closing it is the reconciler's, which is M4. The direction is the one M1 chose for the same reason — a release numbering a commit that never reached master is worse, because a deploy could put it live.

**The queue's membership is the service's and not the run's.** Its members are every item of the service at the queued stage, which is what the design says and is not the same set as the candidates one run authored: a run that stops after one merge gate has approved leaves that item queued, and nothing in the crude interface clears one. So a re-verification reads what it needs from the store rather than from what its process happens to remember, and a run that finds an item another one left behind finishes it — tears its environment down and deploys its release beside its own. The alternative was for a run to re-verify only what it authored, and that wedges the service: every later run would spend its model calls, compose an environment, fire two gates, and then fail on somebody else's item, with one more stuck item added each time.

**A reject counts its attempt where the item is sent, at every row that rejects.** M1 and M2 left an item at Implementation on a reject and counted nothing, there being nowhere to send it and no second stage below. With a stage between Implementation and merged, going back up is a real move, so `Dispatch` gains it and the two rows that reject and the queue's rejection all use it — the attempt booked against the stage the item returns to, which is the rule the design gives for a reject, a return, and the queue alike. What that changes for the milestones already built is that a rejected item's Implementation count is one higher than it was, which is the count the attempt bound was always meant to be compared against.

The demonstration is three runs and what each is for, all on one service. The first is M1's, walked along the path M3 builds: one candidate, its own environment created at the candidate deploy gate and named for the item, its build deployed there, the criteria decided by two runs on it, a human at each of the three rows because nothing about the service has been seen before, the queue re-verifying against a repository with no master, fast-forwarding to create one, minting number 1, tearing the environment down, and the production deploy putting it live. The second is the milestone's own, run after that one: two intents at once, two items cut on the same master, two candidate environments live together with different targets and different deploy records, each criteria run attaching to its own build, both merge gates approving with nobody at either, and the queue merging them in its order — the second re-verifying against the master the first one created, which is a build the implementation stage never made — then two releases numbered 2 and 3, two environments torn down, and two production deploys. The third is the queue's rejection: the two candidates write to one file, so the second one's re-verification against the master the first created is a merge that conflicts, and the run ends with the first item merged and deployed, the second back at Implementation with an attempt counted there, its environment still its own and not torn down, no release minted for it, and a wait row in the log naming the queue as its actor. Three more things are demonstrated beside the runs, none of them reachable through one. The settable order: an owner writes a priority between the merge gates and the queue, which one run performs in a single call, so the steps are driven one at a time and the candidate pushed to the front merges while the one behind it is the one whose merge now conflicts. The substrate's ceiling, lowered to a single environment so the second candidate of a run waits and that wait is written. And the dependency hold, driven against an item that waits on one nothing has shipped, because the cut here yields one item per intent and no run declares a dependency. Then, over all of it, `Verify` clean, the link walk from the last deploy back to its intent, and the effective value of each of the seven parameters printed with which of the three reads it came from.

Everything downstream of a deploy: the [health signal](end-goal/how-humans-do-it/08-operations.md#the-health-signal) and the control, the [watch window](end-goal/how-humans-do-it/08-operations.md#the-watch-window) and [K](end-goal/how-humans-do-it/08-operations.md#overlapping-windows), [rollback](end-goal/how-humans-do-it/06-releases.md#rollback) while a control is still running and a revert item after, [pages](end-goal/how-humans-do-it/08-operations.md#pages) and escalation, [incidents](end-goal/how-humans-do-it/08-operations.md#incidents), [the reconciler](end-goal/how-humans-do-it/08-operations.md#the-reconciler), and a comparison that finds a problem [after its window closed](end-goal/how-humans-do-it/08-operations.md#after-the-watch-window) writing an intent at the start of the pipeline. Demonstrated by a deliberately bad deploy: shipped, caught by its window, rolled back, and the whole episode readable as links.

## M5 — Contracts bind services

Two services exist, and what a consumer assumes is [derived from its build](end-goal/how-humans-do-it/07-contracts.md#what-a-consumer-declares) rather than entered by hand; [enforcement](end-goal/how-humans-do-it/07-contracts.md#enforcement) answers what a change breaks by query; [work that spans services](end-goal/how-humans-do-it/07-contracts.md#work-that-spans-services) needs no record type of its own. Demonstrated by a breaking change held at a gate that names the consumer it would break. ## M9 — The factory improves its own agents

[What an agent is told](end-goal/how-humans-do-it/10-fleet.md#what-an-agent-is-told) becomes a record the factory writes: a brief per [role](end-goal/how-humans-do-it/01-one-pipeline.md) and skills per subject, versioned through the [artifact store](end-goal/how-humans-do-it/01-one-pipeline.md), authored from what the [decision log](end-goal/deferred.md) records and never from a [report](end-goal/how-humans-do-it/02-intent-into-items.md#reports), each version decided at [a gate of its own](end-goal/how-humans-do-it/03-gates.md#a-brief-or-a-skill) and undone by withdrawal. Beside it, [_A fleet proposal_](end-goal/how-humans-do-it/10-fleet.md#a-fleet-proposal): the factory arguing for a fleet it may not write.

It is last because it needs everything before it. There is nothing to author a brief from until the log holds decisions with reasons on them (M0, M2), nothing to judge a version by until [_Factory_](end-goal/how-humans-do-it/11-surfaces.md#work-ops-factory-people) reports rates over a real span (M7), and no reason to trust the [score](end-goal/how-humans-do-it/04-risk-score.md) with the gate that decides one until the score has been learning for a while (M6). Building it earlier would have the factory rewriting what its agents are told on evidence it had not yet collected.

Demonstrated by a skill the factory wrote from its own rejects going into force and an item being authored under it, and by a brief version reaching the gate and stopping there — the second half being the point, since reach is what puts a human at that row.
